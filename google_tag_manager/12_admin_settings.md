# Администрирование и настройки

## Описание

Модуль «Администрирование и настройки» Google Tag Manager отвечает за управление аккаунтами, контейнерами, пользователями, правами доступа, средами (environments), версионированием, импортом/экспортом конфигураций, настройками согласия (Consent Mode), журналом действий и корпоративными функциями GTM 360 (зоны, согласования, интеграция с Google Marketing Platform). Модуль является центральным звеном управления всей инфраструктурой тегирования организации.

---

## Роли пользователей

### Уровень аккаунта

| Роль | Описание |
|------|----------|
| **Пользователь (User)** | Может просматривать базовую информацию об аккаунте. Назначается по умолчанию при добавлении пользователя |
| **Администратор (Administrator)** | Может создавать новые контейнеры, управлять пользователями и их правами на уровне аккаунта и контейнеров |

### Уровень контейнера

| Право | Описание |
|-------|----------|
| **Нет доступа (No Access)** | Пользователь не видит контейнер и не может с ним взаимодействовать |
| **Чтение (Read)** | Может просматривать контейнер и его компоненты, но не может вносить изменения |
| **Редактирование (Edit)** | Может создавать и редактировать теги, триггеры и переменные, но не может публиковать или создавать версии |
| **Одобрение (Approve)** | Может создавать, редактировать и одобрять изменения, но не может публиковать |
| **Публикация (Publish)** | Полный контроль — может создавать, редактировать и публиковать изменения |

### Наследование прав

- **Наследованные права (Inherited)** — получены косвенно от группы пользователей или роли в организации
- **Прямые права (Direct)** — назначены конкретному пользователю. Сохраняются даже при потере наследованных прав

## Функциональные требования

### FR-ADM-001: Управление аккаунтом

**Описание:** Система должна позволять создавать и настраивать аккаунты GTM, определяющие верхний уровень иерархии управления.

**User Stories:**
- Как администратор, я хочу создать аккаунт GTM для своей организации, чтобы объединить все контейнеры под одной учётной записью
- Как администратор, я хочу указать название компании и страну аккаунта для корректной идентификации
- Как администратор, я хочу включить или отключить анонимную отправку данных в Google для бенчмаркинга

**Бизнес-правила:**
- Один Google-аккаунт может владеть несколькими аккаунтами GTM
- Каждый аккаунт GTM может содержать до 500 контейнеров
- В аккаунте должен быть минимум один администратор. Рекомендуется иметь не менее двух активных администраторов для предотвращения потери доступа
- При смене роли единственного администратора весь аккаунт может стать недоступным

---

### FR-ADM-002: Управление пользователями и правами доступа

**Описание:** Система должна обеспечивать гранулярное управление доступом пользователей на уровне аккаунта и каждого контейнера.

**User Stories:**
- Как администратор, я хочу добавить нового пользователя по email и назначить ему роль на уровне аккаунта и конкретных контейнеров
- Как администратор, я хочу изменить права существующего пользователя, если его обязанности изменились
- Как администратор, я хочу удалить пользователя, который покинул проект, чтобы отозвать доступ
- Как администратор, я хочу видеть список всех пользователей с их правами для аудита доступа

**Бизнес-правила:**
- Права контейнера выстроены иерархически: Publish > Approve > Edit > Read > No Access
- Каждый более высокий уровень включает все права нижележащих уровней
- Пользователь с правом Publish на контейнер автоматически имеет права Approve, Edit и Read
- Прямые права всегда приоритетнее наследованных
- Нельзя удалить последнего администратора аккаунта
- Пользователь с правом Edit не может публиковать изменения — только создавать и редактировать

---

### FR-ADM-003: Управление контейнерами

**Описание:** Система должна позволять создавать, настраивать и удалять контейнеры разных типов внутри аккаунта.

**User Stories:**
- Как администратор, я хочу создать новый контейнер для моего веб-сайта, указав его тип и название
- Как администратор, я хочу создать серверный контейнер для server-side тегирования
- Как администратор, я хочу переименовать контейнер при ребрендинге сайта
- Как администратор, я хочу удалить неиспользуемый контейнер для очистки аккаунта

**Бизнес-правила:**
- Поддерживаемые типы контейнеров: Web, AMP, Android, iOS, Server
- Каждый контейнер имеет уникальный идентификатор (GTM-XXXXXX)
- Тип контейнера задаётся при создании и не может быть изменён позднее
- Максимум 500 контейнеров на один аккаунт GTM
- Размер контейнера (скомпилированного) не должен превышать 200 КБ — при превышении публикация новых версий блокируется

**Лимиты по содержимому контейнера (стандартный GTM):**
- Теги: до 5 000
- Триггеры: до 2 000
- Пользовательские переменные: до 2 000

**Лимиты по содержимому контейнера (GTM 360):**
- Теги: до 50 000
- Триггеры: до 10 000
- Пользовательские переменные: до 10 000

### FR-ADM-004: Управление рабочими пространствами (Workspaces)

**Описание:** Система должна поддерживать параллельную работу нескольких пользователей над одним контейнером через независимые рабочие пространства.

**User Stories:**
- Как маркетолог, я хочу создать отдельное рабочее пространство для настройки новой рекламной кампании, не мешая работе коллег
- Как разработчик, я хочу работать над изменениями в своём рабочем пространстве и протестировать их до публикации
- Как администратор, я хочу видеть все активные рабочие пространства и понимать, кто над чем работает
- Как пользователь, я хочу получить уведомление, если мое рабочее пространство устарело из-за публикации другой версии

**Бизнес-правила:**
- Стандартный GTM: максимум 3 рабочих пространства (1 по умолчанию + 2 дополнительных)
- GTM 360: неограниченное количество рабочих пространств
- Каждое рабочее пространство содержит независимый набор изменений
- При публикации одного пространства остальные получают уведомление об устаревании
- При попытке опубликовать устаревшее пространство система автоматически предлагает синхронизацию
- Конфликты между пространствами должны быть разрешены перед публикацией

---

### FR-ADM-005: Версионирование и публикация

**Описание:** Система должна обеспечивать полный контроль версий конфигурации контейнера с возможностью отката.

**User Stories:**
- Как маркетолог, я хочу опубликовать изменения из своего рабочего пространства, чтобы они стали активными на сайте
- Как администратор, я хочу добавить описание к версии при публикации для документирования изменений
- Как администратор, я хочу откатить контейнер к предыдущей версии, если обнаружены проблемы
- Как аудитор, я хочу просмотреть историю публикаций и понять, кто и когда публиковал каждую версию
- Как пользователь, я хочу сохранить текущее состояние как версию без публикации для фиксации промежуточного результата

**Бизнес-правила:**
- Каждая публикация автоматически создаёт новую версию контейнера
- Версию можно создать без публикации (сохранение снимка)
- Каждая версия хранит полный снимок конфигурации контейнера на момент создания
- Откат выполняется через действие «Set as Latest Version» — копирует старую версию в рабочее пространство, после чего требуется повторная публикация
- Откат не удаляет проблемную версию из истории
- История публикаций фиксирует: дату, автора, номер версии, описание
- Версии нумеруются последовательно и автоматически

### FR-ADM-006: Управление средами (Environments)

**Описание:** Система должна поддерживать множественные среды для тестирования изменений контейнера до публикации в production.

**User Stories:**
- Как разработчик, я хочу создать среду «staging» для тестирования новых тегов перед выкаткой на боевой сайт
- Как QA-инженер, я хочу установить сниппет тестовой среды на staging-сервер для проверки тегов
- Как маркетолог, я хочу поделиться ссылкой предпросмотра среды с коллегой для согласования
- Как администратор, я хочу включить режим отладки по умолчанию для среды разработки

**Бизнес-правила:**
- По умолчанию каждый контейнер имеет две встроенные среды: Live и Latest
- Среда Live всегда указывает на текущую опубликованную версию контейнера
- Среда Latest указывает на последнюю сохранённую версию (может отличаться от Live)
- Пользователь может создавать неограниченное количество пользовательских сред
- Каждая пользовательская среда имеет собственный сниппет кода для установки
- Публикация в пользовательскую среду не затрагивает Live-версию
- Для пользовательской среды можно включить автоматический режим отладки (Preview Mode)
- Ссылку предпросмотра среды можно сгенерировать и передать любому пользователю
- Для production-сайтов рекомендуется использовать стандартный сниппет (среда Live), а не пользовательские среды

### FR-ADM-007: Импорт и экспорт контейнеров

**Описание:** Система должна поддерживать экспорт конфигурации контейнера в JSON-файл и импорт из JSON-файла.

**User Stories:**
- Как администратор, я хочу экспортировать контейнер в JSON для резервного копирования
- Как консультант, я хочу экспортировать настроенный контейнер и импортировать его в аккаунт клиента
- Как разработчик, я хочу экспортировать контейнер для хранения в системе контроля версий (Git)
- Как администратор, я хочу импортировать готовый набор тегов из JSON-файла (рецепт), предоставленный вендором
- Как администратор, я хочу выборочно экспортировать только определённые теги, триггеры и переменные

**Бизнес-правила:**
- Экспорт доступен для любой версии контейнера или текущего состояния рабочего пространства
- Экспортированный файл содержит теги, триггеры, переменные и шаблоны в формате JSON
- При импорте доступны два режима:
  - **Перезапись (Overwrite):** удаляет все существующие элементы и заменяет их импортированными. Перед перезаписью автоматически создаётся версия-бэкап
  - **Слияние (Merge):** добавляет импортированные элементы к существующим. При конфликтах имён доступны варианты: перезаписать конфликтующий элемент или переименовать импортируемый
- JSON-файл может быть отредактирован вручную в текстовом редакторе (массовые изменения ID, конвенций именования)
- Поддерживается частичный экспорт — выбор конкретных элементов для экспорта
- Импорт требует прав Edit или выше на целевой контейнер

### FR-ADM-008: Журнал действий (Activity Log)

**Описание:** Система должна вести полный журнал всех действий, выполненных пользователями в аккаунте и контейнерах.

**User Stories:**
- Как администратор, я хочу просмотреть историю изменений в рабочем пространстве, чтобы понять, кто и что менял
- Как аудитор, я хочу проверить, кто опубликовал последнюю версию контейнера
- Как руководитель, я хочу убедиться, что только авторизованные пользователи вносили изменения
- Как разработчик, я хочу найти, кто удалил конкретный тег, чтобы понять причину

**Бизнес-правила:**
- Каждое действие записывается с фиксацией: тип действия (Add, Edit, Delete), название изменённого объекта, имя пользователя, дата и время
- Журнал доступен на уровне каждого рабочего пространства
- История изменений сохраняется бессрочно в рамках существования аккаунта
- Журнал действий доступен только пользователям с правами Read и выше
- При публикации версии описание изменений сохраняется в метаданных версии
- История публикаций отображает: дату, автора, номер версии

### FR-ADM-009: Настройка Consent Mode

**Описание:** Система должна поддерживать управление согласием пользователей (Consent Mode) для соблюдения законодательства о защите данных.

**User Stories:**
- Как администратор, я хочу настроить параметры согласия по умолчанию для тегов, чтобы обеспечить соответствие GDPR
- Как маркетолог, я хочу настроить поведение тегов в зависимости от статуса согласия пользователя
- Как администратор, я хочу установить Consent Mode override для определённых регионов, чтобы по умолчанию блокировать сбор данных в ЕЭЗ
- Как юрист, я хочу убедиться, что теги не срабатывают до получения явного согласия пользователя

**Бизнес-правила:**
- Consent Mode управляет следующими параметрами согласия:
  - `ad_storage` — хранение данных для рекламы (куки)
  - `analytics_storage` — хранение данных для аналитики (куки)
  - `ad_user_data` — передача пользовательских данных для рекламы
  - `ad_personalization` — персонализация рекламы
  - `functionality_storage` — хранение функциональных данных
  - `personalization_storage` — хранение данных персонализации
  - `security_storage` — хранение данных безопасности
- Два режима реализации:
  - **Basic Mode:** теги полностью блокируются до получения согласия
  - **Advanced Mode:** теги загружаются с настройками по умолчанию и адаптируют поведение после получения согласия (позволяет конверсионное моделирование)
- По умолчанию все параметры согласия должны быть установлены в `denied` для регионов, требующих согласия
- После получения согласия пользователя система обновляет параметры через dataLayer-событие
- Настройка «Set consent mode override» позволяет переопределить значения по умолчанию для выбранных регионов
- Consent Mode v2 обязателен — включает параметры `ad_user_data` и `ad_personalization`
- По решению суда (Ганновер, 2025) — загрузка GTM в ряде юрисдикций сама по себе требует предварительного согласия пользователя

### FR-ADM-010: Связка с Google Analytics и Google-тегами

**Описание:** Система должна обеспечивать интеграцию GTM с Google Analytics, Google Ads и другими продуктами Google через единый Google-тег.

**User Stories:**
- Как маркетолог, я хочу настроить отправку данных в Google Analytics 4 через GTM для отслеживания поведения на сайте
- Как рекламный специалист, я хочу настроить конверсионное отслеживание Google Ads через GTM
- Как администратор, я хочу использовать единый Google-тег для отправки данных в несколько сервисов Google одновременно
- Как администратор, я хочу связать аккаунт GTM с организацией Google Marketing Platform для централизованного управления

**Бизнес-правила:**
- Google-тег (gtag.js) может быть настроен в GTM для отправки данных в несколько пунктов назначения (Google Analytics, Google Ads, Floodlight и др.)
- Один контейнер GTM может содержать несколько Google-тегов для разных аккаунтов
- Связь Google Analytics и Google Ads должна быть настроена как в GTM, так и в панелях управления самих сервисов
- При привязке аккаунта GTM к организации Google Marketing Platform все объекты (контейнеры, свойства Analytics) становятся доступны из единой панели администрирования
- GTM поддерживает интеграцию с: Google Analytics 4, Google Ads, Campaign Manager 360, Display & Video 360, Search Ads 360, Floodlight

### FR-ADM-011: Зоны (Zones) — GTM 360

**Описание:** Система должна поддерживать зоны — механизм делегирования управления тегами сторонним командам с ограничениями по страницам и типам компонентов. Доступно только в GTM 360.

**User Stories:**
- Как владелец сайта, я хочу предоставить рекламному агентству возможность управлять своими тегами на определённых страницах, не давая доступ ко всему контейнеру
- Как администратор, я хочу ограничить типы тегов, которые стороннее агентство может использовать в своей зоне
- Как администратор, я хочу подключить контейнер партнёра к определённым страницам моего сайта
- Как партнёр, я хочу управлять своим контейнером независимо, зная, что он будет работать только в границах, определённых владельцем сайта

**Бизнес-правила:**
- Зона позволяет связать один или несколько дополнительных (дочерних) контейнеров с основным контейнером
- Дочерний контейнер может принадлежать любому аккаунту GTM (включая сторонние)
- Границы зоны (Boundaries) определяют, на каких страницах срабатывает дочерний контейнер:
  - «Все страницы» (по умолчанию)
  - «Некоторые страницы» — с условиями на URL, путь, хост и др.
- Ограничения типов (Type Restrictions) позволяют указать, какие типы тегов, триггеров и переменных разрешены в дочернем контейнере
- Права пользователей основного и дочернего контейнеров настраиваются независимо
- Дочерний контейнер срабатывает только при загрузке основного контейнера
- Зоны доступны исключительно в GTM 360

### FR-ADM-012: Согласования (Approvals) — GTM 360

**Описание:** Система должна поддерживать процесс согласования изменений перед публикацией для обеспечения корпоративного контроля. Доступно только в GTM 360.

**User Stories:**
- Как маркетолог с правом Approve, я хочу запросить одобрение на публикацию своих изменений у ответственного лица
- Как ревьюер, я хочу просмотреть предложенные изменения и оставить комментарий перед одобрением
- Как администратор, я хочу настроить обязательное согласование перед публикацией для определённых пользователей
- Как менеджер, я хочу видеть очередь запросов на согласование

**Бизнес-правила:**
- Пользователь с правом Approve может предлагать изменения к публикации, но не может опубликовать самостоятельно
- Запрос на согласование содержит описание изменений и может быть прокомментирован
- Только пользователь с правом Publish может утвердить и опубликовать запрошенные изменения
- Встроенная система комментариев позволяет вести обсуждение по конкретному запросу
- Согласования доступны исключительно в GTM 360
- Workflow: предложение → обсуждение (комментарии) → одобрение/отклонение → публикация

### FR-ADM-013: Интеграция с Google Marketing Platform

**Описание:** Система должна поддерживать привязку аккаунтов GTM к организации Google Marketing Platform для централизованного корпоративного управления.

**User Stories:**
- Как корпоративный администратор, я хочу привязать аккаунт GTM к нашей организации GMP для единого управления
- Как администратор организации, я хочу видеть все связанные аккаунты GTM, Analytics и Ads в одной панели
- Как администратор, я хочу перенести аккаунт GTM между организациями при реструктуризации
- Как корпоративный менеджер, я хочу обновить стандартный GTM до GTM 360 через GMP

**Бизнес-правила:**
- Привязка к организации даёт доступ ко всем объектам аккаунта (контейнеры, свойства) из единой панели Administration в GMP
- Организация может содержать множество аккаунтов GTM, Analytics, Google Ads
- Перенос аккаунта между организациями требует прав администратора в обеих организациях
- Обновление до GTM 360 доступно только через организацию GMP (платная подписка)
- Роли организации могут наследоваться на уровне аккаунтов GTM

### FR-ADM-014: Безопасность и защита данных

**Описание:** Система должна обеспечивать соответствие требованиям безопасности и защиты данных при управлении тегами.

**User Stories:**
- Как DPO (ответственный за защиту данных), я хочу убедиться, что через GTM не собираются персональные данные без согласия
- Как администратор, я хочу контролировать, какие сторонние скрипты могут выполняться через GTM
- Как администратор, я хочу принять Соглашение об обработке данных (Data Processing Amendment) для соответствия GDPR

**Бизнес-правила:**
- GTM сам по себе не устанавливает куки и не собирает персональные данные — это делают теги, управляемые через GTM
- Ответственность за данные, собираемые через теги, лежит на владельце аккаунта
- Data Processing Amendment (DPA) доступно для подписания в настройках аккаунта
- Ограничения типов в зонах (GTM 360) позволяют контролировать, какие типы скриптов могут запускаться
- Consent Mode обеспечивает техническую блокировку сбора данных до получения согласия
- Загрузка GTM на сайт может требовать предварительного согласия в некоторых юрисдикциях (ЕЭЗ)

## Состояния и статусы

### Состояния рабочего пространства (Workspace)

```
[Создано] → [Активно] → [Опубликовано] → [Закрыто/Удалено]
                ↓
          [Устарело] → [Синхронизировано] → [Активно]
                              ↓
                       [Конфликт] → [Разрешён] → [Активно]
```

- **Создано** — рабочее пространство только что создано, изменений нет
- **Активно** — ведётся работа, есть несохранённые изменения
- **Устарело** — другое пространство опубликовало версию, текущее пространство не синхронизировано
- **Синхронизировано** — пространство обновлено до актуальной версии
- **Конфликт** — при синхронизации обнаружены конфликтующие изменения, требуется ручное разрешение
- **Опубликовано** — изменения пространства опубликованы как новая версия
- **Закрыто/Удалено** — пространство более не используется

### Состояния версии (Version)

```
[Черновик] → [Сохранена] → [Опубликована] → [Заменена]
                                                ↓
                                          [Восстановлена] → [Опубликована]
```

- **Черновик** — изменения в рабочем пространстве ещё не оформлены в версию
- **Сохранена** — версия создана, но не опубликована
- **Опубликована** — версия активна в Live-среде
- **Заменена** — версия была Live, но вытеснена более новой публикацией
- **Восстановлена** — ранее опубликованная версия скопирована обратно в рабочее пространство для повторной публикации

### Состояния среды (Environment)

```
[Создана] → [Настроена] → [Активна (сниппет установлен)] → [Удалена]
```

- **Создана** — среда определена, но сниппет не установлен
- **Настроена** — указан URL назначения, режим отладки, сгенерирован сниппет
- **Активна** — сниппет установлен на целевом сайте, среда используется
- **Удалена** — среда удалена из GTM

### Состояния запроса на согласование (Approval) — GTM 360

```
[Создан] → [На рассмотрении] → [Одобрен] → [Опубликован]
                    ↓
              [Отклонён] → [Доработан] → [На рассмотрении]
```

- **Создан** — пользователь создал запрос на публикацию
- **На рассмотрении** — запрос отправлен ревьюеру, идёт обсуждение в комментариях
- **Одобрен** — ревьюер утвердил изменения
- **Отклонён** — ревьюер отклонил изменения с комментарием
- **Доработан** — автор внёс правки по замечаниям
- **Опубликован** — одобренные изменения опубликованы

### Параметры Consent Mode

```
[Не настроен] → [По умолчанию: denied] → [Обновлён: granted] (после согласия)
                                          [Остаётся: denied] (отказ пользователя)
```

- **Не настроен** — Consent Mode не активирован для тега
- **По умолчанию: denied** — начальное состояние, данные не собираются
- **Обновлён: granted** — пользователь дал согласие, сбор данных активирован
- **Остаётся: denied** — пользователь отказал, сбор данных заблокирован

## Ограничения и лимиты

| Параметр | Стандартный GTM | GTM 360 |
|----------|----------------|---------|
| Контейнеры на аккаунт | 500 | 500 |
| Рабочие пространства на контейнер | 3 | Неограниченно |
| Теги на контейнер | 5 000 | 50 000 |
| Триггеры на контейнер | 2 000 | 10 000 |
| Пользовательские переменные | 2 000 | 10 000 |
| Размер контейнера | 200 КБ | 200 КБ |
| Зоны | Недоступно | Доступно |
| Согласования (Approvals) | Недоступно | Доступно |
| API: запросов в день | 10 000 | 10 000 |
| API: запросов в секунду | 0.25 QPS (25 за 100 сек) | 0.25 QPS |
| Пользовательские среды | Неограниченно | Неограниченно |

### Критические ограничения
- При превышении размера контейнера 200 КБ публикация блокируется до оптимизации
- При превышении API-квот возвращается ошибка 403 Forbidden
- Увеличение API-квот возможно через запрос в Google API Console
- Минимум один администратор в аккаунте — система не позволяет удалить последнего
