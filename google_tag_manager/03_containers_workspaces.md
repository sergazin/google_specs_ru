# Контейнеры и рабочие области (Workspaces)

## Описание

Контейнеры -- основная организационная единица Google Tag Manager, объединяющая теги, триггеры, переменные и шаблоны в единый управляемый пакет, привязанный к конкретному цифровому ресурсу (сайту, мобильному приложению, AMP-странице или серверному окружению). Каждый контейнер получает уникальный идентификатор в формате `GTM-XXXXXXX` и содержит сниппет для установки на целевой ресурс.

Рабочие области (Workspaces) обеспечивают параллельную работу нескольких пользователей над одним контейнером. Каждая рабочая область -- это изолированная копия контейнера, в которой можно вносить изменения независимо от других рабочих областей. Изменения из рабочей области публикуются через создание версии контейнера.

Среды (Environments) позволяют тестировать изменения контейнера на разных стадиях разработки (dev, staging, QA) до публикации в production.

## Роли пользователей

### Уровень аккаунта

| Роль | Описание |
|------|----------|
| **Администратор (Admin)** | Создание контейнеров, управление пользователями и правами на уровне аккаунта и контейнеров. Наследует право Read на все контейнеры аккаунта. Может назначать себе дополнительные права |
| **Пользователь (User)** | Просмотр базовой информации аккаунта. Не наследует никаких прав на контейнеры -- права назначаются отдельно администратором |

### Уровень контейнера

| Право | Описание |
|-------|----------|
| **Чтение (Read)** | Просмотр списка контейнеров, тегов, триггеров, переменных. Без возможности внесения изменений |
| **Редактирование (Edit)** | Создание рабочих областей, редактирование тегов/триггеров/переменных. Без возможности создания версий и публикации. В GTM 360 -- может отправлять запрос на одобрение вместо публикации |
| **Одобрение (Approve)** | Все права Edit + создание версий + одобрение запросов (GTM 360). Без возможности публикации |
| **Публикация (Publish)** | Полные права: редактирование, создание версий, одобрение, публикация |

### Дополнительные роли (GTM 360)

| Роль | Описание |
|------|----------|
| **Рецензент (Reviewer)** | Получает запросы на одобрение, может утвердить или отклонить изменения перед публикацией |

## Функциональные требования

### FR-CNT-001: Создание контейнера

**Описание:** Пользователь с правами администратора аккаунта создает новый контейнер внутри аккаунта GTM.

**Акторы:** Администратор аккаунта

**Предусловия:**
- Пользователь авторизован и имеет права Admin на уровне аккаунта
- Аккаунт не достиг лимита контейнеров (500)

**Основной сценарий:**
1. Пользователь указывает название контейнера
2. Пользователь выбирает тип контейнера: Web, iOS, Android, AMP или Server
3. Система генерирует уникальный идентификатор контейнера в формате GTM-XXXXXXX
4. Система создает контейнер с рабочей областью "Default Workspace"
5. Для Web-контейнера система генерирует два сниппета кода для установки на сайт
6. Для Server-контейнера система предлагает настроить серверную инфраструктуру (автоматическое развертывание в GCP или ручная настройка)

**Альтернативный сценарий (Server-контейнер):**
1. При выборе типа Server пользователь выбирает способ развертывания:
   - Автоматическое развертывание (GCP Cloud Run) -- система создает GCP-проект, два Cloud Run-сервиса (tagging server + preview server)
   - Ручная настройка на существующей инфраструктуре
2. Система создает два сервиса: server-side-tagging (основной) и server-side-tagging-preview (для предпросмотра)

**Результат:** Контейнер создан, доступен для настройки тегов/триггеров/переменных

**Бизнес-правила:**
- BR-CNT-001: Один аккаунт может содержать до 500 контейнеров
- BR-CNT-002: Тип контейнера нельзя изменить после создания
- BR-CNT-003: Каждый контейнер получает уникальный GTM-ID, который не переиспользуется
- BR-CNT-004: Набор доступных тегов, триггеров и переменных зависит от типа контейнера

---

### FR-CNT-002: Типы контейнеров и их особенности

**Описание:** Система поддерживает пять типов контейнеров, каждый из которых оптимизирован для своего типа ресурса.

| Тип | Целевой ресурс | Способ установки | Особенности |
|-----|---------------|------------------|-------------|
| **Web** | Веб-сайт | JavaScript-сниппет в head и body | Наиболее полный набор тегов и триггеров. Данные отправляются из браузера пользователя |
| **iOS** | iOS-приложение | Firebase SDK | Специфичный набор тегов/триггеров для мобильных приложений |
| **Android** | Android-приложение | Firebase SDK | Специфичный набор тегов/триггеров для мобильных приложений |
| **AMP** | AMP-страницы | AMP-совместимый сниппет | Ограниченный набор тегов, совместимых с AMP-форматом |
| **Server** | Серверное окружение | Cloud Run / App Engine / собственный сервер | Данные обрабатываются на сервере, а не в браузере. Повышенная безопасность и контроль данных. Требует отдельную серверную инфраструктуру с оплатой хостинга |

**Бизнес-правила:**
- BR-CNT-005: Мобильные контейнеры (iOS, Android) имеют иной набор тегов, триггеров и переменных, чем Web
- BR-CNT-006: AMP-контейнеры имеют ограниченный набор тегов из-за ограничений AMP-формата
- BR-CNT-007: Server-контейнер требует отдельной серверной инфраструктуры (минимум ~120 USD/мес для production: 3 сервера по ~40 USD)
- BR-CNT-008: Server-контейнер получает данные от клиента и перенаправляет их в аналитические и рекламные платформы на стороне сервера

---

### FR-CNT-003: Установка контейнера на целевой ресурс

**Описание:** Пользователь устанавливает контейнер на свой цифровой ресурс для активации управления тегами.

**Акторы:** Пользователь с правами Read и выше на контейнер, Веб-разработчик

**Основной сценарий (Web):**
1. Пользователь получает два фрагмента кода из интерфейса GTM
2. Первый фрагмент (JavaScript) размещается в секции `<head>` сайта как можно выше
3. Второй фрагмент (noscript) размещается сразу после открывающего тега `<body>`
4. После установки сниппетов контейнер начинает функционировать на сайте

**Бизнес-правила:**
- BR-CNT-009: Для CMS-платформ (WordPress, Wix и др.) достаточно указать GTM-ID в плагине без полного сниппета
- BR-CNT-010: Нельзя размещать noscript-фрагмент в `<head>` -- только после `<body>`
- BR-CNT-011: Для production-окружения рекомендуется использовать стандартный сниппет, а не snippet среды

---

### FR-CNT-004: Создание рабочей области (Workspace)

**Описание:** Пользователь создает новую рабочую область для параллельной работы над изменениями контейнера.

**Акторы:** Пользователь с правами Edit и выше

**Предусловия:**
- Контейнер существует
- Не достигнут лимит рабочих областей (3 для бесплатной версии)

**Основной сценарий:**
1. Пользователь указывает название рабочей области
2. Пользователь (опционально) добавляет описание
3. Система создает копию текущего состояния контейнера (последняя опубликованная версия) как новую рабочую область
4. Пользователь может вносить изменения в теги, триггеры, переменные внутри рабочей области
5. Изменения в одной рабочей области не влияют на другие рабочие области

**Результат:** Новая изолированная рабочая область создана и готова к редактированию

**Бизнес-правила:**
- BR-WS-001: Бесплатная версия GTM -- до 3 одновременных рабочих областей (1 Default + 2 пользовательские)
- BR-WS-002: GTM 360 -- неограниченное количество рабочих областей
- BR-WS-003: Рабочая область "Default Workspace" создается автоматически при создании контейнера и не может быть удалена
- BR-WS-004: Каждая рабочая область -- независимая копия контейнера, изолированная от других

---

### FR-CNT-005: Редактирование в рабочей области

**Описание:** Пользователь вносит изменения в теги, триггеры и переменные внутри своей рабочей области.

**Акторы:** Пользователь с правами Edit и выше

**Основной сценарий:**
1. Пользователь открывает нужную рабочую область
2. Пользователь создает, редактирует или удаляет теги, триггеры, переменные
3. Все изменения автоматически сохраняются внутри рабочей области
4. Обзорная страница рабочей области отображает список всех внесенных изменений (добавленных, измененных, удаленных сущностей)

**Бизнес-правила:**
- BR-WS-005: Изменения в рабочей области не влияют на живой контейнер до публикации
- BR-WS-006: Пользователь может отменить (revert) индивидуальные изменения тегов, триггеров, переменных -- откат к состоянию последней синхронизации
- BR-WS-007: Рабочая область отслеживает все несохраненные изменения и отображает их на странице обзора

---

### FR-CNT-006: Синхронизация рабочей области

**Описание:** Система обнаруживает расхождения между рабочей областью и последней версией контейнера, позволяя подтянуть свежие изменения.

**Акторы:** Пользователь с правами Edit и выше

**Предусловия:**
- Другой пользователь опубликовал новую версию контейнера после создания текущей рабочей области

**Основной сценарий:**
1. Система уведомляет пользователя о наличии обновлений в контейнере
2. Пользователь запускает синхронизацию рабочей области
3. Система обновляет все неизмененные сущности до последней версии контейнера
4. Если сущность была изменена и в рабочей области, и в новой версии контейнера -- фиксируется конфликт

**Результат:** Рабочая область обновлена до последней версии контейнера, конфликты выявлены

**Бизнес-правила:**
- BR-WS-008: Синхронизация обновляет только неизмененные в рабочей области сущности
- BR-WS-009: Конфликтные сущности не обновляются автоматически -- требуется ручное разрешение
- BR-WS-010: Синхронизация обязательна перед публикацией, если контейнер был обновлен

---

### FR-CNT-007: Разрешение конфликтов

**Описание:** При конфликте между изменениями рабочей области и новой версией контейнера пользователь вручную разрешает каждый конфликт.

**Акторы:** Пользователь с правами Edit и выше

**Предусловия:**
- Синхронизация выявила конфликты

**Основной сценарий:**
1. Система отображает страницу разрешения конфликтов
2. Для каждого конфликта показывается два варианта:
   - Слева: конфигурация из последней синхронизированной версии контейнера
   - Справа: конфигурация из текущей рабочей области
3. Отличия подсвечиваются цветом:
   - Синий -- изменение в текущей рабочей области относительно последней синхронизации
   - Красный -- изменение в последней версии контейнера, отсутствующее в рабочей области
4. Для каждого конфликта пользователь выбирает:
   - Игнорировать изменение из новой версии (сохранить свою правку)
   - Принять изменение из новой версии (перезаписать свою правку)
5. После разрешения всех конфликтов пользователь сохраняет результат

**Бизнес-правила:**
- BR-WS-011: Конфликты разрешаются по одному, для каждой сущности отдельно
- BR-WS-012: Нельзя публиковать рабочую область с неразрешенными конфликтами
- BR-WS-013: Частичное слияние (cherry-pick отдельных полей) не поддерживается -- выбирается вариант целиком

### FR-CNT-008: Публикация версии контейнера

**Описание:** Пользователь публикует изменения из рабочей области, создавая новую версию контейнера, которая становится активной на целевом ресурсе.

**Акторы:** Пользователь с правами Publish (или Approve для создания версии без публикации)

**Предусловия:**
- Рабочая область синхронизирована с последней версией контейнера
- Все конфликты разрешены
- Есть хотя бы одно изменение в рабочей области

**Основной сценарий:**
1. Пользователь нажимает "Submit" (Отправить)
2. Пользователь указывает название версии и описание изменений
3. Система создает новую версию контейнера с инкрементным номером
4. Пользователь выбирает: "Publish and Create Version" (публикация) или "Create Version" (только сохранение версии без публикации)
5. При публикации новая версия немедленно становится активной на production-ресурсе
6. Рабочая область очищается (возвращается к состоянию без изменений)

**Альтернативный сценарий (GTM 360 -- запрос одобрения):**
1. Пользователь с правами Edit нажимает "Submit"
2. Вместо публикации создается запрос на одобрение
3. Пользователь может назначить конкретного рецензента
4. Пользователь может добавить комментарий с описанием и инструкциями
5. Рецензент получает уведомление
6. Рецензент утверждает или отклоняет запрос
7. При утверждении -- пользователь с правами Publish может опубликовать версию
8. При отклонении -- автор получает уведомление с комментарием

**Бизнес-правила:**
- BR-VER-001: Каждая публикация создает версию с уникальным инкрементным номером
- BR-VER-002: История версий сохраняется бессрочно
- BR-VER-003: Workflow одобрения доступен только в GTM 360
- BR-VER-004: Публикация немедленно влияет на все страницы/приложения с установленным контейнером
- BR-VER-005: После публикации рабочая область сбрасывается до состояния опубликованной версии

---

### FR-CNT-009: Управление историей версий

**Описание:** Система ведет полную историю всех версий контейнера с возможностью просмотра, сравнения и восстановления.

**Акторы:** Пользователь с правами Read и выше

**Основной сценарий:**
1. Пользователь открывает раздел "Versions" (Версии)
2. Система отображает список всех версий с информацией:
   - Номер версии
   - Название и описание
   - Автор публикации
   - Дата и время публикации
   - Период, в течение которого версия была активна (live)
3. Пользователь может просмотреть содержимое любой версии
4. Пользователь может сравнить две версии

**Бизнес-правила:**
- BR-VER-006: Все версии хранятся бессрочно и не могут быть удалены
- BR-VER-007: Система фиксирует, когда каждая версия была активна (live) и кто ее опубликовал

---

### FR-CNT-010: Откат к предыдущей версии

**Описание:** Пользователь восстанавливает предыдущую версию контейнера в случае обнаружения проблем.

**Акторы:** Пользователь с правами Publish

**Предусловия:**
- Существует хотя бы одна предыдущая версия контейнера

**Основной сценарий (быстрый откат через прямую публикацию):**
1. Пользователь открывает раздел "Versions"
2. Пользователь находит нужную версию
3. Пользователь выбирает действие "Publish" из меню действий версии
4. Система немедленно публикует выбранную версию как текущую
5. Проблемная версия остается в истории

**Альтернативный сценарий (откат через рабочую область):**
1. Пользователь выбирает действие "Set as Latest Version" для нужной версии
2. Система копирует содержимое выбранной версии в рабочую область
3. Пользователь проверяет содержимое и нажимает "Submit" для публикации

**Бизнес-правила:**
- BR-VER-008: Откат не удаляет проблемную версию из истории -- она остается для анализа
- BR-VER-009: Прямая публикация старой версии -- самый быстрый способ отката
- BR-VER-010: "Set as Latest Version" позволяет проверить содержимое перед повторной публикацией

### FR-CNT-011: Экспорт контейнера

**Описание:** Пользователь экспортирует конфигурацию контейнера (теги, триггеры, переменные, шаблоны) в файл для переноса или резервного копирования.

**Акторы:** Пользователь с правами Read и выше

**Основной сценарий:**
1. Пользователь переходит в Admin > Export Container
2. Пользователь выбирает источник: конкретную версию или рабочую область
3. Система генерирует JSON-файл с полной конфигурацией контейнера
4. Пользователь скачивает файл

**Бизнес-правила:**
- BR-EXP-001: Экспорт включает теги, триггеры, переменные и шаблоны
- BR-EXP-002: Можно экспортировать как опубликованную версию, так и текущее состояние рабочей области
- BR-EXP-003: Экспортированный файл можно редактировать вручную для частичного экспорта (удаление ненужных сущностей из JSON)

---

### FR-CNT-012: Импорт контейнера

**Описание:** Пользователь импортирует конфигурацию контейнера из ранее экспортированного файла.

**Акторы:** Пользователь с правами Edit и выше

**Основной сценарий:**
1. Пользователь выбирает JSON-файл для импорта
2. Пользователь выбирает целевую рабочую область (новую или существующую)
3. Пользователь выбирает режим импорта:
   - **Перезапись (Overwrite):** полная замена всех тегов, триггеров и переменных контейнера содержимым файла
   - **Слияние (Merge):** добавление и обновление сущностей из файла без удаления существующих
4. При слиянии система показывает предпросмотр изменений для каждого конфликтующего элемента
5. Пользователь подтверждает импорт

**Бизнес-правила:**
- BR-IMP-001: Перезапись удаляет ВСЕ существующие теги, триггеры и переменные
- BR-IMP-002: Слияние сохраняет существующие сущности и добавляет/обновляет из файла
- BR-IMP-003: Импорт не создает автоматически версию -- изменения попадают в рабочую область для ревью и последующей публикации
- BR-IMP-004: При импорте в другой аккаунт контейнер получает новый GTM-ID -- прямой перенос контейнера между аккаунтами невозможен

### FR-CNT-013: Управление средами (Environments)

**Описание:** Пользователь создает и настраивает среды для тестирования изменений контейнера на разных стадиях разработки.

**Акторы:** Пользователь с правами Publish

**Предусловия:**
- Контейнер создан

**Основной сценарий:**
1. Пользователь создает новую среду (например: Development, Staging, QA)
2. Пользователь указывает название и описание среды
3. Система генерирует уникальный сниппет контейнера для этой среды (с токеном авторизации)
4. Разработчик устанавливает среду-специфичный сниппет на соответствующий сервер (dev, staging, QA)
5. Пользователь публикует конкретную версию контейнера в нужную среду
6. Среда показывает только назначенную ей версию контейнера

**Бизнес-правила:**
- BR-ENV-001: По умолчанию существуют две встроенные среды: Live (production) и Latest (последняя версия)
- BR-ENV-002: Пользовательские среды требуют установки отдельного сниппета с токеном авторизации
- BR-ENV-003: Каждая среда может отображать свою версию контейнера
- BR-ENV-004: На production-сайте рекомендуется использовать стандартный сниппет (без среды) для лучшей производительности
- BR-ENV-005: Ссылку предпросмотра среды можно поделиться с коллегами для тестирования

### FR-CNT-014: Зоны (Zones) -- GTM 360

**Описание:** Зоны позволяют привязать дополнительные контейнеры к определенным разделам сайта с независимым управлением правами и публикацией.

**Акторы:** Администратор (GTM 360)

**Основной сценарий:**
1. Администратор создает зону в основном контейнере
2. Администратор задает границы зоны -- на каких страницах зона активна (URL-правила)
3. Администратор задает ограничения по типам тегов, которые зона может запускать
4. Администратор привязывает дочерний контейнер к зоне
5. Дочерний контейнер получает собственных пользователей и права, независимые от основного контейнера
6. Публикация дочернего контейнера происходит независимо от основного

**Бизнес-правила:**
- BR-ZONE-001: Зоны доступны только в GTM 360
- BR-ZONE-002: Дочерний контейнер зоны имеет собственный набор пользователей и прав
- BR-ZONE-003: Очередь одобрения для дочернего контейнера отделена от основного
- BR-ZONE-004: Границы зоны ограничивают, на каких страницах дочерний контейнер может запускать теги
- BR-ZONE-005: Администратор может ограничить типы тегов, доступных внутри зоны

### FR-CNT-015: Предпросмотр и отладка контейнера

**Описание:** Пользователь тестирует изменения рабочей области в режиме предпросмотра перед публикацией.

**Акторы:** Пользователь с правами Edit и выше

**Основной сценарий:**
1. Пользователь нажимает "Preview" в своей рабочей области
2. Система активирует режим предпросмотра -- подключает Tag Assistant для отладки
3. Пользователь открывает целевой сайт в том же браузере
4. Tag Assistant показывает, какие теги сработали, какие нет, значения переменных и события data layer
5. Пользователь может поделиться ссылкой предпросмотра с коллегами

**Бизнес-правила:**
- BR-PREV-001: Предпросмотр работает только в рамках текущего браузера пользователя (через cookie)
- BR-PREV-002: Предпросмотр не влияет на живой контейнер -- посетители сайта видят опубликованную версию
- BR-PREV-003: Ссылкой предпросмотра можно поделиться для совместного тестирования

### FR-CNT-016: Удаление рабочей области

**Описание:** Пользователь удаляет рабочую область, отбрасывая все неопубликованные изменения.

**Акторы:** Пользователь с правами Edit и выше

**Предусловия:**
- Рабочая область не является Default Workspace

**Основной сценарий:**
1. Пользователь выбирает рабочую область для удаления
2. Система предупреждает, что все неопубликованные изменения будут потеряны
3. Пользователь подтверждает удаление
4. Система удаляет рабочую область и все неопубликованные изменения

**Бизнес-правила:**
- BR-WS-014: Default Workspace нельзя удалить
- BR-WS-015: Удаление рабочей области необратимо -- все неопубликованные изменения теряются
- BR-WS-016: Удаление рабочей области не влияет на опубликованные версии контейнера

---

### FR-CNT-017: Удаление контейнера

**Описание:** Администратор удаляет контейнер из аккаунта.

**Акторы:** Администратор аккаунта

**Основной сценарий:**
1. Администратор выбирает контейнер для удаления
2. Система предупреждает о последствиях (контейнер перестанет функционировать на всех ресурсах)
3. Администратор подтверждает удаление
4. Контейнер удаляется со всеми версиями, рабочими областями и настройками

**Бизнес-правила:**
- BR-CNT-012: После удаления контейнера установленные на сайте сниппеты перестают функционировать
- BR-CNT-013: GTM-ID удаленного контейнера не переиспользуется

## Интеграции с другими модулями

### Теги, триггеры и переменные
- Контейнер является контейнером (хранилищем) для тегов, триггеров и переменных
- Тип контейнера определяет доступный набор тегов, триггеров и переменных
- Публикация версии контейнера активирует все настроенные теги на целевом ресурсе

### Управление пользователями и правами
- Права на контейнер (Read/Edit/Approve/Publish) назначаются на уровне контейнера
- Администратор аккаунта наследует Read-доступ ко всем контейнерам
- Зоны (GTM 360) позволяют настраивать отдельные права для дочерних контейнеров

### Google Analytics и другие продукты Google
- Контейнер может содержать теги для Google Analytics, Google Ads, Floodlight
- Server-контейнер может перенаправлять данные в GA4, Google Ads и другие платформы на стороне сервера

### Google Cloud Platform (для серверных контейнеров)
- Автоматическое развертывание серверного контейнера в Cloud Run или App Engine
- Биллинг серверной инфраструктуры идет через Google Cloud
- Масштабирование серверов управляется через GCP

### Шаблоны (Community Template Gallery)
- Контейнер может использовать шаблоны тегов из галереи сообщества
- Шаблоны импортируются в контейнер и становятся частью его конфигурации

### Предпросмотр и отладка (Tag Assistant)
- Режим предпросмотра рабочей области интегрирован с Tag Assistant
- Tag Assistant отображает активность тегов, триггеров и data layer в реальном времени

### Журнал изменений (Activity Log)
- Все действия с контейнером (создание, редактирование, публикация) фиксируются в журнале
- Журнал связывает действия с конкретными пользователями и версиями
