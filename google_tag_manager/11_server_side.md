# Server-Side Tagging

## Описание

Server-Side Tagging (серверная маркировка) — модуль Google Tag Manager, позволяющий переместить обработку тегов с браузера пользователя на выделенный сервер. Вместо того чтобы браузер отправлял десятки HTTP-запросов к различным рекламным и аналитическим платформам, клиентское устройство генерирует один запрос к серверному контейнеру, а тот уже распределяет данные по всем подключённым вендорам.

Серверный контейнер развёртывается в облачной инфраструктуре (Google Cloud Platform — Cloud Run или App Engine, а также любая сторонняя платформа, поддерживающая Docker). Контейнер принимает входящие запросы через сущность «Клиент» (Client), преобразует их в унифицированную модель Event Data, а затем серверные теги формируют исходящие запросы к конечным платформам (Google Analytics 4, Google Ads, Meta CAPI, TikTok и др.).

Ключевые бизнес-преимущества:
- **Производительность** — сокращение количества скриптов и HTTP-запросов на стороне браузера
- **Приватность и контроль данных** — фильтрация, редакция и обогащение данных до их отправки вендорам
- **First-party cookies** — установка серверных cookie от имени домена сайта, что увеличивает их срок жизни и устойчивость к блокировкам браузеров
- **Соответствие GDPR/CCPA** — централизованное управление согласием и минимизация передачи персональных данных третьим сторонам
- **Устойчивость к Ad Blockers** — запросы отправляются на собственный домен, а не на домены рекламных платформ

## Роли пользователей

Управление доступом к серверному контейнеру идентично модели прав GTM и действует на двух уровнях.

### Уровень аккаунта GTM

| Роль | Описание |
|------|----------|
| **Пользователь (User)** | Просмотр базовой информации об аккаунте |
| **Администратор (Administrator)** | Создание контейнеров, управление пользователями и их правами на уровне аккаунта и контейнеров |

### Уровень серверного контейнера

| Роль | Описание |
|------|----------|
| **Чтение (Read)** | Просмотр клиентов, тегов, триггеров, переменных, трансформаций. Без права изменения |
| **Редактирование (Edit)** | Создание рабочих пространств, редактирование всех сущностей контейнера. Без права создания версий и публикации |
| **Утверждение (Approve)** | Все права Edit + создание версий контейнера. Без права публикации |
| **Публикация (Publish)** | Полные права: редактирование, создание версий, публикация |

### Дополнительные роли (Tag Manager 360)

| Роль | Описание |
|------|----------|
| **Запросчик утверждения** | Пользователь с правами Edit и выше может запросить одобрение на публикацию |
| **Утверждающий** | Пользователь с правами Approve/Publish рассматривает запрос и принимает/отклоняет |

### Роль инфраструктурного администратора

Отдельно от GTM существует роль администратора облачной инфраструктуры (Google Cloud IAM), который управляет:
- Развёртыванием и масштабированием серверов
- Биллингом облачных ресурсов
- Настройкой домена и SSL-сертификатов
- Мониторингом и логированием на уровне инфраструктуры

## Функциональные требования

### FR-SST-001: Создание серверного контейнера

**Описание:** Пользователь с правами Administrator создаёт новый контейнер с типом «Server».

**Предусловия:**
- У пользователя есть аккаунт GTM
- Пользователь имеет роль Administrator на уровне аккаунта

**Основной сценарий:**
1. Пользователь выбирает «Создать контейнер»
2. Указывает название контейнера
3. Выбирает целевую платформу «Server»
4. Система создаёт серверный контейнер с предустановленными клиентами GA4 и переменными по умолчанию
5. Система предлагает настроить сервер тегирования (автоматическое или ручное развёртывание)

**Бизнес-правила:**
- BR-001: Один аккаунт GTM может содержать до 500 контейнеров (серверных и веб- суммарно)
- BR-002: При создании серверного контейнера автоматически подключаются встроенные клиенты: GA4, Universal Analytics, Measurement Protocol (GA4)
- BR-003: Контейнер создаётся в состоянии «Не опубликован» без привязки к серверу

---

### FR-SST-002: Развёртывание сервера тегирования

**Описание:** Настройка серверной инфраструктуры, на которой будет работать контейнер.

**Предусловия:**
- Серверный контейнер создан
- Пользователь имеет доступ к облачной платформе

**Вариант A — Автоматическое развёртывание (Google Cloud):**
1. Пользователь выбирает «Автоматическая настройка»
2. Авторизуется в Google Cloud
3. Система автоматически создаёт проект GCP и разворачивает контейнер на Cloud Run
4. Система возвращает URL серверного контейнера

**Вариант B — Ручное развёртывание:**
1. Пользователь получает конфигурационные параметры контейнера (Container Config)
2. Разворачивает Docker-образ на выбранной платформе (Cloud Run, App Engine, любой Docker-хостинг)
3. Передаёт Container Config как переменную окружения
4. Указывает URL развёрнутого сервера в настройках контейнера GTM

**Бизнес-правила:**
- BR-004: Автоматическое развёртывание создаёт один экземпляр сервера — только для тестирования
- BR-005: Для продакшена рекомендуется минимум 3 экземпляра сервера для обеспечения отказоустойчивости
- BR-006: Container Config содержит зашифрованные параметры контейнера и не должен быть публично доступен

---

### FR-SST-003: Настройка пользовательского домена (Custom Domain)

**Описание:** Привязка собственного домена или поддомена сайта к серверному контейнеру для обеспечения first-party контекста.

**Предусловия:**
- Сервер тегирования развёрнут и доступен
- Пользователь имеет доступ к управлению DNS

**Основной сценарий (Same Origin — рекомендуемый):**
1. Пользователь настраивает CDN/балансировщик для маршрутизации запросов по пути (например, `example.com/sgtm`) на сервер тегирования
2. Серверный контейнер становится доступен по тому же домену что и сайт

**Альтернативный сценарий (Subdomain):**
1. Пользователь создаёт поддомен (например, `metrics.example.com`)
2. Настраивает DNS A/AAAA-записи, указывающие на IP-адрес сервера тегирования
3. Сервер тегирования автоматически получает SSL-сертификат

**Бизнес-правила:**
- BR-007: Same Origin подход обеспечивает максимальную устойчивость cookie — они считаются полностью first-party
- BR-008: При использовании поддомена рекомендуются A/AAAA-записи, а не CNAME, для обхода ограничений браузеров по отслеживанию (ITP)
- BR-009: CNAME-записи менее эффективны для продления жизни cookie из-за механизмов защиты от трекинга в Safari и Firefox
- BR-010: Пользовательский домен обязателен для установки first-party серверных cookie

---

### FR-SST-004: Управление клиентами (Clients)

**Описание:** Клиенты — первый компонент серверного контейнера, который принимает входящие HTTP-запросы, распознаёт их формат и преобразует в объект Event Data.

**Предусловия:**
- Серверный контейнер создан
- Пользователь имеет права Edit и выше

**Основной сценарий:**
1. Пользователь переходит в раздел «Clients» серверного контейнера
2. Создаёт нового клиента или редактирует существующий
3. Выбирает тип клиента (встроенный или из галереи шаблонов)
4. Настраивает параметры клиента
5. Задаёт приоритет выполнения клиента

**Встроенные клиенты:**

| Клиент | Описание |
|--------|----------|
| **Google Analytics: GA4** | Принимает запросы формата GA4 (gtag.js) |
| **Google Analytics: Universal Analytics** | Принимает запросы формата analytics.js / gtag.js (UA) |
| **Measurement Protocol (GA4)** | Принимает запросы Measurement Protocol |

**Бизнес-правила:**
- BR-011: Клиент «заявляет» (claims) входящий запрос, если распознаёт его формат. После заявки другие клиенты запрос не обрабатывают
- BR-012: Порядок обработки клиентов определяется приоритетом — клиент с наивысшим приоритетом проверяет запрос первым
- BR-013: Если ни один клиент не заявил запрос, он отбрасывается
- BR-014: Клиент преобразует входящий HTTP-запрос в объект Event Data — унифицированную структуру данных события
- BR-015: Пользовательские клиенты могут быть добавлены из Community Template Gallery или созданы вручную

---

### FR-SST-005: Управление серверными тегами (Server Tags)

**Описание:** Серверные теги получают объект Event Data от клиента, преобразуют его и отправляют исходящий HTTP-запрос на конечную платформу.

**Предусловия:**
- Серверный контейнер создан
- Настроен хотя бы один клиент
- Пользователь имеет права Edit и выше

**Основной сценарий:**
1. Пользователь создаёт новый тег
2. Выбирает тип тега (встроенный, из галереи или пользовательский)
3. Настраивает параметры тега (идентификаторы, маппинг событий и параметров)
4. Привязывает триггер(ы) активации
5. Опционально настраивает трансформации

**Встроенные серверные теги:**

| Тег | Описание |
|-----|----------|
| **Google Analytics: GA4** | Отправка данных в Google Analytics 4 |
| **Google Ads Conversion Tracking** | Отслеживание конверсий Google Ads |
| **Google Ads Remarketing** | Ремаркетинг-теги Google Ads |
| **Floodlight Counter** | Счётчик Floodlight (Campaign Manager 360) |
| **Floodlight Sales** | Тег продаж Floodlight (Campaign Manager 360) |
| **HTTP Request** | Универсальный тег для отправки произвольных HTTP-запросов |

**Популярные теги из галереи:**

| Тег | Описание |
|-----|----------|
| **Meta Conversions API (CAPI)** | Отправка серверных событий в Meta (Facebook) |
| **TikTok Events API** | Серверное отслеживание TikTok |
| **Snapchat Conversions API** | Серверное отслеживание Snapchat |
| **LinkedIn Conversions API** | Серверное отслеживание LinkedIn |
| **Pinterest Conversions API** | Серверное отслеживание Pinterest |

**Бизнес-правила:**
- BR-016: Тег срабатывает только если привязанный триггер активирован и клиент заявил входящий запрос
- BR-017: Один и тот же тег может быть привязан к нескольким триггерам (логика ИЛИ)
- BR-018: Тег может иметь триггеры исключения — условия, при которых тег НЕ срабатывает (приоритет выше триггеров активации)
- BR-019: С апреля 2025 контейнеры с тегами Google Ads и Floodlight автоматически загружают Google Tag перед отправкой событий
- BR-020: Тег GA4 в серверном контейнере автоматически маршрутизирует данные в региональный дата-центр на основе местоположения пользователя

### FR-SST-006: Управление триггерами (Triggers)

**Описание:** Триггеры определяют условия, при которых серверные теги должны сработать. Триггеры проверяют параметры объекта Event Data.

**Предусловия:**
- Серверный контейнер создан
- Пользователь имеет права Edit и выше

**Основной сценарий:**
1. Пользователь создаёт новый триггер
2. Выбирает тип триггера
3. Задаёт условия фильтрации по параметрам Event Data
4. Привязывает триггер к одному или нескольким тегам

**Типы серверных триггеров:**

| Тип | Описание |
|-----|----------|
| **Custom** | Срабатывает на основе пользовательских условий по любым параметрам Event Data |
| **All Events** | Срабатывает на каждое событие, обработанное любым клиентом |
| **Page View** | Срабатывает при событии page_view |

**Бизнес-правила:**
- BR-021: Условия триггера основаны на параметрах объекта Event Data (event_name, page_location, user_id и др.)
- BR-022: Триггер может содержать несколько условий — все должны быть выполнены одновременно (логика И)
- BR-023: Триггер срабатывает только после того, как клиент заявил запрос и создал объект Event Data

---

### FR-SST-007: Управление переменными (Variables)

**Описание:** Переменные извлекают значения из объекта Event Data, HTTP-запросов, cookie и других источников для использования в тегах и триггерах.

**Предусловия:**
- Серверный контейнер создан
- Пользователь имеет права Edit и выше

**Типы встроенных переменных:**

| Переменная | Описание |
|------------|----------|
| **Event Name** | Название события из Event Data |
| **Client Name** | Имя клиента, который заявил запрос |
| **Container ID** | Идентификатор серверного контейнера |
| **Container Version** | Текущая версия контейнера |
| **Random Number** | Случайное число |
| **Request Method** | HTTP-метод входящего запроса (GET, POST) |
| **Request URL** | URL входящего запроса |
| **Request Path** | Путь входящего запроса |
| **Request Query** | Параметры запроса |

**Типы пользовательских переменных:**

| Переменная | Описание |
|------------|----------|
| **Event Data** | Извлечение любого параметра из объекта Event Data по ключу |
| **Query String** | Извлечение параметра из строки запроса |
| **Request Header** | Извлечение значения HTTP-заголовка |
| **Cookie** | Чтение значения cookie из входящего запроса |
| **Lookup Table** | Маппинг значений на основе таблицы соответствий |
| **RegEx Table** | Маппинг значений на основе регулярных выражений |
| **Constant** | Константное значение |
| **Undefined** | Возвращает undefined |
| **Google Tag: Settings** | Настройки Google Tag |

**Бизнес-правила:**
- BR-024: Переменные могут использоваться в любом поле тега или условии триггера через синтаксис {{имя_переменной}}
- BR-025: Пользовательские переменные могут быть созданы из Community Template Gallery
- BR-026: Встроенные переменные по умолчанию отключены — их нужно явно активировать

### FR-SST-008: Трансформации (Transformations)

**Описание:** Трансформации — промежуточный объект между клиентом и тегами, позволяющий модифицировать объект Event Data до его обработки тегами.

**Предусловия:**
- Серверный контейнер создан
- Пользователь имеет права Edit и выше

**Основной сценарий:**
1. Пользователь создаёт новую трансформацию
2. Привязывает её к конкретному тегу или группе тегов
3. Выбирает тип трансформации
4. Настраивает правила модификации данных

**Типы трансформаций:**

| Тип | Описание |
|-----|----------|
| **Allow Parameters** | Белый список — тег получает только перечисленные параметры Event Data. Все остальные отбрасываются |
| **Exclude Parameters** | Чёрный список — указанные параметры удаляются из Event Data перед передачей тегу |
| **Event Enrichment** | Добавление или изменение параметров Event Data (обогащение из внешних источников: Firestore, API) |

**Бизнес-правила:**
- BR-027: Трансформация применяется к конкретному тегу и не влияет на другие теги
- BR-028: Несколько трансформаций могут быть применены к одному тегу — они выполняются последовательно
- BR-029: Allow Parameters и Exclude Parameters взаимоисключающи для одной трансформации
- BR-030: Event Enrichment позволяет выполнять HTTP-запросы к внешним API и Firestore для получения дополнительных данных в реальном времени
- BR-031: Трансформации — ключевой механизм минимизации данных (data minimization) для соответствия GDPR

---

### FR-SST-009: Галерея шаблонов (Community Template Gallery)

**Описание:** Централизованный каталог готовых шаблонов клиентов, тегов и переменных, созданных сообществом и Google.

**Предусловия:**
- Серверный контейнер создан
- Пользователь имеет права Edit и выше

**Основной сценарий:**
1. Пользователь переходит в раздел «Templates»
2. Нажимает «Search Gallery» в секции Tag Templates, Client Templates или Variable Templates
3. Находит нужный шаблон (поиск по названию, вендору)
4. Нажимает «Add to workspace»
5. Шаблон становится доступен для создания новых экземпляров тегов/клиентов/переменных

**Бизнес-правила:**
- BR-032: Шаблоны из галереи проходят проверку Google перед публикацией
- BR-033: Пользователь может создать собственный шаблон через Template Editor с использованием Sandboxed JavaScript
- BR-034: Пользовательские шаблоны можно опубликовать в галерее для использования сообществом
- BR-035: Шаблон определяет набор полей конфигурации, логику обработки данных и разрешения (Permissions) на доступ к API
- BR-036: Разрешения шаблона ограничивают действия кода: доступ к cookie, отправка HTTP-запросов, чтение Event Data и т.д.

### FR-SST-010: Предпросмотр и отладка (Preview & Debug)

**Описание:** Режим предпросмотра позволяет инспектировать входящие и исходящие запросы серверного контейнера в реальном времени без влияния на продакшен.

**Предусловия:**
- Серверный контейнер создан и развёрнут на сервере
- Пользователь имеет права Read и выше

**Основной сценарий:**
1. Пользователь нажимает «Preview» в серверном контейнере GTM
2. Система открывает окно отладки (Tag Assistant)
3. Пользователь генерирует трафик на сайте или отправляет тестовые запросы
4. Система отображает: входящие запросы, объекты Event Data, сработавшие клиенты, триггеры, теги, исходящие запросы

**Доступная информация в режиме отладки:**

| Вкладка | Содержание |
|---------|-----------|
| **Requests** | Список входящих HTTP-запросов с заголовками и телом |
| **Claims** | Какой клиент заявил каждый запрос |
| **Event Data** | Содержимое объекта Event Data после обработки клиентом |
| **Tags** | Какие теги сработали/не сработали и почему |
| **Outgoing Requests** | Исходящие HTTP-запросы, сформированные тегами |
| **Console** | Ошибки и предупреждения от тегов и клиентов |
| **Variables** | Значения всех переменных для каждого события |

**Альтернативный сценарий — ручная отправка запросов:**
1. Пользователь активирует режим «Send requests manually»
2. Система генерирует HTTP-заголовок `X-Gtm-Server-Preview`
3. Пользователь добавляет этот заголовок к запросам (через инструменты или скрипт)
4. Только запросы с этим заголовком отображаются в Preview

**Бизнес-правила:**
- BR-037: Preview-режим работает в отдельном окружении и не влияет на живой трафик
- BR-038: Для отображения входящих запросов в Preview необходимо, чтобы запрос содержал специальный cookie или заголовок X-Gtm-Server-Preview
- BR-039: Режим отладки показывает полную цепочку обработки: запрос → клиент → Event Data → трансформации → триггеры → теги → исходящие запросы

### FR-SST-011: Рабочие пространства (Workspaces)

**Описание:** Рабочие пространства позволяют нескольким пользователям одновременно работать над изменениями в серверном контейнере независимо друг от друга.

**Предусловия:**
- Серверный контейнер создан
- Пользователь имеет права Edit и выше

**Основной сценарий:**
1. Пользователь создаёт новое рабочее пространство
2. Вносит изменения в клиенты, теги, триггеры, переменные, трансформации
3. Тестирует изменения через Preview
4. Создаёт версию контейнера
5. Публикует версию (при наличии прав)

**Бизнес-правила:**
- BR-040: Бесплатные аккаунты — до 3 одновременных рабочих пространств (1 по умолчанию + 2 дополнительных)
- BR-041: Tag Manager 360 — неограниченное количество рабочих пространств
- BR-042: При конфликте изменений между рабочими пространствами система требует ручного разрешения перед созданием версии
- BR-043: Каждое рабочее пространство содержит независимый набор изменений

### FR-SST-012: Версионирование и публикация

**Описание:** Система контроля версий серверного контейнера с возможностью публикации и отката.

**Предусловия:**
- В рабочем пространстве есть неопубликованные изменения
- Пользователь имеет права Approve (создание версии) или Publish (публикация)

**Основной сценарий:**
1. Пользователь создаёт версию контейнера из текущего рабочего пространства
2. Указывает название и описание версии
3. Публикует версию — изменения вступают в силу на серверах

**Альтернативный сценарий — откат:**
1. Пользователь открывает список версий
2. Выбирает предыдущую стабильную версию
3. Публикует её — серверный контейнер возвращается к этой версии

**Сценарий — запрос утверждения (Tag Manager 360):**
1. Пользователь с правами Edit создаёт версию
2. Отправляет запрос на утверждение
3. Пользователь с правами Approve или Publish рассматривает изменения
4. Утверждает или отклоняет запрос с комментарием
5. При утверждении версия может быть опубликована

**Бизнес-правила:**
- BR-044: Каждая публикация автоматически создаёт пронумерованную версию
- BR-045: Все версии хранятся бессрочно и доступны для просмотра и отката
- BR-046: Публикация мгновенно применяет изменения ко всем экземплярам серверного контейнера
- BR-047: Workflow утверждения доступен только в Tag Manager 360

### FR-SST-014: Consent Mode (управление согласием)

**Описание:** Серверный контейнер поддерживает Consent Mode — механизм динамической адаптации поведения тегов в зависимости от статуса согласия пользователя.

**Предусловия:**
- На клиентской стороне реализован сбор согласия (CMP — Consent Management Platform)
- Статус согласия передаётся в серверный контейнер вместе с событиями

**Основной сценарий:**
1. Клиентский контейнер GTM собирает согласие пользователя и передаёт consent state
2. Серверный контейнер получает информацию о согласии вместе с событиями
3. Теги Google (GA4, Google Ads, Floodlight) автоматически адаптируют поведение:
   - При отсутствии согласия (ad_storage denied) — не устанавливаются рекламные cookie, отправляется анонимный ping
   - При наличии согласия — полная передача данных

**Типы согласия:**

| Тип | Описание |
|-----|----------|
| **ad_storage** | Согласие на хранение рекламных cookie |
| **analytics_storage** | Согласие на хранение аналитических cookie |
| **ad_user_data** | Согласие на отправку пользовательских данных для рекламы |
| **ad_personalization** | Согласие на персонализацию рекламы |

**Бизнес-правила:**
- BR-051: Теги Google в серверном контейнере являются consent-aware — автоматически адаптируются к статусу согласия
- BR-052: При denial of ad_storage серверные теги Google Ads не отправляют запросы на сохранение данных
- BR-053: Cookieless ping отправляется в GA4 без идентификаторов пользователя при отсутствии согласия
- BR-054: Трансформации могут использоваться для дополнительной фильтрации данных в зависимости от согласия
- BR-055: Ответственность за корректный сбор и передачу согласия лежит на клиентской стороне

### FR-SST-015: First-Party Cookie Management

**Описание:** Серверный контейнер может устанавливать и читать cookie от имени домена сайта, обеспечивая их статус first-party.

**Предусловия:**
- Настроен пользовательский домен (FR-SST-003)
- Серверный контейнер доступен на том же домене (или поддомене) что и сайт

**Основной сценарий:**
1. Клиент серверного контейнера получает входящий запрос
2. Тег или клиент устанавливает cookie в HTTP-ответе
3. Cookie устанавливается с доменом сайта (first-party)
4. Браузер принимает cookie как first-party — без ограничений ITP/ETP

**Бизнес-правила:**
- BR-056: Серверные cookie, установленные через Same Origin, считаются полностью first-party и не подлежат ограничениям ITP
- BR-057: Серверные cookie, установленные через поддомен, имеют увеличенный срок жизни по сравнению с клиентскими cookie (JavaScript), но могут подлежать некоторым ограничениям в Safari при использовании CNAME
- BR-058: Клиент GA4 по умолчанию устанавливает/обновляет cookie _ga и _ga_* через серверный ответ
- BR-059: Срок жизни серверных cookie по умолчанию — 2 года (настраивается)
- BR-060: Cookie могут быть установлены как HttpOnly для дополнительной безопасности

### FR-SST-016: Масштабирование и управление инфраструктурой

**Описание:** Управление количеством серверных экземпляров и инфраструктурными параметрами для обеспечения стабильной работы.

**Предусловия:**
- Серверный контейнер развёрнут
- Пользователь имеет доступ к облачной платформе

**Основной сценарий:**
1. Администратор оценивает объём трафика
2. Настраивает минимальное и максимальное количество экземпляров сервера
3. Настраивает автомасштабирование на основе нагрузки
4. Мониторит потребление ресурсов и стоимость

**Варианты развёртывания:**

| Платформа | Описание | Масштабирование до нуля |
|-----------|----------|------------------------|
| **Google Cloud Run** | Контейнеризированный сервис | Да (экономия при отсутствии трафика) |
| **Google App Engine** | Управляемая платформа | Нет (минимум 1 экземпляр всегда) |
| **Custom Docker** | Любая платформа с Docker | Зависит от платформы |
| **Стороннние хостинги** | Stape, Addingwell, Taggrs и др. | Управляется провайдером |

**Бизнес-правила:**
- BR-061: Минимум 3 экземпляра сервера для продакшена (рекомендация Google)
- BR-062: Каждый экземпляр Cloud Run — 1 vCPU, 0.5 GB RAM (стандартная конфигурация)
- BR-063: Стоимость одного экземпляра Cloud Run — ~$45/мес при постоянной работе
- BR-064: App Engine — ~$100/мес минимальный порог
- BR-065: Автоматическое развёртывание GTM создаёт ограниченный по ресурсам экземпляр — только для тестирования
- BR-066: Для GDPR: серверы, обрабатывающие данные европейских пользователей, должны располагаться в европейском регионе

## Состояния и статусы

### Серверный контейнер

```
[Создан] → [Сервер не настроен] → [Сервер развёрнут] → [Домен настроен] → [Опубликован]
                                          ↓
                                   [Сервер недоступен]
```

| Состояние | Описание | Переход |
|-----------|----------|---------|
| Создан | Контейнер создан, сервер не развёрнут | → Сервер развёрнут (после деплоя) |
| Сервер развёрнут | Инфраструктура готова, домен по умолчанию | → Домен настроен (после custom domain) |
| Домен настроен | Пользовательский домен привязан | → Опубликован (после первой публикации) |
| Опубликован | Контейнер работает, обрабатывает запросы | → Сервер недоступен (при сбое инфраструктуры) |
| Сервер недоступен | Ошибка инфраструктуры | → Сервер развёрнут (после восстановления) |

### Рабочее пространство

```
[Чистое] → [Есть изменения] → [Версия создана] → [Публикация запрошена] → [Опубликовано]
                  ↑                                        ↓
                  ←────────── [Запрос отклонён] ←──────────┘
```

| Состояние | Описание |
|-----------|----------|
| Чистое | Нет неопубликованных изменений |
| Есть изменения | Внесены изменения в сущности контейнера |
| Версия создана | Создана версия, но не опубликована |
| Публикация запрошена | Отправлен запрос на утверждение (360) |
| Опубликовано | Версия опубликована, рабочее пространство очищено |
| Запрос отклонён | Утверждающий отклонил запрос — возврат к редактированию |

### Входящий запрос (жизненный цикл)

```
[Получен] → [Заявлен клиентом] → [Event Data создан] → [Трансформации применены] → [Теги сработали] → [Исходящие запросы отправлены]
    ↓
[Отброшен] (ни один клиент не заявил)
```

### Тег (статус при обработке события)

| Статус | Описание |
|--------|----------|
| Не вызван | Триггер не сработал для этого события |
| Сработал | Тег успешно выполнен, исходящий запрос отправлен |
| Ошибка | Тег сработал, но исходящий запрос вернул ошибку |
| Заблокирован | Тег заблокирован триггером исключения |
| Пропущен (consent) | Тег не сработал из-за отсутствия согласия пользователя |

## Интеграции с другими модулями

### С клиентским контейнером GTM (Web Container)

- Клиентский контейнер отправляет данные в серверный контейнер (вместо прямой отправки вендорам)
- Клиентский контейнер передаёт consent state в серверный
- Настройка transport_url в gtag.js или GTM Web для маршрутизации запросов на серверный контейнер
- Серверный контейнер может отправить данные обратно в клиентский (DataLayer push через HTTP-ответ)

### С Google Analytics 4

- Встроенный клиент GA4 принимает запросы gtag.js
- Встроенный тег GA4 пересылает события в серверы GA4
- Поддержка региональной маршрутизации данных
- Поддержка Measurement Protocol для серверных событий

### С Google Ads

- Серверный тег Google Ads Conversion Tracking для отслеживания конверсий
- Серверный тег Google Ads Remarketing для ремаркетинга
- Автоматическая загрузка Google Tag с апреля 2025
- Enhanced Conversions через серверный тег

### С Campaign Manager 360 (Floodlight)

- Серверные теги Floodlight Counter и Floodlight Sales
- Поддержка user-provided data в тегах Floodlight
- Автоматическая загрузка Google Tag с апреля 2025

### С Meta (Facebook) Conversions API

- Шаблон тега из Community Template Gallery
- Автоматический маппинг событий GA4 → Meta: purchase → Purchase, add_to_cart → AddToCart, begin_checkout → InitiateCheckout, page_view → PageView
- Поддержка дедупликации событий (event_id)

### С Google Cloud Platform

- Cloud Run / App Engine — хостинг серверного контейнера
- Firestore — хранилище для обогащения данных (Event Enrichment)
- Cloud Logging — логирование запросов и ошибок
- Cloud Monitoring — мониторинг состояния серверов
- BigQuery — возможность отправки данных через HTTP Request тег

### С CMP (Consent Management Platforms)

- Серверный контейнер потребляет consent signals от любой CMP
- Поддержка Google Consent Mode v2
- Интеграция через стандартный протокол consent state в Event Data

### Со сторонними платформами (через Community Templates / HTTP Request)

- TikTok Events API
- Snapchat Conversions API
- LinkedIn Conversions API
- Pinterest Conversions API
- Любая платформа через универсальный HTTP Request тег
