# Онбординг и первый опыт

## Описание

Модуль онбординга Google Tag Manager охватывает полный путь нового пользователя: от создания аккаунта GTM и первого контейнера до установки кода на сайт, создания первого тега (как правило, Google Analytics 4), тестирования через режим предварительного просмотра и первой публикации. Модуль включает принятие условий использования, настройку прав доступа, обучающие подсказки и связку с экосистемой Google Marketing Platform.

---

## Роли пользователей

### На уровне аккаунта GTM

| Роль | Описание |
|------|----------|
| **Администратор (Admin)** | Полный доступ к настройкам аккаунта, управление пользователями, автоматический доступ на чтение ко всем контейнерам аккаунта. Создатель аккаунта автоматически получает эту роль |
| **Пользователь (User)** | Просмотр настроек аккаунта и активности. По умолчанию не имеет доступа ни к одному контейнеру — доступ назначается отдельно |

### На уровне контейнера

| Роль | Описание |
|------|----------|
| **Чтение (Read)** | Просмотр тегов, триггеров и переменных. Без возможности редактирования |
| **Редактирование (Edit)** | Создание рабочих областей, редактирование тегов/триггеров/переменных. Без права создания версий и публикации |
| **Утверждение (Approve)** | Всё из Edit + создание версий. Без права публикации |
| **Публикация (Publish)** | Полный доступ: редактирование, создание версий, публикация на сайт |

## Функциональные требования

### FR-ONB-001: Создание аккаунта GTM

**Описание:** Пользователь создаёт новый аккаунт Google Tag Manager, представляющий компанию или организацию.

**Роли:** Любой пользователь с Google-аккаунтом (становится Администратором).

**Предусловия:**
- У пользователя есть активный Google-аккаунт
- Пользователь авторизован в Google

**Основной сценарий:**
1. Пользователь переходит на tagmanager.google.com
2. Система перенаправляет на авторизацию Google (если не авторизован)
3. Пользователь нажимает "Создать аккаунт" (Create Account)
4. Пользователь вводит название аккаунта (рекомендуется — название компании)
5. Пользователь выбирает страну расположения
6. Система одновременно предлагает создать первый контейнер (см. FR-ONB-002)
7. Пользователь принимает Условия использования Google Tag Manager (см. FR-ONB-003)
8. Аккаунт создан, пользователь становится Администратором

**Альтернативные сценарии:**
- Если пользователь находится в EEA — автоматически подключаются условия обработки персональных данных (Data Processing Amendment)
- Если у пользователя уже есть аккаунт GTM — система показывает существующие аккаунты на главном экране, но не блокирует создание нового
- Если достигнут лимит аккаунтов (400) — система отказывает в создании

**Бизнес-правила:**
- BR-001: Один Google-аккаунт может владеть до 400 аккаунтов GTM
- BR-002: Название аккаунта — произвольная строка, рекомендуется имя компании
- BR-003: Создатель аккаунта автоматически получает роль Администратора
- BR-004: Страна указывается для юридических и регуляторных целей

**Результат:** Создан аккаунт GTM. Пользователь — Администратор. Создание контейнера выполняется в рамках того же процесса.

### FR-ONB-002: Создание первого контейнера

**Описание:** В процессе создания аккаунта пользователь одновременно создаёт первый контейнер, определяя платформу и имя.

**Роли:** Администратор аккаунта.

**Предусловия:**
- Аккаунт GTM создан или создаётся одновременно (FR-ONB-001)

**Основной сценарий:**
1. В форме создания аккаунта пользователь вводит имя контейнера (рекомендуется URL сайта, например www.example.com)
2. Пользователь выбирает тип платформы контейнера:
   - Web (веб-сайт)
   - iOS (приложение)
   - Android (приложение)
   - AMP (ускоренные мобильные страницы)
   - Server (серверный контейнер)
3. Пользователь нажимает "Создать"
4. Система создаёт контейнер и присваивает ему уникальный идентификатор формата GTM-XXXXXXX
5. Для Web-контейнера система сразу показывает код для установки (см. FR-ONB-004)

**Альтернативные сценарии:**
- Создание дополнительного контейнера в существующем аккаунте: через Accounts > три точки рядом с аккаунтом > Create Container
- Если выбран тип Server — пользователю предлагается дополнительная настройка серверной среды
- Если достигнут лимит контейнеров (500 на аккаунт) — система отказывает в создании

**Бизнес-правила:**
- BR-005: Один аккаунт GTM может содержать до 500 контейнеров
- BR-006: Каждый контейнер получает уникальный ID формата GTM-XXXXXXX
- BR-007: Тип контейнера определяет доступный набор тегов, триггеров и переменных
- BR-008: Тип контейнера нельзя изменить после создания
- BR-009: Для каждого сайта или приложения рекомендуется отдельный контейнер
- BR-010: Имя контейнера — произвольная строка, рекомендуется домен сайта

**Результат:** Контейнер создан с уникальным ID. Для Web-контейнера отображается код для установки.

### FR-ONB-003: Принятие условий использования

**Описание:** Обязательное принятие Terms of Service Google Tag Manager перед началом работы.

**Роли:** Создатель аккаунта (любой Google-пользователь).

**Предусловия:**
- Пользователь заполнил форму создания аккаунта и контейнера

**Основной сценарий:**
1. Система отображает текст Условий использования (Google Tag Manager Terms of Service)
2. Пользователь ставит галочку "Я принимаю условия" (при наличии)
3. Для пользователей из EEA — автоматически включается согласие на Data Processing Amendment (GDPR)
4. Пользователь нажимает "Да" / подтверждает
5. Система фиксирует факт принятия условий

**Альтернативные сценарии:**
- Пользователь отказывается принять условия — аккаунт не создаётся, процесс прерывается
- Пользователь вне EEA/UK — может проактивно принять Data Processing Terms через настройки аккаунта позднее

**Бизнес-правила:**
- BR-011: Без принятия ToS использование GTM невозможно
- BR-012: Применяются три документа: Google Terms of Service, Google Privacy Policy, Google Tag Manager Use Policy
- BR-013: Для EEA-пользователей Data Processing Amendment принимается автоматически при создании аккаунта
- BR-014: GTM сам по себе не устанавливает cookies и не собирает персональные данные, но теги внутри контейнера могут это делать

**Результат:** Условия приняты. Аккаунт и контейнер окончательно созданы.

### FR-ONB-004: Установка кода контейнера на сайт

**Описание:** После создания Web-контейнера пользователь получает два фрагмента кода для установки на все страницы сайта.

**Роли:** Администратор или пользователь с доступом Publish к контейнеру.

**Предусловия:**
- Контейнер типа Web создан
- Есть доступ к исходному коду сайта или CMS

**Основной сценарий:**
1. Система показывает всплывающее окно с двумя фрагментами кода сразу после создания контейнера
2. Фрагмент 1 (JavaScript): пользователь копирует и вставляет как можно выше в секцию `<head>` каждой страницы
3. Фрагмент 2 (noscript): пользователь копирует и вставляет сразу после открывающего тега `<body>`
4. Пользователь проверяет установку (см. FR-ONB-007)

**Альтернативные сценарии:**
- Пользователь закрыл всплывающее окно — код доступен через Admin > Install Google Tag Manager в интерфейсе контейнера
- Сайт на CMS (WordPress, Shopify, Wix) — установка через встроенный плагин/интеграцию без ручного редактирования кода
- Установку выполняет разработчик — администратор пересылает код разработчику
- Для Server-контейнера — другой процесс установки через серверную среду

**Бизнес-правила:**
- BR-015: Фрагмент 1 (JS) — основной, выполняет загрузку GTM в большинстве случаев
- BR-016: Фрагмент 2 (noscript) — резервный, работает при отключённом JavaScript в браузере
- BR-017: Оба фрагмента должны быть установлены на каждой странице сайта
- BR-018: Код содержит уникальный ID контейнера (GTM-XXXXXXX)
- BR-019: Код доступен для повторного просмотра в любой момент через настройки контейнера
- BR-020: До установки кода контейнер существует, но не может собирать данные

**Результат:** Код GTM установлен на сайте. Контейнер готов к работе и доставке тегов.

### FR-ONB-005: Создание первого тега (Google Analytics 4)

**Описание:** Типичный первый шаг после установки кода — создание тега Google Analytics 4 для начала сбора аналитических данных.

**Роли:** Пользователь с правами Edit или выше на контейнере.

**Предусловия:**
- Контейнер создан и код установлен на сайт
- У пользователя есть Measurement ID от Google Analytics 4 (формат G-XXXXXXXXXX)

**Основной сценарий:**
1. Пользователь переходит в раздел Tags (Теги) в рабочей области
2. Нажимает "Новый" (New)
3. Нажимает на блок "Конфигурация тега" (Tag Configuration)
4. Выбирает тип тега "Google Analytics: GA4 Configuration" (или "Google Tag")
5. Вводит Measurement ID (G-XXXXXXXXXX) из GA4
6. Нажимает на блок "Триггер" (Triggering)
7. Выбирает встроенный триггер "Initialization — All Pages" (или "All Pages")
8. Нажимает "Сохранить", указывает имя тега
9. Тег создан в черновике рабочей области

**Альтернативные сценарии:**
- Пользователь не знает Measurement ID — ему нужно перейти в GA4: Admin > Data Streams > скопировать ID
- Пользователь выбирает другой тип первого тега (Google Ads, Facebook Pixel и т.д.) — аналогичный процесс с другими параметрами
- Пользователь использует Community Template Gallery для поиска шаблонов тегов от сообщества

**Бизнес-правила:**
- BR-021: Тег существует только в черновике до момента публикации
- BR-022: Один тег GA4 Configuration достаточен для базового сбора данных обо всех просмотрах страниц
- BR-023: Триггер "Initialization — All Pages" гарантирует, что тег GA4 срабатывает первым
- BR-024: Без привязки триггера тег не будет срабатывать
- BR-025: Максимум 5000 тегов на контейнер

**Результат:** Тег GA4 создан в черновике. Требуется тестирование (FR-ONB-006) и публикация (FR-ONB-008).

### FR-ONB-006: Знакомство с рабочей областью (Workspace)

**Описание:** После создания контейнера пользователь попадает в рабочую область — основное пространство для работы с тегами, триггерами и переменными.

**Роли:** Пользователь с любым уровнем доступа к контейнеру (от Read и выше).

**Предусловия:**
- Контейнер создан

**Основной сценарий:**
1. После создания контейнера пользователь оказывается в Default Workspace
2. Система отображает обзорный экран (Overview) с основными разделами:
   - Tags (Теги) — фрагменты кода для отправки данных
   - Triggers (Триггеры) — условия срабатывания тегов
   - Variables (Переменные) — динамические значения для тегов и триггеров
3. Пользователь видит боковую навигацию с дополнительными разделами:
   - Folders (Папки) — организация элементов
   - Templates (Шаблоны) — пользовательские шаблоны тегов и переменных
4. Панель подсказок и ссылки на документацию доступны для нового пользователя

**Альтернативные сценарии:**
- В бесплатной версии доступно максимум 3 рабочих области (одна — Default)
- В GTM 360 — неограниченное количество рабочих областей
- При наличии нескольких рабочих областей — изменения одной области не влияют на другие до момента публикации

**Бизнес-правила:**
- BR-026: Default Workspace создаётся автоматически при создании контейнера
- BR-027: Free — до 3 рабочих областей; GTM 360 — без ограничений
- BR-028: Каждая рабочая область — это независимый черновик изменений
- BR-029: При публикации одной области создаётся новая версия контейнера; другие области должны синхронизировать изменения

**Результат:** Пользователь ориентируется в интерфейсе и понимает структуру: теги, триггеры, переменные.

### FR-ONB-007: Предварительный просмотр и отладка (Preview & Debug)

**Описание:** Перед публикацией пользователь тестирует теги в режиме предварительного просмотра, не затрагивая продакшн-версию сайта.

**Роли:** Пользователь с правами Edit или выше на контейнере.

**Предусловия:**
- Код контейнера установлен на сайте (FR-ONB-004)
- В рабочей области есть хотя бы один тег с триггером

**Основной сценарий:**
1. Пользователь нажимает кнопку "Preview" (Предварительный просмотр) в верхнем правом углу
2. Открывается новая вкладка Google Tag Assistant
3. Пользователь вводит URL своего сайта и нажимает "Connect"
4. Сайт открывается в режиме предварительного просмотра (видна нижняя панель Tag Assistant)
5. Tag Assistant показывает:
   - Какие теги сработали (Tags Fired)
   - Какие теги не сработали (Tags Not Fired)
   - Порядок срабатывания
   - Данные, переданные каждым тегом
6. Пользователь кликает по сайту, проверяя срабатывание тегов на разных страницах/событиях
7. По завершении тестирования пользователь закрывает вкладку или нажимает "Disconnect"

**Альтернативные сценарии:**
- Preview-режим не подключается — типичные причины: код не установлен, блокировщик рекламы, несоответствие URL
- После изменения тегов в рабочей области нужно перезапустить Preview (нажать Preview ещё раз)
- Режим предварительного просмотра виден только в том же браузере, где был активирован — обычные посетители сайта его не видят

**Бизнес-правила:**
- BR-030: Preview-режим работает с текущим черновиком (не с опубликованной версией)
- BR-031: Изменения в Preview не влияют на продакшн-сайт
- BR-032: Отладочная информация видна только пользователю GTM, не посетителям сайта
- BR-033: Для работы Preview требуется установленный код контейнера на сайте
- BR-034: При изменении тегов/триггеров требуется перезапуск Preview для обновления

**Результат:** Пользователь убедился, что теги срабатывают корректно. Готов к публикации.

### FR-ONB-008: Первая публикация контейнера

**Описание:** Пользователь публикует первую версию контейнера, делая теги активными на продакшн-сайте.

**Роли:** Пользователь с правами Publish на контейнере.

**Предусловия:**
- Код контейнера установлен на сайте
- Теги созданы и протестированы
- Пользователь имеет роль Publish

**Основной сценарий:**
1. Пользователь нажимает кнопку "Submit" (Отправить) в верхнем правом углу
2. Система показывает экран "Submit Changes" с опцией "Publish and Create Version"
3. Пользователь вводит:
   - Version Name (Название версии) — например, "Версия 1 — GA4 базовая"
   - Version Description (Описание) — произвольный текст об изменениях
4. Пользователь видит раздел "Workspace Changes" со списком всех изменений
5. Пользователь может просмотреть изменения, сравнить с предыдущей версией
6. Пользователь нажимает "Publish" (Опубликовать)
7. Система создаёт версию и публикует контейнер
8. Теги начинают работать на продакшн-сайте

**Альтернативные сценарии:**
- Пользователь с ролью Approve (без Publish) — может только запросить утверждение (Request Approval), но не опубликовать (только в GTM 360)
- Пользователь выбирает "Create Version" без публикации — версия сохраняется как снимок, но не становится активной
- При наличии нескольких сред (environments) — пользователь выбирает целевую среду для публикации
- Конфликт с другой рабочей областью — система предупреждает о конфликтах

**Бизнес-правила:**
- BR-035: Каждая публикация автоматически создаёт пронумерованную версию
- BR-036: Версии иммутабельны — после создания не могут быть изменены
- BR-037: Можно откатиться к любой предыдущей версии
- BR-038: Имя и описание версии необязательны, но рекомендуются для аудита
- BR-039: В GTM 360 доступен процесс утверждения (Approval Workflow) перед публикацией
- BR-040: Публикация мгновенная — нет задержки между нажатием и доступностью на сайте

**Результат:** Первая версия контейнера опубликована. Теги активны и собирают данные на продакшн-сайте.

### FR-ONB-009: Приглашение пользователей в аккаунт

**Описание:** Администратор приглашает коллег (маркетологов, разработчиков, агентства) в аккаунт GTM с назначением ролей.

**Роли:** Администратор аккаунта.

**Предусловия:**
- Аккаунт GTM создан
- Приглашаемый имеет Google-аккаунт

**Основной сценарий:**
1. Администратор переходит в Admin > User Management
2. Нажимает "+" (добавить пользователя)
3. Вводит email Google-аккаунта приглашаемого
4. Устанавливает уровень доступа на уровне аккаунта (Admin или User)
5. Устанавливает уровень доступа к каждому контейнеру отдельно (No Access / Read / Edit / Approve / Publish)
6. Нажимает "Пригласить" (Invite)
7. Приглашённый получает доступ (без отдельного принятия приглашения — доступ активируется сразу)

**Альтернативные сценарии:**
- Приглашение несуществующего email — система сообщает об ошибке
- Назначение Admin — система предупреждает о широте полномочий
- Удаление единственного Администратора — система запрещает, чтобы избежать потери контроля над аккаунтом

**Бизнес-правила:**
- BR-041: В аккаунте всегда должен быть хотя бы один Администратор
- BR-042: Рекомендуется иметь минимум два активных Администратора для предотвращения потери доступа
- BR-043: Права доступа могут быть изменены или отозваны Администратором в любой момент
- BR-044: Права на уровне контейнера настраиваются независимо для каждого контейнера
- BR-045: Доступ активируется мгновенно после приглашения

**Результат:** Новый пользователь имеет доступ к аккаунту и контейнерам с назначенными правами.

### FR-ONB-010: Обучающие подсказки и документация

**Описание:** Система предоставляет подсказки, ссылки на документацию и руководства для помощи новым пользователям.

**Роли:** Все пользователи.

**Предусловия:**
- Пользователь авторизован в GTM

**Основной сценарий:**
1. При первом входе система показывает обзорную навигацию по интерфейсу
2. На экране обзора контейнера (Overview) отображаются подсказки о назначении разделов
3. При создании тега — подсказки о выборе типа тега и настройке триггера
4. Ссылки на Google Tag Manager Help Center доступны из интерфейса
5. Google предоставляет пошаговые руководства (Getting Started Guide) из 4 шагов:
   - Шаг 1: Создание аккаунта и контейнера
   - Шаг 2: Установка контейнера
   - Шаг 3: Добавление тегов
   - Шаг 4: Проверка и публикация

**Альтернативные сценарии:**
- Опытный пользователь может пропустить подсказки
- Документация доступна на нескольких языках

**Бизнес-правила:**
- BR-046: Подсказки контекстуальны — зависят от текущего экрана и действия
- BR-047: Google Tag Manager Help Center — основной источник документации
- BR-048: GTM не имеет интерактивного тура (walkthrough) — обучение через документацию и подсказки

**Результат:** Пользователь понимает основные концепции GTM и может самостоятельно работать с системой.

## Состояния и статусы

### Состояния аккаунта

```
[Не существует] → (Создание аккаунта + принятие ToS) → [Активен]
[Активен] → (Удаление) → [Удалён]
```

### Состояния контейнера

```
[Не существует] → (Создание) → [Создан, без кода]
[Создан, без кода] → (Установка кода на сайт) → [Код установлен, не опубликован]
[Код установлен, не опубликован] → (Первая публикация) → [Активен]
[Активен] → (Новые изменения в workspace) → [Активен + есть неопубликованные изменения]
[Активен + есть неопубликованные изменения] → (Публикация) → [Активен]
```

### Состояния тега в рабочей области

```
[Не существует] → (Создание) → [Черновик]
[Черновик] → (Preview) → [Тестируется]
[Тестируется] → (Публикация) → [Опубликован]
[Опубликован] → (Редактирование) → [Опубликован + есть изменения в черновике]
[Опубликован] → (Приостановка) → [Приостановлен]
[Любое состояние] → (Удаление) → [Удалён в черновике] → (Публикация) → [Удалён окончательно]
```

### Состояния версии

```
[Не существует] → (Submit: Create Version) → [Создана, не опубликована]
[Создана, не опубликована] → (Publish) → [Опубликована (текущая)]
[Опубликована (текущая)] → (Публикация новой версии) → [Опубликована (архивная)]
[Любая версия] → (Rollback) → [Опубликована (текущая)]
```

### Рабочий процесс утверждения (GTM 360)

```
[Черновик] → (Request Approval) → [Ожидает утверждения]
[Ожидает утверждения] → (Approve) → [Утверждён, готов к публикации]
[Ожидает утверждения] → (Reject) → [Отклонён → Черновик]
[Утверждён] → (Publish) → [Опубликован]
```
