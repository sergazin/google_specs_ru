# Управление пользователями и права доступа

## Описание

Модуль управления пользователями и правами доступа в Google Tag Manager реализует двухуровневую систему разрешений: на уровне аккаунта и на уровне контейнера. Система позволяет гибко распределять доступ между владельцами сайтов, маркетологами, разработчиками и внешними агентствами, обеспечивая баланс между удобством совместной работы и безопасностью. В версии GTM 360 система расширяется зонами (Zones) и воркфлоу согласования (Approval Workflow), что позволяет организовать корпоративные процессы управления тегами с централизованным контролем.

---

## Роли пользователей

### Уровень аккаунта

| Роль | Описание | Наследуемые права |
|------|----------|-------------------|
| **Administrator** | Полное управление аккаунтом: настройки, создание контейнеров, управление пользователями | Автоматически наследует Read-доступ ко всем контейнерам аккаунта; может назначить себе любой уровень доступа к контейнеру |
| **User** | Просмотр настроек аккаунта, списка пользователей и журнала активности; не может изменять настройки | Автоматически получает "No Access" ко всем контейнерам; требуется явное назначение прав на каждый контейнер |

### Уровень контейнера

| Роль | Просмотр | Редактирование | Создание воркспейсов | Создание версий | Публикация |
|------|----------|----------------|----------------------|-----------------|------------|
| **No Access** | Нет | Нет | Нет | Нет | Нет |
| **Read** | Да | Нет | Нет | Нет | Нет |
| **Edit** | Да | Да | Да | Нет | Нет |
| **Approve** | Да | Да | Да | Да | Нет |
| **Publish** | Да | Да | Да | Да | Да |

Каждая последующая роль контейнера включает все права предыдущей (иерархия: No Access < Read < Edit < Approve < Publish).

### Уровень организации (Google Marketing Platform)

| Роль | Описание |
|------|----------|
| **Organization Admin** | Управление пользователями всех связанных продуктовых аккаунтов, включая GTM; может назначать права и политики |
| **Organization User** | Доступ определяется связанными продуктовыми аккаунтами |

## Функциональные требования

### FR-PRM-001: Приглашение пользователя в аккаунт

**Описание:** Администратор аккаунта приглашает нового пользователя, указывая его email-адрес (Google-аккаунт), уровень доступа к аккаунту и опционально уровень доступа к каждому контейнеру.

**Акторы:** Администратор аккаунта

**Предусловия:**
- Актор имеет роль Administrator на уровне аккаунта
- Приглашаемый email-адрес является валидным Google-аккаунтом

**Основной сценарий:**
1. Администратор открывает раздел управления пользователями
2. Вводит один или несколько email-адресов
3. Назначает роль на уровне аккаунта (Administrator или User)
4. Опционально назначает роли для каждого контейнера аккаунта
5. Подтверждает приглашение
6. Система отправляет приглашение на email
7. На экране приглашённого пользователя появляется карточка "Invitations"

**Постусловия:**
- Пользователь получил email-приглашение
- Приглашение отображается в интерфейсе приглашённого пользователя
- До принятия приглашения пользователь не имеет доступа

**Бизнес-правила:**
- Можно пригласить несколько пользователей одновременно
- Если назначена роль Administrator -- автоматически наследуется Read-доступ ко всем контейнерам
- Если назначена роль User -- по умолчанию ко всем контейнерам назначается No Access

---

### FR-PRM-002: Принятие или отклонение приглашения

**Описание:** Приглашённый пользователь принимает или отклоняет приглашение в аккаунт GTM.

**Акторы:** Приглашённый пользователь

**Предусловия:**
- Пользователь получил приглашение (email или карточка в интерфейсе GTM)

**Основной сценарий:**
1. Пользователь видит карточку "Invitations" на экране аккаунтов GTM
2. Раскрывает детали приглашения (какой аккаунт, какие права)
3. Нажимает "Accept" для принятия или "Decline" для отклонения

**Постусловия:**
- При принятии: пользователь получает доступ согласно назначенным правам
- При отклонении: приглашение удаляется, доступ не предоставляется

---

### FR-PRM-003: Изменение прав существующего пользователя

**Описание:** Администратор аккаунта изменяет уровень доступа уже добавленного пользователя как на уровне аккаунта, так и на уровне отдельных контейнеров.

**Акторы:** Администратор аккаунта

**Предусловия:**
- Актор имеет роль Administrator
- Целевой пользователь уже является участником аккаунта

**Основной сценарий:**
1. Администратор открывает раздел управления пользователями
2. Выбирает пользователя из списка
3. Изменяет роль на уровне аккаунта (Administrator / User)
4. Изменяет роли для отдельных контейнеров
5. Сохраняет изменения
6. Изменения вступают в силу немедленно

**Бизнес-правила:**
- При повышении до Administrator пользователь автоматически наследует Read ко всем контейнерам
- При понижении с Administrator до User наследованный Read-доступ к контейнерам снимается; остаются только явно назначенные права
- Нельзя понизить права последнего Administrator аккаунта (система блокирует операцию)

---

### FR-PRM-004: Удаление пользователя из аккаунта

**Описание:** Администратор удаляет пользователя, лишая его доступа к аккаунту и всем контейнерам.

**Акторы:** Администратор аккаунта

**Предусловия:**
- Актор имеет роль Administrator
- Удаляемый пользователь не является последним Administrator

**Основной сценарий:**
1. Администратор открывает профиль пользователя
2. Нажимает "Remove"
3. Система запрашивает подтверждение
4. Доступ пользователя ко всем контейнерам аккаунта отзывается немедленно

**Бизнес-правила:**
- Нельзя удалить последнего администратора аккаунта -- система выдаёт ошибку
- После удаления пользователь теряет доступ ко всему аккаунту и его контейнерам
- Изменения, ранее сделанные удалённым пользователем, сохраняются в истории

---

### FR-PRM-005: Наследование прав при привязке к организации

**Описание:** При привязке аккаунта GTM к организации Google Marketing Platform пользователи аккаунта автоматически добавляются в организацию, а администраторы организации получают возможности управления.

**Акторы:** Администратор аккаунта GTM, Администратор организации GMP

**Предусловия:**
- Аккаунт GTM существует и имеет администратора
- Организация GMP существует

**Основной сценарий:**
1. Администратор аккаунта GTM инициирует привязку к организации
2. Все пользователи аккаунта добавляются в организацию с ролью "User" по умолчанию
3. Администраторы организации получают права управления пользователями связанных аккаунтов
4. Контейнеры аккаунта становятся доступны со страницы администрирования организации

**Бизнес-правила:**
- Прямые (direct) права пользователя сохраняются даже при потере наследованных (inherited) прав
- Администраторы организации могут управлять пользователями связанных аккаунтов
- Привязка к организации открывает доступ к расширенным политикам управления пользователями

---

### FR-PRM-006: Требование двухфакторной аутентификации

**Описание:** Администратор аккаунта включает обязательную двухэтапную верификацию (2SV) для определённых операций в контейнере.

**Акторы:** Администратор аккаунта

**Предусловия:**
- Актор имеет роль Administrator

**Основной сценарий:**
1. Администратор открывает настройки безопасности контейнера
2. Включает требование 2SV для изменения Custom HTML Tags и/или Custom JavaScript Variables
3. Система сохраняет настройку
4. С этого момента пользователи, не прошедшие 2SV, не могут изменять указанные типы элементов

**Бизнес-правила:**
- 2SV привязана к Google-аккаунту пользователя, а не к аккаунту GTM
- Требование 2SV может быть включено избирательно: только для Custom HTML и Custom JavaScript
- Пользователь без 2SV сохраняет все остальные права, но блокируется при попытке редактировать защищённые элементы

---

### FR-PRM-007: Управление воркспейсами и контроль конфликтов

**Описание:** Система контролирует параллельную работу нескольких пользователей в разных воркспейсах одного контейнера, обнаруживая и разрешая конфликты.

**Акторы:** Пользователь с правами Edit и выше

**Предусловия:**
- Пользователь имеет права Edit, Approve или Publish на контейнер
- Контейнер имеет хотя бы один воркспейс

**Основной сценарий:**
1. Пользователь создаёт воркспейс или работает в существующем
2. Вносит изменения в теги, триггеры или переменные
3. При синхронизации с последней версией контейнера система обнаруживает конфликты
4. Для каждого конфликта пользователь выбирает: принять своё изменение или принять изменение из основной версии
5. После разрешения всех конфликтов воркспейс синхронизирован

**Бизнес-правила:**
- Конфликт возникает, когда один и тот же тег, триггер или переменная изменён и в воркспейсе, и в последней версии контейнера
- Пользователь может использовать "Resolve All" для массового принятия решения
- Обычные аккаунты: максимум 3 воркспейса на контейнер (1 по умолчанию + 2 дополнительных)
- GTM 360: неограниченное количество воркспейсов

---

### FR-PRM-008: Запрос согласования (Approval Request) -- GTM 360

**Описание:** Пользователь с правами Edit или выше отправляет запрос на согласование своих изменений перед публикацией. Функция доступна только в GTM 360.

**Акторы:** Пользователь с правами Edit или выше (запрашивающий), Пользователь с правами Approve или Publish (рецензент)

**Предусловия:**
- Аккаунт имеет лицензию GTM 360
- Запрашивающий внёс изменения в воркспейс

**Основной сценарий:**
1. Пользователь завершает изменения в воркспейсе
2. Нажимает "Submit" и выбирает "Request Approval"
3. Опционально назначает конкретного рецензента
4. Опционально оставляет комментарий с пояснениями
5. Нажимает "Request"
6. Запрос появляется во вкладке "Approvals"
7. Рецензент получает уведомление

**Постусловия:**
- Запрос создан и виден всем пользователям с правами Approve/Publish
- Воркспейс заблокирован для дальнейших изменений до решения по запросу

---

### FR-PRM-009: Рассмотрение запроса согласования -- GTM 360

**Описание:** Рецензент просматривает запрос на согласование и принимает решение: одобрить, вернуть на доработку или отозвать.

**Акторы:** Пользователь с правами Approve или Publish

**Предусловия:**
- Существует активный запрос на согласование

**Основной сценарий:**
1. Рецензент открывает вкладку "Approvals"
2. Выбирает запрос из очереди
3. Просматривает детали изменений
4. Принимает решение:
   - **Approve** -- одобрить изменения (версия готова к публикации)
   - **Send Back** -- вернуть автору на доработку с комментариями
   - **Withdraw** -- отозвать запрос (отменить)
5. Опционально оставляет комментарий

**Постусловия:**
- При Approve: создаётся версия контейнера, готовая к публикации пользователем с правами Publish
- При Send Back: воркспейс возвращается автору; автор может внести правки и повторно запросить согласование
- При Withdraw: запрос отменяется

**Бизнес-правила:**
- Любой пользователь с правами Approve или Publish может рассмотреть запрос, даже если он назначен другому рецензенту
- Назначение конкретного рецензента служит для уведомления, но не ограничивает права других рецензентов
- В рамках запроса поддерживается обмен комментариями между автором и рецензентом

---

### FR-PRM-010: Управление зонами (Zones) -- GTM 360

**Описание:** Администратор создаёт зоны внутри контейнера, привязывая дочерние контейнеры к определённым страницам сайта с ограничениями по типам тегов. Функция доступна только в GTM 360.

**Акторы:** Администратор аккаунта, Пользователь с правами Publish на основной контейнер

**Предусловия:**
- Аккаунт имеет лицензию GTM 360
- Существует основной (родительский) контейнер

**Основной сценарий:**
1. Администратор создаёт зону в основном контейнере
2. Привязывает к зоне дочерний контейнер GTM
3. Настраивает границы зоны (Boundaries): все страницы или определённые страницы по условиям
4. Настраивает ограничения типов (Type Restrictions): разрешённые типы тегов, триггеров, переменных и скриптов
5. Назначает пользователей и права для дочернего контейнера (независимо от основного)

**Постусловия:**
- Дочерний контейнер срабатывает внутри основного контейнера в пределах заданных границ
- Теги, триггеры и переменные основного и дочернего контейнеров изолированы друг от друга
- Data Layer общий для обоих контейнеров

**Бизнес-правила:**
- Каждая зона может иметь полностью отдельный набор пользователей и прав
- Пользователи дочернего контейнера могут публиковать независимо от основного контейнера
- Границы зоны работают аналогично триггерам: поддерживают условия по URL, переменным и т.д.
- Ограничения типов позволяют заблокировать определённые типы тегов (например, Custom HTML) в дочернем контейнере
- Зона используется для делегирования прав внешним агентствам или отдельным командам без предоставления доступа к основному контейнеру

---

### FR-PRM-011: Просмотр журнала активности аккаунта

**Описание:** Пользователь просматривает журнал действий, совершённых в аккаунте, для аудита и контроля.

**Акторы:** Любой пользователь аккаунта (Administrator или User)

**Предусловия:**
- Пользователь имеет роль Administrator или User на уровне аккаунта

**Основной сценарий:**
1. Пользователь открывает раздел активности аккаунта
2. Просматривает журнал действий: кто, когда и какие изменения внёс
3. Фильтрует записи по типу действия, пользователю, дате

**Бизнес-правила:**
- Журнал активности доступен только на чтение
- Записи журнала нельзя удалить или отредактировать
- Журнал фиксирует: изменения прав пользователей, создание/удаление контейнеров, публикации версий, изменения настроек аккаунта
- User видит журнал, но не может выполнять действия, которые в нём записаны

---

### FR-PRM-012: Защита последнего администратора

**Описание:** Система предотвращает ситуацию, при которой аккаунт может остаться без администратора.

**Акторы:** Система (автоматически)

**Предусловия:**
- В аккаунте остался единственный пользователь с ролью Administrator

**Основной сценарий:**
1. Кто-либо пытается:
   - Удалить последнего администратора
   - Понизить роль последнего администратора до User
   - Последний администратор пытается удалить себя
2. Система блокирует операцию
3. Отображается сообщение об ошибке: невозможно удалить или понизить последнего администратора

**Бизнес-правила:**
- В аккаунте GTM всегда должен быть хотя бы один администратор
- Правило применяется ко всем операциям: удаление, изменение роли, выход из аккаунта

## Сущности данных

### Пользователь аккаунта (Account User)

| Поле | Описание |
|------|----------|
| Email (Google Account) | Уникальный идентификатор пользователя |
| Роль аккаунта | Administrator или User |
| Дата добавления | Когда пользователь был приглашён |
| Статус приглашения | Pending / Accepted / Declined |
| Источник прав | Direct (назначены напрямую) или Inherited (наследованы от организации) |

### Права контейнера (Container Permission)

| Поле | Описание |
|------|----------|
| Пользователь | Ссылка на Account User |
| Контейнер | Ссылка на контейнер |
| Роль контейнера | No Access / Read / Edit / Approve / Publish |
| Источник прав | Direct или Inherited (от роли аккаунта) |

### Приглашение (Invitation)

| Поле | Описание |
|------|----------|
| Email приглашённого | Google-аккаунт |
| Аккаунт GTM | Целевой аккаунт |
| Назначенная роль аккаунта | Administrator / User |
| Назначенные роли контейнеров | Набор пар (контейнер, роль) |
| Статус | Pending / Accepted / Declined |
| Дата создания | Когда отправлено приглашение |

### Запрос согласования (Approval Request) -- GTM 360

| Поле | Описание |
|------|----------|
| Воркспейс | Ссылка на воркспейс с изменениями |
| Автор | Пользователь, создавший запрос |
| Назначенный рецензент | Опционально: конкретный пользователь |
| Статус | Pending / Approved / Sent Back / Withdrawn |
| Комментарии | Цепочка комментариев между автором и рецензентом |
| Дата создания | Когда создан запрос |
| Дата решения | Когда принято решение |

### Зона (Zone) -- GTM 360

| Поле | Описание |
|------|----------|
| Основной контейнер | Родительский контейнер |
| Дочерний контейнер | Привязанный контейнер зоны |
| Границы (Boundaries) | Все страницы или условия (аналогично триггерам) |
| Ограничения типов | Разрешённые типы тегов, триггеров, переменных, скриптов |

## Состояния и статусы

### Статусы приглашения пользователя

```
[Создано] --> Pending --> Accepted --> [Активный пользователь]
                    \--> Declined --> [Приглашение отклонено]
```

- **Pending**: приглашение отправлено, ожидает решения пользователя
- **Accepted**: пользователь принял приглашение, получил доступ
- **Declined**: пользователь отклонил приглашение

### Статусы запроса согласования (GTM 360)

```
[Создан] --> Pending --> Approved --> [Готов к публикации]
                    \--> Sent Back --> [Возвращён автору] --> Pending (повторная подача)
                    \--> Withdrawn --> [Отменён]
```

- **Pending**: запрос ожидает рассмотрения
- **Approved**: изменения одобрены, версия готова к публикации
- **Sent Back**: запрос возвращён автору на доработку; автор может внести правки и подать снова
- **Withdrawn**: запрос отозван (отменён)

### Состояния пользователя в аккаунте

```
[Не в аккаунте] --> Приглашён (Pending) --> Активный --> Удалён
                                       \--> Отклонил
```

- **Приглашён**: получил приглашение, ещё не ответил
- **Активный**: полноценный участник аккаунта с назначенными правами
- **Удалён**: доступ отозван

## Интеграции с другими модулями

### Модуль контейнеров и воркспейсов
- Права контейнера определяют, какие операции доступны пользователю в воркспейсах (создание, редактирование, публикация)
- При создании нового контейнера все пользователи-User получают No Access; администраторы наследуют Read

### Модуль версий и публикации
- Только пользователи с правами Publish могут опубликовать версию контейнера
- Пользователи с правами Approve могут создавать версии, но не публиковать
- Approval Workflow (GTM 360) добавляет промежуточный шаг согласования перед публикацией

### Модуль тегов, триггеров и переменных
- Права Edit и выше необходимы для создания и редактирования тегов, триггеров и переменных
- Требование 2SV может дополнительно ограничить редактирование Custom HTML Tags и Custom JavaScript Variables
- Зоны (GTM 360) ограничивают типы тегов, доступные в дочернем контейнере

### Модуль окружений (Environments)
- Права на публикацию в конкретные окружения определяются ролью Publish
- Управление окружениями доступно администраторам аккаунта

### Google Marketing Platform (организация)
- Привязка аккаунта к организации позволяет централизованно управлять пользователями
- Администраторы организации получают дополнительные полномочия по управлению пользователями связанных аккаунтов
- Наследованные права (от организации) сосуществуют с прямыми правами; при отзыве наследованных прав прямые сохраняются

### Модуль аудита и истории
- Все действия по управлению пользователями фиксируются в журнале активности
- История версий сохраняет информацию об авторе каждой версии
- Запросы согласования (GTM 360) сохраняют полную цепочку комментариев и решений
