# Версионирование и публикация

## Описание

Модуль «Версионирование и публикация» обеспечивает полный жизненный цикл изменений в Google Tag Manager: от создания рабочего пространства (Workspace) и внесения правок до публикации контейнера на сайт. Каждая публикация создаёт неизменяемую версию контейнера — полный снимок всех тегов, триггеров и переменных на момент публикации. Система поддерживает параллельную работу нескольких пользователей через механизм Workspaces, разрешение конфликтов при слиянии изменений, предварительный просмотр (Preview) перед публикацией, Environments для тестирования в различных средах, а также Approval Workflow (GTM 360) для согласования изменений.

---

## Роли пользователей

### На уровне аккаунта

| Роль | Описание |
|------|----------|
| Администратор (Admin) | Полное управление аккаунтом: создание/удаление контейнеров, управление пользователями и их правами |
| Пользователь (User) | Базовый доступ к аккаунту, конкретные права определяются на уровне контейнера |

### На уровне контейнера

| Уровень доступа | Описание |
|-----------------|----------|
| Нет доступа (No Access) | Пользователь не видит контейнер в списке |
| Чтение (Read) | Просмотр конфигурации контейнера, версий и истории. Без возможности вносить изменения |
| Редактирование (Edit) | Создание Workspace, редактирование тегов/триггеров/переменных. Без права создавать версии и публиковать |
| Согласование (Approve) | Все права Edit + создание версий. Без права публикации. Может одобрять/отклонять запросы на публикацию |
| Публикация (Publish) | Полные права: редактирование, создание версий, публикация контейнера |

> Каждый уровень включает все права предыдущего: Publish > Approve > Edit > Read > No Access.

## Функциональные требования

### FR-VER-001: Создание рабочего пространства (Workspace)

**Описание:** Пользователь с правами Edit и выше может создать новое рабочее пространство для изолированной работы над набором изменений.

**Предусловия:**
- Пользователь авторизован и имеет доступ к контейнеру с правами Edit или выше
- Не превышен лимит Workspace для данного аккаунта

**Основной сценарий:**
1. Пользователь переходит в раздел Workspaces контейнера
2. Система отображает список существующих Workspace (включая Default Workspace)
3. Пользователь инициирует создание нового Workspace
4. Пользователь задаёт имя и описание Workspace
5. Система создаёт Workspace на основе текущей последней версии контейнера
6. Пользователь начинает работу в новом Workspace

**Бизнес-правила:**
- Бесплатные аккаунты: максимум 3 Workspace одновременно (1 Default + 2 пользовательских)
- GTM 360: неограниченное количество Workspace
- Каждый Workspace содержит полную копию конфигурации контейнера на момент создания
- Default Workspace всегда существует и не может быть удалён
- Имя Workspace должно быть уникальным в рамках контейнера

**Результат:** Создан изолированный Workspace, в котором можно вносить изменения без влияния на другие Workspace и опубликованную версию.

---

### FR-VER-002: Внесение изменений в Workspace

**Описание:** Пользователь вносит изменения в теги, триггеры и переменные в рамках своего Workspace.

**Предусловия:**
- Пользователь имеет доступ к Workspace
- Пользователь имеет права Edit или выше

**Основной сценарий:**
1. Пользователь переключается на нужный Workspace
2. Пользователь создаёт, редактирует или удаляет теги, триггеры, переменные
3. Система автоматически сохраняет все изменения в контексте данного Workspace
4. На странице обзора Workspace отображается список всех внесённых изменений (Workspace Changes)

**Бизнес-правила:**
- Изменения в одном Workspace не влияют на другие Workspace
- Изменения не влияют на опубликованную версию контейнера до момента публикации
- Система ведёт учёт каждого изменённого элемента (Added, Modified, Deleted)
- Workspace Changes показывает diff между текущим состоянием Workspace и последней синхронизированной версией

**Результат:** Все изменения зафиксированы в Workspace и готовы к синхронизации, созданию версии или публикации.

---

### FR-VER-003: Синхронизация Workspace с последней версией контейнера

**Описание:** Workspace обновляется до последней версии контейнера, чтобы включить изменения, опубликованные из других Workspace.

**Предусловия:**
- С момента создания или последней синхронизации Workspace была опубликована новая версия контейнера из другого Workspace

**Основной сценарий (без конфликтов):**
1. Система обнаруживает, что Workspace отстаёт от последней версии контейнера
2. Система отображает уведомление о доступных обновлениях
3. Пользователь инициирует синхронизацию (Sync)
4. Система применяет все изменения из новой версии к Workspace, не затрагивая пользовательские правки
5. Workspace обновлён

**Альтернативный сценарий (с конфликтами):**
1. При синхронизации система обнаруживает, что один или несколько элементов изменены и в новой версии контейнера, и в текущем Workspace
2. Система показывает экран разрешения конфликтов
3. Для каждого конфликтного элемента отображается сравнение: слева — версия из последнего контейнера, справа — версия из текущего Workspace
4. Конфликты выделяются цветом: синий — изменения в Workspace; красный — изменения в версии контейнера, которых нет в Workspace
5. Пользователь для каждого конфликта решает: принять версию контейнера или сохранить свою версию из Workspace
6. Конфликты разрешаются по одному элементу за раз
7. После разрешения всех конфликтов Workspace синхронизирован

**Бизнес-правила:**
- Синхронизация обязательна перед публикацией, если Workspace отстаёт от последней версии
- Конфликт возникает только когда один и тот же элемент (тег, триггер или переменная) изменён и в Workspace, и в новой версии контейнера
- Неконфликтные изменения применяются автоматически
- Пользователь не может опубликовать Workspace с неразрешёнными конфликтами

**Результат:** Workspace содержит актуальную версию контейнера вместе с пользовательскими изменениями, все конфликты разрешены.

### FR-VER-004: Предварительный просмотр (Preview & Debug)

**Описание:** Пользователь может протестировать изменения из текущего Workspace на реальном сайте без публикации, используя режим Preview.

**Предусловия:**
- Пользователь имеет доступ к Workspace с правами Edit или выше
- На целевом сайте установлен код контейнера GTM

**Основной сценарий:**
1. Пользователь нажимает кнопку «Preview» в Workspace
2. Система запускает Tag Assistant в новой вкладке браузера
3. Пользователь вводит URL целевого сайта
4. Система открывает сайт с подключённой debug-панелью
5. На сайте работают теги из текущего Workspace (а не из опубликованной версии)
6. Debug-панель отображает: временную шкалу событий, сработавшие и несработавшие теги, значения переменных, данные Data Layer

**Бизнес-правила:**
- Preview виден только в браузере пользователя, инициировавшего сессию, или получившего ссылку на Preview
- Обычные посетители сайта не видят Preview-режим
- Preview работает в контексте конкретного Workspace
- Пользователь может поделиться Preview-ссылкой с коллегами для совместного тестирования
- Preview не влияет на данные аналитики рядовых пользователей сайта

**Результат:** Пользователь видит, как будут работать теги из Workspace на реальном сайте, до публикации.

### FR-VER-005: Отправка на публикацию (Submit)

**Описание:** Пользователь отправляет изменения из Workspace на публикацию, при этом создаётся новая версия контейнера.

**Предусловия:**
- Workspace содержит хотя бы одно изменение
- Workspace синхронизирован с последней версией контейнера (нет неразрешённых конфликтов)
- Пользователь имеет соответствующие права (Publish или Approve, в зависимости от настроек)

**Основной сценарий (прямая публикация):**
1. Пользователь нажимает «Submit» в Workspace
2. Система отображает экран Submit Changes со списком всех изменений
3. Пользователь выбирает режим: «Publish and Create Version» или «Create Version» (без публикации)
4. Пользователь вводит имя версии (Version Name) и описание (Version Description)
5. Если выбрана публикация — пользователь при необходимости выбирает целевое окружение (Environment)
6. Система создаёт новую версию контейнера (инкрементальный номер)
7. Если выбрана публикация — версия разворачивается в выбранное окружение
8. Workspace очищается (возвращается к состоянию опубликованной версии)

**Бизнес-правила:**
- При публикации создаётся неизменяемый снимок (snapshot) всего контейнера
- Номер версии инкрементируется автоматически и не может быть изменён
- Имя и описание версии — необязательные, но рекомендуемые поля
- Публикация в Live-окружение делает изменения видимыми для всех посетителей сайта
- После публикации Workspace сбрасывается: его изменения входят в новую версию контейнера
- Контейнер не может быть опубликован, если его размер превышает 200 КБ

**Результат:** Создана новая версия контейнера. При публикации — изменения активны на сайте.

### FR-VER-006: Создание версии без публикации

**Описание:** Пользователь может сохранить текущее состояние Workspace как версию, не публикуя её на сайт.

**Предусловия:**
- Workspace содержит изменения
- Пользователь имеет права Approve или Publish

**Основной сценарий:**
1. Пользователь нажимает «Submit»
2. На экране Submit Changes выбирает «Create Version» (вместо «Publish and Create Version»)
3. Вводит имя и описание версии
4. Система создаёт версию и присваивает ей номер
5. Версия появляется в истории версий со статусом «не опубликована»
6. Workspace очищается

**Бизнес-правила:**
- Версия без публикации доступна в Latest Environment
- Версию можно опубликовать позднее из раздела Versions
- Версия без публикации не влияет на Live-окружение
- Используется для сохранения контрольных точек, ревью и отложенных релизов

**Результат:** Изменения сохранены как версия для будущей публикации или ревью, Live-окружение не затронуто.

### FR-VER-007: Approval Workflow (GTM 360)

**Описание:** В GTM 360 пользователи с правами Edit могут запросить одобрение для публикации своих изменений. Пользователи с правами Approve или Publish рассматривают запрос.

**Предусловия:**
- Контейнер принадлежит аккаунту GTM 360
- В контейнере есть пользователи с правами Approve и/или Publish
- Пользователь с правами Edit подготовил изменения в Workspace

**Основной сценарий:**
1. Пользователь с правами Edit нажимает «Request Approval» (вместо Submit)
2. Система предлагает назначить конкретного рецензента (необязательно)
3. Пользователь может оставить комментарий с пояснениями
4. Запрос на одобрение создан и виден пользователям с правами Approve/Publish
5. Рецензент просматривает список изменений в Workspace
6. Рецензент выполняет одно из действий:
   - **Approve** — одобряет изменения, версия готова к публикации
   - **Send Back** — отклоняет запрос с комментарием, возвращает автору для доработки
7. После одобрения пользователь с правами Publish может опубликовать версию

**Альтернативный сценарий — отзыв запроса:**
1. Автор запроса решает отозвать его до рассмотрения
2. Автор нажимает «Withdraw»
3. Запрос отменяется, изменения остаются в Workspace для дальнейшей работы

**Бизнес-правила:**
- Approval Workflow доступен только в GTM 360
- Любой пользователь с правами Approve или Publish может рассмотреть запрос, даже если он адресован конкретному человеку
- Назначение рецензента — рекомендательный механизм, а не ограничение
- Одобрение не равно публикации — после Approve нужен отдельный шаг Publish
- Отклонённый запрос (Send Back) возвращает Workspace автору без потери изменений
- Автор может отозвать запрос (Withdraw) в любой момент до принятия решения

**Результат:** Изменения проходят ревью перед публикацией, обеспечивая контроль качества и безопасности.

### FR-VER-008: Управление историей версий

**Описание:** Система ведёт полную историю всех созданных версий контейнера с возможностью просмотра деталей каждой версии.

**Предусловия:**
- Пользователь имеет доступ к контейнеру с правами Read или выше

**Основной сценарий:**
1. Пользователь переходит в раздел «Versions»
2. Система отображает таблицу всех версий в обратном хронологическом порядке
3. Для каждой версии отображается: номер версии, имя, описание, автор, дата создания, статус публикации, дата публикации (если была опубликована)
4. Пользователь может открыть любую версию для просмотра полной конфигурации контейнера на тот момент
5. В детальном просмотре видны все теги, триггеры и переменные данной версии

**Бизнес-правила:**
- Версии нумеруются последовательно и неизменяемо
- Удалить версию нельзя
- Содержимое опубликованной версии неизменяемо
- История версий хранится бессрочно
- Текущая опубликованная версия отмечена в списке

**Результат:** Полная прозрачность всех изменений контейнера с точной атрибуцией авторства.

### FR-VER-009: Откат к предыдущей версии

**Описание:** Пользователь может вернуть контейнер к любой ранее созданной версии.

**Предусловия:**
- Существует хотя бы одна предыдущая версия контейнера
- Пользователь имеет соответствующие права

**Сценарий 1 — Установка как последняя версия (Set as Latest Version):**
1. Пользователь выбирает нужную версию в истории
2. Нажимает «Set as Latest Version» через меню Actions
3. Система копирует содержимое выбранной версии в текущий Workspace
4. Пользователь при необходимости вносит дополнительные правки
5. Пользователь публикует через стандартный процесс Submit

**Сценарий 2 — Прямая публикация предыдущей версии:**
1. Пользователь выбирает нужную версию в истории
2. Открывает версию и нажимает «Publish» через Action
3. Система публикует выбранную версию напрямую
4. Создаётся новая запись в истории публикаций

**Бизнес-правила:**
- «Set as Latest Version» не публикует сразу — только заменяет содержимое Workspace
- Прямая публикация прошлой версии — быстрый откат в экстренных ситуациях
- При откате через Set as Latest Version все текущие несохранённые изменения в Workspace будут перезаписаны
- Откат не удаляет промежуточные версии из истории
- Каждая публикация (даже откат) создаёт новую запись в журнале публикаций

**Результат:** Контейнер возвращён к предыдущему рабочему состоянию.

### FR-VER-010: Управление средами (Environments)

**Описание:** Пользователь может создавать окружения (Environments) для тестирования версий контейнера в разных средах (Dev, Staging, QA) перед публикацией в Live.

**Предусловия:**
- Пользователь имеет права Publish на контейнер

**Основной сценарий:**
1. Пользователь переходит в Admin → Environments
2. Система отображает список окружений; по умолчанию существуют: Live, Latest, Now Editing
3. Пользователь создаёт пользовательское окружение (например, «Staging», «QA», «Dev»)
4. Система генерирует уникальный код контейнера с токеном аутентификации для данного окружения
5. Код устанавливается на соответствующий сервер (Dev, Staging и т.д.)
6. Пользователь может назначить конкретную версию контейнера для данного окружения
7. На серверах с этим окружением работает назначенная версия контейнера

**Встроенные окружения:**
| Окружение | Описание |
|-----------|----------|
| Live | Всегда указывает на текущую опубликованную версию. Используется на production-сайте |
| Latest | Указывает на последнюю созданную версию (опубликованную или нет) |
| Now Editing | Указывает на текущее состояние выбранного Workspace (включая неопубликованные изменения) |

**Бизнес-правила:**
- Live-окружение нельзя удалить или переименовать
- Каждое пользовательское окружение получает уникальный токен аутентификации
- Токен можно аннулировать (regenerate) для контроля доступа
- Окружение может быть привязано к конкретной версии контейнера или обновляться автоматически
- Код контейнера для пользовательского окружения отличается от стандартного кода (содержит параметры auth и env)
- Не рекомендуется использовать одновременно Share Preview и snippet-интеграцию для одного окружения

**Результат:** Настроена многоуровневая система сред для безопасного тестирования перед выпуском в production.

### FR-VER-011: Публикация в конкретное окружение

**Описание:** При публикации пользователь может выбрать, в какое окружение (Environment) будет развёрнута новая версия.

**Предусловия:**
- Создано хотя бы одно пользовательское окружение
- Пользователь имеет права Publish

**Основной сценарий:**
1. Пользователь нажимает Submit в Workspace
2. На экране Submit Changes в секции «Publish to Environment» пользователь выбирает целевое окружение
3. Пользователь подтверждает публикацию
4. Новая версия создаётся и разворачивается только в выбранное окружение
5. Другие окружения (включая Live) не затрагиваются

**Бизнес-правила:**
- По умолчанию публикация идёт в Live-окружение
- Публикация в пользовательское окружение не влияет на Live
- Одна версия может быть опубликована в несколько окружений последовательно
- Для каждого окружения ведётся отдельная история публикаций

**Результат:** Версия опубликована в указанное окружение для тестирования без влияния на production.

### FR-VER-012: Обмен ссылкой на Preview окружения (Share Preview)

**Описание:** Пользователь может сгенерировать ссылку для Preview конкретного окружения и отправить её коллеге.

**Предусловия:**
- Окружение существует и ему назначена версия контейнера

**Основной сценарий:**
1. Пользователь находит окружение в списке Environments
2. Через меню Actions выбирает «Share Link»
3. Система генерирует Preview-ссылку
4. Пользователь отправляет ссылку коллеге
5. Коллега открывает ссылку и видит сайт с версией контейнера из данного окружения

**Бизнес-правила:**
- Share Preview не требует от получателя прав доступа к GTM
- Ссылка действует до тех пор, пока окружение активно и токен не аннулирован
- Preview виден только перешедшему по ссылке, обычные посетители сайта его не видят

**Результат:** Коллега может протестировать версию контейнера без доступа к GTM.

### FR-VER-013: Удаление Workspace

**Описание:** Пользователь может удалить Workspace, который больше не нужен.

**Предусловия:**
- Workspace не является Default Workspace
- Пользователь имеет права Edit или выше

**Основной сценарий:**
1. Пользователь выбирает Workspace для удаления
2. Система запрашивает подтверждение
3. Workspace удаляется вместе со всеми неопубликованными изменениями
4. Удаление необратимо

**Бизнес-правила:**
- Default Workspace нельзя удалить
- Все несохранённые изменения Workspace будут потеряны
- Если изменения были опубликованы из Workspace ранее — они сохраняются в соответствующих версиях

**Результат:** Workspace удалён, ресурс высвобожден.

### FR-VER-014: История изменений и аудит (Change History)

**Описание:** Система ведёт журнал всех действий, выполненных в контейнере, с атрибуцией авторства.

**Предусловия:**
- Пользователь имеет доступ к контейнеру с правами Read или выше

**Основной сценарий:**
1. Пользователь переходит в раздел «Versions» или «Activity»
2. Система отображает журнал изменений с колонками: тип изменения (Add/Edit/Delete), объект изменения, автор, дата
3. Пользователь может кликнуть на запись для детального просмотра конкретных изменений
4. Поддерживается сортировка по любому столбцу

**Бизнес-правила:**
- Фиксируются все типы изменений: создание, редактирование, удаление тегов/триггеров/переменных
- Фиксируются изменения прав пользователей (Account Activity)
- Если пользователь удалён из системы — его записи в истории сохраняются, но поле «автор» остаётся пустым
- Журнал изменений не может быть отредактирован или удалён
- История хранится бессрочно

**Результат:** Полная аудиторская тропа всех действий в контейнере.

### FR-VER-015: Отмена изменений в Workspace

**Описание:** Пользователь может отменить все или часть изменений в Workspace, вернув элементы к состоянию последней синхронизированной версии.

**Предусловия:**
- Workspace содержит несохранённые изменения

**Основной сценарий:**
1. Пользователь открывает обзор изменений Workspace (Workspace Changes)
2. Для конкретного элемента выбирает «Abandon Changes» / «Revert»
3. Элемент возвращается к состоянию последней синхронизированной версии контейнера
4. Отмена необратима — пользовательские правки для данного элемента теряются

**Бизнес-правила:**
- Можно отменить изменения для отдельных элементов или для всего Workspace целиком
- Отмена возвращает элемент к состоянию последней версии контейнера (не к состоянию до последней правки)
- Отменённые изменения невозможно восстановить

**Результат:** Нежелательные изменения удалены из Workspace.

## Состояния и статусы

### Состояния Workspace

```
[Создан] → [Активный] → [Синхронизация требуется] → [Конфликт] → [Синхронизирован]
                ↓                                                        ↓
          [Удалён]                                                 [Отправлен на Submit]
                                                                         ↓
                                                                   [Очищен (после создания версии)]
```

| Состояние | Описание | Переходы |
|-----------|----------|----------|
| Создан | Workspace только что создан, изменений нет | → Активный (при внесении первого изменения) |
| Активный | В Workspace есть несохранённые изменения | → Синхронизация требуется (если опубликована новая версия), → Отправлен на Submit, → Удалён |
| Синхронизация требуется | Workspace отстаёт от последней версии контейнера | → Синхронизирован (если нет конфликтов), → Конфликт |
| Конфликт | Обнаружены конфликтные изменения при синхронизации | → Синхронизирован (после разрешения всех конфликтов) |
| Синхронизирован | Workspace актуален и содержит изменения | → Отправлен на Submit |
| Очищен | Workspace очищен после создания версии, готов для новых изменений | → Активный |

### Состояния версии контейнера

```
[Создана (не опубликована)] → [Опубликована] → [Заменена новой версией (архивная)]
                                     ↓
                              [Откачена / Повторно опубликована]
```

| Состояние | Описание |
|-----------|----------|
| Создана (не опубликована) | Версия сохранена, но не развёрнута ни в одно окружение |
| Опубликована (Live) | Версия активна в Live-окружении |
| Опубликована (окружение) | Версия активна в пользовательском окружении, но не в Live |
| Архивная | Версия была опубликована ранее, но заменена более новой |

### Состояния запроса на одобрение (GTM 360)

```
[Pending] → [Approved] → (Publish)
    ↓
[Sent Back] → (Доработка) → [Pending]
    ↑
[Withdrawn] (финальное)
```

| Состояние | Описание | Переходы |
|-----------|----------|----------|
| Pending | Запрос создан, ожидает рассмотрения | → Approved, → Sent Back, → Withdrawn |
| Approved | Запрос одобрён, версия готова к публикации | → (Publish — внешний переход) |
| Sent Back | Запрос отклонён, возвращён автору на доработку | → Pending (после доработки и повторного запроса) |
| Withdrawn | Запрос отозван автором | Финальное состояние |

|-------------|----------|------------|
| Максимум Workspace (бесплатный) | 3 (1 Default + 2 пользовательских) | — |

| Хранение истории версий | Бессрочно | — |
| Удаление версий | Невозможно | Версии неизменяемы и не удаляются |

## Интеграции с другими модулями

### Теги, триггеры и переменные
- Все изменения в тегах, триггерах и переменных происходят в контексте Workspace
- Публикация включает полный снимок всех этих сущностей
- При откате восстанавливается полная конфигурация всех элементов

### Управление пользователями и правами
- Уровень доступа к контейнеру (Read/Edit/Approve/Publish) определяет, какие операции версионирования доступны пользователю
- Approval Workflow зависит от разграничения ролей Edit/Approve/Publish
- Журнал изменений фиксирует действия с привязкой к пользователю

### Контейнеры
- Каждый контейнер имеет собственную независимую историю версий
- Workspace принадлежат конкретному контейнеру
- Environments настраиваются на уровне контейнера

### Папки (Folders)
- Структура папок является частью снимка версии
- При откате восстанавливается в том числе организация элементов по папкам

### Preview & Debug
- Preview работает в контексте конкретного Workspace
- Позволяет тестировать изменения до создания версии и публикации
- Share Preview для Environments использует токены аутентификации
