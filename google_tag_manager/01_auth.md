# Аутентификация и управление аккаунтами

## Описание

Модуль отвечает за аутентификацию пользователей в Google Tag Manager (GTM), управление аккаунтами и контейнерами, назначение ролей и прав доступа на двух уровнях (аккаунт и контейнер), интеграцию с Google Account и Google Marketing Platform, а также обеспечение безопасности через двухфакторную аутентификацию. GTM существует в двух версиях: бесплатной и GTM 360 (корпоративной), что влияет на доступные возможности управления.

## Роли пользователей

### Уровень аккаунта

- **Администратор (Administrator)** — полный контроль над аккаунтом: управление настройками аккаунта, создание и удаление контейнеров, управление пользователями и их правами. Автоматически наследует право Read на все контейнеры аккаунта и может назначить себе любые дополнительные права на контейнеры.
- **Пользователь (User)** — базовый доступ к аккаунту: может видеть информацию об аккаунте. Не наследует никаких прав на контейнеры — они должны быть назначены отдельно.

### Уровень контейнера

- **Нет доступа (No Access)** — контейнер не отображается в списке контейнеров ни в интерфейсе, ни через API.
- **Чтение (Read)** — просмотр содержимого контейнера: теги, триггеры, переменные, рабочие области. Без возможности редактирования.
- **Редактирование (Edit)** — создание и редактирование тегов, триггеров, переменных, создание рабочих областей. Без возможности создавать версии и публиковать.
- **Подтверждение (Approve)** — все права Edit, плюс возможность создавать версии контейнера. Без возможности публикации.
- **Публикация (Publish)** — полные права на контейнер: создание, редактирование, создание версий и публикация на сайт.

### Уровень организации (Google Marketing Platform)

- **Администратор организации (Org Admin)** — управление организацией в Google Marketing Platform, привязка/отвязка продуктовых аккаунтов (GTM, GA и др.), централизованное управление пользователями во всех привязанных аккаунтах.
- **Биллинг-администратор (Billing Admin)** — управление биллингом организации, может запрашивать привязку аккаунтов.

### Сервисные аккаунты

- **Сервисный аккаунт Google (Service Account)** — используется для серверного (machine-to-machine) взаимодействия с GTM через API. Применяется для автоматизированных задач: плановые инвентаризации, повторяемые деплои. Права назначаются так же, как обычному пользователю.

## Функциональные требования

### FR-AUTH-001: Аутентификация через Google Account

**Описание:** Доступ к Google Tag Manager осуществляется исключительно через Google Account. Собственной системы регистрации и аутентификации GTM не имеет.

**Роли:** Все пользователи

**Предусловия:** У пользователя есть активный Google Account

**Основной сценарий:**
1. Пользователь переходит на tagmanager.google.com
2. Система перенаправляет на страницу входа Google Account
3. Пользователь вводит учетные данные Google Account
4. При включенной 2FA — проходит второй фактор аутентификации
5. Google возвращает сессию аутентификации
6. GTM проверяет, есть ли у данного Google Account доступ к каким-либо аккаунтам GTM
7. Пользователь получает доступ к интерфейсу GTM

**Альтернативные сценарии:**
- Если у пользователя нет Google Account — необходимо сначала создать его
- Если у аутентифицированного пользователя нет доступа ни к одному аккаунту GTM — предлагается создать новый аккаунт GTM
- Если учетные данные неверны — стандартная обработка ошибок Google Account

**Бизнес-правила:**
- BR-001: GTM поддерживает только аутентификацию через Google Account. Никакие другие протоколы и провайдеры не поддерживаются
- BR-002: Сессия аутентификации управляется на уровне Google Account, а не GTM
- BR-003: Доступ предоставляется только Google-аккаунтам (корпоративные Google Workspace и личные Gmail/Google-аккаунты)

**Результат:** Пользователь аутентифицирован и видит список доступных аккаунтов и контейнеров GTM

---

### FR-AUTH-002: Аутентификация через OAuth 2.0 (API)

**Описание:** Программный доступ к GTM API осуществляется через протокол OAuth 2.0. Поддерживаются несколько потоков авторизации для разных сценариев использования.

**Роли:** Разработчики, сервисные аккаунты

**Предусловия:**
- Приложение зарегистрировано в Google Cloud Console
- Tag Manager API активирован в проекте
- Настроены OAuth credentials (Client ID + Client Secret) или ключ сервисного аккаунта

**Основной сценарий (пользовательский OAuth):**
1. Приложение запрашивает авторизацию у пользователя с указанием необходимых scopes
2. Пользователь дает согласие на доступ
3. Google выдает access token и refresh token
4. Приложение использует access token для запросов к API
5. При истечении access token — обновляет через refresh token

**Альтернативные сценарии:**
- Серверный OAuth (web server flow) — для серверных приложений
- Клиентский OAuth (client-side flow) — для браузерных приложений
- Сервисный аккаунт (service account flow) — для server-to-server без участия пользователя
- Установленное приложение (installed app flow) — для десктопных/мобильных приложений

**Бизнес-правила:**
- BR-004: Каждая уникальная комбинация Client ID / аккаунт пользователя может иметь не более 25 refresh-токенов
- BR-005: API-лимиты: 10 000 запросов в день на проект, 0.25 QPS на проект
- BR-006: Никакие другие протоколы авторизации, кроме OAuth 2.0, не поддерживаются для API

**Результат:** Приложение получает авторизованный доступ к GTM API в рамках предоставленных прав

---

### FR-AUTH-003: Создание аккаунта GTM

**Описание:** Любой пользователь с Google Account может создать новый аккаунт GTM. При создании аккаунта обязательно создается первый контейнер.

**Роли:** Любой аутентифицированный пользователь Google

**Предусловия:** Пользователь аутентифицирован через Google Account

**Основной сценарий:**
1. Пользователь нажимает "Создать аккаунт" в интерфейсе GTM
2. Вводит название аккаунта
3. Выбирает страну расположения аккаунта
4. Опционально включает анонимное предоставление данных Google для бенчмаркинга
5. Вводит название контейнера (рекомендуется URL сайта)
6. Выбирает тип платформы контейнера: Web, iOS, Android, AMP или Server
7. Принимает Условия использования (Terms of Service)
8. Система создает аккаунт и контейнер
9. Для web-контейнера: отображается код установки (два сниппета JavaScript)

**Альтернативные сценарии:**
- Если пользователь уже имеет аккаунты GTM — новый аккаунт добавляется к списку
- Для server-контейнера — требуется дополнительная настройка серверной инфраструктуры

**Бизнес-правила:**
- BR-007: Создатель аккаунта автоматически получает роль Администратора
- BR-008: При создании аккаунта обязательно создается хотя бы один контейнер
- BR-009: Каждый контейнер привязан к одному типу платформы, который не может быть изменен после создания
- BR-010: Название аккаунта обычно соответствует названию компании или проекта

**Результат:** Создан новый аккаунт GTM с первым контейнером, пользователь является Администратором

---

### FR-AUTH-004: Добавление пользователя в аккаунт

**Описание:** Администратор аккаунта может пригласить нового пользователя, указав его email Google Account и назначив права доступа на уровне аккаунта и контейнеров.

**Роли:** Администратор аккаунта

**Предусловия:**
- Текущий пользователь имеет роль Администратора на уровне аккаунта
- Приглашаемый пользователь имеет Google Account

**Основной сценарий:**
1. Администратор переходит в раздел Admin > User Management
2. Нажимает "Добавить пользователя"
3. Вводит email Google Account приглашаемого пользователя
4. Назначает роль на уровне аккаунта: Администратор или Пользователь
5. Для каждого контейнера в аккаунте назначает уровень доступа: No Access / Read / Edit / Approve / Publish
6. Сохраняет настройки
7. Приглашенный пользователь получает доступ при следующем входе в GTM

**Альтернативные сценарии:**
- Если email не принадлежит Google Account — доступ не может быть предоставлен
- Если пользователь уже добавлен — его права обновляются

**Бизнес-правила:**
- BR-011: Доступ предоставляется только Google-аккаунтам (email, привязанный к Google Account)
- BR-012: Пользователь с ролью Администратора аккаунта автоматически наследует Read-доступ ко всем контейнерам
- BR-013: Пользователь с ролью Пользователь аккаунта не наследует никаких прав на контейнеры
- BR-014: Права на контейнеры являются инкрементальными: Publish включает Approve, Approve включает Edit, Edit включает Read

**Результат:** Новый пользователь добавлен в аккаунт с назначенными правами

---

### FR-AUTH-005: Изменение прав доступа пользователя

**Описание:** Администратор может изменить уровень доступа существующего пользователя как на уровне аккаунта, так и на уровне отдельных контейнеров.

**Роли:** Администратор аккаунта

**Предусловия:** Пользователь, чьи права изменяются, уже добавлен в аккаунт

**Основной сценарий:**
1. Администратор переходит в Admin > User Management
2. Выбирает пользователя из списка
3. Изменяет роль на уровне аккаунта и/или права на уровне контейнеров
4. Сохраняет изменения
5. Изменения вступают в силу немедленно

**Альтернативные сценарии:**
- Повышение до Администратора: пользователь получает возможность управлять другими пользователями
- Понижение с Администратора: пользователь теряет административные возможности, но должен остаться хотя бы один Администратор

**Бизнес-правила:**
- BR-015: Нельзя снять роль Администратора с последнего Администратора аккаунта
- BR-016: Администратор может менять свои собственные права, но не может снять с себя роль Администратора, если он последний
- BR-017: Изменения прав вступают в силу немедленно для текущих и будущих сессий

**Результат:** Права доступа пользователя обновлены

---

### FR-AUTH-006: Удаление пользователя из аккаунта

**Описание:** Администратор может удалить пользователя из аккаунта, что приводит к полному отзыву доступа к аккаунту и всем его контейнерам.

**Роли:** Администратор аккаунта

**Предусловия:** Удаляемый пользователь добавлен в аккаунт

**Основной сценарий:**
1. Администратор переходит в Admin > User Management
2. Выбирает пользователя
3. Нажимает "Удалить"
4. Подтверждает удаление
5. Пользователь теряет доступ к аккаунту и всем контейнерам

**Альтернативные сценарии:**
- Удаление пользователя на уровне контейнера: пользователь теряет доступ только к конкретному контейнеру, но остается в аккаунте
- Попытка удалить последнего Администратора — система отклоняет операцию

**Бизнес-правила:**
- BR-018: Удаление пользователя с уровня аккаунта автоматически отзывает доступ ко всем контейнерам
- BR-019: Нельзя удалить последнего Администратора аккаунта
- BR-020: Удаленный пользователь может быть повторно приглашен

**Результат:** Пользователь полностью удален из аккаунта GTM

---

### FR-AUTH-007: Включение обязательной двухфакторной аутентификации

**Описание:** Администратор аккаунта GTM может включить требование двухфакторной аутентификации (2-Step Verification) для выполнения определенных операций внутри аккаунта.

**Роли:** Администратор аккаунта

**Предусловия:** Пользователь имеет роль Администратора

**Основной сценарий:**
1. Администратор переходит в Admin > Account Settings
2. Включает опцию "Require 2-step login verification"
3. Сохраняет настройки
4. С этого момента пользователи без включенной 2FA на своем Google Account не смогут выполнять критические операции

**Альтернативные сценарии:**
- Пользователь без 2FA пытается редактировать Custom HTML тег — получает ошибку и сообщение о необходимости включить 2FA
- Пользователь включает 2FA на уровне Google Account — получает возможность выполнять ограниченные операции

**Бизнес-правила:**
- BR-021: При включенной настройке: создание и редактирование пользовательских тегов (Custom HTML) и пользовательских переменных (Custom JavaScript) требует 2FA
- BR-022: 2FA управляется на уровне Google Account, а не GTM — GTM только проверяет наличие активной 2FA
- BR-023: Методы 2FA определяются Google Account: приложения-аутентификаторы, SMS, физические ключи безопасности, резервные коды
- BR-024: Настройка распространяется на всех пользователей аккаунта GTM без исключений

**Результат:** Критические операции в аккаунте защищены обязательной двухфакторной аутентификацией

---

### FR-AUTH-008: Создание контейнера в существующем аккаунте

**Описание:** Администратор может создавать дополнительные контейнеры внутри аккаунта для разных сайтов, приложений или серверных сред.

**Роли:** Администратор аккаунта

**Предусловия:** Аккаунт GTM существует, пользователь — Администратор

**Основной сценарий:**
1. Администратор переходит в Admin > Container > Create Container
2. Вводит название контейнера
3. Выбирает тип платформы: Web, iOS, Android, AMP или Server
4. Подтверждает создание
5. Контейнер создан, отображается код установки (для web-контейнера)

**Альтернативные сценарии:**
- Создание server-контейнера требует дополнительной инфраструктурной настройки (сервер тегирования)
- AMP-контейнер имеет ограниченный набор поддерживаемых тегов

**Бизнес-правила:**
- BR-025: Тип платформы контейнера задается при создании и не может быть изменен впоследствии
- BR-026: Каждый контейнер получает уникальный идентификатор (GTM-XXXXXX)
- BR-027: Администратор аккаунта автоматически получает полные права на новый контейнер
- BR-028: В бесплатной версии GTM в каждом контейнере доступно 3 рабочих области; в GTM 360 — неограниченно

**Результат:** Новый контейнер создан и готов к настройке

---

### FR-AUTH-009: Удаление аккаунта GTM

**Описание:** Администратор может удалить аккаунт GTM целиком, что приводит к удалению всех контейнеров и данных.

**Роли:** Администратор аккаунта

**Предусловия:** Пользователь — Администратор аккаунта

**Основной сценарий:**
1. Администратор инициирует удаление аккаунта
2. Система запрашивает подтверждение
3. Аккаунт и все контейнеры помечаются как удаленные
4. Пользователи с Read-доступом имеют 30 дней на экспорт данных из корзины
5. После 30 дней данные удаляются безвозвратно

**Альтернативные сценарии:**
- Аккаунт или контейнер без единого Администратора автоматически удаляется системой
- Удаленный аккаунт не может быть восстановлен — требуется создание нового

**Бизнес-правила:**
- BR-029: Удаление аккаунта — необратимая операция после истечения grace-периода
- BR-030: Если у аккаунта или контейнера не остается ни одного Администратора, система автоматически удаляет его
- BR-031: 30-дневный grace-период позволяет пользователям с Read-доступом экспортировать данные

**Результат:** Аккаунт GTM удален вместе со всеми контейнерами и данными

### FR-AUTH-010: Привязка аккаунта к организации Google Marketing Platform

**Описание:** Аккаунт GTM может быть привязан к организации в Google Marketing Platform для централизованного управления пользователями и интеграции с другими продуктами Google (GA, Optimize и др.).

**Роли:** Администратор аккаунта GTM + Администратор организации GMP

**Предусловия:**
- Существует организация в Google Marketing Platform
- Пользователь имеет права Администратора в GTM-аккаунте и/или в организации GMP

**Основной сценарий:**
1. Администратор организации GMP инициирует привязку аккаунта GTM
2. Если инициатор также является Администратором GTM-аккаунта — привязка происходит автоматически
3. Все контейнеры аккаунта становятся доступны на странице Administration в GMP
4. Администраторы организации получают возможность централизованно управлять пользователями

**Альтернативные сценарии:**
- Если инициатор — Администратор организации, но не Администратор GTM-аккаунта: отправляется запрос на привязку Администратору GTM-аккаунта для подтверждения
- Биллинг-администратор организации также может инициировать запрос привязки

**Бизнес-правила:**
- BR-032: Привязка к организации дает возможность централизованного управления пользователями через GMP
- BR-033: Администраторы организации могут управлять пользователями во всех привязанных продуктовых аккаунтах (GTM, GA и др.)
- BR-034: Привязка требует подтверждения со стороны Администратора продуктового аккаунта, если инициатор не является таковым
- BR-035: Можно настраивать групповые политики пользователей на уровне организации

**Результат:** Аккаунт GTM привязан к организации GMP с централизованным управлением

---

### FR-AUTH-011: Настройка доступа через сервисный аккаунт

**Описание:** Для автоматизированных задач (CI/CD пайплайны, плановые инвентаризации, автоматический деплой тегов) можно настроить доступ через сервисный аккаунт Google.

**Роли:** Администратор аккаунта GTM

**Предусловия:**
- Создан сервисный аккаунт в Google Cloud Console
- Tag Manager API активирован в проекте GCP
- Сгенерирован ключ сервисного аккаунта

**Основной сценарий:**
1. Администратор добавляет email сервисного аккаунта как обычного пользователя в GTM
2. Назначает необходимые права на уровне аккаунта и контейнеров
3. Сервисный аккаунт использует ключ для аутентификации через OAuth 2.0 (server-to-server flow)
4. Запросы к API выполняются от имени сервисного аккаунта с назначенными правами

**Альтернативные сценарии:**
- Сервисный аккаунт может иметь ограниченные права (только Read) для мониторинга
- Сервисный аккаунт с правами Publish может автоматически публиковать изменения

**Бизнес-правила:**
- BR-036: Сервисный аккаунт подчиняется тем же правилам прав доступа, что и обычный пользователь
- BR-037: Рекомендуется строго контролировать права сервисных аккаунтов с Publish-доступом (ревью, staging, откат)
- BR-038: Ключ сервисного аккаунта дает полный доступ без участия пользователя — требует безопасного хранения
- BR-039: Сервисный аккаунт не требует прохождения 2FA

**Результат:** Настроен автоматизированный доступ к GTM через сервисный аккаунт

---

### FR-AUTH-012: Передача владения аккаунтом

**Описание:** При уходе сотрудника или смене подрядчика необходимо передать административный контроль над аккаунтом GTM другому пользователю.

**Роли:** Администратор аккаунта

**Предусловия:** В аккаунте есть хотя бы один Администратор

**Основной сценарий:**
1. Текущий Администратор добавляет нового пользователя (или повышает существующего) до роли Администратора
2. Новый Администратор подтверждает доступ, войдя в GTM
3. При необходимости — старый Администратор удаляется из аккаунта или понижается

**Альтернативные сценарии:**
- Если единственный Администратор покинул организацию, а другого нет — аккаунт может быть потерян
- Если аккаунт привязан к организации GMP — Администратор организации может восстановить доступ

**Бизнес-правила:**
- BR-040: GTM не имеет концепции "владельца" — все Администраторы равноправны
- BR-041: Рекомендуется всегда иметь минимум двух Администраторов для предотвращения блокировки
- BR-042: Первоначальный создатель аккаунта может быть удален другим Администратором
- BR-043: Если аккаунт теряет всех Администраторов — он автоматически удаляется системой

**Результат:** Административный контроль над аккаунтом передан новому пользователю

## Сущности данных

### Аккаунт GTM (Account)
- Идентификатор аккаунта (числовой)
- Название аккаунта
- Страна расположения
- Флаг анонимного обмена данными
- Настройка обязательной 2FA
- Привязка к организации GMP (опционально)
- Версия: бесплатная / GTM 360

### Контейнер (Container)
- Идентификатор контейнера (GTM-XXXXXX)
- Название контейнера
- Тип платформы (Web / iOS / Android / AMP / Server)
- Принадлежность к аккаунту
- Размер (текущий, максимум 200 KB)

### Пользователь аккаунта (User Permission)
- Email (Google Account)
- Роль на уровне аккаунта (Administrator / User)
- Набор прав на каждый контейнер (No Access / Read / Edit / Approve / Publish)

### Сервисный аккаунт (Service Account)
- Email сервисного аккаунта (формат: name@project.iam.gserviceaccount.com)
- Роль на уровне аккаунта
- Набор прав на контейнеры
- Привязка к проекту GCP

### OAuth-токен (OAuth Token)
- Access token (краткосрочный)
- Refresh token (долгосрочный, до 25 на пару Client ID / аккаунт)
- Scopes доступа
- Client ID приложения

## Состояния и статусы

### Состояния аккаунта GTM
```
[Не существует] → Создание → [Активный]
[Активный] → Удаление → [Удален (grace-период 30 дней)]
[Удален] → Истечение grace-периода → [Удален безвозвратно]
[Активный] → Потеря всех администраторов → [Автоматическое удаление]
```

### Состояния пользователя в аккаунте
```
[Не добавлен] → Приглашение Администратором → [Активный]
[Активный] → Изменение прав → [Активный (новые права)]
[Активный] → Удаление → [Удален из аккаунта]
[Удален] → Повторное приглашение → [Активный]
```

### Состояния доступа контейнера для пользователя
```
[No Access] ↔ [Read] ↔ [Edit] ↔ [Approve] ↔ [Publish]
```
Переходы между состояниями выполняются Администратором. Права инкрементальны: каждый следующий уровень включает все предыдущие.

### Состояния OAuth-сессии
```
[Не авторизован] → Прохождение OAuth flow → [Авторизован (access token)]
[Авторизован] → Истечение access token → [Требуется обновление]
[Требуется обновление] → Использование refresh token → [Авторизован (новый access token)]
[Авторизован] → Отзыв согласия пользователем → [Не авторизован]
```

## Интеграции с другими модулями

### Google Account / Google Identity
- Единый провайдер аутентификации для всех пользователей GTM
- 2FA управляется через Google Account, GTM проверяет статус
- Сессия и управление паролями — на стороне Google Account

### Google Marketing Platform (организация)
- Централизованное управление пользователями через организацию GMP
- Привязка аккаунтов GTM, GA, Optimize к единой организации
- Групповые политики пользователей на уровне организации

### Google Analytics
- Совместное использование пользователей — доступ к GA и GTM через один Google Account
- Теги GA настраиваются внутри контейнеров GTM
- Общий контекст организации GMP

### Google Cloud Platform
- Сервисные аккаунты создаются и управляются в GCP
- OAuth-приложения регистрируются в GCP Console
- Server-контейнеры GTM развертываются на инфраструктуре GCP (App Engine / Cloud Run)

### Google Ads
- Связка через Google Account для конверсионных тегов
- Общий пользовательский контекст через GMP

### Модуль тегов и триггеров GTM (внутренний)
- Права доступа контейнера определяют, что пользователь может делать с тегами, триггерами и переменными
- 2FA-требование влияет на возможность редактирования Custom HTML и Custom JavaScript

- Права Edit и выше дают возможность создавать рабочие области
- Количество рабочих областей ограничено версией GTM (3 vs. неограниченно)
