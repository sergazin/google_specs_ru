# Google Play: Модуль "Google Play Console (панель разработчика)" -- Core Feature

## Обзор модуля

Google Play Console -- это панель управления для разработчиков Android-приложений, предоставляющая полный набор инструментов для публикации, управления, мониторинга и монетизации приложений в магазине Google Play. Console является единственной точкой входа для размещения приложений на Google Play и охватывает весь жизненный цикл приложения: от регистрации аккаунта разработчика и создания листинга до управления релизами, аналитики, финансовых отчётов и работы с отзывами пользователей.

Каждое приложение в Google Play Console проходит обязательный процесс ревью (App Review) на соответствие политикам Google Play перед публикацией. Разработчик управляет множественными треками релизов (Internal Testing, Closed Testing, Open Testing, Production), может проводить поэтапное развёртывание (Staged Rollout), настраивать A/B-тесты листинга, управлять ценами и распространением по странам, настраивать in-app продукты и подписки, отвечать на отзывы и анализировать качество приложения через Android Vitals.

### Ключевые принципы

- Каждое приложение идентифицируется уникальным Application ID (package name), который нельзя изменить после публикации
- Все приложения проходят обязательную проверку (App Review) на соответствие политикам Google Play
- Play App Signing обязателен для новых приложений -- Google управляет ключом подписи
- Разработчик платит единоразовый взнос $25 за регистрацию аккаунта
- Организации проходят верификацию через D-U-N-S номер; физлица -- через государственный документ
- Приложения распространяются только в формате Android App Bundle (AAB), а не APK (с 2021 г.)
- Финансовая модель: Google удерживает комиссию 15% (первый $1M/год) или 30% с продаж
- Managed Publishing позволяет контролировать момент публикации изменений после одобрения

## Роли и права доступа

### Уровни доступа

| Роль | Описание | Создание приложений | Управление релизами | Финансовые данные | Управление пользователями | Ответы на отзывы |
|------|----------|--------------------|--------------------|-------------------|--------------------------|-------------------|
| Account Owner (Владелец аккаунта) | Создатель и владелец аккаунта разработчика | Да | Да | Да | Да | Да |
| Admin (Администратор) | Полные права, кроме удаления аккаунта | Да | Да | Да | Да | Да |
| User (Пользователь) | Настраиваемые гранулярные разрешения | По разрешению | По разрешению | По разрешению | Нет | По разрешению |

### Гранулярные разрешения (для роли User)

Разрешения применяются на двух уровнях:

**Account-level (уровень аккаунта)** -- распространяются на все приложения, включая будущие:
- View app information (просмотр информации о приложениях)
- Create, edit, and delete draft apps (управление черновиками)
- Edit and delete draft apps (редактирование черновиков)
- Release to production, exclude devices, and use Play App Signing (управление релизами)
- Release apps to testing tracks (управление тестовыми треками)
- Manage store presence (управление листингом)
- View financial data, orders, and cancellation survey responses (просмотр финансовых данных)
- Manage orders and subscriptions (управление заказами)
- Reply to reviews (ответы на отзывы)
- Manage policy declarations (управление декларациями)
- View app quality information (просмотр качества)
- Manage deep links (управление deep links)

**App-level (уровень приложения)** -- ограничены конкретными приложениями:
- Те же разрешения, но применяются только к выбранным приложениям

### Группы разрешений (Permission Groups)

| Возможность | Описание |
|------------|----------|
| Создание группы | Объединение набора разрешений в именованную группу |
| Назначение группы | Присвоение группы разрешений нескольким пользователям одновременно |
| Массовое редактирование | Bulk edit для управления разрешениями множества пользователей |
| Временный доступ | Установка срока истечения (expiration date) для разрешений |

## Функциональные требования

### FR-GPC-001: Регистрация аккаунта разработчика

**Приоритет**: P0

**Описание:** Пользователь создаёт аккаунт разработчика Google Play для получения возможности публиковать приложения. Регистрация требует оплаты единоразового взноса, указания типа аккаунта и прохождения верификации личности.

**Роли:** Любой пользователь с Google-аккаунтом

**Основной сценарий:**
1. Пользователь переходит на play.google.com/console
2. Пользователь выбирает тип аккаунта: Personal (личный) или Organization (организация)
3. Система запрашивает базовую информацию в зависимости от типа:
   - **Personal**: имя разработчика, email для связи, номер телефона
   - **Organization**: название организации, адрес, контактные данные, D-U-N-S номер, размер организации
4. Пользователь привязывает профиль Google Payments
5. Пользователь оплачивает единоразовый регистрационный взнос $25
6. Система запускает процесс верификации личности
7. После верификации аккаунт активируется

**Верификация для Personal аккаунта:**
- Предоставление официального государственного документа (паспорт, ID)
- Подтверждение email-адреса
- Подтверждение номера телефона

**Верификация для Organization аккаунта:**
- Предоставление D-U-N-S номера организации
- Подтверждение полномочий представителя
- Документы от государственного органа, торговой палаты или реестра
- Для государственных организаций: документ на фирменном бланке вместо D-U-N-S

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-001 | Регистрационный взнос $25 является единоразовым и невозвратным |
| BR-GPC-002 | Тип аккаунта (Personal / Organization) нельзя изменить после создания |
| BR-GPC-003 | Верификация обязательна до публикации первого приложения |
| BR-GPC-004 | Подача поддельных или модифицированных документов приводит к немедленному удалению аккаунта |
| BR-GPC-005 | D-U-N-S номер обязателен для организаций, кроме государственных учреждений |
| BR-GPC-006 | Один Google-аккаунт может иметь только один аккаунт разработчика |
| BR-GPC-007 | Верификация должна быть завершена до возможности отправки приложений на ревью |
| BR-GPC-008 | С конца 2026 года все Android-приложения должны быть зарегистрированы верифицированными разработчиками (начиная с Бразилии, Сингапура, Индонезии, Таиланда) |

**Результат:** Аккаунт разработчика создан, верифицирован и готов к публикации приложений.

### FR-GPC-002: Создание приложения и настройка Store Listing

**Приоритет**: P0

**Описание:** Разработчик создаёт новое приложение в Play Console и настраивает его Store Listing -- страницу приложения в Google Play, содержащую всю информацию, необходимую для пользователей: название, описание, скриншоты, иконку, графику и другие элементы.

**Роли:** Account Owner, Admin, User (с разрешением Manage store presence)

**Основной сценарий:**
1. Разработчик нажимает "Create app" в Play Console
2. Система запрашивает базовую информацию:
   - Название приложения (до 30 символов)
   - Язык по умолчанию
   - Тип: App (приложение) или Game (игра)
   - Модель монетизации: Free (бесплатное) или Paid (платное)
3. Разработчик подтверждает соответствие политикам и экспортным ограничениям
4. Система создаёт приложение в статусе Draft
5. Разработчик заполняет Store Listing:
   - **Название** (до 30 символов)
   - **Краткое описание** (до 80 символов)
   - **Полное описание** (до 4000 символов)
   - **Иконка** приложения (512x512 px, PNG/JPEG, 32-bit)
   - **Feature Graphic** (1024x500 px) -- баннер для продвижения
   - **Скриншоты**: минимум 2, максимум 8 для каждого типа устройства (phone, 7-inch tablet, 10-inch tablet, Chromebook, TV, Wear OS, Auto)
   - **Промо-видео** (URL YouTube, необязательно)
   - **Категория и теги**
   - **Контактные данные**: email (обязательно), телефон, сайт
6. Разработчик может добавить локализованные версии для разных языков
7. Разработчик может использовать Gemini AI для автоматического перевода

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-009 | Application ID (package name) задаётся в коде приложения и не может быть изменён после первой публикации |
| BR-GPC-010 | Тип приложения (App / Game) можно изменить |
| BR-GPC-011 | Монетизация Free -> Paid допустима; Paid -> Free допустимо, но обратный переход после этого невозможен |
| BR-GPC-012 | Минимум 2 скриншота для телефона обязательны |
| BR-GPC-013 | Иконка обязательна и должна соответствовать гайдлайнам Google (без текста для продвижения, без рамок) |
| BR-GPC-014 | Store Listing должен быть на языке по умолчанию; локализации опциональны |
| BR-GPC-015 | Gemini AI переводит строки приложения бесплатно |
| BR-GPC-016 | Все текстовые и графические элементы проверяются на соответствие политикам при ревью |

**Результат:** Приложение создано в Play Console с заполненным Store Listing, готовое к загрузке бинарного файла.

### FR-GPC-003: Загрузка App Bundle и управление артефактами

**Приоритет**: P0

**Описание:** Разработчик загружает Android App Bundle (AAB) -- формат публикации приложений, из которого Google Play автоматически генерирует оптимизированные APK для каждого устройства пользователя. Управление артефактами включает загрузку, просмотр истории и работу с App Bundle Explorer.

**Роли:** Account Owner, Admin, User (с разрешением Release to production / Release apps to testing tracks)

**Основной сценарий:**
1. Разработчик переходит в раздел "Test and release" -> "Production" (или тестовый трек)
2. Разработчик нажимает "Create new release"
3. Система предлагает загрузить App Bundle (.aab файл)
4. Разработчик загружает AAB
5. Система валидирует AAB:
   - Проверка подписи (Upload Key)
   - Проверка версии (versionCode должен быть выше текущего)
   - Проверка структуры бандла
   - Проверка размера (максимум 150 МБ для AAB, до 2 ГБ с Play Asset Delivery)
6. Система отображает информацию о бандле: versionCode, versionName, размер, поддерживаемые устройства
7. Разработчик заполняет Release Notes (что нового) для каждого языка
8. Разработчик отправляет релиз на ревью

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-017 | Формат AAB (Android App Bundle) обязателен для новых приложений с 2021 года |
| BR-GPC-018 | versionCode каждого нового релиза должен быть строго больше предыдущего |
| BR-GPC-019 | Максимальный размер AAB -- 150 МБ; для больших приложений используется Play Asset Delivery (до 2 ГБ) |
| BR-GPC-020 | Загруженный AAB подписывается Upload Key разработчика; Google перeподписывает App Signing Key |
| BR-GPC-021 | Release Notes рекомендованы, но не обязательны; отображаются пользователям в "Что нового" |
| BR-GPC-022 | Asset Library позволяет загружать визуальные ассеты, в том числе из Google Drive, организовывать тегами и обрезать |

**Результат:** App Bundle загружен, провалидирован и готов к отправке в релизный трек.

### FR-GPC-004: Управление треками релизов (Release Tracks)

**Приоритет**: P0

**Описание:** Разработчик управляет четырьмя треками релизов, каждый из которых предназначен для определённого этапа тестирования и распространения. Треки позволяют последовательно проверять приложение перед публикацией в Production.

**Роли:** Account Owner, Admin, User (с соответствующими разрешениями)

**Треки релизов:**

| Трек | Описание | Максимум тестеров | Видимость в Google Play | Отзывы влияют на рейтинг |
|------|----------|-------------------|------------------------|--------------------------|
| Internal Testing | Быстрое тестирование с минимальной задержкой ревью | До 100 | Нет | Нет |
| Closed Testing | Целевое тестирование с управляемыми списками | Без ограничений (по спискам email / Google Groups) | Нет (по приглашению) | Нет |
| Open Testing | Публичное бета-тестирование | Без ограничений | Да (как бета) | Нет (отдельный фидбек) |
| Production | Полный публичный релиз | Все пользователи Google Play | Да | Да |

**Основной сценарий (Internal Testing):**
1. Разработчик переходит в "Test and release" -> "Internal testing"
2. Разработчик создаёт список тестеров (до 100 email-адресов)
3. Разработчик создаёт релиз и загружает AAB
4. Релиз проходит минимальную проверку (часы, не дни)
5. Тестеры получают доступ к приложению по ссылке

**Основной сценарий (Closed Testing):**
1. Разработчик создаёт Closed Testing трек (можно несколько: alpha, custom)
2. Разработчик определяет тестеров: через списки email или Google Groups
3. Разработчик загружает AAB и отправляет на ревью
4. После одобрения тестеры получают приложение
5. Разработчик собирает фидбек через Play Console (приватный, не влияет на публичный рейтинг)

**Основной сценарий (Open Testing):**
1. Разработчик создаёт Open Testing трек
2. Разработчик загружает AAB и отправляет на ревью
3. После одобрения приложение доступно для скачивания как бета
4. Пользователи могут присоединиться к тестированию через Google Play
5. Фидбек отправляется приватно разработчику

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-023 | Internal Testing ограничен 100 тестерами |
| BR-GPC-024 | Рекомендуется начинать с Internal Testing перед переходом к Closed/Open |
| BR-GPC-025 | Closed Testing поддерживает несколько треков (alpha + кастомные) |
| BR-GPC-026 | Open Testing делает приложение видимым в Google Play как бета-версию |
| BR-GPC-027 | Тестовые отзывы не влияют на публичный рейтинг и видны только разработчику |
| BR-GPC-028 | Каждый трек имеет независимое управление странами распространения |
| BR-GPC-029 | Продвижение между треками (promote): Internal -> Closed -> Open -> Production |
| BR-GPC-030 | Internal Testing проходит ревью значительно быстрее (часы vs дни) |

**Результат:** Приложение размещено в соответствующем треке и доступно целевой аудитории тестеров.

### FR-GPC-005: Поэтапное развёртывание (Staged Rollout)

**Приоритет**: P0

**Описание:** Разработчик выпускает обновление приложения постепенно, начиная с малого процента пользователей и увеличивая долю по мере подтверждения стабильности. Staged Rollout минимизирует риски при обновлении: при обнаружении проблем разработчик может остановить (halt) раскатку.

**Роли:** Account Owner, Admin, User (с разрешением Release to production)

**Основной сценарий:**
1. Разработчик создаёт новый релиз в Production (или тестовом треке)
2. Разработчик выбирает процент развёртывания (например, 5%, 10%, 25%, 50%, 100%)
3. Система начинает распространение обновления выбранному проценту пользователей
4. Разработчик мониторит метрики: крэш-рейт, ANR, отзывы
5. При стабильных показателях разработчик увеличивает процент
6. При критических проблемах разработчик выполняет Halt Rollout

**Halt Rollout (остановка раскатки):**
1. Разработчик нажимает "Halt rollout" в Play Console (или через Publishing API)
2. Система останавливает распространение проблемной версии новым пользователям
3. Пользователи, уже получившие обновление, сохраняют его
4. Разработчик исправляет проблему и выпускает новый релиз

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-031 | Staged Rollout доступен только для обновлений, не для первой публикации |
| BR-GPC-032 | Минимальный начальный процент -- 1%, рекомендуемый -- 5-20% |
| BR-GPC-033 | Halt Rollout останавливает распространение, но не откатывает уже установленные обновления |
| BR-GPC-034 | После Halt разработчик может либо возобновить раскатку, либо выпустить новый фикс-релиз |
| BR-GPC-035 | Процент можно увеличивать, но нельзя уменьшать (кроме Halt) |
| BR-GPC-036 | При Staged Rollout Google Play случайным образом выбирает пользователей для обновления |
| BR-GPC-037 | Полная раскатка (100%) завершает staged rollout и делает версию доступной всем |
| BR-GPC-038 | Halt Rollout доступен через Play Console и Publishing API |

### FR-GPC-006: Обзор приложения Google (App Review)

**Приоритет**: P0

| Правило | Описание |

### FR-GPC-007: Политики Google Play и Policy Compliance

**Приоритет**: P0

**Описание:** Все приложения в Google Play обязаны соблюдать Google Play Developer Program Policies. Система Policy Status отслеживает соответствие приложения политикам и применяет enforcement actions при нарушениях. Разработчик может отслеживать статус политик и подавать апелляции.

**Роли:** Account Owner, Admin, User (с разрешением Manage policy declarations)

**Типы enforcement actions:**

| Действие | Описание | Последствия |
|----------|----------|-------------|

| Suspension (Приостановка) | Серьёзные или многократные нарушения | Потеря пользователей, статистики, рейтингов; аккаунт под угрозой |
| Account Termination | Терминация аккаунта разработчика | Все приложения удаляются; запрет на создание новых аккаунтов |

**Policy Status Page:**
1. Разработчик переходит в "Policy status" в Play Console

3. При наличии нарушений отображается:
   - Тип нарушения
   - Конкретная политика
   - Дедлайн на исправление
   - Рекомендации по исправлению
4. Разработчик исправляет нарушение и повторно отправляет на ревью

**Процесс апелляции:**
1. Разработчик получает уведомление о enforcement action
2. Разработчик изучает указанное нарушение
3. Если считает решение ошибочным -- подаёт апелляцию через ссылку в уведомлении
4. Google рассматривает апелляцию и принимает решение о восстановлении или подтверждении

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-046 | Разработчик обязан соблюдать все актуальные Google Play Developer Program Policies |
| BR-GPC-047 | Repeated или серьёзные нарушения (malware, fraud) ведут к терминации аккаунта |
| BR-GPC-048 | Удаление/приостановка не означает перечисление всех нарушений -- разработчик обязан провести полный аудит |

### FR-GPC-008: Статистика и аналитика (Android Vitals & Statistics)

**Приоритет**: P0

**Описание:** Play Console предоставляет комплексную систему мониторинга технического качества приложения (Android Vitals) и бизнес-статистики (Statistics). Android Vitals отслеживает крэши, ANR, энергопотребление и другие метрики, влияющие на видимость в Google Play. Statistics предоставляет данные об установках, удалениях, рейтингах и аудитории.

**Роли:** Account Owner, Admin, User (с разрешением View app quality information)

**Android Vitals -- ключевые метрики:**

| Метрика | Описание | Bad Behavior Threshold |
|---------|----------|----------------------|
| User-perceived crash rate | Процент пользователей, столкнувшихся хотя бы с одним крэшем за день | > 1.09% |
| User-perceived ANR rate | Процент пользователей с Application Not Responding за день | > 0.47% |
| Excessive wake locks | Частичные wake locks, удерживаемые дольше 1 часа | Зависит от контекста |
| Stuck partial wake locks | Wake locks, не освобождаемые после перехода в фон | Зависит от контекста |
| Excessive background Wi-Fi scans | Избыточные сканирования Wi-Fi в фоне | Зависит от контекста |

**Crash Reporting:**
1. Система собирает данные о крэшах от пользователей, давших согласие
2. Крэши группируются в кластеры по общей корневой причине
3. Для каждого кластера отображается:
   - Stack trace
   - Количество затронутых пользователей
   - Версии приложения
   - Модели устройств
   - Версии Android
   - Event tags
4. Разработчик может фильтровать по версии, устройству, периоду
5. Данные доступны за последние 90 дней в Console, 3 года через API

**Statistics:**
- Установки и удаления (по дням, странам, устройствам)
- Активные устройства (DAU, MAU)
- Обновления
- Рейтинг и количество отзывов
- Доход (для платных приложений и in-app purchases)
- Конверсия страницы листинга
- Источники трафика (органический, реклама, deep links)
- Gemini AI генерирует описания трендов на графиках

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-052 | Превышение Bad Behavior Threshold негативно влияет на ранжирование в Google Play |
| BR-GPC-053 | Android Vitals данные доступны только для приложений с достаточным количеством пользователей |
| BR-GPC-054 | Данные Android Vitals хранятся 90 дней в Console и 3 года через Play Developer Reporting API |
| BR-GPC-055 | Крэш-рейт учитывает только "user-perceived" крэши (в foreground activity или foreground service) |
| BR-GPC-056 | Gemini AI может генерировать текстовые описания трендов на странице Statistics |
| BR-GPC-057 | Метрики обновляются с задержкой 24-48 часов |

**Результат:** Разработчик имеет полную картину технического качества и бизнес-показателей приложения.

### FR-GPC-011: Настройка In-app Products и подписок

**Приоритет**: P0

**Описание:** Разработчик создаёт и управляет in-app продуктами (одноразовые покупки) и подписками через Play Console. Подписки имеют иерархическую структуру: подписка -> базовые планы -> предложения (offers). Все продажи in-app проходят через Google Play Billing.

**Роли:** Account Owner, Admin, User (с разрешением Manage orders and subscriptions)

   - Цена (базовая; локальные рассчитываются автоматически)
   - Статус: Active / Inactive
3. Типы in-app продуктов:
   - **Consumable** (расходуемый): можно купить многократно (игровая валюта, жизни)
   - **Non-consumable** (неразовый): покупается один раз (разблокировка уровня, удаление рекламы)

**Subscriptions (подписки):**
1. Разработчик переходит в "Monetize with Play" -> "Products" -> "Subscriptions"
2. Разработчик создаёт подписку:
   - Subscription ID (уникальный, неизменяемый, не переиспользуемый)
   - Название и описание
   - Список benefits (преимуществ)
3. Разработчик создаёт Base Plan (базовый план):
   - Период подписки (1 неделя, 1 месяц, 3 месяца, 6 месяцев, 1 год)
   - Тип: Auto-renewing (автопродление) или Prepaid (предоплата)
   - Цена для каждого региона
   - Grace period (период отсрочки платежа)
   - Account hold (удержание аккаунта при неуплате)
4. Разработчик создаёт Offers (предложения):
   - Free trial (бесплатный пробный период)
   - Introductory price (вводная скидка)
   - Условия: для новых подписчиков, для возвращающихся, для апгрейда

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-071 | Product ID уникален, неизменяем и не может быть переиспользован после удаления |
| BR-GPC-072 | Необходимо загрузить AAB хотя бы в один трек перед настройкой монетизации |
| BR-GPC-073 | Для каждой подписки допускается суммарно до 250 Base Plans + Offers, максимум 50 активных одновременно |
| BR-GPC-074 | Free trial и introductory price доступны как incentive для новых подписчиков |
| BR-GPC-075 | Auto-renewing подписки поддерживают Grace Period и Account Hold |
| BR-GPC-076 | Все продажи in-app обязаны проходить через Google Play Billing (за исключением категорий-исключений) |
| BR-GPC-077 | Prepaid подписки не продлеваются автоматически; пользователь пополняет вручную |

**Результат:** In-app продукты и подписки настроены и готовы к продаже через Google Play Billing.

### FR-GPC-017: Play App Signing (подпись приложений)

**Приоритет**: P0

**Описание:** Play App Signing -- сервис, при котором Google управляет ключом подписи приложения (App Signing Key) и использует его для подписи оптимизированных APK, генерируемых из App Bundle. Разработчик подписывает загружаемый AAB своим Upload Key, а Google переподписывает финальный APK.

**Роли:** Account Owner, Admin, User (с разрешением Release to production / Use Play App Signing)

**Типы ключей:**

| Ключ | Описание | Управление |
|------|----------|------------|
| App Signing Key | Основной ключ подписи, идентифицирующий приложение для пользователей | Управляется Google (на инфраструктуре Google KMS) |
| Upload Key | Ключ для подписи AAB перед загрузкой в Play Console | Управляется разработчиком |

**Основной сценарий (новое приложение):**
1. Разработчик переходит в "Test and release" -> "Setup" -> "App signing"
2. Система предлагает два варианта:
   - **Google-generated key**: Google генерирует RSA 4096-bit ключ (рекомендуется)
   - **Upload your own key**: разработчик загружает свой ключ (минимум RSA 2048-bit)
3. Разработчик настраивает Upload Key для подписи загружаемых AAB
4. Система сохраняет конфигурацию
5. При загрузке AAB: разработчик подписывает Upload Key -> Google верифицирует -> Google подписывает App Signing Key

**Компрометация Upload Key:**
1. Разработчик обнаруживает компрометацию Upload Key
2. Разработчик обращается в Google через Play Console
3. Google помогает сбросить Upload Key без влияния на App Signing Key
4. Разработчик генерирует новый Upload Key и продолжает загрузку

**Доступные fingerprints:**
- MD5, SHA-1, SHA-256 сертификата App Signing Key
- Используются для настройки API-ключей (Google Maps, Firebase и др.)

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-108 | Play App Signing обязателен для новых приложений, публикуемых через AAB |
| BR-GPC-109 | App Signing Key хранится на инфраструктуре Google Key Management Service |
| BR-GPC-110 | Google-generated key использует RSA 4096-bit; загружаемый ключ -- минимум RSA 2048-bit |
| BR-GPC-111 | Upload Key можно сбросить при компрометации без потери App Signing Key |
| BR-GPC-112 | App Signing Key нельзя экспортировать из Google (для безопасности) |
| BR-GPC-113 | Fingerprints (SHA-1, SHA-256) доступны на странице App signing для интеграции с API |

**Результат:** Приложение подписано через Play App Signing; ключ подписи защищён инфраструктурой Google.

1. Разработчик переходит в "App content" -> "App access"
2. Система спрашивает: "Is all of your app's functionality available without restrictions?"
3. Если "No" -- разработчик добавляет инструкции:
   - Тестовые учётные данные (логин/пароль)
   - Описание шагов для доступа к ограниченным функциям
   - Информация о специальных требованиях (геолокация, оборудование)
   - Скриншоты или видео демонстрации функциональности (если ревьюер не может воспроизвести)
4. Система сохраняет инструкции для команды ревью

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-134 | Инструкции обязательны, если приложение имеет авторизацию или ограниченный доступ к функциям |
| BR-GPC-135 | Тестовые учётные данные должны быть актуальными и работоспособными |
| BR-GPC-136 | Без инструкций ревьюер может отклонить приложение из-за невозможности проверить функциональность |
| BR-GPC-137 | Инструкции доступны только команде ревью Google и не видны публично |

**Результат:** Команда ревью имеет все необходимые инструкции для полноценной проверки приложения.

### FR-GPC-022: Managed Publishing

**Приоритет**: P1

**Описание:** Managed Publishing -- режим, при котором одобренные изменения не публикуются автоматически, а ожидают ручного подтверждения разработчика. Это позволяет контролировать момент публикации (например, координировать с маркетинговыми кампаниями или запусками).

**Роли:** Account Owner, Admin, User (с разрешением Release to production)

**Основной сценарий:**
1. Разработчик включает Managed Publishing в настройках приложения
2. Разработчик отправляет изменения на ревью (релиз, Store Listing, etc.)
3. Изменения проходят стандартный ревью-процесс
4. После одобрения изменения помещаются в раздел "Ready to publish" (а не публикуются автоматически)
5. Разработчик на Publishing Overview видит все ожидающие изменения
6. Разработчик нажимает "Publish" когда готов
7. Все одобренные изменения публикуются одновременно

**Publishing Overview Page:**
- Отображает все изменения по категориям:
  - Changes not yet sent for review
  - Changes in review
  - Ready to publish
- Разработчик может вернуть одобренные изменения обратно в "not yet sent" (откатить до публикации)

**Типы изменений, контролируемых Managed Publishing:**
- Полные и staged roll-out релизы
- Изменения Store Listing (включая Custom Store Listings)
- Активные Store Listing Experiments
- Конфигурация тестеров для треков

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-138 | Managed Publishing можно включить/выключить в любой момент, в том числе во время ревью |
| BR-GPC-139 | Одобренные изменения можно вернуть обратно в "not yet sent" до публикации |
| BR-GPC-140 | При публикации все "Ready to publish" изменения применяются одновременно |
| BR-GPC-141 | Managed Publishing не влияет на сроки ревью |
| BR-GPC-142 | При выключении Managed Publishing ожидающие изменения публикуются автоматически |

**Результат:** Разработчик полностью контролирует момент публикации одобренных изменений.

### FR-GPC-023: Уведомления и алерты

**Приоритет**: P1

**Описание:** Play Console предоставляет систему уведомлений для оповещения разработчиков о важных событиях: изменении метрик, статусе ревью, нарушениях политик, аномалиях в крэш-рейтах и других критических событиях.

**Роли:** Account Owner, Admin, User (с настроенными разрешениями)

**Основной сценарий настройки:**
1. Разработчик переходит в "Setup" -> "Notifications"
2. Разработчик выбирает категории уведомлений:
   - **Performance**: значительные изменения в метриках (установки, крэши, рейтинг)
   - **Policy**: уведомления о нарушениях политик и enforcement actions
   - **Release**: статус ревью (одобрено, отклонено)
   - **Financial**: уведомления о выплатах и отчётах
   - **Reviews**: новые отзывы (по фильтрам: рейтинг, ключевые слова)
3. Разработчик настраивает каналы доставки:
   - Email
   - In-app (в Play Console)
4. Система отправляет уведомления при наступлении событий

**Типы алертов:**

| Категория | Примеры |
|-----------|---------|
| Android Vitals | Крэш-рейт превысил threshold; рост ANR |
| Releases | Ревью одобрено/отклонено; Staged rollout достиг milestone |
| Policy | Нарушение обнаружено; Дедлайн на исправление |
| Reviews | Новый негативный отзыв; Снижение среднего рейтинга |
| Installs | Аномальное снижение установок; Рост удалений |
| Financial | Earnings Report доступен; Выплата произведена |

**Deep Links Alerts:**
- Highlight cards на странице Deep links уведомляют о проблемах с конфигурацией
- Различные типы действий: "View domains", "Learn more" и т.д.

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-143 | Уведомления основаны на статистике приложения и срабатывают при значительных изменениях |
| BR-GPC-144 | Policy-уведомления отправляются автоматически и не могут быть отключены |
| BR-GPC-145 | Уведомления доступны по email и внутри Play Console |
| BR-GPC-146 | Разработчик может настроить пороги и фильтры для уведомлений |

**Результат:** Разработчик своевременно получает уведомления о критических событиях и изменениях метрик.

### FR-GPC-024: Deep Links Management

**Приоритет**: P1

**Описание:** Разработчик управляет deep links приложения через выделенную страницу в Play Console. Deep links обеспечивают переход пользователей из веба, рекламы и других источников напрямую в конкретный контент внутри приложения.

**Роли:** Account Owner, Admin, User (с разрешением Manage deep links)

**Основной сценарий:**
1. Разработчик переходит в "Grow users" -> "Deep links"
2. Система отображает дашборд с информацией:
   - Статус верификации доменов (website-to-app mapping)
   - Список всех зарегистрированных deep links
   - Highlight cards с проблемами и рекомендациями
3. Разработчик проверяет статус каждого домена:
   - Verified: домен корректно привязан
   - Not verified: требуется настройка Digital Asset Links
4. Разработчик может использовать patches для управления deep links без выпуска новой версии:
   - Добавление новых deep links
   - Отключение проблемных deep links
   - Исправление конфигурации
5. Тестирование deep links через встроенный эмулятор в Play Console (без физического устройства)

**Бизнес-правила:**
| Правило | Описание |
|---------|----------|
| BR-GPC-147 | Patches позволяют управлять deep links без выпуска нового релиза |
| BR-GPC-148 | Встроенный эмулятор позволяет тестировать deep links прямо в Play Console |
| BR-GPC-149 | Digital Asset Links (assetlinks.json) обязателен для верификации доменов |
| BR-GPC-150 | Highlight cards проактивно уведомляют о проблемах с deep links |

**Результат:** Deep links настроены, верифицированы и корректно работают для перехода в конкретный контент приложения.

## Состояния и статусы

### Жизненный цикл приложения

```
[Создание] -> Draft
     |
     v
[Заполнение App Content] -> Draft (Data Safety, Content Rating, App Access)
     |
     v
[Загрузка AAB] -> Draft (Release created)
     |
     v
[Submit for Review] -> In Review
     |                      |
     |                      v
     |                Rejected -> [Исправление] -> In Review
     |                      |
     v                      v
[Approved] -> Published (или Ready to Publish при Managed Publishing)
     |
     v
[Обновление] -> In Review -> Approved -> Published
     |
     v
[Policy Violation] -> Warning -> [Исправление] -> Published
                  |-> Removal -> [Апелляция] -> Published / Confirmed Removal
                  |-> Suspension -> [Апелляция] -> Published / Confirmed Suspension
```

### Жизненный цикл релиза

```
[Create Release] -> Draft
     |
     v
[Upload AAB] -> Draft (with artifact)
     |
     v
[Submit] -> In Review
     |          |
     |          v
     |     Rejected -> [Fix & Resubmit] -> In Review
     |
     v
Approved -> [Publish / Managed Publishing]
     |
     v
Published (Staged Rollout: X%)
     |          |
     |          v
     |     Halted -> [Fix] -> New Release
     |
     v
[Increase %] -> Published (100%) -- Full Rollout
```

### Состояния Staged Rollout

```
[Create Staged Release] -> Rollout X%
     |
     +-> [Increase %] -> Rollout Y% -> ... -> Rollout 100% (Full)
     |
     +-> [Halt Rollout] -> Halted
              |
              +-> [Resume] -> Rollout X%
              |
              +-> [New Release] -> Draft
```
