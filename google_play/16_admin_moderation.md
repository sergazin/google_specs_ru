# Администрирование и модерация контента (Google Play)

## Описание

Модуль администрирования и модерации контента Google Play обеспечивает комплексную систему контроля качества, безопасности и соответствия политикам для всех приложений, публикуемых в магазине. Включает многоуровневый процесс ревью приложений (автоматический ML-скрининг + ручная экспертиза), систему политик контента (Developer Program Policies), механизмы enforcement (предупреждения, отклонения, удаления, приостановки, терминация аккаунтов), модерацию пользовательских отзывов, систему Google Play Protect для защиты от вредоносного ПО, обработку жалоб и DMCA-запросов, возрастную классификацию через IARC, контроль Data Safety деклараций, требования к Target API Level, борьбу с мошенничеством (fake installs, review manipulation), прозрачную отчётность (Transparency Report), соответствие Digital Services Act (DSA), процесс апелляций для разработчиков, а также санкционные и географические ограничения. В 2024 году Google заблокировал 2.36 млн приложений и 158 000 аккаунтов разработчиков, а общее число приложений в магазине сократилось на 47% (с 3.4 млн до 1.8 млн) в результате масштабной борьбы с низкокачественным и вредоносным контентом.

## Роли участников

### Роли платформы (Google)

| Роль | Описание |
|------|----------|
| **Automated Review System** | ML-система первичного скрининга приложений. Анализирует код, метаданные, поведение приложения |
| **Human Reviewer** | Специалист Google, выполняющий ручную экспертизу приложений, прошедших или не прошедших автоматический скрининг |
| **Policy Specialist** | Эксперт по политикам Google Play. Рассматривает апелляции, принимает решения по спорным случаям |
| **Trust & Safety Team** | Команда безопасности. Отвечает за выявление вредоносных приложений, мошенничества, борьбу с abuse |
| **Legal Team** | Юридическая команда. Обработка DMCA-запросов, правовые споры, санкционные ограничения |
| **Google Play Protect Engine** | Автономная система сканирования устройств на вредоносное ПО. 200 млрд сканирований в день |
| **DSA Compliance Officer** | Ответственный за соответствие Digital Services Act (ЕС). Подготовка отчётов, взаимодействие с регуляторами |

### Роли разработчиков

| Роль | Описание |
|------|----------|
| **Account Owner** | Владелец аккаунта разработчика. Несёт полную ответственность за все приложения в аккаунте |
| **Developer** | Разработчик, публикующий и обновляющий приложения через Play Console |
| **Organization Admin** | Администратор организационного аккаунта. Управляет командой разработчиков |
| **App Manager** | Менеджер конкретного приложения. Может управлять листингом, отзывами, релизами |

### Роли пользователей

| Роль | Описание |
|------|----------|
| **End User** | Конечный пользователь. Устанавливает приложения, оставляет отзывы, подаёт жалобы |
| **Copyright Holder** | Правообладатель. Подаёт DMCA-запросы на удаление контента, нарушающего авторские права |
| **Trusted Flagger** | Доверенный пользователь/организация с приоритетным правом жалоб (в рамках DSA) |

## Функциональные требования

### FR-MOD-001: Процесс ревью приложений при публикации (App Review)

**Описание:** Многоуровневый процесс проверки приложений перед публикацией в Google Play, включающий автоматический ML-скрининг и ручную экспертизу

**Роли:** Automated Review System, Human Reviewer, Developer

**Предусловия:**
- Разработчик имеет активный аккаунт Google Play Developer
- Разработчик оплатил регистрационный взнос ($25 единоразово)
- Приложение загружено в Play Console (APK или AAB)
- Заполнены все обязательные поля метаданных (листинг, Content Rating, Data Safety)

**Основной сценарий:**
1. Разработчик загружает приложение (APK/AAB) в Play Console и отправляет на проверку
2. Система начинает автоматический скрининг:
   - **Статический анализ кода**: проверка на наличие вредоносного кода, скрытых payload, обфускации
   - **Анализ разрешений**: проверка запрашиваемых permissions на соответствие заявленной функциональности
   - **Анализ метаданных**: проверка описания, скриншотов, иконки на нарушение политик
   - **Проверка на клоны**: сравнение с существующими приложениями для выявления копий
   - **Проверка SDK и библиотек**: анализ встроенных SDK на наличие вредоносных или запрещённых компонентов
   - **Анализ сетевой активности**: проверка доменов, к которым обращается приложение
   - **Проверка Target API Level**: соответствие текущим требованиям (API 35 для новых приложений)
3. Если автоматический скрининг не выявил проблем, приложение направляется на ручную проверку (для первых публикаций и существенных обновлений)
4. Human Reviewer проверяет:
   - Соответствие описания реальной функциональности
   - Корректность скриншотов и видео
   - Отсутствие запрещённого контента
   - Соответствие заявленной возрастной категории
   - Корректность Data Safety декларации
   - Отсутствие обманных практик (misleading claims)
5. При успешном прохождении: статус приложения меняется на "Published"
6. Приложение становится доступным в Google Play

**Альтернативные сценарии:**
- Сценарий А (Автоматическое отклонение): ML-система выявляет критическое нарушение (вредоносное ПО) — приложение отклоняется автоматически без ручной проверки
- Сценарий Б (Запрос дополнительной информации): Reviewer запрашивает у разработчика уточнения (демо-аккаунт, пояснение функциональности)
- Сценарий В (Условное одобрение): Приложение одобрено с требованием устранить незначительные нарушения в следующем обновлении
- Сценарий Г (Обновление существующего приложения): Процесс ускоренный (12-36 часов), автоматический скрининг с выборочной ручной проверкой
- Сценарий Д (Новый аккаунт разработчика): Усиленная проверка, более длительные сроки (до 7 дней)

**Бизнес-правила:**
- BR-MOD-001: Среднее время проверки стандартного приложения — 24-72 часа
- BR-MOD-002: Сложные приложения (финтех, здравоохранение, AI) — 4-7 дней
- BR-MOD-003: Обновления существующих приложений — 12-36 часов
- BR-MOD-004: Новые аккаунты разработчиков проходят усиленную проверку (до 7 дней)
- BR-MOD-005: Все приложения обязаны предоставлять AAB-формат (Android App Bundle) с 2023 года
- BR-MOD-006: Приложение не может быть опубликовано без заполненного Content Rating, Data Safety и Privacy Policy
- BR-MOD-007: В 2024 году Google заблокировал 2.36 млн приложений, не прошедших проверку

**Результат:** Приложение проверено, одобрено и опубликовано в Google Play, либо отклонено с указанием причин

### FR-MOD-002: Developer Program Policies (Политики программы разработчика)

**Описание:** Комплексная система политик, регламентирующих допустимый контент, поведение приложений и требования к разработчикам

**Роли:** Policy Specialist, Developer, Automated Review System

**Предусловия:**
- Разработчик зарегистрирован в Google Play Developer Program
- Разработчик принял Developer Distribution Agreement

**Основной сценарий:**
1. Система политик включает следующие категории:

   **1.1. Restricted Content (Запрещённый контент):**
   - **Сексуальный контент**: изображения сексуальной наготы, откровенные позы, анимации половых актов, непристойные тексты, ключевые слова сексуального характера в листинге
   - **Детская безопасность (CSAM)**: абсолютный запрет на контент, эксплуатирующий детей; немедленное удаление и уведомление правоохранительных органов
   - **Насилие и жестокость**: реалистичное изображение насилия, побуждение к насилию, жестокое обращение с животными
   - **Травля и разжигание ненависти**: контент, унижающий по признаку расы, пола, религии, инвалидности, сексуальной ориентации
   - **Терроризм**: контент, поддерживающий или пропагандирующий террористические организации
   - **Опасные продукты**: взрывчатые вещества, оружие, инструкции по созданию боеприпасов
   - **Контролируемые вещества**: марихуана и производные (независимо от легальности в юрисдикции), незаконные наркотики
   - **Табак и алкоголь**: продажа через приложения, реклама несовершеннолетним

   **1.2. Intellectual Property (Интеллектуальная собственность):**
   - Запрет на нарушение авторских прав, товарных знаков, патентов
   - Запрет на impersonation (имитация чужих приложений или брендов)
   - Запрет на использование чужих ассетов без разрешения

   **1.3. Privacy & Data (Конфиденциальность и данные):**
   - Обязательная Privacy Policy для всех приложений
   - Обязательная Data Safety декларация
   - Запрет на скрытый сбор данных
   - Запрет на продажу персональных данных без явного согласия
   - Минимизация запрашиваемых разрешений
   - Ограничения на доступ к SMS, Call Log, Location

   **1.4. Deceptive Behavior (Обманные практики):**
   - Запрет на misleading claims (обещания невозможного)
   - Запрет на манипуляцию установками и рейтингами
   - Запрет на click injection и attribution fraud
   - Запрет на stealth downloads и скрытую установку

   **1.5. Financial Services (Финансовые услуги):**
   - Запрет на быстрые кредиты (срок менее 60 дней)
   - Регулирование криптовалютных приложений
   - Требования к gambling-приложениям (лицензии)
   - NFT-приложения: обязательное раскрытие информации

   **1.6. Ads (Реклама):**
   - Запрет на обманчивую рекламу
   - Запрет на ads, имитирующие системные уведомления
   - Обязательная пометка рекламного контента
   - Контроль рекламных SDK

2. При нарушении любой политики система инициирует enforcement-процесс (FR-MOD-004)
3. Политики обновляются регулярно (major updates 4-6 раз в год)
4. Разработчики получают уведомления об изменениях политик с указанием дедлайнов для compliance

**Альтернативные сценарии:**
- Сценарий А (Новая политика): Google объявляет новую политику с grace period (обычно 30-90 дней) для приведения приложений в соответствие
- Сценарий Б (Региональная политика): Дополнительные ограничения для конкретных стран (gambling, финтех, крипто)
- Сценарий В (Исключение): Отдельные категории приложений могут получить exemption при соблюдении дополнительных условий

**Бизнес-правила:**
- BR-MOD-008: Политики действуют совместно с Developer Distribution Agreement
- BR-MOD-009: Текущая версия политик вступила в силу 28 января 2026 года
- BR-MOD-010: Нарушение политик CSAM приводит к немедленной терминации и уведомлению правоохранительных органов
- BR-MOD-011: Разработчик обязан привести приложение в соответствие в течение grace period после анонса новой политики
- BR-MOD-012: Незнание политик не является основанием для смягчения наказания
- BR-MOD-013: В 2024 году 55% удалений были связаны с нарушениями конфиденциальности и данных

**Результат:** Разработчик понимает и соблюдает все применимые политики Google Play

### FR-MOD-003: Отклонение приложений (App Rejection)

**Описание:** Процесс отклонения приложений, не прошедших проверку, с указанием причин и рекомендаций по исправлению

**Роли:** Automated Review System, Human Reviewer, Developer

**Предусловия:**
- Приложение отправлено на проверку в Play Console
- Обнаружено нарушение политик или технических требований

**Основной сценарий:**
1. Система или рецензент выявляет нарушение в процессе проверки
2. Приложение получает статус "Rejected"
3. Система отправляет разработчику уведомление, содержащее:
   - Конкретную политику, которая нарушена (ссылка на Developer Policy Center)
   - Описание нарушения
   - Указание на конкретные элементы приложения, вызвавшие отклонение (скриншот, текст, функция)
   - Рекомендации по исправлению
   - Срок для исправления (если применимо)
4. Разработчик вносит исправления в приложение
5. Разработчик повторно отправляет приложение на проверку
6. Система проводит повторную проверку

**Распространённые причины отклонения:**

| Категория | Причина | Частота |
|-----------|---------|---------|
| Конфиденциальность | Отсутствие или некорректная Privacy Policy | Очень высокая |
| Конфиденциальность | Несоответствие Data Safety декларации | Высокая |
| Разрешения | Запрос излишних permissions (SMS, Call Log) | Высокая |
| Контент | Запрещённый контент (adult, violence) | Средняя |
| Обман | Misleading description или скриншоты | Средняя |
| IP | Нарушение авторских прав или товарных знаков | Средняя |
| Техническое | Несоответствие Target API Level | Высокая |
| Безопасность | Вредоносный код или SDK | Средняя |
| UGC | Отсутствие модерации пользовательского контента | Средняя |
| Финансы | Нарушение политик финансовых приложений | Низкая |
| Реклама | Обманчивая или навязчивая реклама | Средняя |

**Альтернативные сценарии:**
- Сценарий А (Повторное отклонение): При повторном отклонении по той же причине — может быть применена более серьёзная мера (предупреждение, страйк)
- Сценарий Б (Множественные нарушения): Если выявлено несколько нарушений одновременно — все перечисляются в уведомлении
- Сценарий В (Ложное отклонение): Разработчик может подать апелляцию (FR-MOD-016)

**Бизнес-правила:**
- BR-MOD-014: Отклонение само по себе не влияет на standing аккаунта разработчика
- BR-MOD-015: Множественные отклонения могут привести к suspension
- BR-MOD-016: Разработчик может повторно отправить исправленное приложение неограниченное количество раз
- BR-MOD-017: Уведомление об отклонении содержит конкретную ссылку на нарушенную политику
- BR-MOD-018: При отклонении обновления — текущая версия приложения остаётся доступной в магазине

**Результат:** Разработчик получает детальную информацию о причинах отклонения и может исправить нарушения

### FR-MOD-004: Enforcement Process (Процесс принуждения)

**Описание:** Многоуровневая система принудительных мер за нарушение политик Google Play, от предупреждений до полной терминации аккаунта

**Роли:** Automated Review System, Policy Specialist, Trust & Safety Team, Developer

**Предусловия:**
- Выявлено нарушение политик Google Play (при проверке или после публикации)
- Нарушение подтверждено

**Основной сценарий:**

1. **Уровень 1: Предупреждение (Warning)**
   - Разработчик получает уведомление о нарушении
   - Указан срок для исправления (обычно 7-30 дней)
   - Предупреждение не является страйком
   - Приложение может оставаться в магазине на время исправления
   - При исправлении в срок — инцидент закрывается

2. **Уровень 2: Удаление приложения (App Removal)**
   - Приложение и все его предыдущие версии удаляются из Google Play
   - Приложение больше не доступно для скачивания
   - Разработчик уведомляется по email
   - Удаление не является автоматическим страйком
   - Множественные удаления могут привести к suspension
   - Статистика, рейтинги и отзывы приложения сохраняются в Play Console

3. **Уровень 3: Приостановка приложения (App Suspension) — Policy Strike**
   - Приложение приостанавливается как policy strike
   - Пользователи, статистика и рейтинги удалённого приложения теряются безвозвратно
   - Suspension считается страйком (strike) против аккаунта
   - Три страйка в течение определённого периода могут привести к терминации аккаунта
   - Разработчик не может переопубликовать приложение с тем же package name

4. **Уровень 4: Терминация аккаунта (Account Termination)**
   - Все приложения в каталоге удаляются из Google Play
   - Разработчик теряет возможность публиковать новые приложения
   - Все связанные Google Play Developer аккаунты также терминируются
   - Регистрационный взнос не возвращается
   - Терминация может быть постоянной

**Состояния аккаунта разработчика:**

```
[Good Standing] --нарушение--> [Warning] --исправлено--> [Good Standing]
                                  |
                          не исправлено
                                  |
                                  v
[Good Standing] --серьёзное--> [App Removal] --повторные--> [App Suspension (Strike)]
                нарушение                      нарушения            |
                                                            повторные страйки
                                                                    |
                                                                    v
                                                            [Account Termination]
                                                                    |
                                                              апелляция
                                                                    |
                                                          [Reinstated] или [Permanent Ban]
```

**Альтернативные сценарии:**
- Сценарий А (Критическое нарушение): Вредоносное ПО, мошенничество, CSAM — немедленная терминация без предупреждений
- Сценарий Б (Массовое нарушение): Множественные приложения нарушают одну политику — enforcement применяется ко всему аккаунту
- Сценарий В (Связанные аккаунты): Если терминированный разработчик создаёт новый аккаунт — он также подлежит терминации

**Бизнес-правила:**
- BR-MOD-019: Предупреждение предоставляет grace period для исправления (7-30 дней в зависимости от серьёзности)
- BR-MOD-020: App Removal не является автоматическим страйком, но множественные removals ведут к suspension
- BR-MOD-021: App Suspension = policy strike; три страйка могут привести к терминации
- BR-MOD-022: Терминация распространяется на все связанные аккаунты (по финансовым данным, устройствам, IP)
- BR-MOD-023: Критические нарушения (malware, fraud, CSAM) ведут к немедленной терминации
- BR-MOD-024: В 2024 году Google терминировал 158 000 аккаунтов разработчиков
- BR-MOD-025: Разработчик может обжаловать любое enforcement-действие через процесс апелляции

**Результат:** Enforcement-мера применена пропорционально серьёзности нарушения

### FR-MOD-005: Модерация отзывов и рейтингов (Review Moderation)

**Описание:** Система модерации пользовательских отзывов и рейтингов, включающая автоматическую фильтрацию, обработку жалоб и борьбу с манипуляциями

**Роли:** Automated Review System, Human Reviewer, End User, Developer

**Предусловия:**
- Приложение опубликовано в Google Play
- Пользователь оставил отзыв или рейтинг

**Основной сценарий:**

1. **Автоматическая фильтрация (ML-based):**
   - Система анализирует каждый отзыв в момент публикации
   - Проверяет на: спам, hate speech, нецензурную лексику, рекламный контент, оскорбления
   - Проверяет на: fake reviews (паттерны поведения, bulk posting, одинаковые тексты)
   - Проверяет на: review bombing (массовые негативные отзывы в короткий период)
   - Отзывы, нарушающие Comment Posting Policy, автоматически скрываются или удаляются

2. **Comment Posting Policy — запрещённый контент в отзывах:**
   - Спам и повторяющийся контент
   - Нецензурная лексика и hate speech
   - Персональные данные третьих лиц
   - Угрозы и побуждение к насилию
   - Контент сексуального характера
   - Impersonation (выдача себя за другое лицо)
   - Conflict of interest (отзывы от разработчика о своём приложении)
   - Off-topic контент (не относящийся к приложению)
   - Рекламный или коммерческий контент

3. **Жалобы на отзывы (от разработчиков):**
   - Разработчик выбирает отзыв в Play Console
   - Нажимает "Report" и указывает тип нарушения
   - Жалоба направляется Policy Specialist
   - Рассмотрение занимает несколько рабочих дней
   - При подтверждении нарушения: отзыв удаляется
   - При отклонении жалобы: отзыв остаётся

4. **Жалобы на отзывы (от пользователей):**
   - Пользователь нажимает флаг на отзыве в Google Play
   - Указывает причину (spam, offensive, irrelevant)
   - Система агрегирует жалобы и применяет enforcement

5. **Ответы разработчика на отзывы:**
   - Разработчик может отвечать на любой отзыв
   - Ответ видим всем пользователям
   - Ответ должен соблюдать те же политики
   - Разработчик не может удалять отзывы пользователей самостоятельно

**Альтернативные сценарии:**
- Сценарий А (Review bombing): Система детектирует аномальный всплеск негативных отзывов и временно блокирует новые отзывы для проверки
- Сценарий Б (Incentivized reviews): Разработчик предлагает вознаграждение за отзывы — все такие отзывы удаляются, приложение может быть наказано
- Сценарий В (Repeat offender): Пользователь, систематически оставляющий fake reviews, теряет право оставлять отзывы

**Бизнес-правила:**
- BR-MOD-026: Google использует комбинацию ML и ручной модерации для выявления нарушений в отзывах
- BR-MOD-027: Разработчик не может удалять отзывы пользователей напрямую; только через жалобу
- BR-MOD-028: Отзывы от аккаунтов с конфликтом интересов (разработчик, конкуренты) удаляются
- BR-MOD-029: Incentivized reviews (за деньги, товары или услуги) запрещены и подлежат удалению
- BR-MOD-030: За неделю Google удаляет миллионы нарушающих отзывов и тысячи вредоносных приложений
- BR-MOD-031: ~10.7% всех отзывов в Google Play оценивается как фейковые
- BR-MOD-032: Повторные нарушения Comment Posting Policy могут привести к потере права оставлять отзывы

**Результат:** Отзывы и рейтинги отражают реальный пользовательский опыт, манипуляции выявлены и устранены

### FR-MOD-006: Google Play Protect (Защита от вредоносного ПО)

**Описание:** Комплексная система защиты устройств от потенциально вредоносных приложений (PHA — Potentially Harmful Applications), работающая на всех этапах жизненного цикла приложения

**Роли:** Google Play Protect Engine, Trust & Safety Team, End User

**Предусловия:**
- Google Play Services установлены на устройстве пользователя
- Play Protect не отключён пользователем (включён по умолчанию)

**Основной сценарий:**

1. **Фаза 1: Проверка при публикации (Pre-distribution scanning):**
   - Все приложения, загружаемые в Play Console, проходят сканирование Play Protect
   - ML-модели анализируют код, поведение, сетевую активность
   - Сравнение с базой известного вредоносного ПО
   - Анализ цепочки поставок (SDK, библиотеки)
   - В 2024 году заблокировано 2.36 млн вредоносных приложений до публикации

2. **Фаза 2: Проверка при установке (Pre-installation scanning):**
   - При скачивании приложения из Google Play — автоматическая проверка
   - При установке из сторонних источников (sideloading) — предупреждение пользователю
   - Real-time code-level scanning для новых/неизвестных приложений
   - Если вредоносный код не обнаружен в базе, система рекомендует scan в реальном времени

3. **Фаза 3: Ежедневное сканирование (Post-installation monitoring):**
   - 200 млрд сканирований в день по всем устройствам
   - Проверка всех установленных приложений (из Play Store и сторонних источников)
   - Мониторинг поведения: доступ к permissions, фоновая активность, сетевые запросы
   - Детектирование динамической загрузки кода (DexClassLoader abuse)
   - Контакт с серверами Google только при обнаружении подозрительной активности (для экономии трафика)

4. **Фаза 4: Реагирование на угрозы:**
   - **Критическая PHA (malware, ransomware):** автоматическое удаление с устройства + уведомление пользователя
   - **Средняя PHA (adware, spyware):** отключение приложения + уведомление с рекомендацией удалить
   - **Низкая PHA (unwanted software):** предупреждение пользователю о рисках

5. **Категории PHA, детектируемые Play Protect:**
   - Backdoors — скрытый удалённый доступ
   - Billing fraud — мошенничество с подписками/SMS
   - Commercial spyware — шпионское ПО
   - Denial of Service — атаки на устройство
   - Hostile downloaders — скрытая загрузка вредоносного ПО
   - Phishing — фишинг
   - Privilege escalation — эскалация привилегий
   - Ransomware — вымогатели
   - Rooting — получение root-доступа
   - Trojan — трояны

**Альтернативные сценарии:**
- Сценарий А (Пользователь отключил Play Protect): Сканирование не выполняется; пользователь принимает риск
- Сценарий Б (Ложное срабатывание): Разработчик может обратиться в Google для пересмотра через Play Console
- Сценарий В (Zero-day malware): Play Protect использует эвристический анализ и real-time scanning для обнаружения ранее неизвестных угроз

**Бизнес-правила:**
- BR-MOD-033: Play Protect включён по умолчанию на всех устройствах с Google Play Services
- BR-MOD-034: Ежедневные сканирования охватывают все установленные приложения, не только из Play Store
- BR-MOD-035: 200 млрд сканирований в день по всем Android-устройствам
- BR-MOD-036: Критическое вредоносное ПО удаляется автоматически без ожидания согласия пользователя
- BR-MOD-037: 1.3 млн приложений было заблокировано за запрос избыточных permissions в 2024 году
- BR-MOD-038: Play Protect отслеживает вредоносных publisher-ов через связи между аккаунтами, поведением и паттернами

**Результат:** Устройства пользователей защищены от вредоносного ПО на всех этапах жизненного цикла приложений

### FR-MOD-007: Система жалоб от пользователей (User Reporting System)

**Описание:** Механизм подачи жалоб пользователями на приложения, контент и нарушения в Google Play

**Роли:** End User, Automated Review System, Human Reviewer, Policy Specialist

**Предусловия:**
- Пользователь имеет Google-аккаунт
- Приложение опубликовано в Google Play

**Основной сценарий:**

1. **Подача жалобы на приложение:**
   - Пользователь открывает страницу приложения в Google Play
   - Нажимает "Flag as inappropriate" (флажок)
   - Выбирает категорию жалобы:
     - Sexual content
     - Hate speech
     - Violence
     - Harmful to device or data
     - Impersonation
     - Gambling (нелегальное)
     - Illegal activity
     - Другое (с описанием)
   - Жалоба отправляется в систему модерации

2. **Подача жалобы на отзыв:**
   - Пользователь нажимает флаг на конкретном отзыве
   - Выбирает причину (spam, offensive, off-topic)
   - Жалоба обрабатывается автоматически + при необходимости вручную

3. **Обработка жалоб:**
   - Система агрегирует жалобы на одно приложение
   - ML-модели оценивают серьёзность и паттерны жалоб
   - При достижении порога — приложение направляется на ручную проверку
   - Human Reviewer оценивает обоснованность жалоб
   - Принимается решение: no action / warning / removal / suspension

4. **Обратная связь заявителю:**
   - Пользователь получает подтверждение получения жалобы
   - Конкретное решение по жалобе обычно не раскрывается заявителю (конфиденциальность)
   - В рамках DSA (для ЕС): пользователь может получить более детальную информацию о решении

**Альтернативные сценарии:**
- Сценарий А (Массовые жалобы): Аномальный рост жалоб на одно приложение — автоматическая эскалация в Trust & Safety
- Сценарий Б (Ложные жалобы): Систематическая подача ложных жалоб — может привести к ограничениям для заявителя
- Сценарий В (DSA Trusted Flagger): Жалобы от доверенных организаций (в ЕС) обрабатываются приоритетно

**Бизнес-правила:**
- BR-MOD-039: Каждый пользователь с Google-аккаунтом может подать жалобу
- BR-MOD-040: Жалобы агрегируются; одиночная жалоба не приводит к автоматическому действию
- BR-MOD-041: Trusted Flaggers (DSA) имеют приоритет в обработке жалоб
- BR-MOD-042: Анонимность заявителя сохраняется перед разработчиком
- BR-MOD-043: Злоупотребление системой жалоб может привести к ограничениям для заявителя

**Результат:** Жалобы пользователей обработаны, нарушения выявлены и устранены

### FR-MOD-008: DMCA и защита авторских прав (Copyright Protection)

**Описание:** Процесс обработки заявлений о нарушении авторских прав в соответствии с DMCA (Digital Millennium Copyright Act) и международным законодательством об интеллектуальной собственности

**Роли:** Copyright Holder, Legal Team, Developer

**Предусловия:**
- Правообладатель обнаружил нарушение авторских прав в приложении на Google Play
- Правообладатель имеет легальные права на спорный контент

**Основной сценарий:**

1. **Подача DMCA Takedown Notice:**
   - Правообладатель (или его уполномоченный агент) заполняет форму DMCA-уведомления через Google Legal Help
   - Обязательные данные:
     - Идентификация оригинального произведения, авторские права на которое нарушены
     - Идентификация нарушающего контента (URL приложения, описание нарушения)
     - Контактные данные правообладателя
     - Заявление о добросовестности (good faith belief)
     - Заявление о точности информации под страхом наказания за лжесвидетельство
     - Электронная или физическая подпись
   - Google рекомендует предварительно связаться с разработчиком напрямую для урегулирования

2. **Рассмотрение заявления:**
   - Legal Team Google проверяет полноту и формальную корректность заявления
   - При необходимости запрашивает дополнительную информацию
   - Срок обработки: примерно одна неделя

3. **Действия по заявлению:**
   - Если заявление обосновано: приложение или нарушающий контент удаляется
   - Google уведомляет разработчика о DMCA takedown
   - Разработчик получает копию заявления (без контактных данных заявителя)

4. **Counter Notice (Контр-уведомление):**
   - Если разработчик считает takedown необоснованным — подаёт counter notice
   - Counter notice содержит:
     - Идентификацию удалённого контента
     - Заявление о добросовестности (good faith belief, что удаление ошибочно)
     - Согласие на юрисдикцию федерального суда
     - Подпись
   - Google пересылает counter notice заявителю через 5 дней
   - У заявителя есть 10 рабочих дней для подачи судебного иска
   - Если иск не подан — приложение восстанавливается

5. **Повторные нарушения (Repeat Infringers):**
   - Google отслеживает повторные нарушения авторских прав
   - Систематическое нарушение может привести к терминации аккаунта

**Альтернативные сценарии:**
- Сценарий А (Ложный DMCA): Подача заведомо ложного DMCA-уведомления — юридическая ответственность заявителя
- Сценарий Б (Trademark violation): Отдельный процесс для нарушений товарных знаков (не DMCA)
- Сценарий В (Международный правообладатель): DMCA применяется к US-контенту; для других юрисдикций — местное законодательство

**Бизнес-правила:**
- BR-MOD-044: DMCA-заявление должно содержать все обязательные элементы; неполные заявления отклоняются
- BR-MOD-045: Срок обработки DMCA — примерно одна неделя
- BR-MOD-046: Counter notice инициирует 10-дневный период ожидания судебного иска
- BR-MOD-047: Повторные нарушения IP могут привести к терминации аккаунта разработчика
- BR-MOD-048: Подача ложного DMCA-заявления влечёт юридическую ответственность для заявителя
- BR-MOD-049: Google рекомендует прямое урегулирование между правообладателем и разработчиком до подачи DMCA

**Результат:** Авторские права защищены, нарушающий контент удалён или восстановлен по результатам контр-уведомления

### FR-MOD-009: Борьба с мошенничеством (Fraud Prevention)

**Описание:** Система выявления и противодействия мошенническим практикам, включая fake installs, review manipulation, click fraud и attribution manipulation

**Роли:** Trust & Safety Team, Automated Review System, Developer

**Предусловия:**
- Приложение опубликовано в Google Play
- Система мониторит метрики приложений в реальном времени

**Основной сценарий:**

1. **Детектирование fake installs:**
   - Система анализирует паттерны установок:
     - Аномальные всплески установок из конкретных регионов/устройств
     - Установки с одного IP-адреса или группы связанных устройств
     - Установки с немедленным удалением (install-uninstall pattern)
     - Эмулятор-based установки
   - Мошеннические установки фильтруются и не учитываются в статистике
   - При выявлении массовых fake installs — разработчик получает предупреждение

2. **Детектирование review manipulation:**
   - ML-модели анализируют:
     - Паттерны текста отзывов (шаблонные, копированные)
     - Временные паттерны (bulk posting)
     - Аккаунты рецензентов (новые, неактивные, связанные)
     - Корреляция между рейтингами и реальным поведением пользователей
   - Incentivized reviews (за деньги, товары) детектируются и удаляются
   - Разработчики, использующие сервисы fake reviews, подвергаются enforcement

3. **Детектирование click injection / attribution fraud:**
   - Система отслеживает аномалии в attribution data
   - Click injection: приложение генерирует клики для перехвата attribution
   - Выявление fraud SDK, встроенных в приложения
   - Блокировка и удаление приложений с fraud SDK

4. **Детектирование ad fraud:**
   - Скрытое показывание рекламы (hidden ads)
   - Автоматические клики по рекламе (click fraud)
   - Manipulation ad rendering (подмена креативов)

5. **Enforcement за мошенничество:**
   - Первое нарушение: предупреждение + удаление мошеннических метрик
   - Повторное нарушение: removal / suspension приложения
   - Систематическое мошенничество: терминация аккаунта
   - В серьёзных случаях: передача информации регуляторам (FTC и др.)

**Альтернативные сценарии:**
- Сценарий А (Разработчик — жертва fraud): Конкурент закупает fake installs для приложения — разработчик может обратиться в поддержку для очистки метрик
- Сценарий Б (Third-party marketing): Разработчик нанял маркетинговое агентство, которое использовало fraud — ответственность на разработчике
- Сценарий В (FTC enforcement): Fake reviews нарушают FTC guidelines — возможны штрафы от регуляторов

**Бизнес-правила:**
- BR-MOD-050: Любая попытка манипуляции рейтингами, отзывами или установками запрещена
- BR-MOD-051: Incentivized actions (деньги, товары в обмен на установку/отзыв) запрещены
- BR-MOD-052: Ответственность за actions маркетинговых агентств несёт разработчик
- BR-MOD-053: Мошеннические метрики фильтруются и не учитываются в ранжировании
- BR-MOD-054: Систематическое мошенничество ведёт к терминации аккаунта
- BR-MOD-055: Fake reviews нарушают как политики Google, так и FTC guidelines

**Результат:** Мошеннические практики выявлены, метрики очищены, нарушители наказаны

### FR-MOD-010: Возрастные ограничения и IARC рейтинги (Age Rating System)

**Описание:** Система возрастной классификации приложений через International Age Rating Coalition (IARC), обеспечивающая локально-релевантные возрастные ограничения

**Роли:** Developer, Automated Review System, Human Reviewer

**Предусловия:**
- Разработчик заполняет Content Rating questionnaire в Play Console
- Приложение готово к публикации

**Основной сценарий:**

1. **Заполнение IARC-опросника:**
   - Разработчик переходит в Play Console > App Content > Content Rating
   - Система предоставляет опросник IARC, состоящий из секций:
     - **Информация о приложении**: тип (игра/не-игра), категория
     - **Насилие**: степень, реалистичность, контекст
     - **Сексуальный контент**: наличие, степень, контекст
     - **Язык**: нецензурная лексика, уровень
     - **Наркотики, алкоголь, табак**: упоминание, контекст
     - **Азартные игры**: наличие gambling-механик
     - **Пользовательское взаимодействие**: UGC, чаты, социальные функции
     - **Покупки**: in-app purchases, loot boxes
     - **Обмен местоположением**: sharing location с другими пользователями
   - Разработчик отвечает на все вопросы

2. **Генерация рейтинга:**
   - На основе ответов система мгновенно генерирует рейтинги для всех рейтинговых организаций:
     - **ESRB** (Северная Америка): E, E10+, T, M, AO
     - **PEGI** (Европа): 3, 7, 12, 16, 18
     - **USK** (Германия): 0, 6, 12, 16, 18
     - **ClassInd** (Бразилия): L, 10, 12, 14, 16, 18
     - **GRAC** (Южная Корея): All, 12, 15, 18, Test
     - **IARC Generic** (все остальные регионы): 3, 7, 12, 16, 18
   - Рейтинг присваивается бесплатно

3. **Трёхкомпонентная система рейтинга:**
   - **Rating Category**: возрастная категория (например, PEGI 12)
   - **Content Descriptors**: что именно вызвало рейтинг (violence, language, drugs)
   - **Interactive Elements**: предупреждения о взаимодействии (location sharing, in-app purchases, users interact)

4. **Отображение пользователям:**
   - Рейтинг показывается на странице приложения в Google Play
   - Пользователи видят рейтинг для своего региона
   - Родительский контроль (Family Link) блокирует приложения выше заданного рейтинга

5. **Age-Restricted Content and Functionality (новая политика 2025-2026):**
   - Приложения с matchmaking, dating, real money gambling обязаны использовать Play Console features для блокировки несовершеннолетних
   - Обязательная возрастная верификация для Age-Restricted функций
   - Использование Age Signals API для определения возраста пользователя

**Альтернативные сценарии:**
- Сценарий А (Некорректное заполнение): Google обнаруживает, что фактический контент не соответствует декларации — рейтинг пересматривается принудительно
- Сценарий Б (Обновление контента): При добавлении нового контента (например, gambling-механик) разработчик обязан обновить опросник
- Сценарий В (Отсутствие рейтинга): Приложение без Content Rating не допускается к публикации

**Бизнес-правила:**
- BR-MOD-056: Content Rating обязателен для всех приложений; без него публикация невозможна
- BR-MOD-057: Рейтинг генерируется бесплатно и мгновенно на основе IARC-опросника
- BR-MOD-058: Разработчик обязан обновить рейтинг при изменении контента приложения
- BR-MOD-059: Некорректная декларация (занижение рейтинга) рассматривается как нарушение политик
- BR-MOD-060: Приложения категории "Everyone" (ESRB E / PEGI 3) не должны содержать UGC без модерации
- BR-MOD-061: С 2026 года приложения с age-restricted функциями обязаны использовать Age Signals API
- BR-MOD-062: Статистика 2026: ~39% приложений имеют рейтинг "Everyone", ~25% — "Teen", ~20% — "Mature"

**Результат:** Приложение имеет корректный возрастной рейтинг, пользователи информированы о содержании

### FR-MOD-011: Data Safety Enforcement (Контроль деклараций о данных)

**Описание:** Система контроля корректности деклараций Data Safety, которые разработчики заполняют для информирования пользователей о сборе и использовании данных

**Роли:** Developer, Automated Review System, Human Reviewer, Policy Specialist

**Предусловия:**
- Приложение опубликовано или готовится к публикации
- Разработчик заполнил Data Safety form в Play Console

**Основной сценарий:**

1. **Заполнение Data Safety формы:**
   - Разработчик переходит в Play Console > App Content > Data Safety
   - Система запрашивает информацию о:
     - **Типы собираемых данных:**
       - Персональные данные (имя, email, телефон, адрес)
       - Финансовые данные (платёжная информация, история покупок)
       - Данные о здоровье и фитнесе
       - Сообщения (email, SMS, chat logs)
       - Фото и видео
       - Аудиофайлы
       - Файлы и документы
       - Контакты
       - Календарь
       - Активность в приложении
       - Веб-сёрфинг
       - Информация об устройстве (device ID, hardware)
       - Геолокация
     - **Цель сбора данных:**
       - Функциональность приложения
       - Аналитика
       - Реклама и маркетинг
       - Персонализация
       - Управление аккаунтом
       - Мошенничество и безопасность
       - Compliance
     - **Передача данных третьим сторонам**: кому и зачем
     - **Шифрование данных при передаче**: да/нет
     - **Удаление данных по запросу пользователя**: возможность/механизм
     - **Соответствие Families Policy** (если приложение для детей)

2. **Верификация декларации:**
   - Automated system сравнивает заявленные данные с фактическим поведением приложения:
     - Анализ запрашиваемых permissions vs. заявленных типов данных
     - Анализ сетевого трафика vs. заявленной передачи третьим сторонам
     - Проверка встроенных SDK на предмет незаявленного сбора данных
   - При расхождении — запрос на исправление или enforcement

3. **Отображение пользователям:**
   - Раздел "Data Safety" на странице приложения в Google Play
   - Показывает: какие данные собираются, для чего, передаются ли третьим сторонам
   - Показывает: есть ли шифрование, можно ли запросить удаление данных

4. **Enforcement:**
   - Несоответствие декларации реальному поведению = нарушение политик
   - Первое нарушение: требование обновить декларацию
   - Повторное нарушение: blocked updates или removal
   - Отсутствие Data Safety формы: приложение не может быть опубликовано

**Альтернативные сценарии:**
- Сценарий А (Обновление SDK): Разработчик добавляет новый SDK, собирающий данные — обязан обновить Data Safety
- Сценарий Б (Third-party SDK сбор данных): Разработчик обязан декларировать данные, собираемые всеми SDK в приложении
- Сценарий В (Изменение Android ID): С апреля 2025 Android ID больше не считается persistent device identifier

**Бизнес-правила:**
- BR-MOD-063: Data Safety форма обязательна для всех приложений
- BR-MOD-064: Разработчик несёт полную ответственность за точность и полноту декларации
- BR-MOD-065: Data Safety должна отражать поведение всех встроенных SDK и библиотек
- BR-MOD-066: Декларация должна обновляться при каждом изменении практик сбора данных
- BR-MOD-067: Несоответствие декларации реальному поведению = enforcement action
- BR-MOD-068: С апреля 2025 Android ID не является persistent device identifier
- BR-MOD-069: С января 2026 данные Age Signals API можно использовать только для age-appropriate experiences

**Результат:** Пользователи информированы о практиках сбора данных, декларации верифицированы

### FR-MOD-012: Target API Level Requirements (Требования к версии API)

**Описание:** Система обязательных требований к Target API Level для обеспечения безопасности и актуальности приложений

**Роли:** Developer, Automated Review System

**Предусловия:**
- Разработчик готовит приложение к публикации или обновлению
- Приложение содержит файл манифеста с targetSdkVersion

**Основной сценарий:**

1. **Требования на август 2025:**

   | Тип | Категория | Минимальный Target API |
   |-----|-----------|----------------------|
   | Новые приложения | Mobile, Android Auto | API 35 (Android 15) |
   | Обновления | Mobile, Android Auto | API 35 (Android 15) |
   | Существующие | Mobile, Android Auto | API 34 (Android 14) |
   | Новые/обновления | Wear OS | API 34 (Android 14) |
   | Существующие | Wear OS | API 33 (Android 13) |
   | Новые/обновления | Android TV | API 34 (Android 14) |
   | Существующие | Android TV | API 33 (Android 13) |
   | Новые/обновления | Android Automotive OS | API 32 (Android 12L) |
   | Существующие | Android Automotive OS | API 32 (Android 12L) |

2. **Процесс enforcement:**
   - При попытке загрузки APK/AAB с targetSdkVersion ниже требуемого — система отклоняет загрузку
   - Для существующих приложений, не соответствующих требованиям:
     - Приложение скрывается из результатов поиска для пользователей с новыми версиями Android
     - Приложение остаётся доступным для пользователей с совместимыми версиями
     - Приложение не может быть установлено на устройства с ОС выше targetSdkVersion + 2

3. **Extension (продление):**
   - Разработчик может запросить extension до 1 ноября 2025
   - Запрос подаётся через Play Console
   - Extension предоставляется автоматически (без ручного рассмотрения)

4. **Ежегодное обновление требований:**
   - Google повышает требования к Target API Level ежегодно
   - Анонс обычно в начале года, вступление в силу — в августе
   - Grace period: 2-3 месяца после анонса

**Альтернативные сценарии:**
- Сценарий А (Legacy-приложение): Приложение не обновляется годами — постепенно теряет видимость в магазине
- Сценарий Б (Технические ограничения): Разработчик не может обновить API из-за зависимостей — запрос extension + план миграции

**Бизнес-правила:**
- BR-MOD-070: Новые приложения и обновления обязаны соответствовать текущему Target API Level
- BR-MOD-071: Существующие приложения должны соответствовать Target API Level предыдущего года
- BR-MOD-072: Extension может быть запрошен до 1 ноября 2025 для текущего цикла
- BR-MOD-073: Приложения с устаревшим Target API скрываются из результатов поиска
- BR-MOD-074: Требования обновляются ежегодно, привязаны к новой версии Android
- BR-MOD-075: Несоответствие Target API не приводит к удалению, но ограничивает видимость и установку

**Результат:** Приложения используют актуальные API, обеспечивая безопасность и совместимость

### FR-MOD-013: Автоматическая модерация (ML-based Moderation)

**Описание:** Система машинного обучения, обеспечивающая масштабируемую автоматическую модерацию контента на всех уровнях Google Play

**Роли:** Automated Review System, Trust & Safety Team

**Предусловия:**
- ML-модели обучены и развёрнуты
- Приложения и контент поступают на проверку

**Основной сценарий:**

1. **Компоненты ML-системы модерации:**

   **1.1. App Scanning Pipeline:**
   - Статический анализ кода (обнаружение вредоносных паттернов)
   - Динамический анализ (sandbox execution, behavior monitoring)
   - NLP-анализ метаданных (описание, название, changelog)
   - Computer Vision анализ (скриншоты, иконки, видео)
   - Graph analysis (связи между разработчиками, приложениями, аккаунтами)

   **1.2. Review Analysis Pipeline:**
   - Sentiment analysis (определение тональности)
   - Spam detection (шаблонные тексты, bulk posting)
   - Fake review detection (поведенческие паттерны)
   - Hate speech / toxicity detection
   - Language identification и cross-language analysis

   **1.3. Developer Behavior Analysis:**
   - Связи между аккаунтами (device fingerprint, payment methods, IP)
   - Паттерны публикации (массовая загрузка клонов)
   - Историческое поведение (repeat offenders)
   - Risk scoring для новых аккаунтов

   **1.4. User Behavior Analysis:**
   - Паттерны установок (fake installs detection)
   - Паттерны отзывов (review bombing detection)
   - Аномалии в платежах (fraud detection)

2. **Процесс принятия решений:**
   - ML-модель оценивает каждый объект (приложение, отзыв, аккаунт) и присваивает risk score
   - **Low risk (< порога)**: автоматическое одобрение
   - **Medium risk (между порогами)**: направление на ручную проверку Human Reviewer
   - **High risk (> порога)**: автоматическое отклонение/удаление (для критических угроз)

3. **Непрерывное обучение:**
   - Модели переобучаются на основе решений Human Reviewers
   - Feedback loop: ложные срабатывания и пропущенные нарушения корректируют модели
   - A/B тестирование новых моделей перед deployment
   - Мониторинг drift и деградации качества моделей

**Альтернативные сценарии:**
- Сценарий А (Adversarial attack): Разработчики пытаются обойти ML-модели — система эволюционирует в ответ
- Сценарий Б (Ложное срабатывание): Приложение ошибочно заблокировано — доступна апелляция (FR-MOD-016)
- Сценарий В (Новый тип угрозы): Zero-day threat, не детектируемый текущими моделями — эскалация в Trust & Safety для ручного анализа и обновления моделей

**Бизнес-правила:**
- BR-MOD-076: ML-система является первичным фильтром; критические решения подтверждаются людьми
- BR-MOD-077: Модели переобучаются регулярно для адаптации к новым угрозам
- BR-MOD-078: Автоматические решения с высоким уровнем уверенности (malware, CSAM) не требуют ручного подтверждения
- BR-MOD-079: Разработчики отслеживаются по graph analysis (связи между аккаунтами)
- BR-MOD-080: Risk scoring определяет приоритет ручной проверки
- BR-MOD-081: В 2024 году ML + human review предотвратили публикацию 2.36 млн вредоносных приложений

**Результат:** Масштабируемая система модерации, обрабатывающая миллионы объектов ежедневно

### FR-MOD-015: DSA Compliance (Соответствие Digital Services Act)

**Описание:** Обеспечение соответствия Google Play требованиям Digital Services Act (DSA) Европейского Союза как Very Large Online Platform (VLOP)

**Роли:** DSA Compliance Officer, Legal Team, Policy Specialist

**Предусловия:**
- Google Play обозначен Европейской Комиссией как VLOP
- DSA полностью вступил в силу (февраль 2024)

**Основной сценарий:**

1. **Обязательства Google Play как VLOP:**

   **1.1. Risk Assessment (Оценка рисков):**
   - Ежегодная оценка системных рисков:
     - Распространение нелегального контента
     - Влияние на фундаментальные права (свобода слова, конфиденциальность)
     - Влияние на общественную безопасность
     - Влияние на несовершеннолетних
   - Разработка и внедрение mitigation measures
   - Отчёт регуляторам и независимым аудиторам

   **1.2. Independent Audit (Независимый аудит):**
   - Ежегодный аудит независимым аудитором
   - Оценка соответствия всех DSA-обязательств
   - Первый аудит — не позднее 16 месяцев после designation (август 2024)
   - Audit report передаётся Европейской Комиссии и компетентному органу
   - Публичная версия отчёта публикуется в течение 3 месяцев после завершения

   **1.3. Notice and Action Mechanism:**
   - Механизм подачи уведомлений о нелегальном контенте
   - Обязательный ответ заявителю с обоснованием решения
   - Отслеживание сроков рассмотрения

   **1.4. Trusted Flaggers:**
   - Приоритетная обработка жалоб от Trusted Flaggers (организации, назначенные Digital Services Coordinator)
   - Ускоренные сроки рассмотрения
   - Повышенный вес жалоб при принятии решений

   **1.5. Recommender System Transparency:**
   - Раскрытие параметров ранжирования приложений в результатах поиска
   - Объяснение алгоритмов рекомендаций
   - Предоставление опции non-profiling recommender system

   **1.6. Out-of-Court Dispute Resolution:**
   - Пользователи и разработчики в ЕС имеют право на внесудебное разрешение споров
   - Бесплатный доступ к сертифицированным out-of-court dispute resolution bodies
   - Решения dispute resolution body не являются обязательными, но учитываются

2. **Penalties за несоответствие DSA:**
   - Штраф до 6% глобального годового оборота
   - Периодические штрафы до 5% среднего ежедневного оборота
   - В крайнем случае: временное ограничение деятельности в ЕС

**Альтернативные сценарии:**
- Сценарий А (Запрос Commission): Европейская Комиссия запрашивает дополнительную информацию — Google обязан предоставить
- Сценарий Б (Несогласие с аудитом): Google не согласен с выводами аудитора — процедура взаимодействия с Commission
- Сценарий В (Кризисная ситуация): Commission активирует crisis protocol — Google обязан принять дополнительные меры

**Бизнес-правила:**
- BR-MOD-087: Google Play является VLOP и подчиняется повышенным требованиям DSA
- BR-MOD-088: Ежегодный независимый аудит обязателен
- BR-MOD-089: Risk assessment проводится ежегодно с публикацией результатов
- BR-MOD-090: Out-of-court dispute resolution доступно для пользователей и разработчиков из ЕС
- BR-MOD-091: Trusted Flaggers получают приоритет в обработке жалоб
- BR-MOD-092: Штраф за несоответствие — до 6% глобального годового оборота
- BR-MOD-093: Google обязан раскрывать параметры ранжирования и рекомендательных алгоритмов

**Результат:** Google Play полностью соответствует требованиям DSA для VLOP

### FR-MOD-016: Процесс апелляции для разработчиков (Developer Appeal Process)

**Описание:** Формализованный процесс обжалования разработчиками enforcement-действий Google Play (отклонение, удаление, suspension, терминация)

**Роли:** Developer, Policy Specialist, Legal Team

**Предусловия:**
- Против приложения или аккаунта разработчика применено enforcement-действие
- Разработчик получил уведомление с деталями нарушения

**Основной сценарий:**

1. **Получение уведомления:**
   - Разработчик получает email от Google Play с:
     - Описанием enforcement-действия (rejection, removal, suspension, termination)
     - Ссылкой на нарушенную политику
     - Описанием конкретного нарушения
     - Инструкциями по подаче апелляции

2. **Подача апелляции:**
   - Разработчик переходит по ссылке из уведомления
   - Заполняет форму апелляции:
     - Причина, почему решение ошибочно
     - Описание внесённых исправлений (если были)
     - Дополнительные доказательства / контекст
   - Система подтверждает получение апелляции (автоматический email с номером кейса)

3. **Рассмотрение апелляции:**
   - Policy Specialist рассматривает апелляцию в контексте:
     - Конкретного нарушения и предоставленных доказательств
     - Истории аккаунта разработчика
     - Наличия паттерна нарушений
   - Срок рассмотрения: в течение 72 часов (обычно)

4. **Решение по апелляции:**
   - **Апелляция удовлетворена**: enforcement-действие отменяется; приложение восстанавливается
   - **Апелляция отклонена**: enforcement-действие остаётся в силе; разработчик уведомляется
   - **Частичное удовлетворение**: enforcement смягчается (например, suspension заменяется на warning)

5. **Ограничения на апелляции:**
   - Одна апелляция на каждое enforcement-действие
   - Повторная апелляция возможна только при наличии новой существенной информации
   - Злоупотребление процессом апелляции (оскорбительные сообщения) может привести к потере права на email-поддержку

6. **DSA Out-of-Court Resolution (для ЕС):**
   - Если внутренняя апелляция отклонена — разработчик из ЕС может обратиться к сертифицированному out-of-court dispute resolution body
   - Рассмотрение бесплатное для разработчика
   - Решение dispute resolution body не является обязательным, но Google обязан его учитывать

**Альтернативные сценарии:**
- Сценарий А (Апелляция без исправлений): Если разработчик не исправил нарушение и просто подал апелляцию — отклоняется
- Сценарий Б (Терминация аккаунта): При терминации апелляция рассматривается более тщательно; возможно восстановление при доказательстве ошибки
- Сценарий В (Автоматическое enforcement): Разработчик считает, что ML-система ошиблась — предоставляет детальное объяснение для ручного пересмотра

**Бизнес-правила:**
- BR-MOD-094: Одна апелляция на одно enforcement-действие
- BR-MOD-095: Повторная апелляция — только при наличии новой существенной информации
- BR-MOD-096: Срок рассмотрения — в течение 72 часов
- BR-MOD-097: Злоупотребление процессом апелляции ведёт к потере права на email-поддержку
- BR-MOD-098: Google восстанавливает приложения, если обнаружена ошибка в enforcement
- BR-MOD-099: В ЕС доступен out-of-court dispute resolution после исчерпания внутренних апелляций
- BR-MOD-100: Апелляция не приостанавливает enforcement-действие на время рассмотрения

**Результат:** Апелляция рассмотрена, справедливое решение принято

### FR-MOD-017: Модерация UGC-приложений (User-Generated Content Moderation Requirements)

**Описание:** Требования к разработчикам приложений, содержащих пользовательский контент (UGC), по обеспечению модерации внутри приложения

**Роли:** Developer, Human Reviewer, Policy Specialist

**Предусловия:**
- Приложение содержит функции пользовательского контента (чаты, комменты, фото/видео upload, форумы)
- Приложение публикуется в Google Play

**Основной сценарий:**

1. **Обязательные требования для UGC-приложений:**

   **1.1. Модерация контента:**
   - Приложение обязано внедрить робастную, эффективную и непрерывную систему модерации UGC
   - Модерация должна соответствовать типу хостируемого UGC
   - Модерация может быть автоматической, ручной или комбинированной

   **1.2. Система жалоб (In-app Reporting):**
   - Обязательная система жалоб внутри приложения
   - Пользователь должен иметь возможность пожаловаться на любой UGC
   - Пользователь должен иметь возможность заблокировать другого пользователя

   **1.3. Удаление контента:**
   - Механизм оперативного удаления нарушающего контента
   - Реагирование на жалобы в разумные сроки

   **1.4. Правила сообщества:**
   - Публичные Terms of Use / Community Guidelines
   - Описание запрещённого контента
   - Описание последствий нарушений

2. **Дополнительные требования для приложений, ориентированных на детей:**
   - Усиленная модерация (pre-publication review UGC)
   - Фильтрация персональных данных детей
   - Блокировка контактов от незнакомцев
   - Соответствие Children's Online Privacy Protection Act (COPPA)
   - Соответствие Google Families Policy

3. **Проверка при публикации:**
   - Google Play Review проверяет наличие и работоспособность системы модерации
   - Отсутствие модерации UGC = отклонение приложения
   - Неэффективная модерация (обилие нарушающего контента) = enforcement action

**Альтернативные сценарии:**
- Сценарий А (Приложение без модерации): Отклонение при публикации; требование внедрить модерацию
- Сценарий Б (Инцидент с UGC): Обнаружен опасный контент (CSAM, terrorism) — немедленное удаление приложения + уведомление правоохранительных органов
- Сценарий В (AI-модерация): Разработчик использует AI для модерации — приемлемо, если эффективно

**Бизнес-правила:**
- BR-MOD-101: Все UGC-приложения обязаны иметь систему модерации
- BR-MOD-102: In-app reporting и blocking пользователей обязательны
- BR-MOD-103: Модерация должна быть пропорциональна типу и объёму UGC
- BR-MOD-104: Приложения для детей имеют усиленные требования к модерации UGC
- BR-MOD-105: Отсутствие модерации является основанием для отклонения или удаления

**Результат:** UGC-приложения обеспечивают безопасную среду для пользователей

### FR-MOD-018: Санкции и географические ограничения (Sanctions & Geo-Restrictions)

**Описание:** Система применения международных санкций, торговых ограничений и географических ограничений в Google Play

**Роли:** Legal Team, Developer, End User

**Предусловия:**
- Международные санкции и торговые ограничения действуют
- Google Play доступен в стране пользователя

**Основной сценарий:**

1. **Международные санкции:**
   - Google Play соблюдает все применимые санкции и trade compliance laws
   - **Для пользователей в санкционных регионах:**
     - Бесплатные приложения доступны для скачивания
     - Платные приложения и in-app purchases заблокированы
     - Подписки недоступны
   - **Для разработчиков из санкционных регионов:**
     - Возможны ограничения на публикацию
     - Возможна заморозка выплат
     - Возможна терминация аккаунта
   - **Пример (Россия):**
     - После введения санкций Google Play ограничил покупки
     - Разработчики теряют возможность монетизации
     - Бесплатные приложения остаются доступными

2. **Регуляторные ограничения по странам:**
   - **Южная Корея (2025):** Блокировка незарегистрированных криптобирж (не зарегистрированных в FIU)
   - **Gambling:** Приложения gambling доступны только в юрисдикциях, где это легально
   - **Финтех:** Дополнительные требования к лицензированию по странам
   - **VPN-приложения:** Ограничения в определённых юрисдикциях

3. **Гео-распределение разработчиком:**
   - Разработчик выбирает в Play Console страны, где приложение доступно
   - Может включать/исключать конкретные страны
   - Может устанавливать разные цены для разных стран
   - Может публиковать разные версии для разных регионов

4. **EU Anti-Geo-Blocking:**
   - Приложения, распространяемые в ЕС, не должны применять unjustified geo-blocking
   - Запрещена дискриминация пользователей по национальности, месту жительства или регистрации
   - Разные цены допускаются, но блокировка доступа — нет

**Альтернативные сценарии:**
- Сценарий А (Новые санкции): При введении новых санкций — Google Play применяет ограничения в течение нескольких дней
- Сценарий Б (Снятие санкций): При снятии санкций — ограничения снимаются после юридической проверки
- Сценарий В (VPN bypass): Пользователь обходит ограничения через VPN — Google может ограничить по аккаунту или платёжным данным

**Бизнес-правила:**
- BR-MOD-106: Google Play соблюдает все применимые международные санкции
- BR-MOD-107: В санкционных регионах бесплатные приложения остаются доступными, платные — блокируются
- BR-MOD-108: Разработчики несут ответственность за соблюдение local regulations в странах распространения
- BR-MOD-109: EU Anti-Geo-Blocking запрещает unjustified блокировку по национальности
- BR-MOD-110: Регуляторные требования (gambling, финтех, крипто) различаются по юрисдикциям
- BR-MOD-111: Google Play применяет дополнительные ограничения по требованию местных регуляторов

**Результат:** Google Play соблюдает международные санкции и регуляторные требования, обеспечивая легальный доступ

### FR-MOD-019: Families Policy и защита детей (Child Safety)

**Описание:** Специальные требования к приложениям, ориентированным на детей или содержащим функции для несовершеннолетних

**Роли:** Developer, Human Reviewer, Policy Specialist

**Предусловия:**
- Приложение заявлено как "Designed for Families" или его целевая аудитория включает детей
- Приложение подаётся на проверку в Google Play

**Основной сценарий:**

1. **Families Self-Certification:**
   - Разработчик декларирует целевую аудиторию в Play Console:
     - **Children only** (до 13 лет)
     - **Children and older audiences** (смешанная аудитория)
     - **Older audiences** (13+ / 16+ / 18+)
   - Для категорий, включающих детей, применяются усиленные требования

2. **Требования Families Policy:**

   **2.1. Реклама:**
   - Только сертифицированные ad SDK (Google Certified Ad Networks)
   - Запрет на interest-based advertising для детей
   - Запрет на misleading ads
   - Рекламный контент должен быть age-appropriate

   **2.2. APIs и SDK:**
   - Запрещены SDK, не одобренные для детских приложений
   - Запрет на SDK, собирающие GAID (Google Advertising ID) у детей
   - Ограничения на analytics SDK

   **2.3. Данные:**
   - Минимизация сбора данных
   - Запрет на сбор precise location
   - Запрет на использование device identifiers
   - Соответствие COPPA (для US) и GDPR (для ЕС)

   **2.4. Контент:**
   - Age-appropriate контент
   - Отсутствие насилия, сексуального контента, hate speech
   - Отсутствие gambling-механик
   - Отсутствие in-app purchases, требующих оплаты (допускаются только через parental gate)

   **2.5. Social features:**
   - Запрет или ограничение unmoderated social features
   - Обязательная модерация чатов
   - Parental gate для социальных функций

3. **Child Safety Standards Policy (2025-2026):**
   - Social и dating приложения обязаны пройти self-certification
   - Обязательные safety features для защиты несовершеннолетних
   - Проверка возраста пользователей

4. **Enforcement:**
   - Нарушение Families Policy — усиленные enforcement-меры
   - Серьёзные нарушения (сбор данных детей) — немедленное удаление + возможная терминация

**Альтернативные сценарии:**
- Сценарий А (Смешанная аудитория): Приложение должно обеспечивать детскую безопасность для неаутентифицированных пользователей
- Сценарий Б (Неверная декларация аудитории): Разработчик занижает целевой возраст — enforcement при обнаружении
- Сценарий В (Teacher-approved): Приложения могут получить значок "Teacher approved" через программу экспертизы

**Бизнес-правила:**
- BR-MOD-112: Приложения для детей (до 13) обязаны соответствовать Families Policy
- BR-MOD-113: Только сертифицированные ad SDK допускаются в детских приложениях
- BR-MOD-114: Запрещён сбор precise location и device identifiers у детей
- BR-MOD-115: Нарушение Families Policy рассматривается как серьёзное нарушение
- BR-MOD-116: Social/dating приложения обязаны пройти Child Safety Standards self-certification
- BR-MOD-117: С 2026 года обязательно использование Age Signals API для блокировки несовершеннолетних в age-restricted приложениях
- BR-MOD-118: COPPA и GDPR compliance обязательны для соответствующих юрисдикций

**Результат:** Приложения для детей соответствуют повышенным стандартам безопасности

### FR-MOD-020: Verified Developer Program (Верификация разработчиков)

**Описание:** Система верификации identity разработчиков для повышения доверия и снижения мошенничества

**Роли:** Developer, Account Owner, Automated Review System

**Предусловия:**
- Разработчик регистрирует аккаунт в Google Play Developer Program

**Основной сценарий:**

1. **Типы аккаунтов:**
   - **Personal account**: физическое лицо
   - **Organization account**: юридическое лицо

2. **Верификация Personal account:**
   - Предоставление government-issued ID
   - Верификация адреса
   - Верификация контактной информации
   - Проверка может занять несколько дней

3. **Верификация Organization account:**
   - Предоставление D-U-N-S number (Dun & Bradstreet)
   - Верификация юридического адреса
   - Верификация контактного лица
   - Проверка через независимые бизнес-реестры
   - Проверка может занять до 7-14 дней

4. **Testing period для новых аккаунтов:**
   - Новые аккаунты проходят усиленную проверку первых приложений
   - Ограниченная видимость приложений на начальном этапе
   - Постепенное повышение привилегий при хорошей истории

5. **Verified badge:**
   - Верифицированные организации могут получить badge в магазине
   - Badge повышает доверие пользователей
   - Требования для badge: verified organization + хорошая история + significant user base

6. **Trend 2026: Mandatory Verification:**
   - Google движется к обязательной верификации для всех разработчиков
   - Неверифицированные аккаунты будут иметь ограниченные возможности

**Альтернативные сценарии:**
- Сценарий А (Верификация не пройдена): Аккаунт ограничен; публикация невозможна до завершения верификации
- Сценарий Б (Связь с терминированным аккаунтом): При обнаружении связи — новый аккаунт также терминируется
- Сценарий В (Смена типа аккаунта): Переход с Personal на Organization — повторная верификация

**Бизнес-правила:**
- BR-MOD-119: Регистрационный взнос: $25 (единоразово)
- BR-MOD-120: Organization accounts требуют D-U-N-S number
- BR-MOD-121: Новые аккаунты проходят усиленную проверку первых публикаций
- BR-MOD-122: Google отслеживает связи между аккаунтами для предотвращения обхода терминации
- BR-MOD-123: В 2026 году Google движется к обязательной верификации всех разработчиков
- BR-MOD-124: 158 000 аккаунтов было терминировано в 2024 году, связанные аккаунты также блокировались

**Результат:** Разработчик верифицирован, аккаунт готов к публикации приложений

## Глоссарий

| Термин | Определение |
|--------|------------|
| **PHA** | Potentially Harmful Application — потенциально вредоносное приложение, детектируемое Google Play Protect |
| **Policy Strike** | Штрафной балл за серьёзное нарушение политик; три страйка могут привести к терминации аккаунта |
| **IARC** | International Age Rating Coalition — организация, обеспечивающая единую систему возрастных рейтингов |
| **DMCA** | Digital Millennium Copyright Act — закон США о защите авторских прав в цифровой среде |
| **DSA** | Digital Services Act — Закон ЕС о цифровых услугах, предъявляющий требования к платформам |
| **VLOP** | Very Large Online Platform — очень крупная онлайн-платформа по классификации DSA (>45M пользователей в ЕС) |
| **Trusted Flagger** | Организация, назначенная Digital Services Coordinator, с приоритетным правом подачи жалоб (DSA) |
| **Content Rating** | Возрастная классификация приложения на основе IARC-опросника |
| **Data Safety** | Раздел в листинге приложения, описывающий практики сбора и использования данных |
| **Target API Level** | Версия Android API, на которую ориентировано приложение (targetSdkVersion в манифесте) |
| **AAB** | Android App Bundle — формат публикации приложений в Google Play (вместо APK) |
| **Counter Notice** | Ответ разработчика на DMCA takedown с заявлением о неправомерности удаления |
| **Review Bombing** | Массовая координированная атака негативными отзывами на приложение |
| **Incentivized Review** | Отзыв, оставленный в обмен на вознаграждение (деньги, товары); запрещён |
| **Fake Install** | Мошенническая установка приложения для искусственного завышения счётчика |
| **Click Injection** | Мошенничество с перехватом attribution через генерацию кликов |
| **Sideloading** | Установка приложения из источника, отличного от Google Play (через APK-файл) |
| **Grace Period** | Период времени, предоставленный разработчику для исправления нарушения |
| **Parental Gate** | Механизм подтверждения действия родителем (для детских приложений) |
| **Families Policy** | Специальные политики Google Play для приложений, ориентированных на детей |
| **D-U-N-S Number** | Уникальный идентификатор бизнеса Dun & Bradstreet, требуемый для Organization accounts |
| **Risk Score** | Оценка риска, присваиваемая ML-моделью приложению, отзыву или аккаунту |
| **Enforcement** | Принудительные меры Google Play за нарушение политик (warning, removal, suspension, termination) |
| **Age Signals API** | API Google Play для определения возрастной категории пользователя (2026) |
| **Out-of-Court Dispute Resolution** | Внесудебное разрешение споров, доступное в рамках DSA для ЕС |
