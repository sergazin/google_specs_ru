# Сбор данных и потоки данных

## Описание

Модуль «Сбор данных и потоки данных» (Data Collection & Data Streams) является фундаментальным ядром Google Analytics 4. Он отвечает за непрерывный приём, фильтрацию, классификацию и первичную обработку данных о взаимодействиях пользователей с веб-сайтами и мобильными приложениями. В отличие от Universal Analytics, где веб- и мобильная аналитика обрабатывались раздельно, GA4 объединяет данные из нескольких платформ в единое свойство (Property) посредством потоков данных (Data Streams).

Модуль охватывает полный жизненный цикл данных — от момента взаимодействия пользователя до поступления события в хранилище GA4: конфигурация потоков, автоматический сбор событий, расширенное измерение (Enhanced Measurement), пользовательские события, параметры, фильтрация, идентификация пользователей, управление согласием (Consent Mode), редакция персональных данных (Data Redaction) и серверный сбор через Measurement Protocol.

## Роли пользователей

| Роль | Уровень доступа | Полномочия в модуле |
|------|----------------|---------------------|
| **Администратор (Administrator)** | Аккаунт / Свойство | Полный доступ: создание/удаление потоков данных, настройка фильтров данных, управление Consent Mode, настройка Data Redaction, создание API-секретов Measurement Protocol, управление BigQuery-экспортом, настройка кросс-доменного отслеживания, управление таймаутами сессий |
| **Редактор (Editor)** | Свойство | Создание и изменение потоков данных, настройка Enhanced Measurement, создание/модификация событий через интерфейс, определение внутреннего трафика, настройка фильтров данных, создание пользовательских измерений и метрик, управление списком нежелательных рефералов |
| **Маркетолог (Marketer)** | Свойство | Создание и модификация событий через интерфейс, пометка событий как ключевых (Key Events), изменение метода подсчёта конверсий |
| **Аналитик (Analyst)** | Свойство | Просмотр конфигурации потоков и событий, чтение данных через отчёты и Explorations, без возможности изменения конфигурации сбора |
| **Viewer (Просмотр)** | Свойство | Только просмотр отчётов и конфигурации, без каких-либо изменений |

## Функциональные требования

### FR-DCL-001: Потоки данных (Data Streams)
**Priority**: P0-Critical

**Description**: Система должна поддерживать создание и управление потоками данных трёх типов: Web, iOS и Android. Каждый поток данных представляет собой непрерывный канал передачи данных от конкретного источника (веб-сайт или мобильное приложение) в свойство GA4.

**Acceptance Criteria**:
- [ ] Поддерживается создание потоков данных трёх типов: Web, iOS, Android
- [ ] В рамках одного свойства допускается не более одного потока каждого типа (один веб, один iOS, один Android)
- [ ] Для веб-потока генерируется уникальный Measurement ID (формат G-XXXXXXXXXX)
- [ ] Для iOS-потока требуется указание App Store ID и bundle ID
- [ ] Для Android-потока требуется указание package name из Google Play
- [ ] Для мобильных потоков обязательна привязка к проекту Firebase
- [ ] Каждый поток данных имеет уникальный Stream ID
- [ ] Поддерживается активация/деактивация потоков
- [ ] Система отображает диагностику состояния потока (активен, неактивен, ошибка конфигурации)
- [ ] Предоставляется информация о последнем полученном событии для каждого потока

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-001 | Measurement ID является основным идентификатором для веб-потока и используется при установке тега gtag.js или GTM |
| BR-DCL-002 | Мобильные потоки данных не могут функционировать без привязки к Firebase проекту |
| BR-DCL-003 | Удаление потока данных приводит к необратимой потере данных, собранных через этот поток |
| BR-DCL-004 | Автоматическая диагностика уведомляет администратора в реальном времени, если поток стал неактивным или некорректно сконфигурирован |

### FR-DCL-002: Автоматически собираемые события (Automatically Collected Events)
**Priority**: P0-Critical

**Description**: Система должна автоматически собирать набор предопределённых событий без каких-либо дополнительных настроек со стороны пользователя. Эти события запускаются при определённых действиях пользователей на сайте или в приложении.

**Acceptance Criteria**:
- [ ] Автоматический сбор более 30 предопределённых событий
- [ ] События собираются сразу после установки кода отслеживания без дополнительной конфигурации
- [ ] Каждое событие содержит набор автоматически заполняемых параметров
- [ ] События корректно классифицируются по платформам (Web, iOS, Android)

**Полный перечень автоматически собираемых событий**:

#### События, общие для Web и App:
| Событие | Описание | Автоматические параметры |
|---------|----------|-------------------------|
| `first_visit` | Первое посещение пользователем сайта/приложения; используется для подсчёта новых пользователей | — |
| `session_start` | Начало новой сессии; генерируется при первом взаимодействии или после истечения таймаута сессии | `ga_session_id`, `ga_session_number` |
| `user_engagement` | Фиксация активного времени взаимодействия пользователя; срабатывает периодически при активности | `engagement_time_msec` |

#### События только для Web:
| Событие | Описание | Автоматические параметры |
|---------|----------|-------------------------|
| `page_view` | Загрузка страницы или изменение URL в SPA (history state change) | `page_location`, `page_referrer`, `page_title` |
| `scroll` | Прокрутка страницы до 90% высоты (Enhanced Measurement) | `percent_scrolled` (всегда 90) |
| `click` | Клик по исходящей ссылке (Enhanced Measurement) | `link_url`, `link_domain`, `link_classes`, `link_id`, `outbound` (true) |
| `view_search_results` | Пользователь выполнил поиск по сайту (Enhanced Measurement) | `search_term` |

| `video_progress` | Воспроизведение видео достигло 10%, 25%, 50%, 75% (Enhanced Measurement) | `video_percent`, `video_current_time`, `video_duration`, `video_url`, `video_title` |
| `video_complete` | Видео воспроизведено до конца (Enhanced Measurement) | `video_url`, `video_title`, `video_provider` |
| `file_download` | Клик по ссылке, ведущей к скачиванию файла (Enhanced Measurement) | `file_name`, `file_extension`, `link_url`, `link_text` |
| `form_start` | Пользователь начал взаимодействие с формой (Enhanced Measurement) | `form_id`, `form_name`, `form_destination` |
| `form_submit` | Пользователь отправил форму (Enhanced Measurement) | `form_id`, `form_name`, `form_destination`, `form_submit_text` |

#### События только для App (iOS / Android):
| Событие | Описание | Автоматические параметры |
|---------|----------|-------------------------|
| `first_open` | Первый запуск приложения после установки или переустановки | `previous_first_open_count` |
| `screen_view` | Просмотр экрана в приложении | `firebase_screen`, `firebase_screen_class`, `firebase_screen_id`, `firebase_previous_screen` |
| `in_app_purchase` | Покупка внутри приложения через App Store или Google Play | `product_id`, `price`, `currency`, `quantity` |
| `app_update` | Обновление приложения до новой версии | `previous_app_version` |
| `app_remove` | Удаление приложения (только Android) | — |
| `os_update` | Обновление операционной системы устройства | `previous_os_version` |
| `notification_receive` | Получение push-уведомления (только Android, когда приложение в фоне) | `message_id`, `message_name`, `topic` |
| `notification_foreground` | Получение push-уведомления, когда приложение на переднем плане | `message_id`, `message_name` |

| `ad_click` | Клик по рекламному объявлению | `ad_platform`, `ad_source`, `ad_format`, `ad_unit_name` |

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-005 | Автоматически собираемые события нельзя отключить (за исключением Enhanced Measurement событий) |
| BR-DCL-006 | Каждое автоматическое событие содержит как минимум 5 базовых параметров: `page_location`, `page_referrer`, `page_title`, `language`, `screen_resolution` |
| BR-DCL-007 | Названия автоматически собираемых событий зарезервированы; пользователь не должен создавать события с такими же именами |
| BR-DCL-008 | Сбор данных начинается немедленно после корректной установки тега на сайт или SDK в приложение |

### FR-DCL-003: Enhanced Measurement (Расширенное измерение)
**Priority**: P0-Critical

**Description**: Система должна предоставлять набор расширенных измерений, которые автоматически отслеживают дополнительные типы взаимодействий на веб-сайте без необходимости написания кода или настройки через GTM. Enhanced Measurement активируется по умолчанию при создании веб-потока данных.

**Acceptance Criteria**:
- [ ] Enhanced Measurement включен по умолчанию при создании веб-потока
- [ ] Каждую из функций Enhanced Measurement можно включить/выключить по отдельности
- [ ] Поддерживаются следующие типы измерений:

| Функция | Событие | Описание | Ограничения |
|---------|---------|----------|-------------|
| Просмотры страниц (Page views) | `page_view` | Срабатывает при загрузке страницы и при изменении URL через History API (SPA) | Можно настроить отслеживание по History Change и/или Browser History Events |
| Прокрутка (Scrolls) | `scroll` | Фиксирует прокрутку до 90% высоты страницы | Только порог 90%; для других порогов требуется GTM |
| Исходящие клики (Outbound clicks) | `click` | Клик по ссылке, ведущей на домен, отличный от текущего | Ссылки на домены, настроенные для кросс-доменного отслеживания, не считаются исходящими |
| Поиск по сайту (Site search) | `view_search_results` | Обнаружение поискового запроса в URL (параметры q, s, search, query, keyword) | Можно настроить до 10 дополнительных параметров поиска |
| Взаимодействие с видео (Video engagement) | `video_start`, `video_progress`, `video_complete` | Отслеживание встроенных YouTube-видео с включённой поддержкой JS API | Работает только с YouTube; для других плееров требуется кастомная реализация |
| Скачивание файлов (File downloads) | `file_download` | Клик по ссылке на файл с расширением: pdf, xls, xlsx, doc, docx, txt, rtf, csv, exe, key, pps, ppt, pptx, 7z, pkg, rar, gz, zip, avi, mov, mp4, mpeg, wmv, midi, mp3, wav, wma | Только предопределённые расширения |
| Взаимодействие с формами (Form interactions) | `form_start`, `form_submit` | Начало взаимодействия с формой и её отправка | Работает только с HTML-формами (<form>) |

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-009 | Enhanced Measurement доступен только для веб-потоков данных; для мобильных приложений не применяется |
| BR-DCL-010 | Отключение отдельной функции Enhanced Measurement немедленно прекращает сбор соответствующих событий |
| BR-DCL-011 | Для отслеживания YouTube-видео требуется включённая поддержка JS API на видео-плеере |
| BR-DCL-012 | Параметры поиска по сайту можно расширить, добавив до 10 пользовательских параметров URL |

### FR-DCL-004: Рекомендуемые события (Recommended Events)
**Priority**: P1-High

**Description**: Система должна предоставлять набор рекомендуемых событий с предопределёнными именами и параметрами для различных отраслей и типов бизнеса. Рекомендуемые события не собираются автоматически — их необходимо реализовать самостоятельно, но при этом использовать стандартизированные имена и параметры для получения расширенных отчётов.

**Acceptance Criteria**:
- [ ] Документирован полный список рекомендуемых событий с предписанными параметрами
- [ ] При отправке рекомендуемых событий с корректными параметрами автоматически заполняются специализированные отчёты
- [ ] Рекомендуемые события поддерживают items-массив для передачи информации о товарах

| BR-DCL-014 | Отправка рекомендуемых событий без обязательных параметров не приведёт к ошибке, но данные не будут отображаться в специализированных отчётах |
| BR-DCL-015 | Для e-commerce событий обязательно наличие хотя бы одного из параметров `item_id` или `item_name` в массиве items[] |
| BR-DCL-016 | Параметр `transaction_id` обязателен для события `purchase` и используется для дедупликации транзакций |

### FR-DCL-005: Пользовательские события (Custom Events)
**Priority**: P1-High

**Description**: Система должна позволять создавать и отправлять пользовательские события для отслеживания специфических взаимодействий, которые не покрываются автоматическими или рекомендуемыми событиями. Пользовательские события могут быть реализованы через код (gtag.js, GTM, Firebase SDK) или через интерфейс администрирования GA4.

**Acceptance Criteria**:
- [ ] Пользователь может создать пользовательское событие с произвольным именем (с учётом правил именования)
- [ ] Поддерживается создание событий через интерфейс GA4 (Admin > Events > Create events)
- [ ] Поддерживается модификация существующих событий через интерфейс (Admin > Events > Modify events)
- [ ] Для создания события через интерфейс задаются условия соответствия (matching conditions)
- [ ] Поддерживается до 25 параметров на одно событие
- [ ] Нет ограничения на количество различных пользовательских событий для веб-потока
- [ ] Для мобильных потоков — не более 500 уникальных событий на пользователя в день

**Правила именования событий**:
| Правило | Описание |
|---------|----------|
| Длина имени | Максимум 40 символов |
| Допустимые символы | Только латинские буквы, цифры и символ подчёркивания |
| Начало имени | Должно начинаться с буквы |
| Регистр | Имена чувствительны к регистру; `click` и `Click` — два разных события |
| Соглашение | Рекомендуется snake_case (нижний регистр, слова разделены подчёркиванием) |
| Запрещённые префиксы | Нельзя использовать `ga_`, `firebase_`, `google_` |

**Зарезервированные имена событий** (нельзя использовать для пользовательских событий):
`ad_activeview`, `ad_click`, `ad_exposure`, `ad_impression`, `ad_query`, `adunit_exposure`, `app_clear_data`, `app_exception`, `app_install`, `app_remove`, `app_store_refund`, `app_store_subscription_cancel`, `app_store_subscription_convert`, `app_store_subscription_renew`, `app_update`, `app_upgrade`, `click`, `dynamic_link_app_open`, `dynamic_link_app_update`, `dynamic_link_first_open`, `error`, `file_download`, `first_open`, `first_visit`, `form_start`, `form_submit`, `in_app_purchase`, `notification_dismiss`, `notification_foreground`, `notification_open`, `notification_receive`, `os_update`, `page_view`, `screen_view`, `scroll`, `session_start`, `user_engagement`, `video_complete`, `video_progress`, `video_start`, `view_search_results`

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-017 | Создание и модификация событий через интерфейс применяются только к данным, собранным после сохранения конфигурации; обратная сила не действует |
| BR-DCL-018 | При модификации события все заданные условия соответствия (matching conditions) должны быть выполнены одновременно (логическое И) |
| BR-DCL-019 | Условия соответствия поддерживают опцию «ignore case» для нечувствительного сравнения |
| BR-DCL-020 | При создании события через интерфейс оригинальное событие-источник продолжает собираться наряду с новым |

### FR-DCL-006: Параметры событий и пользовательские параметры
**Priority**: P1-High

**Description**: Система должна поддерживать передачу дополнительных метаданных вместе с событиями через параметры событий (event parameters), а также хранение атрибутов пользователей через пользовательские свойства (user properties). Для отображения параметров в отчётах они должны быть зарегистрированы как пользовательские измерения (custom dimensions) или метрики (custom metrics).

**Acceptance Criteria**:
- [ ] Поддерживается до 25 параметров на одно событие
- [ ] Имена параметров — до 40 символов, только буквы, цифры и подчёркивания
- [ ] Значения параметров — до 100 символов (стандартные свойства) или 500 символов (GA4 360)
- [ ] Специальные лимиты значений: `page_location` — 1000 символов, `page_referrer` — 420 символов, `page_title` — 300 символов
- [ ] Имена пользовательских свойств (user properties) — до 24 символов
- [ ] Значения пользовательских свойств — до 36 символов
- [ ] Для отображения в отчётах параметры необходимо зарегистрировать как Custom Dimensions / Custom Metrics

**Лимиты пользовательских измерений и метрик (стандартные свойства)**:
| Тип | Лимит (Standard) | Лимит (GA4 360) |
|-----|-------------------|-----------------|
| Event-scoped custom dimensions | 50 | 125 |
| User-scoped custom dimensions | 25 | 100 |
| Item-scoped custom dimensions | 10 | 10 |
| Event-scoped custom metrics | 50 | 125 |

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-021 | Регистрация пользовательского измерения/метрики может занять до 24-48 часов до появления данных в отчётах |
| BR-DCL-022 | После удаления пользовательского измерения необходимо ждать 48 часов перед созданием нового на освободившемся слоте |
| BR-DCL-023 | Высококардинальные пользовательские измерения (с большим количеством уникальных значений) могут привести к агрегации данных в строку «(other)» в отчётах |
| BR-DCL-024 | Параметры, превышающие лимит 25 на событие, отбрасываются без уведомления |

### FR-DCL-007: Ключевые события (Key Events / Conversions)
**Priority**: P0-Critical

**Description**: Система должна позволять помечать любое событие (автоматическое, рекомендуемое или пользовательское) как ключевое событие (Key Event, ранее — Conversion). Ключевые события используются для измерения бизнес-результатов и оптимизации рекламных кампаний.

**Acceptance Criteria**:
- [ ] Любое событие может быть отмечено как Key Event через переключатель в интерфейсе
- [ ] Поддерживается два метода подсчёта: «Once per event» (раз за событие) и «Once per session» (раз за сессию)
- [ ] По умолчанию используется метод «Once per event» (рекомендуемый)
- [ ] Максимум 30 Key Events на свойство (стандартное) или 50 (GA4 360)
- [ ] Key Events автоматически передаются в связанные рекламные аккаунты Google Ads как конверсии

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-025 | Метод «Once per event»: если событие срабатывает 5 раз за сессию, засчитывается 5 конверсий |
| BR-DCL-026 | Метод «Once per session»: если событие срабатывает 5 раз за сессию, засчитывается 1 конверсия |
| BR-DCL-027 | Изменение метода подсчёта применяется только к данным, собранным после изменения |
| BR-DCL-028 | При привязке к Google Ads ключевые события автоматически становятся доступными как конверсии для оптимизации ставок |

### FR-DCL-008: Фильтры данных (Data Filters)
**Priority**: P1-High

**Description**: Система должна поддерживать фильтрацию входящих данных для исключения нерелевантного трафика из отчётов. Поддерживается два типа фильтров: фильтр внутреннего трафика и фильтр трафика разработчиков.

**Acceptance Criteria**:
- [ ] Поддерживается создание до 10 фильтров данных на свойство
- [ ] Тип 1 — Фильтр внутреннего трафика (Internal Traffic): исключает трафик на основании параметра `traffic_type`
- [ ] Тип 2 — Фильтр трафика разработчиков (Developer Traffic): исключает трафик с параметрами `debug_mode` или `debug_event`
- [ ] Фильтры поддерживают три состояния: Testing (тестирование), Active (активный), Inactive (неактивный)
- [ ] В состоянии Testing данные продолжают собираться, но помечаются специальным измерением «Test data filter name»
- [ ] В состоянии Active данные полностью исключаются из обработки

**Настройка определения внутреннего трафика**:
- [ ] Определение по IP-адресу: точное совпадение, начинается с, заканчивается на, содержит, в диапазоне (CIDR-нотация), регулярное выражение
- [ ] Каждому правилу присваивается имя и значение параметра `traffic_type` (по умолчанию — `internal`)
- [ ] Поддерживается создание нескольких правил определения внутреннего трафика

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-029 | Эффект активного фильтра данных необратим: исключённые данные никогда не обрабатываются и не доступны в Analytics или BigQuery |
| BR-DCL-030 | Рекомендуется оставлять фильтр в состоянии Testing не менее 24-48 часов перед переводом в Active |
| BR-DCL-031 | Трафик разработчиков определяется по наличию параметров `debug_mode` или `debug_event` и отображается в DebugView |
| BR-DCL-032 | Внутренний трафик, в отличие от трафика разработчиков, не отображается в DebugView |

### FR-DCL-009: Measurement Protocol
**Priority**: P1-High

**Description**: Система должна поддерживать серверный сбор данных через Measurement Protocol — HTTP API, позволяющий отправлять события непосредственно на серверы GA4 с любого подключённого к интернету устройства. Measurement Protocol дополняет (но не заменяет) клиентский сбор данных.

**Acceptance Criteria**:
- [ ] Поддерживается отправка событий через HTTP POST-запросы
- [ ] Аутентификация через API Secret, уникальный для каждого потока данных
- [ ] API Secret создаётся в настройках потока данных; генерируется неограниченное количество секретов
- [ ] API Secret чувствителен к регистру
- [ ] Поддерживается два режима валидации: RELAXED (по умолчанию) и ENFORCE_RECOMMENDATIONS
- [ ] Поддерживается привязка серверных событий к клиентским сессиям через `client_id` и/или `user_id`
- [ ] Отправляемые события обрабатываются так же, как клиентские — попадают в отчёты, Explorations, BigQuery

**Режимы валидации**:
| Режим | Описание |
|-------|----------|
| RELAXED | Отклоняет только некорректно сформированные запросы; игнорирует параметры, превышающие лимиты, принимает некорректные типы данных |
| ENFORCE_RECOMMENDATIONS | Дополнительно отклоняет: некорректные типы данных параметров, параметры, превышающие лимиты, события с timestamp старше 72 часов |

**Ключевые ограничения**:
- [ ] События с timestamp старше 72 часов от момента отправки не будут атрибутированы к корректной сессии и попадут в «Unassigned»
- [ ] Measurement Protocol не поддерживает стандартную атрибуцию GA4 (требуется браузерное отслеживание)
- [ ] Measurement Protocol не создаёт новые сессии автоматически — для корректной атрибуции необходимо передавать `session_id`
- [ ] Данные, отправленные через Measurement Protocol, не проходят через Data Redaction

**Варианты использования**:
| Сценарий | Описание |
|----------|----------|
| Offline-конверсии | Привязка офлайн-покупок к онлайн-сессиям |
| IoT / Kiosk | Отправка данных с устройств без браузера |
| CRM-интеграции | Обогащение GA4-данных информацией из CRM |
| Backend-события | Отслеживание серверных процессов (верификация оплаты, доставка) |
| Отладка | Валидация событий через Validation Server перед отправкой |

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-033 | API Secret не должен быть раскрыт в клиентском коде; он используется только на стороне сервера |
| BR-DCL-034 | Для привязки серверного события к конкретному пользователю необходимо передать `client_id` (обязательный параметр) |
| BR-DCL-035 | Measurement Protocol не поддерживает автоматическую генерацию событий `session_start` и `first_visit` |
| BR-DCL-036 | Максимум 25 событий в одном запросе Measurement Protocol |

### FR-DCL-010: Consent Mode (Режим согласия)
**Priority**: P0-Critical

**Description**: Система должна поддерживать Consent Mode v2 — механизм, позволяющий адаптировать поведение тегов Google в зависимости от статуса согласия пользователя на обработку данных. Consent Mode интегрируется с платформами управления согласием (CMP) и обеспечивает соответствие требованиям GDPR, CCPA и других регуляторных актов.

**Acceptance Criteria**:
- [ ] Поддерживаются четыре параметра согласия:

| Параметр | Описание | Влияние при отказе |
|----------|----------|-------------------|
| `analytics_storage` | Хранение аналитических данных (cookies) | GA4 переключается на безкуковое (cookieless) измерение; не создаются аналитические cookies |
| `ad_storage` | Хранение рекламных данных (cookies) | Не создаются рекламные cookies; ограничивается ретаргетинг |
| `ad_user_data` (v2) | Использование персональных данных для рекламы | Персональные данные не передаются в рекламные платформы |
| `ad_personalization` (v2) | Персонализация рекламы и ремаркетинг | Отключается персонализированная реклама и ремаркетинг |

- [ ] Поддерживаются два режима работы:

| Режим | Описание |
|-------|----------|
| **Basic Consent Mode** | Теги Google не загружаются и не собирают данные до получения согласия |
| **Advanced Consent Mode** | Теги загружаются, но отправляют безкуковые пинги (cookieless pings) при отсутствии согласия; GA4 использует эти пинги для поведенческого и конверсионного моделирования |

- [ ] При Advanced Consent Mode восстанавливается до 70% потерянных атрибуционных данных через моделирование
- [ ] Consent Mode должен быть инициализирован до загрузки любых тегов Google (default consent state)
- [ ] Состояние согласия может обновляться динамически после взаимодействия пользователя с CMP-баннером

**Data Redaction при отказе от согласия**:
- [ ] Параметр `ads_data_redaction` (при `ad_storage` = denied): полная редакция идентификаторов кликов (GCLID, DCLID) и URL с рекламными параметрами
- [ ] Редакция применяется к consent pings и conversion pings

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-037 | Consent Mode v2 обязателен с марта 2024 года для рекламодателей, обслуживающих пользователей из ЕЭЗ (EEA) |
| BR-DCL-038 | Поведенческое моделирование требует минимальный объём данных: не менее 1000 событий в день с `analytics_storage` = granted за последние 7 дней |
| BR-DCL-039 | Конверсионное моделирование требует минимум 70 конверсий в день за последние 7 дней |
| BR-DCL-040 | Consent Mode не заменяет CMP; он работает в связке с платформой управления согласием |
| BR-DCL-041 | При `analytics_storage` = denied сессии не создаются; данные используются исключительно для моделирования |

### FR-DCL-011: Data Redaction (Редакция данных)
**Priority**: P1-High

**Description**: Система должна предоставлять механизм автоматической редакции (удаления) персональных данных (PII) из собираемых событий на стороне клиента до отправки данных на серверы GA4. Data Redaction помогает предотвратить непреднамеренный сбор PII.

**Acceptance Criteria**:
- [ ] Доступна только для веб-потоков данных
- [ ] Поддерживается два типа редакции:

| Тип | Описание |
|-----|----------|
| Email Redaction | Автоматическое обнаружение и удаление текста, соответствующего паттерну email-адреса, из всех параметров событий |
| URL Query Parameter Redaction | Удаление указанных параметров URL из параметров: `page_location`, `page_referrer`, `page_path`, `link_url`, `video_url`, `form_destination` |

- [ ] Для редакции URL-параметров пользователь указывает до 30 имён параметров (например, `firstname`, `lastname`, `email`, `phone`)
- [ ] Редакция происходит на стороне клиента до отправки данных в GA4
- [ ] Редакция выполняется после того, как GA4 модифицирует или создаст события, но до отправки данных на сервер

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-042 | Data Redaction не распространяется на данные, отправленные через Measurement Protocol |
| BR-DCL-043 | Data Redaction не распространяется на данные, загруженные через Data Import |
| BR-DCL-044 | GA4 не хранит IP-адреса; IP используется для геолокации, но не записывается в данные |
| BR-DCL-045 | Термины и условия GA4 запрещают сбор PII любыми способами; Data Redaction — дополнительный уровень защиты, а не единственный |

### FR-DCL-012: Идентификация пользователей (User Identification)
**Priority**: P0-Critical

**Description**: Система должна поддерживать несколько методов идентификации пользователей для обеспечения кросс-платформенного и кросс-устройственного отслеживания. Методы применяются в иерархическом порядке приоритета.

**Acceptance Criteria**:
- [ ] Поддерживаются четыре метода идентификации с приоритетом:

| Приоритет | Метод | Описание |
|-----------|-------|----------|
| 1 (высший) | **User-ID** | Уникальный идентификатор, присваиваемый владельцем сайта/приложения авторизованным пользователям. Обеспечивает кросс-устройственное и кросс-платформенное отслеживание |
| 2 | **Google Signals** | Данные от пользователей Google, которые включили персонализацию рекламы. Позволяет отслеживать кросс-устройственные сессии |
| 3 | **Device ID** | На веб — `client_id` (хранится в cookie `_ga`); в приложениях — `app_instance_id` (Firebase). Отслеживание в рамках одного устройства/браузера |
| 4 (низший) | **Modeling** | Поведенческое моделирование для заполнения пробелов, когда другие методы недоступны (например, при отказе от cookies) |

- [ ] Поддерживаются четыре варианта Reporting Identity:

| Опция | Используемые методы |
|-------|---------------------|
| Blended | User-ID > Google Signals > Device ID > Modeling |
| Observed | User-ID > Google Signals > Device ID |
| Device-based | Только Device ID |
| Business objectives (по умолчанию) | Автоматический выбор на основе бизнес-целей |

- [ ] User-ID не должен содержать PII (email, телефон, имя)
- [ ] User-ID передаётся через `gtag('set', 'user_id', 'USER_ID')` или через Firebase SDK

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-046 | GA4 использует каскадный подход: если User-ID недоступен, применяется Google Signals, затем Device ID, затем моделирование |
| BR-DCL-047 | Google Signals доступен только если включён в настройках свойства и пользователь дал согласие на персонализацию рекламы |
| BR-DCL-048 | Client ID хранится в cookie `_ga` со сроком действия 2 года и обновляется при каждом взаимодействии |
| BR-DCL-049 | User-ID является строкой; не должен быть хеширован, так как GA4 использует его для объединения сессий |

### FR-DCL-013: Кросс-доменное отслеживание (Cross-Domain Measurement)
**Priority**: P1-High

**Description**: Система должна поддерживать отслеживание переходов пользователей между несколькими доменами, принадлежащими одному бизнесу, без потери сессии и атрибуции.

**Acceptance Criteria**:
- [ ] Настройка кросс-доменного отслеживания в разделе Configure tag settings > Configure your domains
- [ ] При переходе между доменами GA4 передаёт идентификатор через URL-параметр `_gl`
- [ ] Параметр `_gl` содержит зашифрованный `client_id` и `timestamp`
- [ ] Домены, настроенные для кросс-доменного отслеживания, автоматически исключаются из списка рефералов
- [ ] Переход между настроенными доменами не создаёт новую сессию

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-050 | Кросс-доменная передача работает только при переходах по ссылкам (`<a>`); переходы через кнопки (`<button>`) не поддерживаются автоматически |
| BR-DCL-051 | Параметр `_gl` имеет ограниченный срок действия (несколько минут) для предотвращения злоупотреблений |
| BR-DCL-052 | Все домены, участвующие в кросс-доменном отслеживании, должны использовать один и тот же Measurement ID |

### FR-DCL-014: Список нежелательных рефералов (Unwanted Referrals)
**Priority**: P2-Medium

**Description**: Система должна позволять исключать определённые домены из списка источников перехода (referrals) для предотвращения искажения атрибуции.

**Acceptance Criteria**:
- [ ] Настройка в разделе Configure tag settings > List unwanted referrals
- [ ] Поддерживается до 50 нежелательных рефералов на поток данных
- [ ] Условия соответствия: точное совпадение домена, содержит, начинается с, заканчивается на, регулярное выражение
- [ ] Домены из кросс-доменной конфигурации не требуют добавления в список нежелательных рефералов (обрабатываются автоматически)

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-053 | Рекомендуется добавлять все домены платёжных систем (PayPal, Stripe и т.д.) для исключения искажения атрибуции |
| BR-DCL-054 | Изменение списка нежелательных рефералов влияет только на данные, собранные после изменения |

### FR-DCL-015: Настройки сессий и вовлечённости
**Priority**: P1-High

**Description**: Система должна позволять настраивать параметры определения сессий и порога вовлечённости пользователей.

**Acceptance Criteria**:
- [ ] Настройка таймаута сессии: от 5 минут до 7 часов 55 минут (по умолчанию — 30 минут)
- [ ] Настройка таймера вовлечённой сессии (engaged session timer): от 10 до 60 секунд (по умолчанию — 10 секунд)
- [ ] Сессия автоматически завершается при истечении периода неактивности
- [ ] Новая сессия начинается при: первом взаимодействии после таймаута, смене источника трафика (campaign source change)

**Определение вовлечённой сессии (Engaged Session)**:
| Условие | Описание |
|---------|----------|
| Длительность | Активное время в сессии превышает порог вовлечённости (по умолчанию 10 секунд) |
| Ключевое событие | В сессии зафиксировано хотя бы одно Key Event |
| Глубина просмотра | В сессии зафиксировано 2 или более pageview/screenview |

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-055 | Для признания сессии вовлечённой достаточно выполнения хотя бы одного из трёх условий |
| BR-DCL-056 | Изменение таймаута сессии влияет на подсчёт количества сессий и показатель bounce rate |
| BR-DCL-057 | Bounce rate в GA4 = 100% минус Engagement rate; не путать с bounce rate в Universal Analytics |

### FR-DCL-016: Хранение данных (Data Retention)
**Priority**: P1-High

**Description**: Система должна предоставлять настройки срока хранения данных на уровне событий и пользователей. Настройки хранения влияют на доступность данных в Explorations, но не на стандартные отчёты.

**Acceptance Criteria**:
- [ ] Два варианта срока хранения для стандартных свойств: 2 месяца (по умолчанию) или 14 месяцев
- [ ] Для GA4 360: дополнительные опции — 26, 38, 50 месяцев
- [ ] Опция «Reset user data on new activity» — при включении срок хранения идентификатора пользователя обновляется при каждом новом событии
- [ ] Стандартные (агрегированные) отчёты не подвержены ограничению хранения данных
- [ ] Explorations и пользовательские отчёты ограничены выбранным периодом хранения

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-058 | Данные о возрасте, поле и интересах пользователей всегда ограничены 2-месячным сроком хранения независимо от настроек |
| BR-DCL-059 | Рекомендуется установить максимальный доступный срок хранения (14 месяцев) сразу после создания свойства |
| BR-DCL-060 | Уменьшение срока хранения приводит к немедленному удалению данных, превышающих новый период |
| BR-DCL-061 | Для сохранения данных сверх лимитов хранения используется экспорт в BigQuery |

### FR-DCL-017: Экспорт данных в BigQuery
**Priority**: P1-High

**Description**: Система должна поддерживать экспорт сырых (неагрегированных) данных о событиях в Google BigQuery для расширенного анализа.

**Acceptance Criteria**:
- [ ] Два режима экспорта: Daily (ежедневный пакетный) и Streaming (непрерывный)
- [ ] Daily-экспорт: лимит 1 млн событий в день для стандартных свойств (без лимита для GA4 360)
- [ ] Streaming-экспорт: без ограничения на количество событий
- [ ] Возможность выбора потоков данных для экспорта
- [ ] Возможность исключения отдельных событий из экспорта
- [ ] Поддерживается привязка к существующему проекту BigQuery с указанием региона хранения

**Business Rules**:
| Rule | Description |
|------|-------------|
| BR-DCL-062 | При превышении лимита 1 млн событий/день для daily-экспорта экспорт приостанавливается; прошлые дни не переобрабатываются |
| BR-DCL-063 | Streaming-экспорт тарифицируется по стоимости $0.05 за ГБ загруженных данных (BigQuery pricing) |
| BR-DCL-064 | Streaming-экспорт работает по принципу best-effort; поздние события и сбои загрузки могут привести к неполноте данных |
| BR-DCL-065 | Для уменьшения объёма экспорта рекомендуется использовать фильтрацию по потокам данных и исключение событий |

## Состояния и статусы

### Состояния потока данных (Data Stream)
```
[Создан] → [Активен] → [Неактивен]
              ↑              ↓
              └──────────────┘

[Активен] → [Ошибка конфигурации] → [Активен] (после исправления)
```

| Состояние | Описание | Переходы |
|-----------|----------|----------|
| Создан | Поток создан, но ещё не получал данные | → Активен (при получении первого события) |
| Активен | Поток получает данные в штатном режиме | → Неактивен (при прекращении поступления данных), → Ошибка конфигурации |
| Неактивен | Поток не получает данные (тег удалён, ошибка) | → Активен (при возобновлении) |
| Ошибка конфигурации | Обнаружена проблема с настройкой потока | → Активен (после исправления) |

### Состояния фильтра данных (Data Filter)
```
[Создан (Testing)] → [Active] → [Inactive]
       ↑                            ↓
       └────────────────────────────┘
```

| Состояние | Описание | Влияние на данные |
|-----------|----------|-------------------|
| Testing | Данные помечаются, но не исключаются | Данные доступны; видна метка «Test data filter name» |
| Active | Данные исключаются из обработки | Исключённые данные навсегда удалены |
| Inactive | Фильтр деактивирован | Данные обрабатываются без фильтрации |

### Состояния согласия (Consent State)
```
[Default (denied)] → [Granted] → [Denied]
                        ↑           ↓
                        └───────────┘
```

| Состояние параметра | Описание |
|---------------------|----------|
| `granted` | Согласие дано; полный сбор данных |
| `denied` | Согласие не дано; ограниченный сбор (cookieless pings в Advanced Mode) или полная блокировка (Basic Mode) |

### Жизненный цикл события
```
[Взаимодействие пользователя]
         ↓
[Генерация события (клиент/сервер)]
         ↓
[Проверка Consent Mode]
         ↓
[Enhanced Measurement обработка]
         ↓
[Модификация/Создание событий (GA4 UI rules)]
         ↓
[Data Redaction (клиентская)]
         ↓
[Отправка на серверы GA4]
         ↓
[Проверка Data Filters]
         ↓
[Обработка и хранение]
         ↓
[Доступность в отчётах (обычно 24-48 часов, DebugView — реальное время)]
```
