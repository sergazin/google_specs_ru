# Google Ads - Администрирование и доступы (Administration & Access Management)

> **Module ID**: GADS-ADMIN
> **Version**: 1.0.0
> **Last Updated**: 2025-01-08
> **Status**: Production Reference

## Общее описание модуля

Модуль "Администрирование и доступы" управляет всеми аспектами контроля доступа к аккаунтам Google Ads: ролями пользователей, уровнями разрешений, приглашениями, аудитом действий и управлением иерархией MCC (Manager Account). Модуль обеспечивает безопасность данных, соответствие политикам Google и гибкое делегирование полномочий в организационных структурах любой сложности.

## Характеристики модуля

| Характеристика | Значение |
|----------------|----------|
| Тип модуля | Управление доступом и безопасность |
| Уровни доступа | 5 (Admin, Standard, Read-only, Billing, Email-only) |
| Глубина MCC-иерархии | До 5 уровней менеджеров |
| Срок хранения истории изменений | 2 года |
| Срок действия приглашения | 30 дней (неявный, зависит от настроек) |
| Период отката изменений | До 30 дней |

### 1.3 Бизнес-правила уровней доступа

**BR-ACCESS-001**: Пользователь может выдать доступ только равный своему уровню или ниже.
> Пример: Standard-пользователь не может пригласить нового Admin.

**BR-ACCESS-002**: Для выдачи Admin-доступа приглашающий сам должен иметь Admin-права.

**BR-ACCESS-003**: В каждом аккаунте обязательно должен быть минимум один пользователь с Admin-доступом.

**BR-ACCESS-004**: Рекомендуется иметь минимум двух администраторов на случай потери доступа одним из них.

**BR-ACCESS-005**: Права доступа назначаются на уровне всего аккаунта — невозможно ограничить доступ к отдельным кампаниям или группам объявлений.

**BR-ACCESS-006**: При получении приглашения на email, который является альтернативным адресом Google Account, можно принять приглашение и использовать как альтернативный, так и основной email для входа.

## 2. Уровни доступа в Manager Account (MCC)

### 2.1 Роли в управляющем аккаунте

| Роль | Описание | Права на управление иерархией |
|------|----------|------------------------------|
| **Administrative (Admin)** | Полный контроль над MCC и всеми связанными аккаунтами | Да — управление структурой, связями, пользователями |
| **Standard** | Управление кампаниями в связанных аккаунтах | Нет — не может изменять структуру иерархии |
| **Read-only** | Просмотр данных по всем связанным аккаунтам | Нет |

### 2.2 Специальные права MCC

| Право | Описание | Требуемая роль |
|-------|----------|----------------|
| Связывание новых аккаунтов | Отправка приглашений клиентским аккаунтам | Admin |
| Отвязка аккаунтов | Разрыв связи с клиентскими аккаунтами | Admin |
| Создание суб-MCC | Создание вложенных управляющих аккаунтов | Admin |
| Установка владения (Ownership) | Назначение MCC владельцем клиентского аккаунта | Admin |
| Передача владения | Передача прав владельца другому MCC | Admin |
| Настройка security mandates | Требование 2FA для всех пользователей | Admin |
| Настройка allowed domains | Ограничение доменов для приглашений | Admin |

### 2.3 Владение аккаунтом (Ownership)

**Концепция владения**: MCC может стать владельцем (Owner) клиентского аккаунта, получив расширенные административные права.

**Права владельца (Owner):**
- Приглашение пользователей с Admin-доступом в клиентский аккаунт
- Передача владения другому MCC
- Отвязка других менеджеров от клиентского аккаунта
- Включение шаринга списков ремаркетинга
- Доступ к персональным данным клиентского аккаунта

**Ограничения владения:**

**BR-OWNER-001**: Клиентский аккаунт может иметь только одного владельца.

**BR-OWNER-002**: Если MCC создаёт новый аккаунт, он автоматически становится владельцем.

**BR-OWNER-003**: При связывании существующего аккаунта MCC не получает владение автоматически.

**BR-OWNER-004**: Клиентский аккаунт может отвязаться от владельца в любой момент при наличии собственного Admin-пользователя.

**BR-OWNER-005**: Для передачи владения новый MCC должен быть уже связан с клиентским аккаунтом.

### 2.4 Иерархия доступа

**Правило наследования**: Доступ, предоставленный на уровне MCC, распространяется на все связанные аккаунты в иерархии ниже.

```
[Корневой MCC] — Пользователь А (Admin)
     |
     +-- [Суб-MCC: Регион] — Пользователь Б (Standard)
     |       |
     |       +-- [Клиент 1] — Пользователь А видит (Admin от MCC)
     |       |              — Пользователь Б видит (Standard от Суб-MCC)
     |       |
     |       +-- [Клиент 2]
     |
     +-- [Клиент 3] — Пользователь А видит (Admin)
                    — Пользователь Б НЕ видит
```

**BR-HIER-001**: Пользователь на верхнем уровне MCC имеет доступ ко всем аккаунтам в иерархии ниже.

**BR-HIER-002**: Пользователь на уровне суб-MCC имеет доступ только к аккаунтам под этим суб-MCC.

**BR-HIER-003**: Нельзя настроить разные уровни доступа для разных аккаунтов внутри одного MCC для одного пользователя.

## 3. Управление пользователями

### 3.1 Приглашение пользователя

#### User Story: US-INVITE-001 — Приглашение нового пользователя в аккаунт

```
КАК администратор Google Ads аккаунта
Я ХОЧУ пригласить нового пользователя
ЧТОБЫ он мог работать с рекламными кампаниями
```

**Предусловия:**
- Приглашающий имеет Admin-доступ к аккаунту
- Email приглашаемого привязан к Google Account

**Основной сценарий:**
1. Администратор переходит в Admin → Access and Security
2. Нажимает кнопку "+" (Add user)
3. Вводит email-адрес приглашаемого пользователя
4. Выбирает уровень доступа (Admin/Standard/Read-only/Billing/Email-only)
5. [Опционально] Устанавливает срок истечения доступа
6. Нажимает "Send invitation"
7. Система отправляет email с приглашением
8. Приглашение отображается в разделе "Pending invitations"

**Альтернативные сценарии:**
- 3a. Email не связан с Google Account → Приглашённому потребуется создать Google Account
- 4a. Выбран уровень выше, чем у приглашающего → Ошибка, выбор недоступен

**Критерии приёмки:**
- AC-001: Приглашение отправлено на указанный email
- AC-002: Приглашение видно в списке "Pending invitations"
- AC-003: Указан срок действия приглашения
- AC-004: Доступна кнопка отзыва приглашения

### 3.2 Принятие приглашения

#### User Story: US-INVITE-002 — Принятие приглашения в аккаунт

```
КАК приглашённый пользователь
Я ХОЧУ принять приглашение в Google Ads аккаунт
ЧТОБЫ получить доступ к рекламным кампаниям
```

**Основной сценарий:**
1. Пользователь получает email с приглашением
2. Кликает на кнопку "Accept invitation" в письме
3. Перенаправляется на страницу входа Google
4. Входит в свой Google Account (или создаёт новый)
5. Подтверждает принятие приглашения
6. Получает доступ к аккаунту с назначенным уровнем
7. Аккаунт появляется в списке доступных при входе в Google Ads

**Альтернативные сценарии:**
- 1a. Письмо в папке "Spam" или "Promotions" → Необходимо найти письмо
- 4a. Приглашение истекло → Ошибка, требуется новое приглашение

**Бизнес-правила принятия:**

**BR-INVITE-001**: Доступ активируется мгновенно после принятия приглашения.

**BR-INVITE-002**: Статус приглашения в интерфейсе администратора обновляется в течение 24 часов.

**BR-INVITE-003**: Приглашение можно принять с любого email, связанного с Google Account (основного или альтернативного).

### 3.3 Отзыв приглашения

#### User Story: US-INVITE-003 — Отзыв неактивного приглашения

```
КАК администратор аккаунта
Я ХОЧУ отозвать отправленное приглашение
ЧТОБЫ отменить предоставление доступа до его принятия
```

**Основной сценарий:**
1. Администратор переходит в Admin → Access and Security
2. Находит раздел "Pending invitations"
3. Выбирает нужное приглашение
4. Нажимает "Revoke" в колонке "Actions"
5. Подтверждает отзыв
6. Приглашение удаляется из списка
7. Ссылка в письме становится недействительной

**BR-INVITE-004**: Отозванное приглашение не может быть принято.

**BR-INVITE-005**: После отзыва можно отправить новое приглашение тому же пользователю.

### 3.4 Удаление доступа пользователя

#### User Story: US-ACCESS-001 — Удаление пользователя из аккаунта

```
КАК администратор аккаунта
Я ХОЧУ удалить доступ пользователя
ЧТОБЫ прекратить его работу с аккаунтом (увольнение, смена агентства)
```

**Предусловия:**
- Приглашающий имеет Admin-доступ
- Удаляемый пользователь не является последним Admin

**Основной сценарий:**
1. Администратор переходит в Admin → Access and Security
2. Находит пользователя в списке "Users"
3. Нажимает "Remove access" в колонке "Actions"
4. Подтверждает удаление
5. Доступ пользователя отзывается мгновенно
6. Пользователь больше не видит аккаунт в своём списке

**Бизнес-правила удаления:**

**BR-REMOVE-001**: Удаление доступа происходит мгновенно.

**BR-REMOVE-002**: Нельзя удалить последнего администратора аккаунта.

**BR-REMOVE-003**: Пользователь не получает уведомление об удалении доступа.

**BR-REMOVE-004**: Действия удалённого пользователя сохраняются в истории изменений.

### 3.5 Изменение уровня доступа

#### User Story: US-ACCESS-002 — Изменение прав пользователя

```
КАК администратор аккаунта
Я ХОЧУ изменить уровень доступа существующего пользователя
ЧТОБЫ расширить или ограничить его права
```

**Основной сценарий:**
1. Администратор переходит в Admin → Access and Security
2. Находит пользователя в списке "Users"
3. Нажимает на выпадающий список в колонке "Access level"
4. Выбирает новый уровень доступа
5. Изменение применяется мгновенно
6. Пользователь получает email-уведомление об изменении прав

**BR-LEVEL-001**: Администратор может назначить только уровень равный своему или ниже.

**BR-LEVEL-002**: Изменение уровня доступа не требует повторного приглашения.

**BR-LEVEL-003**: История изменения прав фиксируется в Change History.

## 4. Управление менеджерами (MCC)

### 4.1 Связывание с Manager Account

#### User Story: US-MCC-001 — Принятие запроса на связывание с MCC

```
КАК администратор клиентского аккаунта
Я ХОЧУ связать аккаунт с управляющим аккаунтом агентства
ЧТОБЫ делегировать управление рекламой
```

**Основной сценарий:**
1. Администратор клиентского аккаунта получает уведомление о запросе на связывание
2. Переходит в Admin → Access and Security → вкладка "Managers"
3. Видит запрос в разделе "Link requests"
4. Проверяет название и ID запрашивающего MCC
5. Нажимает "Accept" для принятия связи
6. MCC получает доступ к аккаунту
7. Аккаунт появляется в списке суб-аккаунтов MCC

**Альтернативные сценарии:**
- 5a. Нажимает "Reject" → Запрос отклоняется, MCC уведомляется

**Ограничения связывания:**

**BR-MCC-001**: Клиентский аккаунт может быть связан максимум с 5 разными MCC.

**BR-MCC-002**: Нельзя связать аккаунт с двумя MCC в одной иерархии.

**BR-MCC-003**: Связывание не должно нарушать ограничение в 5 уровней менеджеров.

### 4.2 Отвязка от Manager Account

#### User Story: US-MCC-002 — Отвязка от управляющего аккаунта

```
КАК администратор клиентского аккаунта
Я ХОЧУ отвязаться от MCC
ЧТОБЫ прекратить внешнее управление
```

**Предусловия:**
- Клиентский аккаунт связан с MCC
- Пользователь имеет Admin-доступ в клиентском аккаунте

**Основной сценарий:**
1. Администратор переходит в Admin → Access and Security → Managers
2. Находит нужный MCC в списке связанных менеджеров
3. Нажимает "Remove access" в колонке "Actions"
4. Подтверждает отвязку
5. Связь разрывается мгновенно
6. MCC теряет доступ к аккаунту
7. Данные и кампании остаются в аккаунте

**Важные последствия отвязки:**

**BR-UNLINK-001**: При отвязке от платящего MCC (если MCC оплачивает рекламу) показ рекламы останавливается.

**BR-UNLINK-002**: Если аккаунт использовал cross-account conversion tracking от MCC, тег перестанет записывать новые конверсии.

**BR-UNLINK-003**: Данные и история кампаний остаются в клиентском аккаунте.

**BR-UNLINK-004**: MCC должен перенастроить биллинг перед отвязкой, если является плательщиком.

### 4.3 Передача аккаунта между агентствами

#### User Story: US-MCC-003 — Передача клиента другому агентству

```
КАК администратор текущего агентства (MCC)
Я ХОЧУ передать клиентский аккаунт другому агентству
ЧТОБЫ новое агентство могло продолжить управление без перерыва
```

**Основной сценарий:**
1. Текущее агентство инициирует процесс передачи
2. Указывает email администратора нового агентства
3. Новое агентство получает уведомление о передаче
4. Новое агентство связывает аккаунт со своим MCC в течение 7 дней
5. После подтверждения аккаунт переходит под управление нового MCC
6. Текущее агентство теряет доступ

**Бизнес-правила передачи:**

**BR-TRANSFER-001**: Новое агентство должно связать аккаунт в течение 7 дней, иначе реклама остановится.

**BR-TRANSFER-002**: Уведомление о передаче получают все администраторы нового MCC.

**BR-TRANSFER-003**: Запрос на передачу может принять любой админ в иерархии нового MCC.

## 5. История изменений (Change History)

### 5.1 Общее описание

**Change History** — инструмент для отслеживания всех изменений в аккаунте за последние 2 года. Позволяет видеть, кто, когда и какие изменения внёс.

### 5.2 Отслеживаемые категории изменений

| Категория | Примеры отслеживаемых изменений |
|-----------|--------------------------------|
| **Кампании** | Создание, пауза, удаление, изменение настроек |
| **Группы объявлений** | Создание, изменение ставок, изменение статуса |
| **Объявления** | Создание, редактирование текста, изменение URL |
| **Ключевые слова** | Добавление, удаление, изменение типа соответствия |
| **Ставки и бюджеты** | Изменение ставок, бюджетов, стратегий назначения ставок |
| **Таргетинг** | Изменение геотаргетинга, аудиторий, демографии |
| **Расширения** | Добавление/редактирование расширений объявлений |
| **Конверсии** | Создание, настройка действий-конверсий |
| **Настройки аккаунта** | Изменение названия, часового пояса, валюты |
| **Пользователи** | Приглашения, изменение прав, удаление доступа |

### 5.3 Источники изменений

| Источник | Отображение в колонке "User" |
|----------|------------------------------|
| Интерфейс Google Ads | Email пользователя |
| Google Ads Editor | Email пользователя |
| Google Ads API | "Google Ads API" или название стороннего инструмента |
| Автоматические правила | "Automated rule: [название правила]" |
| Системные изменения Google | "ads-dartsearch-budget", "Google Ads system" |
| Рекомендации Google (принятые) | "Google Ads recommendations" |

### 5.4 Фильтрация истории изменений

**Доступные фильтры:**
- **По дате**: Произвольный диапазон в пределах 2 лет
- **По пользователю**: Фильтрация по email или источнику изменений
- **По типу изменения**: Кампании, ключевые слова, объявления и т.д.
- **По кампании/группе**: Изменения в конкретной кампании или группе объявлений

### 5.5 Функция отмены изменений (Undo)

#### User Story: US-HISTORY-001 — Отмена недавнего изменения

```
КАК менеджер аккаунта
Я ХОЧУ отменить ошибочное изменение
ЧТОБЫ вернуть настройку к предыдущему состоянию
```

**Основной сценарий:**
1. Пользователь переходит в Campaigns → Change history
2. Находит нужное изменение в списке
3. Нажимает кнопку "Undo" рядом с изменением
4. Система возвращает настройку к предыдущему значению
5. В истории создаётся новая запись об отмене

**Ограничения функции Undo:**

**BR-UNDO-001**: Отмена доступна только для изменений за последние 30 дней.

**BR-UNDO-002**: Не все типы изменений можно отменить (например, удалённые элементы не восстанавливаются).

**BR-UNDO-003**: Отмена изменения создаёт новую запись в истории.

**BR-UNDO-004**: Изменения пароля не отслеживаются в истории из соображений безопасности.

### 5.6 User Story: Аудит действий команды

#### User Story: US-HISTORY-002 — Аудит изменений за период

```
КАК руководитель отдела маркетинга
Я ХОЧУ просмотреть все изменения, сделанные командой за месяц
ЧТОБЫ проконтролировать работу и выявить ошибки
```

**Критерии приёмки:**
- AC-001: Доступен фильтр по диапазону дат
- AC-002: Видны все изменения с указанием авторов
- AC-003: Можно экспортировать данные в отчёт
- AC-004: Отображается предыдущее и новое значение для каждого изменения

## 6. Безопасность и настройки доступа

### 6.1 Двухфакторная аутентификация (2-Step Verification)

#### User Story: US-SECURITY-001 — Включение обязательной 2FA для всех пользователей

```
КАК администратор MCC
Я ХОЧУ сделать двухфакторную аутентификацию обязательной
ЧТОБЫ защитить все аккаунты в иерархии от взлома
```

**Основной сценарий:**
1. Администратор MCC переходит в Admin → Access and Security → Security
2. Выбирает вкладку "Authentication"
3. Включает опцию "2-Step Verification"
4. Выбирает область применения:
   - "This manager account" — только для текущего MCC
   - "This manager account and all accounts it owns" — для всей иерархии
5. Сохраняет настройки
6. Все пользователи без 2FA получают уведомление
7. Пользователи без 2FA теряют доступ до её настройки

**Бизнес-правила 2FA:**

**BR-2FA-001**: Администратор MCC может требовать 2FA для всех пользователей всех подчинённых аккаунтов.

**BR-2FA-002**: Пользователи без настроенной 2FA не смогут войти в аккаунт.

**BR-2FA-003**: Уведомление о требовании 2FA отправляется по email и отображается в интерфейсе.

**BR-2FA-004**: Требование 2FA называется "Manager Account Security Mandate".

### 6.2 Ограничение доменов для приглашений (Allowed Domains)

#### User Story: US-SECURITY-002 — Ограничение доменов email для приглашений

```
КАК администратор корпоративного MCC
Я ХОЧУ ограничить домены email для приглашаемых пользователей
ЧТОБЫ только сотрудники компании могли получить доступ
```

**Основной сценарий:**
1. Администратор переходит в Admin → Access and Security → Security
2. Находит настройку "Allowed domains"
3. Добавляет разрешённые домены (например: company.com, agency.com)
4. Сохраняет настройки
5. При попытке пригласить пользователя с другим доменом система выдаёт ошибку

**BR-DOMAIN-001**: Настройка распространяется на MCC и все аккаунты с административным владением.

**BR-DOMAIN-002**: Существующие пользователи с неразрешёнными доменами не удаляются автоматически.

**BR-DOMAIN-003**: Можно указать несколько разрешённых доменов.

### 6.3 Уведомления о безопасности

**Типы уведомлений безопасности:**
- Вход с нового устройства
- Вход из нового местоположения
- Изменение пароля Google Account
- Добавление/удаление пользователей
- Изменение настроек безопасности

**Настройка уведомлений:**
1. Переход в Admin → Notification settings
2. Включение/отключение типов уведомлений по категориям
3. Выбор формата (email, in-app, или оба)

## 7. Управление уведомлениями

### 7.1 Типы уведомлений

| Категория | Описание | Возможность отключения |
|-----------|----------|------------------------|
| **Критические** | Остановка рекламы, проблемы с оплатой, блокировка | Нет (обязательные) |
| **Эффективность** | Отчёты по эффективности, рекомендации | Да |
| **Информационные** | Новости Google Ads, обновления | Да |
| **Маркетинговые** | Специальные предложения, исследования | Да |

### 7.2 Бизнес-правила уведомлений

**BR-NOTIFY-001**: Как минимум один пользователь в аккаунте должен получать критические уведомления.

**BR-NOTIFY-002**: Если пользователь единственный в аккаунте, он обязан получать критические уведомления.

**BR-NOTIFY-003**: Каждый пользователь настраивает свои предпочтения уведомлений индивидуально.

**BR-NOTIFY-004**: Email-only пользователи могут получать только уведомления без доступа к интерфейсу.

### 7.3 In-app уведомления

**Приоритеты отображения:**
- **Красный баннер**: Критические проблемы (реклама не показывается, требуется действие)
- **Жёлтый баннер**: Важные предупреждения (низкий баланс, истекающие настройки)
- **Иконка колокольчика**: Информационные уведомления и рекомендации

## 8. Биллинг и доступ к платежам

### 8.1 Управление платёжным профилем

#### Пользователи платёжного профиля (Payments Profile Users)

| Право | Описание |
|-------|----------|
| **Admin** | Полный контроль над платёжным профилем |
| **Manage users** | Добавление/удаление пользователей профиля |
| **Edit payments profile** | Изменение информации о плательщике |
| **Make purchases** | Проведение платежей |
| **View payments** | Просмотр истории платежей |
| **Read only** | Только просмотр информации |

### 8.2 Бизнес-правила биллинга

**BR-BILLING-001**: Пользователи с Billing-доступом в Google Ads могут управлять способами оплаты, даже не будучи пользователями Payments Profile.

**BR-BILLING-002**: Admin-пользователи Google Ads также могут управлять биллингом.

**BR-BILLING-003**: Для ежемесячного выставления счетов (Monthly Invoicing) требуется Admin-доступ в Google Ads или соответствующем MCC.

**BR-BILLING-004**: Пользователь Payments Profile может выдавать права только равные своим или ниже.

### 8.3 Консолидированный биллинг в MCC

**BR-BILLING-005**: MCC может оплачивать рекламу за связанные аккаунты.

**BR-BILLING-006**: При отвязке от платящего MCC реклама в клиентском аккаунте останавливается.

**BR-BILLING-007**: Перед отвязкой необходимо настроить альтернативный способ оплаты в клиентском аккаунте.

## 9. Audit Trail и соответствие требованиям

### 9.1 Автоматически логируемые события

| Категория | События |
|-----------|---------|
| **Аутентификация** | Успешный вход, неудачные попытки, выход |
| **Управление доступом** | Приглашения, изменения ролей, удаление пользователей |
| **Изменения кампаний** | Все CRUD-операции с кампаниями, группами, объявлениями |
| **Биллинг** | Изменения способов оплаты, транзакции |
| **Связывание** | Подключение/отключение MCC, интеграций |
| **Настройки аккаунта** | Изменения в настройках аккаунта |

### 9.2 Хранение данных аудита

**BR-AUDIT-001**: История изменений хранится 2 года.

**BR-AUDIT-002**: Данные старше 2 лет недоступны для просмотра.

**BR-AUDIT-003**: Экспорт истории возможен через отчёты.

### 9.3 User Story: Расследование инцидента

#### User Story: US-AUDIT-001 — Расследование несанкционированных изменений

```
КАК администратор аккаунта
Я ХОЧУ определить, кто внёс неавторизованные изменения в кампанию
ЧТОБЫ принять меры и предотвратить повторение
```

**Основной сценарий:**
1. Администратор замечает неожиданные изменения в кампании
2. Переходит в Change History
3. Фильтрует по кампании и типу изменения
4. Находит запись об изменении с указанием:
   - Даты и времени
   - Email пользователя или источника (API, редактор)
   - Предыдущего и нового значения
5. Определяет автора изменения
6. При необходимости изменяет права пользователя или отзывает доступ

## 11. Интеграция с разделом Access and Security

### 11.1 Структура раздела

**Вкладка "Users":**
- Список всех пользователей с их уровнями доступа
- Методы аутентификации (2FA включена/выключена)
- Действия: изменение прав, удаление
- Раздел "Pending invitations" с неактивированными приглашениями

**Вкладка "Managers":**
- Список связанных MCC
- Статус владения (Owner/Manager)
- Входящие запросы на связывание
- Действия: отвязка от MCC

**Вкладка "Security":**
- Настройки 2-Step Verification
- Allowed domains
- Security mandates для подчинённых аккаунтов

### 11.2 Просмотр пользователей в иерархии MCC

**Функция "Show users in full hierarchy":**
- Отображает всех пользователей во всех аккаунтах иерархии
- Показывает, в каком аккаунте назначен доступ
- Позволяет администратору MCC видеть полную картину доступов

## 12. Сценарии использования

### 12.1 Онбординг нового агентства

**Сценарий**: Компания нанимает рекламное агентство для управления Google Ads.

**Шаги:**
1. Агентство создаёт MCC (если не существует)
2. Клиент предоставляет ID своего Google Ads аккаунта (XXX-XXX-XXXX)
3. Агентство отправляет запрос на связывание из MCC
4. Клиент принимает запрос в разделе Managers
5. [Опционально] Клиент делает MCC владельцем для расширенных прав
6. Агентство получает доступ и начинает работу

### 12.2 Смена агентства

**Сценарий**: Клиент меняет рекламное агентство.

**Шаги:**
1. Текущее агентство инициирует передачу аккаунта
2. Новое агентство получает уведомление и запрос на связывание
3. Новое агентство принимает связь в течение 7 дней
4. [Если нужно] Клиент переносит биллинг на новое агентство или на свой профиль
5. Клиент отвязывает старое агентство
6. Новое агентство продолжает работу без прерывания рекламы

### 12.3 Увольнение сотрудника

**Сценарий**: Сотрудник с доступом к Google Ads увольняется.

**Шаги:**
1. Администратор переходит в Access and Security → Users
2. Находит сотрудника в списке
3. Удаляет доступ (Remove access)
4. Доступ отзывается мгновенно
5. [Рекомендуется] Проверить Change History на предмет недавних изменений
6. [При необходимости] Отменить нежелательные изменения через Undo

### 12.4 Расширение команды

**Сценарий**: Компания нанимает нового специалиста по контекстной рекламе.

**Шаги:**
1. Администратор добавляет нового пользователя с уровнем Standard
2. Сотрудник принимает приглашение
3. Сотрудник получает доступ к управлению кампаниями
4. Сотрудник не может изменять настройки аккаунта или приглашать других

### 12.5 Аудит для руководства

**Сценарий**: Руководитель хочет просматривать отчёты без риска случайных изменений.

**Шаги:**
1. Администратор приглашает руководителя с уровнем Read-only
2. Руководитель принимает приглашение
3. Руководитель видит все данные, отчёты, настройки
4. Руководитель не может вносить никаких изменений

## 14. Глоссарий

| Термин | Определение |
|--------|-------------|
| **Access Level** | Уровень доступа, определяющий набор разрешений пользователя |
| **Admin** | Уровень доступа с полными правами управления аккаунтом |
| **Allowed Domains** | Настройка безопасности, ограничивающая домены email для приглашений |
| **Change History** | Журнал всех изменений в аккаунте за последние 2 года |
| **Manager Account (MCC)** | Управляющий аккаунт для централизованного управления несколькими аккаунтами |
| **Owner** | MCC с особыми расширенными правами над клиентским аккаунтом |
| **Payments Profile** | Платёжный профиль с информацией о плательщике |
| **Pending Invitation** | Отправленное, но ещё не принятое приглашение |
| **Security Mandate** | Обязательное требование безопасности от MCC к подчинённым аккаунтам |
| **Sub-manager** | MCC, находящийся под другим MCC в иерархии |
| **2-Step Verification** | Двухфакторная аутентификация Google |
