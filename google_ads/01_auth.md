# Аутентификация и управление аккаунтом Google Ads

## 1. Обзор модуля

Модуль аутентификации и управления аккаунтом Google Ads обеспечивает безопасный доступ к рекламной платформе Google через интеграцию с Google Account. Система поддерживает многоуровневую структуру доступа: от индивидуальных рекламодателей до крупных агентств с сотнями клиентских аккаунтов через Manager Account (MCC).

### 1.1 Ключевые особенности

- Единая аутентификация через Google Account (OAuth 2.0)
- Двухфакторная аутентификация (2-Step Verification)
- Иерархическая система доступа (индивидуальный аккаунт → MCC)
- Обязательная верификация рекламодателя
- Интеграция с экосистемой Google (Analytics, YouTube, Merchant Center)

## 2. Роли и уровни доступа

### 2.1 Уровни доступа к аккаунту Google Ads

| Уровень доступа | Описание | Права |
|-----------------|----------|-------|
| **Admin (Администратор)** | Полный контроль над аккаунтом | Управление кампаниями, биллингом, пользователями, связями с MCC |
| **Standard (Стандартный)** | Управление рекламой без административных функций | Создание/редактирование кампаний, просмотр отчётов, НЕ может управлять пользователями |
| **Read-only (Только чтение)** | Просмотр без возможности изменений | Просмотр кампаний, отчётов, настроек, исторических данных |
| **Billing (Биллинг)** | Управление платежами | Обновление платёжной информации, просмотр счетов |
| **Email-only (Только email)** | Получение уведомлений | Получение отчётов и уведомлений по email, без доступа к интерфейсу |

### 2.2 Роли в Manager Account (MCC)

| Роль | Описание | Возможности |
|------|----------|-------------|
| **Владелец MCC** | Полный контроль над иерархией | Управление всеми клиентскими аккаунтами, создание под-MCC |
| **Администратор MCC** | Управление структурой и пользователями | Добавление/удаление клиентских аккаунтов, управление доступом |
| **Стандартный пользователь MCC** | Работа с кампаниями клиентов | Управление кампаниями в рамках назначенных аккаунтов |
| **Только чтение MCC** | Просмотр всех клиентских аккаунтов | Мониторинг без возможности изменений |

### 2.3 Бизнес-правила ролей

**BR-ROLE-001**: Пользователь может выдавать права только своего уровня или ниже.

**BR-ROLE-002**: Для выдачи Admin-доступа необходимо самому иметь Admin-права.

**BR-ROLE-003**: Клиентский аккаунт может иметь только одного владельца (Owner) среди MCC.

**BR-ROLE-004**: Рекомендуется иметь минимум двух администраторов на случай потери доступа.

**BR-ROLE-005**: Права назначаются на уровне всего аккаунта — невозможно ограничить доступ к отдельным кампаниям.

## 3. Сценарии аутентификации

### 3.1 Вход в систему

#### User Story: US-AUTH-001 — Базовый вход
```
КАК рекламодатель
Я ХОЧУ войти в Google Ads через свой Google Account
ЧТОБЫ управлять рекламными кампаниями
```

**Предусловия:**
- У пользователя есть активный Google Account
- Аккаунт Google Ads связан с этим Google Account

**Основной сценарий:**
1. Пользователь переходит на ads.google.com
2. Система перенаправляет на страницу входа Google
3. Пользователь вводит email
4. Пользователь вводит пароль
5. [Опционально] Пользователь проходит 2FA
6. Система проверяет права доступа
7. Пользователь попадает в интерфейс Google Ads

**Альтернативные сценарии:**
- 4a. Неверный пароль → показ ошибки, предложение восстановления
- 5a. 2FA обязательна, но не настроена → перенаправление на настройку
- 6a. Аккаунт заблокирован → показ уведомления о блокировке

### 3.2 Двухфакторная аутентификация (2-Step Verification)

#### User Story: US-AUTH-002 — Настройка 2FA
```
КАК администратор аккаунта
Я ХОЧУ включить двухфакторную аутентификацию
ЧТОБЫ защитить аккаунт от несанкционированного доступа
```

**Доступные методы 2FA:**
| Метод | Уровень безопасности | Описание |
|-------|---------------------|----------|
| **Passkeys** | Высший | Биометрия (отпечаток, лицо) или PIN устройства |
| **Аппаратный ключ безопасности** | Высокий | Физическое устройство (YubiKey, Titan) |
| **Google Authenticator** | Высокий | TOTP-коды в приложении |
| **SMS-код** | Средний | Код в текстовом сообщении (уязвим к SIM-свапу) |
| **Голосовой звонок** | Средний | Код через голосовой вызов |

**Бизнес-правила 2FA:**

**BR-2FA-001**: Администратор MCC может сделать 2FA обязательной для всех пользователей аккаунта.

**BR-2FA-002**: При включении обязательной 2FA все пользователи без настроенной 2FA теряют доступ до её настройки.

**BR-2FA-003**: При смене телефона пользователь должен перенести коды Google Authenticator на новое устройство.

**BR-2FA-004**: Доверенные устройства можно пометить для пропуска повторной 2FA-проверки.

#### User Story: US-AUTH-003 — Обязательная 2FA для команды
```
КАК администратор MCC
Я ХОЧУ требовать 2FA от всех пользователей
ЧТОБЫ обеспечить безопасность клиентских аккаунтов
```

**Сценарий:**
1. Администратор переходит в Tools → Account Access
2. Включает опцию "Require 2-Step Verification"
3. Система отправляет уведомление всем пользователям
4. Пользователи без 2FA должны настроить её для доступа

## 4. Управление доступом к аккаунту

### 4.1 Приглашение пользователя

#### User Story: US-ACCESS-001 — Приглашение нового пользователя
```
КАК администратор аккаунта
Я ХОЧУ пригласить нового пользователя
ЧТОБЫ он мог работать с рекламными кампаниями
```

**Основной сценарий:**
1. Администратор переходит в Admin → Access and Security
2. Нажимает кнопку "+" для добавления пользователя
3. Вводит email приглашаемого
4. Выбирает уровень доступа (Admin/Standard/Read-only/Billing/Email-only)
5. [Опционально] Устанавливает срок истечения доступа
6. Нажимает "Send invitation"
7. Система отправляет приглашение на email
8. Приглашённый отображается в разделе "Pending invitations"

**Состояния приглашения:**
```
[Создано] → [Отправлено] → [Принято] / [Отклонено] / [Истекло]
                ↓
           [Отозвано]
```

### 4.2 Принятие приглашения

#### User Story: US-ACCESS-002 — Принятие доступа
```
КАК приглашённый пользователь
Я ХОЧУ принять приглашение в Google Ads аккаунт
ЧТОБЫ начать работу с рекламой
```

**Сценарий:**
1. Пользователь получает email с приглашением
2. Кликает на ссылку в письме
3. Авторизуется в Google Account (или создаёт новый)
4. Подтверждает принятие доступа
5. Доступ активируется мгновенно

**Бизнес-правила приглашений:**

**BR-INV-001**: Приглашение можно принять с любого email, связанного с Google Account (основного или альтернативного).

**BR-INV-002**: Статус приглашения обновляется в течение 24 часов после принятия.

**BR-INV-003**: Администратор может отозвать приглашение до его принятия.

### 4.3 Запрос доступа

#### User Story: US-ACCESS-003 — Запрос доступа к аккаунту
```
КАК агентство/подрядчик
Я ХОЧУ запросить доступ к аккаунту клиента
ЧТОБЫ управлять его рекламой
```

**Предусловия:**
- Запрашивающий знает 10-значный номер аккаунта клиента

**Сценарий:**
1. Агентство вводит номер аккаунта клиента
2. Выбирает запрашиваемый уровень доступа
3. Отправляет запрос
4. Владелец аккаунта получает уведомление
5. Владелец одобряет или отклоняет запрос
6. Запрашивающий получает уведомление о решении

### 4.4 Отзыв доступа

#### User Story: US-ACCESS-004 — Отзыв доступа сотрудника
```
КАК администратор
Я ХОЧУ отозвать доступ уволенного сотрудника
ЧТОБЫ защитить данные аккаунта
```

**Бизнес-правила отзыва:**

**BR-REV-001**: Отзыв доступа происходит мгновенно.

**BR-REV-002**: Нельзя отозвать доступ у последнего администратора аккаунта.

**BR-REV-003**: При отзыве доступа владельца MCC к клиентскому аккаунту необходимо назначить нового владельца.

## 5. Верификация рекламодателя

### 5.1 Обязательная верификация

#### User Story: US-VERIF-001 — Прохождение верификации
```
КАК рекламодатель
Я ХОЧУ пройти верификацию
ЧТОБЫ запускать рекламу без ограничений
```

**Типы верификации:**

| Тип | Для кого | Требуемые документы |
|-----|----------|---------------------|
| **Верификация личности** | Физические лица, ИП | Государственный ID (паспорт, водительские права) |
| **Верификация бизнеса** | Юридические лица | Регистрационные документы + ID представителя |
| **Расширенная верификация** | Финансовые услуги, медицина | Дополнительные лицензии и сертификаты |

### 5.2 Процесс верификации

**Этапы:**
```
[Уведомление] → [Начало верификации] → [Загрузка документов] → [Проверка Google] → [Завершено/Отклонено]
     ↓                                                              ↓
30 дней на старт                                           3-5 рабочих дней
     ↓
30 дней на завершение
```

**Бизнес-правила верификации:**

**BR-VERIF-001**: После получения уведомления есть 30 дней на начало верификации.

**BR-VERIF-002**: После начала верификации есть ещё 30 дней на её завершение.

**BR-VERIF-003**: Незавершённая верификация приводит к приостановке показа рекламы.

**BR-VERIF-004**: Данные в документах должны точно совпадать с данными в платёжном профиле.

**BR-VERIF-005**: Повторная верификация требуется при существенных изменениях аккаунта (смена биллинга, адреса).

### 5.3 Требования к документам

**Для организаций (США):**
- Документы IRS (CP575, 147C, Forms 8871, 990)
- Certificate of Business Incorporation
- SEC filings (10-K, 10-Q, 8-K)
- Бизнес-кредитные отчёты (Experian, Equifax, TransUnion)

**Для физических лиц:**
- Государственный ID с фотографией
- Документ должен быть читаемым (не размытым)
- Имя должно совпадать с данными аккаунта

**Частые ошибки:**
- Размытые или нечитаемые сканы документов
- Несовпадение имён между документами и аккаунтом
- Несоответствие платёжной информации

## 6. Верификация платёжных методов

### 6.1 Добавление способа оплаты

#### User Story: US-PAY-001 — Добавление карты
```
КАК рекламодатель
Я ХОЧУ добавить банковскую карту
ЧТОБЫ оплачивать рекламу
```

**Поддерживаемые методы:**
- Кредитные/дебетовые карты (Visa, MasterCard, UnionPay)
- Виртуальные карты
- Банковский счёт (прямое списание)
- Ежемесячное выставление счетов (для крупных рекламодателей)

### 6.2 Процесс верификации карты

**Сценарий:**
1. Пользователь добавляет данные карты
2. Google списывает тестовую сумму (около $1)
3. Пользователь подтверждает списание
4. Карта верифицирована

**Для банковского счёта:**
1. Пользователь вводит реквизиты счёта
2. Google делает контрольный депозит ($0.15-$1.15) в течение 3-5 дней
3. Пользователь вводит точную сумму депозита в Google Ads
4. Счёт верифицирован

**Бизнес-правила платежей:**

**BR-PAY-001**: Должен быть хотя бы один основной способ оплаты.

**BR-PAY-002**: Рекомендуется добавить резервный способ оплаты.

**BR-PAY-003**: Для EEA требуется дополнительная аутентификация (PSD2).

**BR-PAY-004**: Ежемесячное выставление счетов требует Admin-доступа для настройки.

## 7. Восстановление доступа

### 7.1 Восстановление пароля

#### User Story: US-RECOV-001 — Сброс пароля
```
КАК пользователь, забывший пароль
Я ХОЧУ восстановить доступ к аккаунту
ЧТОБЫ продолжить работу с рекламой
```

**Методы восстановления:**
1. Код на резервный телефон
2. Код на резервный email
3. Ответы на контрольные вопросы
4. Подтверждение через доверенное устройство

**Бизнес-правила восстановления:**

**BR-RECOV-001**: Рекомендуется всегда иметь актуальный резервный телефон и email.

**BR-RECOV-002**: Восстановление проще выполнить с устройства, ранее использовавшегося для входа.

**BR-RECOV-003**: Google может запросить дополнительную верификацию при подозрительной активности.

### 7.2 Восстановление доступа к аккаунту организации

#### User Story: US-RECOV-002 — Восстановление аккаунта после ухода сотрудника
```
КАК владелец бизнеса
Я ХОЧУ восстановить доступ к Google Ads
ЧТОБЫ продолжить рекламные кампании после ухода менеджера
```

**Сценарий:**
1. Владелец обращается в поддержку Google Ads
2. Предоставляет доказательства владения бизнесом
3. Google верифицирует информацию
4. Доступ передаётся новому администратору

**BR-RECOV-004**: Только пользователи с Admin-доступом могут реактивировать отменённый аккаунт.

## 8. Блокировка и приостановка аккаунта

### 8.1 Причины блокировки

| Категория | Примеры | Возможность восстановления |
|-----------|---------|---------------------------|
| **Нарушение политик** | Запрещённый контент, мошенничество | Через апелляцию |
| **Подозрительная активность** | Необычные платежи, массовые изменения | После верификации |
| **Неоплата** | Просроченные платежи | После погашения долга |
| **Грубые нарушения** | Фишинг, контрафакт, незаконная деятельность | Обычно без восстановления |

### 8.2 Система страйков

```
[1-й страйк] → Предупреждение
     ↓
[2-й страйк] → Временные ограничения
     ↓
[3-й страйк] → Приостановка аккаунта
```

**Бизнес-правила блокировки:**

**BR-SUSP-001**: Страйки выдаются за повторные нарушения одной и той же политики.

**BR-SUSP-002**: Максимум 3 страйка по одной политике до блокировки.

**BR-SUSP-003**: Грубые нарушения приводят к немедленной блокировке без предупреждения.

**BR-SUSP-004**: У грубых нарушений есть только одна попытка апелляции.

### 8.3 Процесс апелляции

#### User Story: US-APPEAL-001 — Подача апелляции
```
КАК заблокированный рекламодатель
Я ХОЧУ подать апелляцию
ЧТОБЫ восстановить работу аккаунта
```

**Этапы:**
```
[Блокировка] → [Исправление нарушений] → [Подача апелляции] → [Рассмотрение 3-5 дней] → [Решение]
                                                                                            ↓
                                                                          [Восстановлен] / [Отказ]
```

**Бизнес-правила апелляции:**

**BR-APP-001**: На подачу апелляции есть 6 месяцев с момента блокировки.

**BR-APP-002**: Среднее время рассмотрения — 3-5 рабочих дней.

**BR-APP-003**: Множественные апелляции по одному случаю снижают приоритет рассмотрения.

**BR-APP-004**: При отклонении апелляции создание новых аккаунтов также будет заблокировано.

**BR-APP-005**: К апелляции рекомендуется прикладывать доказательства (скриншоты, документы, история переписки).

## 9. Интеграция с сервисами Google

### 9.1 Связывание аккаунтов

| Сервис | Требования | Возможности после связывания |
|--------|------------|------------------------------|
| **Google Analytics** | Editor-доступ в GA + Admin в Ads | Импорт конверсий, создание аудиторий |
| **YouTube** | Владение каналом или разрешение | Реклама на основе взаимодействий, аналитика |
| **Merchant Center** | Admin-доступ в обоих сервисах | Shopping-кампании, товарная реклама |
| **Search Console** | Подтверждённый сайт | Данные о поисковых запросах |
| **Google Play** | Аккаунт разработчика | Реклама приложений |

### 9.2 Процесс связывания

#### User Story: US-LINK-001 — Связывание с Merchant Center
```
КАК e-commerce рекламодатель
Я ХОЧУ связать Google Ads с Merchant Center
ЧТОБЫ запускать Shopping-кампании
```

**Сценарий:**
1. В Merchant Center: Settings → Access and Services
2. Выбрать "Add service" → Google Ads
3. Выбрать аккаунт Google Ads для связывания
4. Подтвердить в Google Ads (требуется Admin-доступ)
5. Связь активна

**Бизнес-правила связывания:**

**BR-LINK-001**: Один Merchant Center можно связать с несколькими Google Ads аккаунтами.

**BR-LINK-002**: Один Google Ads можно связать с несколькими Merchant Center.

**BR-LINK-003**: Для связывания YouTube-канала владелец канала должен дать разрешение.

**BR-LINK-004**: Связывание требует Admin-доступа в Google Ads.

## 10. Manager Account (MCC)

### 10.1 Структура MCC

```
[Корневой MCC]
     ├── [Под-MCC: Регион 1]
     │        ├── Клиент A
     │        └── Клиент B
     ├── [Под-MCC: Регион 2]
     │        └── Клиент C
     └── [Клиент D] (прямое подключение)
```

### 10.2 Владение клиентскими аккаунтами

**Типы связи:**
| Тип | Описание | Контроль |
|-----|----------|----------|
| **Владелец (Owner)** | Полный контроль, включая billing | Может отключить другие MCC |
| **Менеджер** | Управление кампаниями | Ограниченные права |

**Бизнес-правила MCC:**

**BR-MCC-001**: Клиентский аккаунт может иметь только одного владельца.

**BR-MCC-002**: Владелец имеет полный административный доступ и доступ к данным.

**BR-MCC-003**: Можно создавать иерархию до 5 уровней вложенности MCC.

**BR-MCC-004**: MCC-администратор может требовать 2FA для всех пользователей всех клиентских аккаунтов.

## 11. Безопасность сессий

### 11.1 Управление сессиями

**Параметры сессии:**
- Длительность веб-сессии по умолчанию: 14 дней
- Сессия Admin Console: 1 час (не изменяется)
- Возможность настройки для Google Workspace организаций

**Бизнес-правила сессий:**

**BR-SESS-001**: Администратор Workspace может ограничить длительность сессии для повышения безопасности.

**BR-SESS-002**: Для высокочувствительных данных рекомендуется сессия 5-15 минут.

**BR-SESS-003**: Мобильные приложения не подчиняются настройкам длительности сессии.

### 11.2 Рекомендации по безопасности

1. Включить 2-Step Verification
2. Использовать уникальный пароль
3. Регулярно проверять список пользователей с доступом
4. Настроить резервные способы восстановления
5. Не делиться паролем от Google Account
6. Использовать актуальную версию браузера

## 12. Состояния аккаунта

### 12.1 Диаграмма состояний

```
[Создание] → [Активный] ←→ [На модерации]
                 ↓              ↓
          [Приостановлен] ← [Ограничен]
                 ↓
          [Заблокирован] → [Отменён]
                 ↓
            [Восстановлен] (через апелляцию)
```

### 12.2 Описание состояний

| Состояние | Описание | Возможные действия |
|-----------|----------|-------------------|
| **Активный** | Полнофункциональный аккаунт | Все операции доступны |
| **На модерации** | Проверка кампаний или верификация | Ожидание решения Google |
| **Ограничен** | Частичные ограничения | Исправление нарушений |
| **Приостановлен** | Реклама не показывается | Апелляция, оплата долга |
| **Заблокирован** | Доступ заблокирован | Апелляция |
| **Отменён** | Аккаунт закрыт пользователем | Реактивация (Admin) |

### 13.1 Отслеживаемые события

| Категория | События |
|-----------|---------|
| **Аутентификация** | Вход, выход, неудачные попытки входа |
| **Управление доступом** | Приглашения, изменения ролей, отзыв доступа |
| **Биллинг** | Изменения платёжных методов, транзакции |
| **Связывание** | Подключение/отключение MCC, интеграций |
| **Верификация** | Подача документов, результаты проверки |

### 13.2 История изменений

**Доступ к истории:**
- Admin и Standard пользователи могут просматривать историю изменений
- Хранение истории: зависит от политики Google
- Экспорт: доступен через отчёты

## 15. Глоссарий

| Термин | Определение |
|--------|-------------|
| **MCC (Manager Account)** | Управляющий аккаунт для работы с несколькими клиентскими аккаунтами |
| **2-Step Verification** | Двухфакторная аутентификация Google |
| **Passkeys** | Аутентификация через биометрию или PIN устройства |
| **OAuth 2.0** | Протокол авторизации для доступа к Google Ads |
| **Страйк** | Предупреждение за нарушение политики |
| **Верификация рекламодателя** | Проверка личности/бизнеса для подтверждения легитимности |
| **Owner** | Владелец клиентского аккаунта (максимум один на аккаунт) |
