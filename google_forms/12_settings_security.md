# Настройки и безопасность

## Описание

Модуль "Настройки и безопасность" обеспечивает комплексную защиту данных, собранных через Google Forms, и предоставляет владельцам форм широкий спектр инструментов для управления конфиденциальностью, контроля доступа и соответствия требованиям законодательства о защите персональных данных. Модуль включает настройки ограничения доступа к формам (публичный доступ, ограничение по домену организации, требование авторизации), сбор и верификацию email-адресов, защиту от спама и ботов через встроенные механизмы валидации, управление хранением и удалением данных в соответствии с политиками retention, а также обеспечение соответствия GDPR, CCPA и другим стандартам защиты данных. Система использует сквозное шифрование (TLS 1.3+ для передачи данных и AES-256 для хранения), поддерживает двухфакторную аутентификацию (2FA) для владельцев форм, предоставляет детальные логи доступа и активности, а также интегрируется с Google Workspace для централизованного управления безопасностью на уровне организации.

## Роли пользователей

- **Владелец формы** - создатель формы с полными правами на настройки безопасности, управление доступом, экспорт и удаление данных
- **Редактор формы** - имеет доступ к просмотру настроек безопасности, но не может изменять критические параметры (требование авторизации, ограничения домена)
- **Администратор Google Workspace** - управляет политиками безопасности на уровне организации, настройками retention, DLP-правилами и compliance
- **Респондент** - пользователь, заполняющий форму, права которого определяются настройками доступа (анонимный или авторизованный)
- **Внешний аудитор** - роль для compliance-проверок с доступом к логам и настройкам безопасности (только для Workspace Enterprise)

## Функциональные требования

### FR-SEC-001: Ограничение доступа к форме

**Описание:** Владелец формы может настроить уровень доступа к форме, определив, кто может просматривать и заполнять форму: любой пользователь интернета, только пользователи с ссылкой, только авторизованные пользователи Google или только пользователи определенной организации (Google Workspace).

**Роли:** Владелец формы, Администратор Google Workspace

**Предусловия:**
- Форма создана и открыта в режиме редактирования
- Пользователь имеет права владельца формы
- Для ограничений по организации: форма создана в аккаунте Google Workspace

**Основной сценарий:**
1. Владелец формы открывает форму в режиме редактирования
2. Пользователь кликает на иконку "Settings" (шестеренка) в правом верхнем углу
3. Система открывает панель настроек с тремя вкладками: "General", "Presentation", "Quizzes"
4. Во вкладке "General" в разделе "Responses" пользователь видит опции:
   - "Restrict to [organization name] users" (чекбокс) - только для Google Workspace
   - "Require sign in" (включается автоматически при выборе ограничения по организации)
5. Пользователь активирует чекбокс "Restrict to [organization name] users"
6. Система автоматически активирует опцию "Require sign in"
7. Система отображает предупреждение: "Only users in [organization name] will be able to respond to this form"
8. Пользователь кликает "Save" для сохранения настроек
9. Система применяет ограничения доступа к форме
10. При попытке доступа к форме с внешнего аккаунта:
    - Система проверяет домен email пользователя
    - Если домен не соответствует организации, система показывает сообщение: "You need permission. This form can only be viewed by users in the [organization name] organization"
    - Предлагается войти через другой аккаунт или запросить доступ

**Альтернативные сценарии:**
- Сценарий А (Публичный доступ): Все чекбоксы ограничений отключены - форма доступна любому пользователю с ссылкой
- Сценарий Б (Требование авторизации без ограничения домена): Включен только "Require sign in" - форма доступна любому пользователю Google, но требуется вход в аккаунт
- Сценарий В (Настройка через Google Drive): Владелец может управлять доступом через стандартные настройки sharing Google Drive, где форма хранится как файл
- Сценарий Г (Временное ограничение доступа): Владелец может добавить дополнительные ограничения через Google Apps Script (например, доступ только в определенные даты)

**Бизнес-правила:**
- BR-001: Ограничение по домену организации доступно только для аккаунтов Google Workspace (Business Standard, Business Plus, Enterprise)
- BR-002: При включении "Restrict to organization" автоматически включается "Require sign in" и не может быть отключен
- BR-003: Изменение настроек доступа не влияет на уже собранные ответы
- BR-004: URL формы остается тем же независимо от настроек доступа (изменяется только логика проверки прав)
- BR-005: Администратор Workspace может принудительно применить ограничения для всех форм в организации через Admin Console
- BR-006: Настройки sharing в Google Drive имеют приоритет над настройками формы (если файл формы не имеет прав доступа, форма не откроется)
- BR-007: При публикации формы через "Send" система автоматически проверяет настройки доступа и предупреждает о возможных конфликтах

**Результат:** Доступ к форме ограничен согласно выбранным настройкам, неавторизованные или внешние пользователи не могут просматривать и заполнять форму

### FR-SEC-002: Сбор email-адресов респондентов

**Описание:** Владелец формы может активировать автоматический сбор email-адресов всех респондентов, что позволяет идентифицировать пользователей, отправлять подтверждения о получении ответов и связываться с респондентами для уточнения информации.

**Роли:** Владелец формы, Редактор формы

**Предусловия:**
- Форма создана и открыта для редактирования
- Включена опция "Require sign in" (сбор email возможен только при авторизации)

**Основной сценарий:**
1. Владелец формы открывает Settings > General
2. В разделе "Responses" пользователь видит опцию "Collect email addresses" (чекбокс)
3. Пользователь активирует чекбокс "Collect email addresses"
4. Система автоматически:
   - Активирует "Require sign in" (если не было включено)
   - Добавляет информационное сообщение в начало формы: "This form is collecting email addresses"
   - Создает скрытую колонку "Email Address" в таблице ответов
5. Пользователь может активировать дополнительную опцию "Response receipts" (выпадающее меню):
   - "Off" - не отправлять подтверждения
   - "Respondents can request a copy" - респондент может запросить копию своего ответа
   - "Always send" - автоматически отправлять копию всем респондентам
6. Пользователь сохраняет настройки (кнопка "Save")
7. При заполнении формы респондентом:
   - Система автоматически захватывает email из Google аккаунта пользователя
   - Email отображается в начале формы: "Your email ([email]) will be collected when you submit this form"
   - Email сохраняется в отдельной колонке таблицы ответов
8. Если включены Response receipts:
   - После отправки формы система отправляет email на адрес респондента
   - Email содержит копию всех ответов и timestamp отправки
   - В теме письма: "[Form Title] - Your response"

**Альтернативные сценарии:**
- Сценарий А (Ручной ввод email): Владелец может добавить отдельный вопрос типа "Short answer" с валидацией email, но это не заменяет автоматический сбор
- Сценарий Б (Скрытый сбор email): В Google Workspace администратор может настроить автоматический сбор email без явного уведомления респондентов (требует согласия и соблюдения GDPR)
- Сценарий В (Экспорт email-адресов): Владелец может экспортировать список email через Google Sheets (столбец "Email Address")
- Сценарий Г (Ограничение одного ответа по email): При включении "Limit to 1 response" система использует email как уникальный идентификатор

**Исключительные ситуации:**
- Исключение А (Email не доступен): Если пользователь использует аккаунт без email (невозможно для Google), система запрещает отправку формы
- Исключение Б (Email скрыт в профиле): Система всегда получает email из Google Account API независимо от настроек приватности профиля
- Исключение В (Ошибка отправки receipt): Если письмо-подтверждение не отправлено, система не блокирует сохранение ответа, но логирует ошибку

**Бизнес-правила:**
- BR-008: Сбор email возможен только при включенной авторизации ("Require sign in")
- BR-009: Email-адреса хранятся в том же Google Sheets, что и ответы, в отдельной колонке
- BR-010: Владелец формы всегда видит email респондентов (даже если респондент скрыл его в профиле)
- BR-011: Response receipts отправляются с адреса noreply@google.com с указанием владельца формы в поле "Reply-To"
- BR-012: При удалении ответа из Google Sheets email-адрес также удаляется (не хранится отдельно)
- BR-013: Система не отправляет marketing-emails или spam на собранные адреса (контролируется Google Terms of Service)
- BR-014: Для соблюдения GDPR владелец формы должен включить уведомление о сборе email в описании формы

**Результат:** Email-адреса всех респондентов автоматически собираются и сохраняются в таблице ответов, опционально отправляются подтверждения о получении ответов

### FR-SEC-003: Ограничение количества ответов от одного пользователя

**Описание:** Владелец формы может ограничить возможность многократной отправки ответов, разрешив каждому пользователю отправить форму только один раз (на основе Google аккаунта).

**Роли:** Владелец формы, Редактор формы

**Предусловия:**
- Форма создана и открыта для редактирования
- Включена опция "Require sign in" (ограничение работает только для авторизованных пользователей)

**Основной сценарий:**
1. Владелец формы открывает Settings > General
2. В разделе "Responses" пользователь видит опцию "Limit to 1 response" (чекбокс)
3. Пользователь активирует чекбокс "Limit to 1 response"
4. Система автоматически:
   - Активирует "Require sign in" (если не было включено)
   - Добавляет информационное сообщение в форму: "You can submit this form only once"
   - Создает внутренний список Google Account IDs, отправивших ответы
5. Пользователь сохраняет настройки
6. При первой отправке формы респондентом:
   - Система сохраняет Google Account ID пользователя в базу данных формы
   - Ответ успешно отправляется
   - Система показывает сообщение: "Your response has been recorded"
7. При повторной попытке открыть форму:
   - Система проверяет Google Account ID пользователя в базе
   - Обнаруживает, что ответ уже был отправлен
   - Отображает сообщение: "You've already responded to this form. You can submit only 1 response."
   - Показывает опции:
     - "Submit another response" (если владелец разрешил редактирование)
     - "View your response" (если включено "Respondents can see summary charts and text responses")
8. Если включена опция "Respondents can edit after submit":
   - Пользователь может нажать "Edit your response"
   - Система загружает ранее отправленный ответ для редактирования
   - После редактирования создается новая версия (старая перезаписывается)

**Альтернативные сценарии:**
- Сценарий А (Разрешить редактирование ответа): Владелец включает "Respondents can edit after submit" - респонденты могут вернуться и изменить свой ответ
- Сценарий Б (Удаление ответа для повторной отправки): Владелец может вручную удалить ответ из Google Sheets и из списка отправивших (через Apps Script или вручную)
- Сценарий В (Обход ограничения через разные аккаунты): Пользователь может отправить несколько ответов, используя разные Google аккаунты (система не определяет физическое лицо, только аккаунт)
- Сценарий Г (Анонимные формы без ограничения): Если "Require sign in" отключен, ограничение на 1 ответ не работает (пользователь может отправить сколько угодно)

**Исключительные ситуации:**
- Исключение А (Изменение настройки после получения ответов): Если владелец включает "Limit to 1 response" после получения нескольких ответов от одного пользователя, система не удаляет дубликаты, но блокирует новые отправки
- Исключение Б (Удаление аккаунта Google): Если пользователь удалил Google аккаунт и создал новый с тем же email, система считает это новым аккаунтом и разрешает отправку
- Исключение В (Конфликт с Apps Script): Если форма использует кастомные скрипты для обработки ответов, ограничение может быть обойдено через programmatic submission

**Бизнес-правила:**
- BR-015: Ограничение работает только при включенной авторизации ("Require sign in")
- BR-016: Система идентифицирует пользователей по Google Account ID (внутренний уникальный идентификатор), а не по email
- BR-017: Изменение email пользователя не позволяет обойти ограничение (используется Account ID)
- BR-018: Владелец формы может вручную сбросить список отправивших через удаление файла cookie-хранилища (требует технических знаний)
- BR-019: При включении "Respondents can edit after submit" пользователь видит свой предыдущий ответ и может изменить его неограниченное количество раз
- BR-020: Система не хранит историю изменений ответов (только последняя версия)
- BR-021: Ограничение применяется к URL формы, а не к копиям - при создании копии формы список отправивших не копируется

**Результат:** Каждый авторизованный пользователь может отправить форму только один раз, повторные попытки блокируются с информативным сообщением

### FR-SEC-004: Защита от спама и ботов

**Описание:** Система автоматически применяет механизмы защиты от спама, ботов и автоматизированных массовых отправок через встроенные алгоритмы валидации, rate limiting и опциональную интеграцию с reCAPTCHA для подозрительных активностей.

**Роли:** Система (автоматически), Владелец формы (настройка дополнительных параметров)

**Предусловия:**
- Форма опубликована и доступна для заполнения
- Включен публичный доступ (без требования авторизации) - максимальный риск спама

**Основной сценарий (автоматическая защита):**
1. Респондент открывает публичную форму
2. Система в фоновом режиме выполняет проверки:
   - Анализ User-Agent браузера (определение ботов по известным сигнатурам)
   - Проверка IP-адреса на наличие в списках spam-сетей и VPN/proxy
   - Анализ скорости заполнения формы (слишком быстрое заполнение = подозрительная активность)
   - Проверка паттернов ввода (copy-paste всех полей, идентичные ответы от разных IP)
   - Анализ JavaScript-выполнения (боты часто не выполняют JS)
3. При обнаружении подозрительной активности:
   - Система инкрементирует счетчик "подозрительных действий" для данного IP/session
   - Если счетчик превышает пороговое значение (3-5 подозрительных признаков), система:
     - Отображает reCAPTCHA challenge (Google reCAPTCHA v3 или v2 fallback)
     - Пользователь должен пройти проверку "I'm not a robot"
     - После успешного прохождения - форма отправляется
     - При неуспешном прохождении - отображается ошибка: "Unable to submit form. Please try again later."
4. Система применяет rate limiting на уровне IP-адреса:
   - Максимум 20 отправок с одного IP в течение 10 минут
   - При превышении лимита: блокировка на 1 час с сообщением "Too many requests. Please try again later."
5. Ответы от подозрительных источников помечаются внутренним флагом (не видимым владельцу напрямую)
6. При массовом спаме (более 100 ответов за 5 минут):
   - Система автоматически приостанавливает прием ответов
   - Отправляет email владельцу формы: "Unusual activity detected on your form"
   - Предлагает включить "Require sign in" для защиты

**Альтернативные сценарии:**
- Сценарий А (Ручная активация reCAPTCHA): Владелец может принудительно включить reCAPTCHA для всех респондентов через настройки (доступно для Google Workspace Enterprise)
- Сценарий Б (Защита через авторизацию): Включение "Require sign in" автоматически снижает риск спама (боты не могут массово создавать Google аккаунты)
- Сценарий В (Валидация ответов через Apps Script): Владелец может настроить кастомные правила фильтрации через Google Apps Script (например, проверка текста на стоп-слова, валидация email-доменов)
- Сценарий Г (Блокировка по географии): Для Workspace Enterprise доступна настройка региональных ограничений (блокировка доступа из определенных стран)

**Исключительные ситуации:**
- Исключение А (Ложные срабатывания): Легитимный пользователь может быть заблокирован из-за быстрого заполнения или использования VPN - решение: пройти reCAPTCHA
- Исключение Б (Обход reCAPTCHA ботами): Продвинутые боты могут обходить reCAPTCHA v3 - система автоматически переключается на v2 (визуальный challenge)
- Исключение В (DDoS-атака на форму): При массированной атаке (тысячи запросов в секунду) Google Cloud автоматически применяет защиту уровня инфраструктуры (429 Too Many Requests)
- Исключение Г (Spam через API): При использовании Google Forms API spam может обойти фронтенд-защиту - применяется rate limiting на уровне API keys

**Бизнес-правила:**
- BR-022: reCAPTCHA автоматически интегрирован в Google Forms и не требует отдельной настройки
- BR-023: Система использует Google reCAPTCHA v3 (невидимый) по умолчанию, с fallback на v2 (чекбокс) при необходимости
- BR-024: Rate limiting применяется на уровне IP-адреса, но не блокирует корпоративные сети (определяется по ASN)
- BR-025: Владелец формы не может отключить встроенную защиту от спама
- BR-026: Подозрительные ответы не помечаются явно в Google Sheets, но доступны через API для анализа
- BR-027: При обнаружении массового спама Google автоматически уведомляет владельца и предлагает меры защиты
- BR-028: Система не удаляет автоматически spam-ответы, но может их скрывать (владелец решает, удалять ли)
- BR-029: Для форм с "Require sign in" защита от спама минимальная (Google аккаунты считаются доверенными)

**Результат:** Форма защищена от автоматизированных спам-атак и ботов, легитимные пользователи могут заполнять форму без помех, подозрительные активности блокируются или требуют дополнительной верификации

### FR-SEC-005: Шифрование данных при передаче и хранении

**Описание:** Все данные, передаваемые между браузером респондента и серверами Google Forms, а также хранящиеся на серверах Google Cloud, защищены современными стандартами шифрования для обеспечения конфиденциальности и целостности данных.

**Роли:** Система (автоматически), Администратор Google Workspace (управление ключами для Enterprise)

**Предусловия:**
- Форма создана и доступна через интернет
- Респондент использует современный браузер с поддержкой TLS 1.2+

**Основной сценарий (автоматическое шифрование):**
1. Респондент открывает форму через HTTPS (forms.google.com)
2. Система устанавливает защищенное соединение:
   - Протокол: TLS 1.3 (Transport Layer Security, fallback на TLS 1.2 для старых браузеров)
   - Шифрование: AES-256-GCM или ChaCha20-Poly1305 (cipher suite выбирается автоматически)
   - Сертификат: Google Trust Services (GTS Root R1), проверка цепочки сертификатов
3. Респондент заполняет форму и нажимает "Submit"
4. Данные формы:
   - Сериализуются в JSON-формат
   - Шифруются на стороне клиента перед отправкой (TLS encryption)
   - Передаются на серверы Google через защищенное HTTPS-соединение
   - HTTP Strict Transport Security (HSTS) предотвращает downgrade-атаки на HTTP
5. На стороне сервера Google Forms:
   - Данные дешифруются из транспортного шифрования
   - Сохраняются в Google Cloud Storage с шифрованием at-rest:
     - Алгоритм: AES-256 (Advanced Encryption Standard)
     - Ключи шифрования: управляются Google Key Management Service (KMS)
     - Разделение ключей: каждый файл данных (chunk) шифруется отдельным Data Encryption Key (DEK)
     - DEK сам шифруется Key Encryption Key (KEK), хранящимся в Google KMS
6. При доступе владельца к ответам:
   - Данные дешифруются на сервере
   - Передаются в браузер владельца через защищенное TLS-соединение
   - Отображаются в Google Sheets или интерфейсе Forms

**Альтернативные сценарии:**
- Сценарий А (Customer-Managed Encryption Keys - CMEK): Для Google Workspace Enterprise Plus владелец организации может использовать собственные ключи шифрования:
  1. Администратор генерирует ключи в Google Cloud KMS или внешнем HSM
  2. Настраивает политику использования ключей для Google Forms через Admin Console
  3. Все данные форм в организации шифруются этими ключами
  4. Google не имеет доступа к ключам (zero-knowledge encryption для данных at-rest)
- Сценарий Б (Client-Side Encryption - CSE): Для максимальной конфиденциальности (Workspace Enterprise Plus):
  1. Данные шифруются на стороне браузера респондента перед отправкой
  2. Ключи хранятся в организации клиента (не на серверах Google)
  3. Google Forms хранит зашифрованные данные, но не может их прочитать
  4. Владелец формы дешифрует данные локально с помощью своих ключей
- Сценарий В (Шифрование файлов, загруженных через форму): Файлы, загруженные респондентами (через File Upload вопросы), хранятся в Google Drive владельца формы с тем же уровнем шифрования (AES-256 at-rest)

**Исключительные ситуации:**
- Исключение А (Устаревший браузер без TLS 1.2+): Система отказывает в доступе с сообщением "Your browser is not supported. Please update to the latest version."
- Исключение Б (Man-in-the-Middle атака): При обнаружении подозрительного сертификата браузер показывает предупреждение безопасности, соединение блокируется
- Исключение В (Потеря ключей CMEK): Если организация потеряла customer-managed ключи, данные невозможно восстановить (Google не имеет backup ключей)

**Бизнес-правила:**
- BR-030: Все соединения принудительно используют HTTPS, HTTP-запросы автоматически перенаправляются на HTTPS (301 Permanent Redirect)
- BR-031: Google Forms использует TLS 1.3 по умолчанию, с fallback на TLS 1.2 для совместимости
- BR-032: Сертификаты обновляются автоматически до истечения срока действия
- BR-033: Шифрование at-rest (AES-256) применяется ко всем данным: ответам, загруженным файлам, настройкам форм
- BR-034: Ключи шифрования ротируются автоматически каждые 90 дней (Google-managed keys)
- BR-035: CMEK и CSE доступны только для Google Workspace Enterprise Plus
- BR-036: Метаданные (timestamp, IP-адреса, User-Agent) также шифруются at-rest
- BR-037: Данные в Google Sheets, связанные с формой, наследуют те же настройки шифрования
- BR-038: Backup-копии данных также шифруются AES-256

**Результат:** Все данные форм защищены сквозным шифрованием при передаче (TLS 1.3) и в покое (AES-256), обеспечивая конфиденциальность и защиту от несанкционированного доступа

### FR-SEC-006: Управление хранением и retention данных

**Описание:** Владелец формы и администраторы Google Workspace могут управлять политиками хранения данных, настраивать автоматическое удаление ответов по истечении определенного срока и экспортировать данные для архивирования в соответствии с требованиями законодательства и внутренними политиками организации.

**Роли:** Владелец формы, Администратор Google Workspace, Compliance-офицер

**Предусловия:**
- Форма создана и имеет собранные ответы
- Для настройки retention на уровне организации: Google Workspace Business Standard или выше с доступом к Google Vault

**Основной сценарий (владелец формы):**
1. Владелец формы открывает Google Forms и выбирает форму
2. Переходит в раздел "Responses" для просмотра ответов
3. Видит информацию о количестве ответов и дате последнего обновления
4. Для удаления всех ответов:
   - Кликает меню (три точки) в правом верхнем углу раздела "Responses"
   - Выбирает "Delete all responses"
   - Система показывает предупреждение: "This will permanently delete all responses. Are you sure?"
   - Опция "Also delete responses from Google Sheets" (чекбокс)
   - Владелец подтверждает действие
   - Система удаляет все ответы из базы данных формы
   - Если выбрано удаление из Sheets - строки удаляются из связанной таблицы
5. Для выборочного удаления:
   - Владелец открывает Google Sheets со связанными ответами
   - Выбирает строки для удаления (респонденты) и удаляет через контекстное меню
   - Удаление в Sheets не удаляет данные из базы Forms (односторонняя синхронизация)
6. Для настройки автоматического удаления (через Apps Script):
   - Владелец открывает Google Sheets > Extensions > Apps Script
   - Создает скрипт с триггером по времени (time-driven trigger)
   - Скрипт проверяет timestamp каждого ответа и удаляет строки старше N дней
   - Триггер запускается ежедневно

**Сценарий Б (администратор Workspace - Google Vault retention):**
1. Администратор открывает Google Vault (vault.google.com)
2. Переходит в раздел "Retention" > "Create retention rule"
3. Настраивает правило для Google Drive (Forms хранятся как Drive-файлы):
   - Scope: "Specific organizational units" или "All users"
   - Entity: "Drive files"
   - Time period: "Retain for [N days/months/years]" или "Indefinitely"
   - После истечения: "Purge data automatically" или "Keep for hold and audit"
4. Применяет правило к организации
5. Система автоматически:
   - Отслеживает возраст всех ответов в формах
   - По истечении retention period удаляет данные из всех систем (Forms, Sheets, backups)
   - Логирует удаление в Audit Log
6. Для Legal Hold (сохранение данных для судебных разбирательств):
   - Администратор создает "Matter" в Google Vault
   - Добавляет формы конкретных пользователей в Hold
   - Данные сохраняются неограниченно и не могут быть удалены даже владельцем формы

**Альтернативные сценарии:**
- Сценарий В (Экспорт данных перед удалением): Владелец экспортирует ответы в CSV/PDF через Google Sheets перед удалением
- Сценарий Г (Архивирование в Google Cloud Storage): Администратор настраивает автоматический экспорт данных форм в Google Cloud Storage для долгосрочного архивирования
- Сценарий Д (Анонимизация вместо удаления): Скрипт заменяет персональные данные (email, имена) на анонимизированные значения вместо полного удаления (для статистического анализа)

**Исключительные ситуации:**
- Исключение А (Удаление формы с ответами): При удалении файла формы из Google Drive все ответы также удаляются через 30 дней (период Trash)
- Исключение Б (Конфликт retention rules): Если установлено несколько правил с разными периодами, применяется самое длинное (максимальная защита данных)
- Исключение В (Восстановление удаленных ответов): После удаления ответов через "Delete all responses" восстановление невозможно (Google не хранит backup)
- Исключение Г (Legal Hold отменяет удаление): Если на данные наложен Legal Hold, retention policy не применяется до снятия Hold

**Бизнес-правила:**
- BR-039: По умолчанию Google Forms хранит ответы неограниченно долго (до удаления владельцем)
- BR-040: Удаление ответов из Google Sheets не влияет на summary charts и statistics в интерфейсе Forms
- BR-041: Данные в Trash (корзине) хранятся 30 дней, после чего удаляются безвозвратно
- BR-042: Google Vault retention rules применяются только к аккаунтам Google Workspace (недоступно для личных gmail.com)
- BR-043: Минимальный retention period в Vault - 1 день, максимальный - неограниченно (indefinite)
- BR-044: При экспорте данных через Takeout (Google Data Export) включаются все ответы форм в JSON-формате
- BR-045: Автоматическое удаление (purge) происходит в течение 24 часов после истечения retention period
- BR-046: Логи удаления данных сохраняются в Google Admin Audit Log минимум 6 месяцев (для Workspace Enterprise - до 2 лет)
- BR-047: Владелец формы получает email-уведомление перед автоматическим удалением данных (если настроено администратором)

**Результат:** Данные форм хранятся согласно настроенным политикам retention, автоматически удаляются по истечении срока хранения или вручную владельцем, экспортируются для архивирования при необходимости

### FR-SEC-007: Соответствие GDPR и требованиям защиты персональных данных

**Описание:** Google Forms обеспечивает соответствие требованиям Общего регламента по защите данных (GDPR), предоставляя инструменты для уведомления респондентов о сборе данных, управления согласием, обработки запросов на доступ и удаление персональных данных, а также настройки географического расположения хранилищ данных.

**Роли:** Владелец формы (Data Controller), Администратор Google Workspace (Data Controller), Google (Data Processor)

**Предусловия:**
- Форма собирает персональные данные (email, имена, адреса и т.д.)
- Респонденты находятся в ЕС или подпадают под действие GDPR
- Для настройки региона данных: Google Workspace Business Standard или выше

**Основной сценарий (владелец формы - обеспечение compliance):**
1. Владелец формы создает форму для сбора персональных данных
2. Добавляет раздел "Уведомление о конфиденциальности" в описание формы:
   - Цель сбора данных
   - Типы собираемых персональных данных
   - Основание для обработки (согласие, договор, законное право)
   - Период хранения данных
   - Права респондентов (доступ, исправление, удаление, возражение)
   - Контактная информация Data Controller
3. Добавляет обязательный вопрос типа "Checkbox" (согласие):
   - Текст: "I consent to the collection and processing of my personal data as described in the Privacy Notice"
   - Делает вопрос обязательным (Required)
   - Респондент не может отправить форму без согласия
4. Включает "Collect email addresses" для идентификации субъектов данных
5. Настраивает ссылку на полную Privacy Policy в описании формы:
   - Добавляет markdown-ссылку на страницу политики конфиденциальности организации
   - Обеспечивает доступность политики на языке респондентов
6. Обрабатывает запросы субъектов данных (Data Subject Requests):
   - **Право на доступ (Article 15)**: При запросе респондента владелец экспортирует данные из Google Sheets, находит строку с email запрашивающего, отправляет копию данных в течение 30 дней
   - **Право на исправление (Article 16)**: Владелец вручную редактирует данные в Google Sheets или предоставляет респонденту ссылку для редактирования ответа (если включено "Respondents can edit after submit")
   - **Право на удаление (Article 17 - Right to be forgotten)**: Владелец находит и удаляет строку с данными респондента из Google Sheets и базы данных формы
   - **Право на переносимость (Article 20)**: Владелец экспортирует данные респондента в машиночитаемом формате (CSV, JSON)
7. Ведет реестр обработки персональных данных (Record of Processing Activities):
   - Документирует все формы, собирающие персональные данные
   - Указывает категории данных, цели обработки, сроки хранения
   - Хранит документацию для демонстрации compliance при проверке регулятора

**Сценарий Б (администратор Workspace - настройка региона данных):**
1. Администратор открывает Google Admin Console (admin.google.com)
2. Переходит в "Data region" settings
3. Выбирает регион для хранения данных:
   - "European Union" - данные хранятся только в ЕС (соответствие GDPR)
   - "United States" - данные в США (Data Privacy Framework compliance)
   - Другие доступные регионы (зависит от подписки)
4. Применяет настройку для всех сервисов Google Workspace, включая Forms
5. Система автоматически:
   - Мигрирует существующие данные в выбранный регион (в течение 24-48 часов)
   - Обеспечивает, что все новые ответы сохраняются в выбранном регионе
   - Логирует все перемещения данных в Audit Log
6. Настраивает Data Processing Amendment (DPA):
   - Подписывает DPA с Google (доступно в Admin Console)
   - DPA определяет Google как Data Processor, организацию как Data Controller
   - Включает Standard Contractual Clauses (SCC) для трансфера данных за пределы ЕС

**Альтернативные сценарии:**
- Сценарий В (Автоматизация GDPR-запросов): Организация разрабатывает портал для респондентов, где они могут самостоятельно запросить доступ/удаление данных, система обрабатывает запросы через Google Forms API
- Сценарий Г (Анонимизация данных): Владелец формы не собирает email и использует анонимные формы для минимизации GDPR-обязательств (anonymized data не подпадает под GDPR)
- Сценарий Д (Third-party DPA Management): Для больших организаций используется специализированное ПО для управления DPA и GDPR-запросами (интеграция через API)

**Исключительные ситуации:**
- Исключение А (Нарушение GDPR): При несоблюдении требований (отсутствие согласия, игнорирование запросов на удаление) организация может получить штраф до €20 млн или 4% годового оборота
- Исключение Б (Data Breach): При обнаружении утечки данных владелец формы обязан уведомить регулятора в течение 72 часов (Google автоматически уведомляет администраторов Workspace при инцидентах)
- Исключение В (Конфликт с локальными законами): При противоречии GDPR и локального законодательства (например, China Data Law) применяется более строгий стандарт

**Бизнес-правила:**
- BR-048: Google Forms соответствует GDPR через сертификацию ISO 27001, ISO 27018, ISO 27701 и SOC 2 Type II
- BR-049: Google выступает Data Processor, владелец формы - Data Controller (ответственность за compliance на владельце)
- BR-050: Региональное хранение данных доступно для Workspace Business Standard, Business Plus, Enterprise (недоступно для личных аккаунтов)
- BR-051: По умолчанию данные могут храниться в любом регионе Google Cloud (multi-region), настройка региона изменяет это поведение
- BR-052: Google автоматически обрабатывает запросы на экспорт данных через Google Takeout (GDPR Article 20)
- BR-053: Владелец формы должен ответить на Data Subject Request в течение 30 дней (GDPR требование)
- BR-054: Согласие на обработку данных должно быть добровольным, информированным, конкретным и однозначным (GDPR Article 7)
- BR-055: При сборе данных детей младше 16 лет требуется согласие родителей (GDPR Article 8)
- BR-056: Google предоставляет стандартный DPA для всех Workspace-клиентов, доступный в Admin Console
- BR-057: Data breach notification отправляется администратору Workspace в течение 72 часов с момента обнаружения Google

**Результат:** Форма соответствует требованиям GDPR, респонденты уведомлены о сборе данных и дали согласие, владелец формы может обрабатывать запросы субъектов данных, данные хранятся в выбранном регионе

### FR-SEC-008: Аудит и логирование доступа к данным

**Описание:** Система автоматически ведет детальные логи всех действий с формой и ответами, включая доступ к данным, изменения настроек, экспорт ответов и административные операции, что позволяет отслеживать безопасность и соответствие compliance-требованиям.

**Роли:** Владелец формы (базовые логи), Администратор Google Workspace (расширенные логи), Аудитор (чтение логов)

**Предусловия:**
- Форма создана и имеет активность (просмотры, ответы, изменения)
- Для расширенных логов: Google Workspace Business Plus или Enterprise с доступом к Admin Console

**Основной сценарий (владелец формы - базовый аудит):**
1. Владелец формы открывает Google Drive и находит файл формы
2. Кликает правой кнопкой мыши > "View details" (или иконку "i" в правом верхнем углу)
3. Система показывает базовую информацию:
   - "Created": дата и время создания формы
   - "Modified": дата последнего изменения (любого элемента формы)
   - "Opened by me": когда владелец последний раз открывал форму
   - "Owner": email владельца
   - "Viewers": количество пользователей, имеющих доступ
4. Во вкладке "Activity" владелец видит:
   - Timeline событий: "You edited this file", "You shared with [email]", "User [email] viewed this file"
   - Timestamp каждого события
   - Ограниченная история (последние 30 дней для личных аккаунтов)
5. Для просмотра статистики ответов:
   - Открывает форму > вкладка "Responses"
   - Видит график "Response timeline" - количество ответов по дням
   - "Average time to complete": среднее время заполнения формы (доступно для квизов)

**Сценарий Б (администратор Workspace - расширенные логи):**
1. Администратор открывает Google Admin Console (admin.google.com)
2. Переходит в "Reporting" > "Audit" > "Drive log events"
3. Настраивает фильтры:
   - Event type: "View", "Edit", "Share", "Download", "Delete"
   - User: конкретный пользователь или "All users"
   - Date range: период для анализа
   - Search: название формы или form ID
4. Система отображает детальные события:
   - **View events**: Кто и когда открывал форму для просмотра/редактирования
   - **Edit events**: Какие изменения внесены (добавлен вопрос, изменены настройки)
   - **Share events**: С кем была расшарена форма, уровень доступа (viewer, editor)
   - **Download events**: Экспорт ответов (CSV, PDF), кто и когда скачивал
   - **Settings change events**: Изменение настроек безопасности (Require sign in, Limit to 1 response)
5. Для каждого события доступна детальная информация:
   - User email: кто выполнил действие
   - IP address: с какого IP был выполнен доступ
   - User-Agent: браузер и ОС пользователя
   - Timestamp: точное время события (с точностью до секунды)
   - Action details: конкретные изменения (например, "Added question: What is your name?")
6. Администратор может экспортировать логи:
   - В BigQuery для долгосрочного хранения и анализа
   - В CSV для ручного анализа или передачи аудиторам
   - Интеграция с SIEM-системами (Splunk, LogRhythm) через API

**Сценарий В (Google Vault - логи для e-discovery):**
1. Администратор открывает Google Vault (vault.google.com)
2. Создает "Matter" для судебного расследования или compliance-аудита
3. Добавляет пользователей (владельцев форм) в Matter
4. Система автоматически сохраняет все логи активности этих пользователей
5. Доступен поиск по логам:
   - По ключевым словам в названиях форм
   - По email-адресам респондентов
   - По диапазону дат
6. Логи экспортируются в MBOX или PST формат для передачи юристам

**Альтернативные сценарии:**
- Сценарий Г (Алерты на подозрительную активность): Администратор настраивает правила в Google Admin Console для автоматических уведомлений:
  - Алерт при массовом экспорте данных (более 10 форм за час)
  - Уведомление при изменении настроек безопасности критичных форм
  - Алерт при доступе к формам с необычных IP-адресов (другая страна)
- Сценарий Д (Интеграция с третьими сторонами): Использование Google Workspace Marketplace приложений для расширенного аудита (например, GAT+, BetterCloud)

**Исключительные ситуации:**
- Исключение А (Логи недоступны для личных аккаунтов): Детальные audit logs доступны только для Google Workspace, личные gmail.com аккаунты видят только базовую Activity
- Исключение Б (Задержка логирования): События могут появляться в логах с задержкой до 24 часов (обычно в течение 1-2 часов)
- Исключение В (Ротация логов): Для Workspace Business Standard логи хранятся 180 дней, для Enterprise - до 2 лет (после чего автоматически удаляются)

**Бизнес-правила:**
- BR-058: Все действия с формами автоматически логируются, отключить логирование невозможно
- BR-059: Логи хранятся в инфраструктуре Google Cloud с тем же уровнем шифрования, что и основные данные (AES-256)
- BR-060: Детальные audit logs доступны для Workspace Business Plus и Enterprise (не доступны для Business Starter)
- BR-061: IP-адреса респондентов логируются только если включена опция "Collect email addresses" (для соблюдения GDPR)
- BR-062: Администратор Workspace может видеть логи всех пользователей организации, но не может видеть содержимое ответов (если не является владельцем формы)
- BR-063: Экспорт логов в BigQuery обновляется каждые 24 часа
- BR-064: Google сохраняет security logs (попытки несанкционированного доступа) отдельно от activity logs
- BR-065: При удалении формы логи сохраняются согласно retention policy (не удаляются автоматически)
- BR-066: Логи соответствуют стандарту ISO 27001 и могут использоваться для compliance-аудитов

**Результат:** Все действия с формами и ответами логируются, администраторы могут отслеживать доступ к данным, выявлять подозрительную активность и обеспечивать соответствие требованиям аудита

### FR-SEC-009: Управление доступом через Google Workspace Security Center

**Описание:** Администраторы Google Workspace могут централизованно управлять безопасностью всех форм в организации через Security Center, настраивая политики DLP (Data Loss Prevention), правила external sharing, мониторинг угроз и compliance-отчеты.

**Роли:** Администратор Google Workspace, Security Officer, Compliance Officer

**Предусловия:**
- Организация использует Google Workspace Enterprise или Education Plus
- Доступ к Google Admin Console и Security Center
- Формы создаются пользователями организации

**Основной сценарий (настройка DLP для форм):**
1. Администратор открывает Security Center (admin.google.com/ac/security)
2. Переходит в "Data protection" > "Data Loss Prevention (DLP)"
3. Создает новое DLP-правило для Google Forms:
   - Нажимает "Create rule" > "New rule"
   - Выбирает scope: "Organizational units" (конкретные подразделения) или "All users"
   - Выбирает приложение: "Google Drive" (Forms хранятся как Drive-файлы)
4. Настраивает условия (Conditions):
   - **Content match**: Детекция конфиденциальных данных в ответах форм:
     - Credit card numbers (номера кредитных карт)
     - Social Security Numbers (SSN, СНИЛС и другие идентификаторы)
     - Passport numbers (номера паспортов)
     - Medical record numbers (медицинские данные)
     - Custom patterns (регулярные выражения для специфических данных)
   - **Sharing settings**: Формы, расшаренные публично или за пределы организации
   - **User/Group**: Конкретные пользователи или группы, к которым применяется правило
5. Настраивает действия (Actions):
   - **Block external sharing**: Запретить публичный доступ к формам с конфиденциальными данными
   - **Alert administrators**: Отправить email/push-уведомление администратору при обнаружении нарушения
   - **Alert user**: Уведомить владельца формы о потенциальной утечке данных
   - **Audit only**: Только логировать события без блокировки (режим мониторинга)
6. Сохраняет правило и активирует его
7. Система начинает сканирование:
   - Анализирует все существующие формы в организации
   - Проверяет ответы на наличие конфиденциальных паттернов
   - При обнаружении нарушения:
     - Блокирует external sharing (если настроено)
     - Отправляет алерт администратору: "DLP rule triggered for form [Form Name] by user [email]"
     - Логирует событие в Audit Log

**Сценарий Б (настройка правил External Sharing):**
1. Администратор переходит в Admin Console > "Apps" > "Google Workspace" > "Drive and Docs"
2. Выбирает "Sharing settings" > "Sharing outside of [organization]"
3. Настраивает политики для форм:
   - **Off**: Запретить публичный доступ к формам (только внутри организации)
   - **On - Public on the web**: Разрешить владельцам делать формы публичными
   - **On - Anyone with the link**: Разрешить sharing по ссылке, но не индексацию в поисковиках
4. Дополнительные опции:
   - "Warning when sharing outside organization": Показывать предупреждение при попытке публичного sharing
   - "Allow only specific domains": Разрешить sharing только с указанными доменами (например, партнерские организации)
5. Применяет настройки к Organizational Units (подразделениям)
6. Владельцы форм при попытке публичного sharing видят сообщение:
   - "Sharing outside [organization] is restricted by your administrator"
   - Опция "Request access from admin" (запрос на исключение)

**Сценарий В (мониторинг угроз и аномалий):**
1. Администратор открывает Security Center > "Security dashboard"
2. Видит карточки с метриками:
   - "Suspicious activity detected": количество подозрительных событий за последние 7 дней
   - "External sharing violations": формы, расшаренные в нарушение политики
   - "DLP rule triggers": срабатывания DLP-правил
3. Кликает на карточку для детального анализа:
   - Список форм с подозрительной активностью
   - Типы угроз: "Unusual login location", "Mass data export", "Sharing with suspicious domains"
   - Рекомендуемые действия: "Review sharing settings", "Contact user", "Suspend account"
4. Для критичных угроз:
   - Администратор может немедленно отозвать доступ к форме
   - Заблокировать аккаунт пользователя
   - Инициировать расследование через Google Vault

**Альтернативные сценарии:**
- Сценарий Г (Context-Aware Access): Настройка доступа к формам на основе контекста:
  - Разрешить доступ только с корпоративных устройств (managed devices)
  - Блокировать доступ из определенных стран (geo-blocking)
  - Требовать дополнительную аутентификацию при доступе из необычных локаций
- Сценарий Д (Compliance reports): Автоматическая генерация отчетов для регуляторов:
  - Отчет о формах, собирающих персональные данные
  - Список нарушений GDPR/HIPAA за период
  - Статистика Data Subject Requests

**Исключительные ситуации:**
- Исключение А (Конфликт DLP и бизнес-процессов): DLP-правило блокирует легитимную форму (false positive) - администратор добавляет исключение
- Исключение Б (Обход политик): Пользователь экспортирует ответы вручную и отправляет за пределы организации - DLP не может отследить (требуется training персонала)
- Исключение В (Задержка применения правил): Новые DLP-правила применяются в течение 24 часов, существующие формы могут временно не соответствовать политике

**Бизнес-правила:**
- BR-067: DLP и Security Center доступны только для Google Workspace Enterprise и Education Plus
- BR-068: DLP-правила применяются к новым ответам форм в real-time (задержка до 5 минут)
- BR-069: Сканирование существующих форм на соответствие DLP происходит в фоновом режиме (в течение 24-48 часов после создания правила)
- BR-070: Администратор может создать до 100 DLP-правил для организации
- BR-071: External sharing policies применяются ко всем формам организации, исключения настраиваются per-user или per-OU
- BR-072: Security alerts отправляются в течение 15 минут с момента обнаружения нарушения
- BR-073: Context-Aware Access требует отдельной лицензии (Endpoint Management)
- BR-074: Compliance reports генерируются автоматически раз в месяц и доступны для скачивания в PDF/CSV

**Результат:** Администраторы централизованно управляют безопасностью всех форм в организации, предотвращают утечки конфиденциальных данных через DLP, контролируют external sharing и мониторят подозрительную активность

### FR-SEC-010: Двухфакторная аутентификация (2FA) и защита аккаунта

**Описание:** Владельцы форм могут защитить свои Google аккаунты с помощью двухфакторной аутентификации (2FA), security keys и других механизмов верификации, что предотвращает несанкционированный доступ к формам и собранным данным даже при компрометации пароля.

**Роли:** Владелец формы (настройка 2FA), Администратор Google Workspace (принудительное включение 2FA для организации)

**Предусловия:**
- Пользователь имеет Google аккаунт (личный или Workspace)
- Доступ к телефону или аппаратному токену для 2FA
- Для принудительного включения: администраторские права в Workspace

**Основной сценарий (владелец формы настраивает 2FA):**
1. Владелец формы переходит в Google Account settings (myaccount.google.com)
2. Открывает раздел "Security" в левом меню
3. Находит секцию "2-Step Verification" и кликает "Get started"
4. Система запрашивает повторный ввод пароля для верификации
5. Выбирает метод второго фактора:
   - **Google Prompt** (рекомендуется): push-уведомление на телефон с Android/iOS
   - **Authenticator app**: одноразовые коды из приложения (Google Authenticator, Authy)
   - **SMS or Voice call**: получение кода по SMS или голосовому звонку
   - **Security Key**: физический USB/NFC-ключ (YubiKey, Google Titan Key)
6. Настраивает выбранный метод:
   - Для Google Prompt: подтверждает телефон, на который будут приходить уведомления
   - Для Authenticator: сканирует QR-код приложением, вводит тестовый код
   - Для SMS: вводит номер телефона, получает и вводит код верификации
   - Для Security Key: вставляет ключ в USB и касается его для регистрации
7. Система предлагает настроить резервные опции:
   - Backup codes: 10 одноразовых кодов для восстановления доступа (рекомендуется распечатать)
   - Backup phone: альтернативный номер телефона для получения кодов
8. Подтверждает включение 2FA, нажимая "Turn on"
9. Система активирует 2FA для аккаунта
10. При следующем входе в Google Forms (или любой Google-сервис):
    - Пользователь вводит email и пароль
    - Система запрашивает второй фактор (push-уведомление, код из app, SMS)
    - Пользователь подтверждает вход через выбранный метод
    - После успешной верификации получает доступ к формам

**Сценарий Б (администратор Workspace включает принудительную 2FA):**
1. Администратор открывает Google Admin Console
2. Переходит в "Security" > "Authentication" > "2-Step Verification"
3. Выбирает организационное подразделение (OU) для применения политики
4. Активирует опцию "Enforcement":
   - "Off": 2FA опциональна для пользователей
   - "On": 2FA обязательна, период внедрения (grace period) настраивается:
     - "1 week", "2 weeks", "1 month" - пользователи должны настроить 2FA в течение этого периода
     - После истечения grace period доступ без 2FA блокируется
5. Настраивает разрешенные методы 2FA:
   - "Allow any method": пользователи выбирают любой метод (Google Prompt, SMS, Security Key)
   - "Only Security Keys": требовать только аппаратные токены (максимальная безопасность для критичных ролей)
   - "No SMS-based verification": запретить SMS (менее безопасный метод, подвержен SIM-swapping атакам)
6. Применяет политику к организации
7. Система автоматически:
   - Отправляет email всем пользователям с инструкциями по настройке 2FA
   - Показывает баннер при входе в Google: "Your admin requires 2-Step Verification. Set it up now."
   - После истечения grace period блокирует доступ пользователям без 2FA
8. Пользователи без 2FA при попытке входа видят сообщение:
   - "2-Step Verification required. You must enroll in 2-Step Verification to access your account."
   - Ссылку на setup: "Get started"

**Альтернативные сценарии:**
- Сценарий В (Advanced Protection Program): Для владельцев критичных форм (журналисты, активисты, VIP):
  1. Пользователь регистрируется в Google Advanced Protection Program (landing.google.com/advancedprotection)
  2. Обязательное использование двух Security Keys (один основной, один backup)
  3. Дополнительные меры безопасности:
     - Блокировка доступа к формам через сторонние приложения (только официальные Google-клиенты)
     - Усиленная верификация при восстановлении аккаунта (процесс занимает 3-5 дней)
     - Автоматическое сканирование на вредоносные вложения в ответах форм
- Сценарий Г (Passwordless authentication): Использование только Security Key без пароля (доступно для Workspace Enterprise)

**Исключительные ситуации:**
- Исключение А (Потеря доступа к 2FA-устройству): Пользователь использует backup codes или backup phone для восстановления доступа
- Исключение Б (Потеря всех методов 2FA): Процесс восстановления аккаунта через Google Account Recovery (может занять несколько дней, требует верификации личности)
- Исключение В (SIM-swapping атака): Злоумышленник перехватывает SMS-коды - рекомендуется переход на Security Key или Authenticator app
- Исключение Г (Конфликт с устаревшими приложениями): Некоторые старые приложения не поддерживают 2FA - требуется использование App Passwords (одноразовых паролей для приложений)

**Бизнес-правила:**
- BR-075: 2FA защищает доступ к Google аккаунту, а значит ко всем формам и ответам, связанным с этим аккаунтом
- BR-076: Google Prompt и Security Keys наиболее безопасны (защита от фишинга), SMS менее безопасен (подвержен перехвату)
- BR-077: При включенной 2FA пользователь может выбрать "Trust this device" - на этом устройстве 2FA не запрашивается в течение 30 дней
- BR-078: Backup codes одноразовые (после использования более недействительны), рекомендуется сгенерировать новые после использования нескольких
- BR-079: Администратор Workspace не может обойти 2FA для доступа к аккаунту пользователя (даже admin должен использовать 2FA)
- BR-080: Принудительная 2FA применяется к новым пользователям немедленно, к существующим - после grace period
- BR-081: Security Keys работают через WebAuthn/FIDO2 стандарт, поддерживают биометрическую аутентификацию (fingerprint, Face ID)
- BR-082: Google рекомендует использовать минимум 2 метода 2FA (один основной, один backup)

**Результат:** Аккаунт владельца формы защищен двухфакторной аутентификацией, несанкционированный доступ к формам и ответам предотвращен даже при компрометации пароля

### FR-SEC-011: Контроль доступа к загруженным файлам

**Описание:** При использовании вопросов типа "File Upload" в формах, система обеспечивает безопасное хранение загруженных файлов в Google Drive владельца формы с настраиваемыми правами доступа, сканированием на вирусы и контролем типов и размеров файлов.

**Роли:** Владелец формы, Респондент (загружает файлы), Администратор Google Workspace

**Предусловия:**
- Форма содержит вопрос типа "File Upload"
- Респондент авторизован в Google аккаунт (File Upload требует "Require sign in")
- Владелец формы имеет достаточно места в Google Drive

**Основной сценарий:**
1. Владелец формы добавляет вопрос типа "File Upload" в форму
2. Настраивает параметры загрузки:
   - Allowed file types: "Any", "Documents", "Spreadsheets", "PDFs", "Presentations", "Drawings", "Images", "Videos", "Audio" (множественный выбор)
   - Maximum file size: от 1 MB до 10 GB (default: 10 MB)
   - Maximum number of files: от 1 до 10 файлов (default: 1)
3. Система автоматически:
   - Включает опцию "Require sign in" (File Upload невозможен для анонимных форм)
   - Создает папку в Google Drive владельца: "[Form Name] (Responses)"
   - Настраивает права доступа к папке: только владелец формы (private)
4. Респондент заполняет форму и достигает вопроса File Upload
5. Видит информацию:
   - "Your file will upload to the form owner's Google Drive"
   - "Allowed file types: [list]"
   - "Max file size: [size]"
6. Нажимает кнопку "Add file" или drag-and-drop файл
7. Система выполняет валидацию:
   - Проверяет размер файла (если превышен лимит: ошибка "File too large. Maximum size is [X] MB")
   - Проверяет тип файла по MIME-type (если не разрешен: "File type not allowed")
   - Проверяет количество файлов (если превышен лимит: "Maximum [N] files allowed")
8. При успешной валидации:
   - Файл загружается в папку "[Form Name] (Responses)" в Drive владельца
   - Система сканирует файл на вирусы (Google VirusTotal integration)
   - Если обнаружен вирус: загрузка отменяется, респондент видит ошибку "File cannot be uploaded due to security concerns"
   - Если файл чистый: загрузка завершается, респондент видит имя файла и иконку типа
9. После отправки формы:
   - Ссылка на загруженный файл сохраняется в Google Sheets в соответствующей ячейке (формат: hyperlink)
   - Файл остается в папке "[Form Name] (Responses)" с именем: "[Question title] - [Respondent email] - [Timestamp].[extension]"
10. Владелец формы может:
    - Открыть папку с файлами через ссылку в Google Sheets
    - Просмотреть, скачать или удалить файлы
    - Изменить права доступа к конкретным файлам (если нужно расшарить с другими пользователями)

**Альтернативные сценарии:**
- Сценарий А (Недостаточно места в Drive): Если у владельца формы недостаточно свободного места в Google Drive:
  - При попытке загрузки респондент видит ошибку: "File cannot be uploaded. Form owner has insufficient storage."
  - Владелец получает email: "Your form '[Form Name]' cannot accept file uploads due to storage limits"
  - Решение: владелец освобождает место или обновляет тариф Google One
- Сценарий Б (Ограничение загрузки по организации): Администратор Workspace может запретить File Upload в формах для всей организации (через Admin Console > Drive settings)
- Сценарий В (Автоматическая организация файлов): Владелец может настроить Apps Script для автоматической сортировки файлов по подпапкам (по дате, по типу респондента и т.д.)
- Сценарий Г (Защита от malware через DLP): Для Workspace Enterprise DLP-правила могут сканировать содержимое загруженных документов на наличие конфиденциальной информации

**Исключительные ситуации:**
- Исключение А (Загрузка большого файла): При загрузке файла близкого к максимальному размеру (10 GB) может произойти timeout - рекомендуется увеличить таймаут браузера или разбить файл
- Исключение Б (Респондент удаляет файл после загрузки): Файл в Google Drive принадлежит владельцу формы, респондент не может его удалить (даже если это его файл)
- Исключение В (Вирус обнаружен после загрузки): Если вирус обнаружен уже после сохранения, Google Drive автоматически блокирует файл и уведомляет владельца

**Бизнес-правила:**
- BR-083: File Upload доступен только для авторизованных форм ("Require sign in" обязателен)
- BR-084: Загруженные файлы хранятся в Google Drive владельца формы, не в инфраструктуре Google Forms
- BR-085: Максимальный размер одного файла - 10 GB (ограничение Google Drive API)
- BR-086: Файлы занимают место в квоте Google Drive владельца формы, не респондента
- BR-087: Система поддерживает все типы файлов, поддерживаемые Google Drive (более 100 MIME-types)
- BR-088: Все загруженные файлы автоматически сканируются Google Safe Browsing и VirusTotal
- BR-089: Владелец формы может удалить файлы из папки без влияния на запись в Google Sheets (ссылка останется, но будет вести на несуществующий файл)
- BR-090: Права доступа к файлам по умолчанию: только владелец формы, респондент не имеет доступа к своему загруженному файлу (если владелец не расшарит вручную)
- BR-091: При удалении формы папка с файлами не удаляется автоматически (остается в Drive владельца)

**Результат:** Файлы, загруженные респондентами, безопасно хранятся в Google Drive владельца формы с контролем типов, размеров, сканированием на вирусы и настраиваемыми правами доступа

### FR-SEC-012: Уведомления и алерты о безопасности

**Описание:** Владельцы форм и администраторы Workspace получают автоматические уведомления о важных событиях безопасности, таких как подозрительная активность, изменение настроек доступа, DLP-нарушения, превышение лимитов хранения и попытки несанкционированного доступа.

**Роли:** Владелец формы (получает уведомления о своих формах), Администратор Google Workspace (получает org-wide алерты)

**Предусловия:**
- Форма создана и активна
- Email-уведомления не отключены в настройках Google аккаунта
- Для org-wide алертов: Google Workspace Business Plus или Enterprise

**Основной сценарий (владелец формы):**
1. Владелец формы создает форму и публикует ее
2. Система автоматически мониторит активность формы
3. При обнаружении критичных событий отправляет email-уведомления:

   **Тип А - Подозрительная активность:**
   - Тема: "Unusual activity detected on your form '[Form Name]'"
   - Содержание:
     - Описание активности: "We detected [X] responses from the same IP address in [Y] minutes"
     - Рекомендации: "Consider enabling 'Require sign in' or reviewing responses"
     - Ссылка на форму для проверки
     - Timestamp события

   **Тип Б - Изменение настроек доступа:**
   - Тема: "Sharing settings changed for form '[Form Name]'"
   - Содержание:
     - Кто изменил: "[User email] changed sharing settings"
     - Что изменилось: "Form is now publicly accessible" или "Restricted to [organization] users"
     - Ссылка для отмены изменений (если владелец не выполнял действие)

   **Тип В - Превышение лимитов хранения:**
   - Тема: "Storage limit reached - Form cannot accept file uploads"
   - Содержание:
     - "Your Google Drive storage is [X] GB / [Y] GB used"
     - "Form '[Form Name]' cannot accept file uploads until you free up space"
     - Ссылки: "Manage storage" (Google One), "Review form responses"

   **Тип Г - Массовый spam:**
   - Тема: "High volume of responses detected on form '[Form Name]'"
   - Содержание:
     - "[X] responses received in the last [Y] minutes"
     - "This may indicate spam or bot activity"
     - Рекомендации: "Enable 'Require sign in' or 'Limit to 1 response'"
     - Кнопка "Stop accepting responses" для немедленной приостановки

4. Владелец получает уведомления на email, указанный в Google аккаунте
5. Может кликнуть на ссылку в email для немедленного перехода к форме или настройкам

**Сценарий Б (администратор Workspace - Security alerts):**
1. Администратор настраивает Security alerts в Admin Console:
   - Переходит в "Security" > "Alert center"
   - Включает нужные типы алертов:
     - "DLP rule violations" (нарушения DLP)
     - "Government-backed attack warnings" (попытки целенаправленных атак)
     - "Suspicious login activity" (подозрительные входы в аккаунты)
     - "Device compromise" (компрометация устройств)
2. Настраивает получателей: добавляет email security-команды
3. Система мониторит активность всех форм в организации
4. При обнаружении нарушений отправляет алерты:

   **Пример алерта DLP:**
   - Тема: "[SECURITY ALERT] DLP rule triggered: Credit card numbers detected"
   - Содержание:
     - Form: "[Form Name]" (link)
     - Owner: "[User email]"
     - Rule: "Prevent sharing forms with financial data"
     - Action taken: "External sharing blocked"
     - Details: "Form contained [N] credit card numbers in responses"
     - Recommended action: "Review form and contact owner"

   **Пример алерта подозрительного входа:**
   - Тема: "[SECURITY ALERT] Suspicious login to account with form access"
   - Содержание:
     - User: "[User email]"
     - Event: "Login from unusual location: [Country, City]"
     - Device: "[Device type, OS]"
     - IP address: "[IP]"
     - Forms at risk: "[List of forms owned by user]"
     - Action: "Account temporarily locked, 2FA challenge required"

5. Администратор может:
   - Просмотреть детали в Alert Center (web-интерфейс)
   - Выполнить рекомендуемые действия (block user, review data, contact owner)
   - Закрыть алерт после расследования

**Альтернативные сценарии:**
- Сценарий В (Push-уведомления на мобильные устройства): Владелец формы устанавливает Google Forms mobile app (iOS/Android) и получает push-уведомления о новых ответах и алертах безопасности
- Сценарий Г (Интеграция с SIEM): Администратор настраивает forwarding алертов в корпоративную SIEM-систему (Splunk, LogRhythm) через API или email-интеграцию
- Сценарий Д (Slack/Teams интеграция): Настройка webhook для отправки security alerts в корпоративные каналы Slack или Microsoft Teams
- Сценарий Е (Еженедельные digest-отчеты): Владелец получает еженедельный email с summary: количество ответов, топ источников трафика, подозрительные активности за неделю

**Исключительные ситуации:**
- Исключение А (Email не доставлен): Если email-сервер респондента блокирует уведомления Google, алерт сохраняется в Alert Center для просмотра в web-интерфейсе
- Исключение Б (False positive alerts): Легитимная активность (например, массовое тестирование формы командой) может вызвать алерты - владелец может отметить как "Not an issue"
- Исключение В (Alert fatigue): При большом количестве алертов администратор может настроить фильтры и приоритеты (critical, high, medium, low)

**Бизнес-правила:**
- BR-092: Email-уведомления отправляются в течение 15 минут с момента обнаружения события
- BR-093: Владелец формы может отключить неважные уведомления (например, о каждом новом ответе), но не может отключить критичные security alerts
- BR-094: Alert Center в Admin Console доступен для Workspace Business Plus и Enterprise
- BR-095: Алерты хранятся в Alert Center 180 дней, после чего архивируются
- BR-096: Push-уведомления работают только при установленном Google Forms mobile app
- BR-097: Система не отправляет более 10 однотипных алертов в час (rate limiting для предотвращения spam)
- BR-098: Критичные алерты (government-backed attacks, data breach) имеют приоритет и доставляются немедленно
- BR-099: Администратор может делегировать управление алертами security-команде без предоставления полных admin-прав
- BR-100: Уведомления соответствуют GDPR - не содержат персональные данные респондентов в теме письма (только в защищенной части)

**Результат:** Владельцы форм и администраторы своевременно информируются о важных событиях безопасности, могут оперативно реагировать на угрозы и предотвращать утечки данных или несанкционированный доступ

## Нефункциональные требования

### NFR-SEC-001: Производительность системы безопасности

**Требование:** Все проверки безопасности (авторизация, валидация, сканирование на вирусы) должны выполняться с минимальным влиянием на скорость заполнения и отправки форм.

**Метрики:**
- Проверка авторизации при открытии формы: < 500 мс
- Валидация прав доступа (Require sign in, Limit to organization): < 200 мс
- Проверка на spam/bot (автоматическая): < 100 мс (фоновый процесс)
- reCAPTCHA challenge (при срабатывании): < 3 сек на отображение
- Сканирование файла на вирусы: < 5 сек для файлов до 100 MB, < 30 сек для файлов до 10 GB
- Применение DLP-правил к новому ответу: < 1 сек (асинхронно)

**Критерии приемки:**
- 95% запросов обрабатываются в пределах указанных метрик
- При высокой нагрузке (1000+ одновременных респондентов) деградация производительности не более 20%
- Асинхронные проверки (DLP, virus scanning) не блокируют отправку формы

---

### NFR-SEC-002: Надежность и доступность

**Требование:** Система безопасности должна быть высокодоступной и не становиться единой точкой отказа для работы форм.

**Метрики:**
- Uptime системы аутентификации: 99.99% (SLA Google Identity Platform)
- Uptime DLP-сервисов: 99.9%
- Recovery Time Objective (RTO) при сбое: < 5 минут
- Recovery Point Objective (RPO): 0 (real-time replication)

**Критерии приемки:**
- При недоступности DLP-сервиса формы продолжают работать (graceful degradation), нарушения логируются для последующей обработки
- При недоступности virus scanning файлы помещаются в карантин, владелец получает уведомление
- Backup authentication методы (backup codes) всегда доступны даже при сбое основной инфраструктуры

---

### NFR-SEC-003: Масштабируемость

**Требование:** Система безопасности должна масштабироваться для обработки форм с большим количеством респондентов без деградации производительности.

**Метрики:**
- Поддержка форм с до 1 миллиона ответов без снижения скорости проверок
- Обработка до 10,000 одновременных отправок формы (spike load)
- DLP-сканирование до 100,000 ответов в день на организацию

**Критерии приемки:**
- Rate limiting применяется динамически на основе паттернов трафика
- Auto-scaling для DLP и virus scanning сервисов
- Горизонтальное масштабирование без downtime

---

### NFR-SEC-004: Compliance и аудит

**Требование:** Система должна соответствовать международным стандартам безопасности и обеспечивать полный audit trail для compliance-проверок.

**Сертификации:**
- ISO 27001 (Information Security Management)
- ISO 27018 (Privacy in Cloud Computing)
- ISO 27701 (Privacy Information Management)
- SOC 2 Type II (Security, Availability, Confidentiality)
- SOC 3 (публичный отчет)

**Соответствие регуляциям:**
- GDPR (General Data Protection Regulation) - ЕС
- CCPA (California Consumer Privacy Act) - США
- HIPAA (Health Insurance Portability and Accountability Act) - для healthcare (с BAA)
- FERPA (Family Educational Rights and Privacy Act) - для образовательных учреждений
- COPPA (Children's Online Privacy Protection Act) - при сборе данных детей до 13 лет

**Audit trail:**
- Логирование всех доступов к персональным данным (кто, когда, что)
- Хранение логов минимум 180 дней (для Enterprise - до 2 лет)
- Immutable logs (невозможность изменения или удаления логов)
- Экспорт логов для внешних аудиторов в стандартных форматах (CSV, JSON, MBOX)

---

### NFR-SEC-005: Шифрование и криптография

**Требование:** Использование современных криптографических стандартов для защиты данных в transit и at rest.

**Стандарты:**
- **In transit**: TLS 1.3 (preferred), TLS 1.2 (fallback), запрет TLS 1.0/1.1
- **At rest**: AES-256-GCM (Google-managed keys), AES-256-CBC (customer-managed keys)
- **Hashing**: SHA-256 для integrity checks, bcrypt для хранения паролей (не применимо к формам напрямую)
- **Key management**: Google Cloud KMS, HSM-backed для Enterprise Plus

**Критерии приемки:**
- Perfect Forward Secrecy (PFS) для всех TLS-соединений
- Automatic key rotation каждые 90 дней
- Zero-knowledge encryption опционально для максимальной конфиденциальности (CSE для Enterprise Plus)

---

### NFR-SEC-006: Usability безопасности

**Требование:** Настройки безопасности должны быть понятны пользователям без технического background и не создавать барьеров для легитимных респондентов.

**Критерии:**
- Все security-опции имеют понятные описания и tooltips
- Включение "Require sign in" автоматически показывает предупреждение респондентам
- reCAPTCHA challenge не показывается легитимным пользователям без необходимости (invisible reCAPTCHA v3)
- Ошибки доступа содержат четкие инструкции для решения (например, "Contact form owner for access")

**User testing:**
- 90%+ пользователей должны понимать назначение каждой security-опции без обращения к документации
- Время на настройку базовой безопасности формы (Require sign in + Email collection): < 2 минуты

---

### NFR-SEC-007: Мобильная безопасность

**Требование:** Все функции безопасности должны корректно работать на мобильных устройствах (iOS, Android).

**Критерии:**
- 2FA (Google Prompt, Authenticator app) работает на мобильных платформах
- reCAPTCHA адаптируется для сенсорных экранов
- Security notifications доставляются как push на мобильные устройства с установленным Google Forms app
- Биометрическая аутентификация (Face ID, Touch ID, fingerprint) поддерживается для Security Keys

---

### NFR-SEC-008: Интеграция и API Security

**Требование:** Google Forms API должен обеспечивать тот же уровень безопасности, что и web-интерфейс.

**Критерии:**
- Все API-запросы требуют OAuth 2.0 аутентификацию
- Rate limiting на API: 300 requests per minute per user, 50,000 per day per project
- API keys rotatable, не содержатся в public repositories
- Scopes для API ограничены минимально необходимыми (principle of least privilege)
- Webhook callbacks подписываются HMAC-SHA256 для верификации источника

## Известные ограничения

1. **Анонимные формы и безопасность:** Формы без "Require sign in" имеют ограниченные механизмы защиты от спама (только rate limiting и reCAPTCHA), невозможно надежно идентифицировать респондентов или ограничить количество ответов.

2. **File Upload и квота:** Загруженные файлы занимают место в Google Drive владельца формы, что может привести к исчерпанию квоты и блокировке приема новых файлов. Решение: регулярный мониторинг или обновление тарифа Google One.

3. **DLP и личные аккаунты:** Data Loss Prevention доступен только для Google Workspace Enterprise, личные gmail.com аккаунты не могут использовать DLP-правила.

4. **Региональное хранение данных:** Настройка конкретного региона хранения (например, только ЕС) доступна только для Workspace Business Standard и выше, личные аккаунты не могут контролировать географию данных.

5. **Backup и восстановление:** Google Forms не предоставляет встроенных инструментов для backup ответов (кроме Google Vault для Workspace). Рекомендуется регулярный экспорт данных в Google Sheets или CSV.

6. **Real-time collaboration и безопасность:** При одновременном редактировании формы несколькими редакторами возможны конфликты при изменении настроек безопасности (last-write-wins), рекомендуется координация через комментарии.

7. **Вирусное сканирование файлов:** Файлы размером более 100 MB могут не сканироваться полностью (ограничение VirusTotal), для таких файлов рекомендуется дополнительное сканирование локально.

8. **HIPAA compliance:** Google Forms может использоваться для HIPAA-compliant сбора медицинских данных только при наличии подписанного Business Associate Agreement (BAA) с Google, доступного для Workspace Enterprise и Education Plus, и при соблюдении дополнительных technical safeguards.

9. **Ограничения 2FA:** SMS-based 2FA подвержен SIM-swapping атакам, рекомендуется переход на Security Keys для критичных аккаунтов, но это требует дополнительных расходов на hardware tokens.

10. **API rate limits:** При программном создании или заполнении форм через API жесткие rate limits могут блокировать массовые операции, требуется планирование и throttling в приложениях.

## Рекомендации по безопасности для владельцев форм

1. **Всегда используйте "Require sign in"** для форм, собирающих чувствительные данные (персональные, финансовые, медицинские).

2. **Включите "Limit to 1 response"** для опросов и голосований, чтобы предотвратить манипуляции результатами.

3. **Добавляйте Privacy Notice** в описание каждой формы с информацией о цели сбора данных, сроках хранения и правах респондентов (GDPR compliance).

4. **Используйте 2FA** для защиты своего Google аккаунта - это защитит доступ ко всем вашим формам и ответам.

5. **Регулярно экспортируйте данные** из Google Sheets в локальное хранилище или облачный backup (например, раз в неделю для критичных форм).

6. **Ограничивайте File Upload** только необходимыми типами файлов и устанавливайте разумные лимиты размера (например, max 10 MB вместо 10 GB).

7. **Мониторьте ответы** на предмет подозрительной активности (идентичные ответы, массовые отправки с одного IP) и своевременно реагируйте.

8. **Используйте "Restrict to organization"** для внутренних корпоративных форм, чтобы предотвратить утечку данных за пределы компании.

9. **Настройте retention policies** через Google Vault (для Workspace) для автоматического удаления старых данных и соответствия законодательству.

10. **Обучайте респондентов** - добавляйте инструкции в форму о том, какие данные безопасно предоставлять, а какие нет (например, никогда не запрашивайте полные номера кредитных карт).

## Глоссарий

- **2FA (Two-Factor Authentication)** - двухфакторная аутентификация, метод защиты аккаунта с использованием двух независимых факторов (пароль + код из SMS/app/Security Key).

- **AES-256** - Advanced Encryption Standard с 256-битным ключом, современный стандарт симметричного шифрования.

- **BAA (Business Associate Agreement)** - соглашение между Google и организацией, необходимое для HIPAA-compliant использования Google Forms.

- **CMEK (Customer-Managed Encryption Keys)** - модель шифрования, где организация управляет ключами шифрования, а не провайдер облака.

- **CSE (Client-Side Encryption)** - шифрование данных на стороне клиента (в браузере) до передачи на серверы Google.

- **Data Controller** - организация или лицо, определяющее цели и методы обработки персональных данных (владелец формы).

- **Data Processor** - организация, обрабатывающая данные от имени Data Controller (Google в контексте Forms).

- **DLP (Data Loss Prevention)** - технологии и политики для предотвращения утечки конфиденциальных данных.

- **GDPR (General Data Protection Regulation)** - Общий регламент по защите данных ЕС, устанавливающий требования к обработке персональных данных.

- **HMAC** - Hash-based Message Authentication Code, метод верификации целостности и подлинности сообщений.

- **Legal Hold** - режим хранения данных для судебных разбирательств, при котором данные не могут быть удалены.

- **OAuth 2.0** - протокол авторизации для безопасного доступа к API без передачи паролей.

- **reCAPTCHA** - сервис Google для защиты от ботов через challenge-response тесты.

- **Retention Policy** - политика хранения данных, определяющая сроки хранения и автоматического удаления.

- **SCC (Standard Contractual Clauses)** - стандартные договорные условия для трансфера персональных данных за пределы ЕС.

- **Security Key** - физический hardware token (USB/NFC) для аутентификации по стандарту FIDO2/WebAuthn.

- **SIEM (Security Information and Event Management)** - системы для централизованного сбора и анализа security logs.

- **TLS (Transport Layer Security)** - протокол шифрования для защиты данных при передаче по сети.

- **WebAuthn** - веб-стандарт для аутентификации через биометрию или Security Keys.
